## ステップ0：検証用メジャーを先に作る（5分）

RLSは「見えないこと」を確認する作業です。目視だけでは確信が持てないので、**検証用のメジャーを先に用意**します。

```dax
現在のユーザー = USERPRINCIPALNAME()
```

```dax
見える店舗数 = CALCULATE( COUNTROWS( Dim_店舗 ), REMOVEFILTERS() )
```

```dax
見える売上 = CALCULATE( [総売上], REMOVEFILTERS() )
```

> [!NOTE] `REMOVEFILTERS()` を付ける理由
> 引数なしの `REMOVEFILTERS()` はモデル全体のフィルターを外しますが、**RLSのフィルターだけは外れません**。つまりこの3本は「スライサーの選択にかかわらず、この人に見えている全範囲」を返します。RLSの効き具合を測る物差しとして最適です。

この3つをカードビジュアルで1ページにまとめ、「RLS検証」という名前を付けておきます。以降のすべてのテストでこのページを使います。

## ステップ2：段階2 — 動的RLS（15分）

### 2-1. 権限テーブルを読み込む

[security_users.csv](data/security_users.csv) を `Dim_ユーザー権限` として読み込みます（[LAB06](lab.html?id=LAB06) で実施済みならそのまま）。`Email` は小文字化しておきます。

### 2-2. 双方向を使わない書き方

[LAB06](lab.html?id=LAB06) ではブリッジテーブルを双方向にしましたが、双方向を使わない方法もあります。**ロールの管理 → 作成** → 名前 `動的_店舗担当`。`Dim_店舗` テーブルに次の式を設定します。

```dax
Dim_店舗[StoreID] IN
    CALCULATETABLE(
        VALUES( Dim_ユーザー権限[StoreID] ),
        Dim_ユーザー権限[Email] = LOWER( USERPRINCIPALNAME() )
    )
```

```figure
{ "type":"formula", "lang":"dax", "title":"IN + CALCULATETABLE による動的RLS",
  "code":"Dim_店舗[StoreID] IN CALCULATETABLE( VALUES( Dim_ユーザー権限[StoreID] ), Dim_ユーザー権限[Email] = LOWER( USERPRINCIPALNAME() ) )",
  "caption":"「この人に許された店舗ID一覧」を作り、その中にあるかどうかで判定する",
  "parts":[
    {"match":"Dim_店舗[StoreID] IN","label":"各行の店舗IDが、右のリストに含まれるか","tone":"blue"},
    {"match":"VALUES( Dim_ユーザー権限[StoreID] )","label":"許可された店舗IDの一覧","tone":"green"},
    {"match":"Dim_ユーザー権限[Email] = LOWER( USERPRINCIPALNAME() )","label":"ログインユーザーの行だけに絞る","tone":"violet"} ] }
```

> [!TIP] 双方向とどちらを選ぶか
> 双方向ブリッジは設定が単純ですが、モデル全体のフィルター経路が増え、他のメジャーの挙動に影響します。`IN + CALCULATETABLE` はモデルを汚さず、権限ロジックがロールの中に閉じます。**新規に作るなら後者を推奨**します。既存モデルで双方向が動いているなら無理に変える必要はありません。

**ロールとして表示** で次を確認します。

| ユーザー | 見える店舗数 | 見える売上 |
|---|---|---|
| tanaka@northstar-retail.example.com | 1 | 新宿本店のみ |
| suzuki@northstar-retail.example.com | 1 | 横浜店のみ |
| area-kanto@northstar-retail.example.com | 4 | 関東4店舗 |
| exec@northstar-retail.example.com | 14 | 全社 |

```figure
{ "type":"interactive", "widget":"rls-simulator", "title":"ユーザーごとの可視範囲",
  "caption":"同じレポートでも、ログインした人によって行が変わる" }
```

> [!TRAP] 権限表に存在しないユーザー
> 権限表にないメールアドレスでログインすると、**何も見えません**（0行）。これは仕様どおりですが、利用者からは「レポートが壊れている」と見えます。空のときに案内を出すメジャーを作っておきます。

```dax
アクセス案内 =

    [見える店舗数] = 0,
```

## ステップ3：段階3 — 階層RLS（25分）

`area-kanto` の権限は、`security_users.csv` に4行（S001〜S004）を手で書くことで実現していました。店舗が増えるたびに行を足す運用は、いずれ破綻します。**組織階層を1本持てば、行を足さなくても配下が自動で見えます。**

```figure
{ "type":"tree", "title":"作る組織階層", "caption":"上位ノードの担当者は、配下のすべてを自動的に見られるようになる",
  "root":{"label":"N000 本社","sub":"exec@..."},
  "children":[
    {"label":"N001 関東エリア","sub":"area-kanto@...","tone":"blue",
     "children":[
       {"label":"S001 新宿本店","sub":"tanaka@..."},
       {"label":"S002 渋谷店","sub":"sato@..."},
       {"label":"S003 横浜店","sub":"suzuki@..."} ]},
    {"label":"N002 中部エリア","sub":"担当者未設定","tone":"green",
     "children":[{"label":"S005 名古屋店","sub":"ito@..."}]},
    {"label":"N003 近畿エリア","sub":"担当者未設定","tone":"amber",
     "children":[{"label":"S007 梅田店","sub":"yamamoto@..."}]} ] }
```

### 3-1. Dim_店舗に親ノードの列を足す

**ホーム → データの変換** で `Dim_店舗` を選び、**列の追加 → カスタム列**（列名 `ParentID`）。

```m
= if [Region] = "関東" then "N001"
  else if [Region] = "中部" then "N002"
  else if [Region] = "近畿" then "N003"
  else if [Region] = "オンライン" then "N000"
  else "N004"
```

型をテキストに設定します。

### 3-2. 組織ノードの行を追加する

**ホーム → データの入力** で次のテーブルを作り、名前を `組織ノード` にします。

| StoreID | StoreName | Prefecture | Region | ParentID |
|---|---|---|---|---|
| N000 | 本社 | — | 全社 | （空欄） |
| N001 | 関東エリア | — | 関東 | N000 |
| N002 | 中部エリア | — | 中部 | N000 |
| N003 | 近畿エリア | — | 近畿 | N000 |
| N004 | その他エリア | — | その他 | N000 |

次に `Dim_店舗` を選び、**ホーム → クエリの追加 → クエリを新規として追加** で `組織ノード` を下に連結します。連結後のクエリ名を `Dim_店舗` にし、元の店舗クエリは読み込み無効にしてください。

> [!TRAP] 列名は完全一致させる
> `クエリの追加` は列名で突き合わせます。1文字でも違うと別の列として追加され、`null` だらけの表になります。追加前に両方の列名を確認してください。

### 3-3. PATH列を作る

**モデリング → 新しい列**（`Dim_店舗` を選んだ状態で）：

```dax
組織パス = PATH( Dim_店舗[StoreID], Dim_店舗[ParentID] )
```

`S001` の行には `N000|N001|S001` という文字列が入ります。これが「本社 → 関東エリア → 新宿本店」という経路そのものです。

補助として階層の深さも持っておくと便利です。

```dax
組織階層レベル = PATHLENGTH( Dim_店舗[組織パス] )
```

> [!TRAP] `PATH` が動かないとき
> `PATH` は**同じテーブル内の2列**しか受け取りません。また、親IDは必ず同じテーブルの主キーに存在する値である必要があります。ルート行（本社）の `ParentID` は空欄にします。ここが空でないと循環参照になり、エラーになります。

### 3-4. 担当ノード表を作る

**データの入力** で `Dim_担当ノード` を作ります。

| Email | NodeID |
|---|---|
| exec@northstar-retail.example.com | N000 |
| area-kanto@northstar-retail.example.com | N001 |
| tanaka@northstar-retail.example.com | S001 |
| sato@northstar-retail.example.com | S002 |
| suzuki@northstar-retail.example.com | S003 |
| ito@northstar-retail.example.com | S005 |

このテーブルは**どのテーブルともリレーションシップを結びません**。ロールの式から直接参照するだけです。

### 3-5. 階層ロールを作る

**ロールの管理 → 作成** → 名前 `階層セキュリティ`。`Dim_店舗` テーブルに次の式を設定します。

```dax
COUNTROWS(
    FILTER(
        Dim_担当ノード,
        Dim_担当ノード[Email] = LOWER( USERPRINCIPALNAME() )
            && PATHCONTAINS( Dim_店舗[組織パス], Dim_担当ノード[NodeID] )
    )
) > 0
```

```figure
{ "type":"formula", "lang":"dax", "title":"階層RLSの判定式",
  "code":"PATHCONTAINS( Dim_店舗[組織パス], Dim_担当ノード[NodeID] )",
  "caption":"「この店舗の経路の中に、私の担当ノードが含まれるか」を1行で判定する",
  "parts":[
    {"match":"PATHCONTAINS","label":"パス文字列に指定の値が含まれるか判定する","tone":"violet"},
    {"match":"Dim_店舗[組織パス]","label":"N000|N001|S001 のような経路","tone":"blue"},
    {"match":"Dim_担当ノード[NodeID]","label":"その人が担当する組織のID","tone":"green"} ] }
```

> [!TIP] `LOOKUPVALUE` ではなく `COUNTROWS( FILTER( ... ) )` を使う理由
> `LOOKUPVALUE` は該当行が2件以上あるとエラーになります。1人が複数の組織を兼務する（関東エリアと中部エリアの両方など）ケースで即座に破綻します。`COUNTROWS( FILTER( ... ) ) > 0` なら、何件あっても「1件でも該当すれば見える」と評価できます。

### 3-6. テストする

**ロールとして表示** で `階層セキュリティ` を選び、次を確認します。

| ユーザー | 担当ノード | 見える店舗数 | 説明 |
|---|---|---|---|
| tanaka@... | S001 | 1 | 自店のみ |
| area-kanto@... | N001 | 5 | 関東4店舗 + エリアノード自身 |
| exec@... | N000 | 19 | 全14店舗 + 組織ノード5行 |

> [!TRAP] 店舗数に組織ノードが混ざる
> `Dim_店舗` に組織ノードの行を追加したため、店舗一覧に「関東エリア」が現れます。実務では次のどちらかで対処します。
> - `Dim_店舗` に `種別` 列（`店舗` / `組織`）を追加し、レポート側のビジュアルレベルフィルターで `店舗` だけに絞る
> - 組織ノード行をレポートビューでは非表示にはできないため、フィルターでの制御が基本

`種別` 列は Power Query のカスタム列で作れます。

```m
= if Text.StartsWith( [StoreID], "N" ) then "組織" else "店舗"
```

## トラブルシューティング

| 症状 | 原因 | 対処 |
|---|---|---|
| `PATH` がエラー | ルート行の `ParentID` が空でない | 本社行を空欄にする |
| `PATH` がエラー | 親IDが主キーに存在しない | `組織ノード` の連結漏れを確認 |
| 階層ロールで何も見えない | `Dim_担当ノード` にメールがない | 小文字・スペルを確認 |
| 階層ロールで全部見える | ロールにチェックを入れていない | ロール名にチェック |
| `LOOKUPVALUE` がエラー | 該当行が複数ある | `COUNTROWS( FILTER( ... ) ) > 0` に変更 |
| 店舗一覧にエリア行が出る | 組織ノードを同一テーブルに入れたため | `種別` 列でフィルター |
| 兼務ユーザーの範囲が足りない | 担当ノードが1行しかない | 担当ノード表に行を追加（式の修正は不要） |
| 更新後にRLSが消えた | クエリ名を変えてロールの参照が切れた | ロールの式を開いて再保存 |

## 発展課題

### 課題1：閲覧ログを仕込む（15分）

`現在のユーザー` メジャーをレポート下部の小さなカードに常時表示してください。ユーザーからの問い合わせで「どのアカウントで見ていますか」を聞く手間が消えます。

### 課題2：組織改編に対応する（20分）

`S003 横浜店` を関東エリアから新設の `N005 首都圏南エリア` に移す、という改編を実施してください。手順は次の2つだけです。

1. `組織ノード` に `N005` の行を追加（親は `N001`）
2. `Dim_店舗` の `ParentID` の条件を `StoreID = "S003"` のとき `N005` に変更

**ロールの式は1文字も変わりません。** これが階層RLSの投資対効果です。

### 課題3：オブジェクトレベルセキュリティと組み合わせる（15分）

RLSは行を隠しますが、`ManagerEmail` のような列そのものを隠すには OLS（オブジェクトレベルセキュリティ）が必要です。Tabular Editor で `Dim_店舗[ManagerEmail]` をロール `階層セキュリティ` から非表示にし、どう見えるかを確認してください。

### 課題4：性能を測る（15分）

RLSは全クエリに追加のフィルターを掛けます。[LAB09](lab.html?id=LAB09) の手順で、ロールなし・動的RLS・階層RLS の3条件で同じページを計測し、差を表にまとめてください。階層RLSは `PATHCONTAINS` の文字列処理を伴うため、数万行のディメンションでは無視できない差が出ます。
