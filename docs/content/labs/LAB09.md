## ステップ1：わざと遅いレポートを作る（15分）

改善の効果を体感するため、代表的なアンチパターンを5つ仕込みます。

### アンチパターン1：`FILTER` にテーブル全体を渡す

```dax
まとめ買い売上_遅い =
CALCULATE(
    SUM( Fact_売上[SalesAmount] ),
    FILTER( Fact_売上, Fact_売上[Quantity] >= 2 )
)
```

### アンチパターン2：反復関数の中で条件分岐する

```dax
高額商品売上_遅い =
SUMX(
    Fact_売上,
    IF( RELATED( Dim_商品[ListPrice] ) >= 50000, Fact_売上[SalesAmount], 0 )
)
```

### アンチパターン3：同じメジャーを何度も呼ぶ

```dax
粗利判定_遅い =
IF(
    DIVIDE( [粗利], [総売上] ) > 0.3,
    DIVIDE( [粗利], [総売上] ),
    DIVIDE( [粗利], [総売上] ) * 0.5
)
```

### アンチパターン4：高カーディナリティ列をビジュアルに置く

テーブルビジュアルに `Fact_売上[OrderID]`（約6,900種類）と `総売上` を置きます。

### アンチパターン5：1ページにビジュアルを詰め込む

上記4つのメジャーを使ったビジュアルを、1ページに12個以上配置します。

> [!TRAP] 「本番はもっと大きい」を言い訳にしない
> このサンプルは約6,900行なので、遅いといっても数百ミリ秒です。**同じコードが1,000万行では数十秒になります。** 行数が10倍になると処理時間は10倍以上に伸びるパターンかどうかを、小さいデータのうちに見極めておくのがこのラボの狙いです。

## ステップ4：1つずつ直す（20分）

### 修正1：`FILTER` を述語に置き換える

```dax
まとめ買い売上_速い =
CALCULATE(
    SUM( Fact_売上[SalesAmount] ),
    Fact_売上[Quantity] >= 2
)
```

`FILTER( Fact_売上, ... )` はファクトの全行を1行ずつ評価します（FE処理）。列に対する述語なら、ストレージエンジンが圧縮データのまま処理できます（SE処理）。

### 修正2：条件をフィルターに移す

```dax
高額商品売上_速い =
CALCULATE(
    [総売上],
    KEEPFILTERS( Dim_商品[ListPrice] >= 50000 )
)
```

反復の中で `IF` を回すのではなく、**そもそも対象を絞ってから合計する**のが速い形です。

### 修正3：`VAR` で計算を1回にする

```dax
粗利判定_速い =
VAR 率 = DIVIDE( [粗利], [総売上] )
RETURN
    IF( 率 > 0.3, 率, 率 * 0.5 )
```

- `Fact_売上[OrderID]` をビジュアルから外す（必要ならドリルスルー先に置く）
- 使っていない列を Power Query で削除する
- 日付列から時刻部分を落とす（`OrderDate` が日付型であることを確認）

### 修正5：自動の日付/時刻をオフにする

**ファイル → オプション → 現在のファイル → データの読み込み** で「自動の日付/時刻」のチェックを外します。日付列1本につき隠れた日付テーブルが1つ消え、モデルが目に見えて軽くなります。

### 修正6：ビジュアルを減らす

1ページのビジュアルは**8個以内**を目安にします。詳細はドリルスルーページに逃がしてください。相互作用が不要なビジュアルは、**書式 → 相互作用の編集** で「なし」に設定すると、クエリの本数そのものが減ります。

## 発展課題

### 課題1：`DISTINCTCOUNT` の代替を比べる（15分）

```dax
顧客数_A = DISTINCTCOUNT( Fact_売上[CustomerID] )
```

```dax
顧客数_B = COUNTROWS( SUMMARIZE( Fact_売上, Fact_売上[CustomerID] ) )
```

両方を同じマトリックスに置いて計測し、どちらが速いかを確認してください。結果はデータの形によって変わります。**「一般論として速い書き方」ではなく「このモデルで速い書き方」を測って選ぶ**のが正しい態度です。

### 課題2：カーディナリティを実感する（15分）

`Fact_売上[OrderID]`（一意）と `Fact_売上[StoreID]`（14種類）を、それぞれ VertiPaq Analyzer でサイズ比較してください。行数は同じなのに、サイズは桁違いになります。

```figure
{ "type":"interactive", "widget":"cardinality-lab", "title":"カーディナリティとモデルサイズ",
  "caption":"一意な値の数が増えるほど圧縮が効かなくなる" }
```

### 課題3：集計テーブルを作る（20分）

日別・店舗別・カテゴリ別に集計した小さなテーブルを作り、明細と使い分けます。

```dax
Agg_日別売上 =
SUMMARIZECOLUMNS(
    Fact_売上[OrderDate],
    Fact_売上[StoreID],
    "売上", SUM( Fact_売上[SalesAmount] ),
    "数量", SUM( Fact_売上[Quantity] )
)
```

行数が数百分の1になることを確認してください。実務では Power Query 側で作り、明細テーブルと併存させます。
