所要45分。[スタースキーマ](lesson.html?id=L0601)〜[日付テーブル](lesson.html?id=L0605)の内容を実際のデータで実装します。ここが Power BI 習得の分水嶺です。

## このラボのゴール

4つのCSVから、日付テーブルを含む完全なスタースキーマを構築します。以降のラボはすべてこのモデルの上に積み上がります。

```figure
{ "type":"star", "title":"完成形のモデル", "caption":"中央のファクトに数値、周囲のディメンションに「切り口」を置く",
  "fact":{"label":"Fact_売上","lines":["OrderDate / StoreID","CustomerID / ProductID","Quantity / SalesAmount","約6,900行"]},
  "dims":[
    {"label":"Dim_日付","lines":["Date / 年 / 月","四半期 / 年度"]},
    {"label":"Dim_商品","lines":["ProductName","Category / SubCategory"]},
    {"label":"Dim_顧客","lines":["CustomerName","Segment / Region"]},
    {"label":"Dim_店舗","lines":["StoreName","Prefecture / Region"]} ],
  "edgeLabel":"1対多・単一方向" }
```

> [!NOTE] スタースキーマとは
> 数値（売上・数量）を持つファクトテーブルを1つ中心に置き、その周りに「いつ・どこで・誰が・何を」を説明するディメンションテーブルを放射状に配置する設計です。Power BI のエンジンはこの形に最適化されています。

## ステップ1：4つのテーブルを読み込む（8分）

各ファイルを **データを取得 → テキスト/CSV → データの変換** で読み込み、クエリ名を変更します。

| ファイル | クエリ名 | 役割 |
|---|---|---|
| sales.csv | `Fact_売上` | ファクト（実績） |
| products.csv | `Dim_商品` | ディメンション |
| customers.csv | `Dim_顧客` | ディメンション |
| stores.csv | `Dim_店舗` | ディメンション |

各テーブルでデータ型を確認してください。特に日付列（`OrderDate` `ShipDate` `SignupDate` `OpenDate`）が日付型になっているかを見ます。

> [!TIP] 4ファイルを一度に読む
> **データを取得 → テキスト/CSV** を4回繰り返す代わりに、**フォルダー** コネクタで1回に済ませる方法もあります。ただし4ファイルの列構成が違うため、このラボでは個別読み込みで進めます。フォルダー接続は [LAB07](lab.html?id=LAB07) で本格的に扱います。

> [!TRAP] `Prefecture` の全角ダッシュ
> `stores.csv` の `S014 オンライン` は `Prefecture` が `—`（全角ダッシュ）です。テキスト型なので読み込みは通りますが、地図ビジュアルでは位置が特定できずエラーになります。地図を使うときは除外してください。

## ステップ2：不要な列を削除（3分）

モデルを軽くするため、この分析で使わない列を削除します。

| テーブル | 削除する列 | 理由 |
|---|---|---|
| Fact_売上 | （今回はすべて使用） | — |
| Dim_店舗 | `Manager` | 分析軸にならない。`ManagerEmail` は [LAB06](lab.html?id=LAB06) のRLSで使うので残す |
| Dim_顧客 | `CustomerName` は残す | ドリルスルーの表示に使う |

> [!TIP] 列を減らすとモデルが速くなる
> Power BI は列単位で圧縮して保持します。使わない列を1つ消すだけでファイルサイズと更新時間が減ります。「後で使うかもしれない」で残すとモデルは太る一方です。必要になったときに追加するほうが常に安上がりです。詳細は [カーディナリティとモデルサイズ](lesson.html?id=L1402) を参照してください。

## ステップ3：日付テーブルを作る（10分）

**閉じて適用** した後、**モデリング → 新しいテーブル** で次を入力します。

```dax
Dim_日付 =
VAR MinDate = MIN( Fact_売上[OrderDate] )
VAR MaxDate = MAX( Fact_売上[OrderDate] )
RETURN
ADDCOLUMNS(
    CALENDAR( DATE( YEAR( MinDate ), 1, 1 ), DATE( YEAR( MaxDate ), 12, 31 ) ),
    "年",           YEAR( [Date] ),
    "月番号",       MONTH( [Date] ),
    "月",           FORMAT( [Date], "M月" ),
    "年月",         FORMAT( [Date], "YYYY/MM" ),
    "四半期",       "Q" & ROUNDUP( MONTH( [Date] ) / 3, 0 ),
    "年度",         IF( MONTH( [Date] ) >= 4, YEAR( [Date] ), YEAR( [Date] ) - 1 ),
    "年度月番号",   IF( MONTH( [Date] ) >= 4, MONTH( [Date] ) - 3, MONTH( [Date] ) + 9 ),
    "曜日番号",     WEEKDAY( [Date], 2 ),
    "曜日",         FORMAT( [Date], "aaa" ),
    "平日区分",     IF( WEEKDAY( [Date], 2 ) >= 6, "週末", "平日" )
)
```

```figure
{ "type":"formula", "lang":"dax", "title":"日付テーブルの骨格",
  "code":"ADDCOLUMNS( CALENDAR( 開始日, 終了日 ), \"年\", YEAR( [Date] ) )",
  "caption":"CALENDAR で連続した日付を作り、ADDCOLUMNS で属性を足す。この2段構えが定石",
  "parts":[
    {"match":"ADDCOLUMNS","label":"既存テーブルに列を足して新しいテーブルを返す","tone":"violet"},
    {"match":"CALENDAR( 開始日, 終了日 )","label":"1日の抜けもない連続した日付を作る","tone":"blue"},
    {"match":"YEAR( [Date] )","label":"各行の日付から属性を計算する","tone":"amber"} ] }
```

### 日付テーブルとしてマーク

1. データペインで `Dim_日付` を選択
2. **テーブルツール → 日付テーブルとしてマーク**
3. 日付列に `Date` を指定 → OK

このマークを付けると、タイムインテリジェンス関数（`SAMEPERIODLASTYEAR` など）が正しく動くようになります。

### 自動の日付/時刻をオフにする

**ファイル → オプションと設定 → オプション → 現在のファイル → データの読み込み** で「自動の日付/時刻」のチェックを外します。

> [!WARN] オフにすると起きること
> 既にビジュアルで使っていた「日付の階層」が消えます。[LAB01](lab.html?id=LAB01) のレポートを開いている場合は、`Dim_日付[年]` `Dim_日付[月]` に置き換えてください。オフにする代わりに、日付列1つにつき隠れた日付テーブルが1つ作られる無駄がなくなり、モデルが目に見えて軽くなります。

## ステップ4：リレーションシップを作る（8分）

モデルビューで、次の4本を作成します（自動検出されている場合は設定の確認のみ）。

| 1側（ディメンション） | 多側（ファクト） | 基数 | 方向 |
|---|---|---|---|
| Dim_日付[Date] | Fact_売上[OrderDate] | 1対多 | 単一 |
| Dim_商品[ProductID] | Fact_売上[ProductID] | 1対多 | 単一 |
| Dim_顧客[CustomerID] | Fact_売上[CustomerID] | 1対多 | 単一 |
| Dim_店舗[StoreID] | Fact_売上[StoreID] | 1対多 | 単一 |

各リレーションシップの線をダブルクリックして、基数と方向を必ず目視確認してください。自動検出は「多対多」を作ってしまうことがあります。

```figure
{ "type":"compare", "title":"フラット1枚表 vs スタースキーマ", "caption":"同じデータでも、形が変わると何ができるかが変わる",
  "panels":[
    {"title":"フラットな1枚表","tone":"bad",
     "items":["商品名が約6,900回繰り返される","売上0の商品は一覧に出てこない","顧客セグメント別の顧客数が数えられない","列を足すたびにファイルが太る"],
     "note":"Excelの延長線上"},
    {"title":"スタースキーマ","tone":"good",
     "items":["商品名は32行に1回だけ持つ","全32商品を一覧できる","顧客テーブルを直接数えられる","DAXが素直に書ける"],
     "note":"Power BIの前提"} ] }
```

> [!TRAP] 自動検出が作る「多対多」
> Power BI はテキスト列が一致すると自動でリレーションシップを作りますが、ディメンション側にキーの重複があると**多対多**を選びます。この状態でもレポートは動いてしまうため、気づかないまま数字がずれ続けます。作成直後に必ず線をダブルクリックし、基数を目で確認してください。

### 出荷日の非アクティブなリレーションシップ

`Dim_日付[Date]` から `Fact_売上[ShipDate]` へも線を引きます。すでに `OrderDate` でつながっているため、これは自動的に**非アクティブ（点線）**になります。

後で次のメジャーを作ると、出荷日ベースの売上を出せます。

```dax
出荷ベース売上 =
CALCULATE(
    [総売上],
    USERELATIONSHIP( Dim_日付[Date], Fact_売上[ShipDate] )
)
```

> [!NOTE] なぜ2本目は非アクティブになるのか
> 2つのテーブル間でアクティブな経路は常に1本だけです。2本ともアクティブだと「この売上を1月と2月のどちらに集計するのか」が決まらなくなるためです。使いたいときだけ `USERELATIONSHIP` で一時的に切り替えます。

## ステップ5：モデルを磨く（8分）

### 並べ替え列の設定

| 列 | 並べ替えの基準 |
|---|---|
| Dim_日付[月] | Dim_日付[月番号] |
| Dim_日付[曜日] | Dim_日付[曜日番号] |

**列を選択 → 列ツール → 列で並べ替え** から設定します。これをしないと「1月, 10月, 11月, 12月, 2月…」という文字列順に並びます。

### キー列を非表示に

レポート作成時に使わない列を、右クリック → **レポートビューでは非表示** にします。

- `Fact_売上[ProductID]` `[CustomerID]` `[StoreID]` `[OrderID]`
- `Dim_日付[月番号]` `[曜日番号]` `[年度月番号]`

> [!TIP] 非表示は親切心ではなく設計
> レポートを作る人（半年後の自分を含む）が「どの列を使えばいいか」で迷わないようにするための作業です。見えている列が少ないほど、間違った列を使う事故が減ります。

### 階層を作る

1. `Dim_商品[Category]` を右クリック → **階層の作成** → 名前を `商品階層` に
2. `SubCategory` と `ProductName` をこの階層へドラッグ

同様に `Dim_店舗` で `Region → Prefecture → StoreName` の `地域階層` を作ります。

### データカテゴリの設定

`Dim_店舗[Prefecture]` を選択 → **列ツール → データカテゴリ → 都道府県**。地図ビジュアルが正しく認識できるようになります。

### 書式の設定

`Fact_売上[SalesAmount]` と `[UnitPrice]` に、桁区切り・小数点0桁を設定します。書式は列に設定しておけば、どのビジュアルでも自動的に適用されます。

## トラブルシューティング

| 症状 | 原因 | 対処 |
|---|---|---|
| リレーションシップが作れない | 両側の列の型が違う | Power Query で両方をテキスト型に統一する |
| 「多対多」になってしまう | ディメンション側にキーの重複がある | Power Query で重複の削除を実行する |
| 月が「1月, 10月, 11月…」の順 | 並べ替え列を設定していない | `月` を `月番号` で並べ替える |
| 「循環依存が検出されました」 | 並べ替え列の設定が相互参照している | `月番号` の並べ替えを既定に戻す |
| スライサーが他のビジュアルに効かない | リレーションシップがない／方向が逆 | 1側から多側へ引き直す |
| `Dim_日付` の作成でエラー | `Fact_売上[OrderDate]` が日付型でない | Power Query で日付型に変更してから再作成 |
| 前年比が常に空白（LAB04で発覚） | 日付テーブルとしてマークしていない | ステップ3のマーク作業を実行 |
| ファイルサイズが100MBを超える | 不要な列・高カーディナリティ列が残っている | `OrderID` などの扱いを見直す |

## 発展課題

### 課題1：売上ゼロの商品を見つける（10分）

商品テーブルには32商品あります。次のメジャーを作ってください。

```dax
販売実績 = IF( ISBLANK( [総売上] ), "実績なし", "あり" )
```

テーブルビジュアルに `Dim_商品[ProductName]` と `販売実績` を置きます。年スライサーで期間を絞ると「実績なし」の商品が現れます。**フラットテーブルではこの表示ができません** — 売れていない商品はそもそも1行も存在しないからです。これがディメンションを分ける実利です。

### 課題2：フィルターの伝播を予想してから確かめる（10分）

顧客セグメントのスライサーで「プラチナ」を選んだとき、`Dim_商品` の商品名だけを置いたテーブルビジュアルは絞り込まれるでしょうか。**予想を紙に書いてから**試してください。

答え：**絞り込まれません。** フィルターは 顧客 → 売上 と流れますが、売上 → 商品 へは（単一方向のため）逆流しません。ただし同じテーブルに `総売上` を追加すると、そのメジャーの値はプラチナ顧客の売上だけになります。この挙動の理屈は [リレーションシップの挙動](lesson.html?id=L0603) と [双方向の罠](lesson.html?id=L1202) で扱います。

### 課題3：粒度の違うテーブルを足してみる（15分）

`Dim_店舗` に「月次の売上目標」を追加する場面を想像してください。目標は「店舗 × 月」の粒度で、売上明細は「注文 × 商品」の粒度です。粒度が違う2つのファクトをどう扱うか、モデル図を紙に描いてみてください。

ヒント：ディメンション（`Dim_日付` `Dim_店舗`）を**両方のファクトから共有する**のが正解です。ファクト同士を直接つないではいけません。

### 課題4：モデルを日本語化する（10分）

すべての列名を日本語に変更してください（`ProductName` → `商品名` など）。列を右クリック → 名前の変更で行います。既存のリレーションシップやメジャーは自動的に追従します。レポートを使うのが日本語話者なら、この投資は必ず回収できます。
