所要45分。行レベルセキュリティ（RLS）を実装し、アプリとして安全に配布するまでを体験します。

## このラボのゴール

「各店舗の店長は自分の店舗のデータだけが見える」レポートを作り、Power BI Service に発行して動作を検証します。

```figure
{ "type":"pipeline", "title":"このラボで作る権限モデル", "caption":"ログインした人のメールアドレスから、見える店舗が自動的に決まる",
  "nodes":[
    {"id":"u","label":"Dim_ユーザー権限\nEmail / StoreID","tone":"blue"},
    {"id":"s","label":"Dim_店舗\n14店舗","tone":"green"},
    {"id":"f","label":"Fact_売上\n約6,900行","tone":"amber"} ],
  "edges":[
    {"from":"u","to":"s","label":"双方向（ブリッジ）"},
    {"from":"s","to":"f","label":"1対多"} ] }
```

> [!NOTE] 行レベルセキュリティ（RLS）とは
> 同じレポートを開いても、閲覧者ごとに**見える行が変わる**仕組みです。レポートを人数分作る必要がなくなります。ロールにDAXのフィルター式を書き、そのロールにユーザーを割り当てて実現します。

## security_users.csv の構造

| 列 | 説明 |
|---|---|
| Email | ユーザーのメールアドレス（UPN） |
| StoreID | そのユーザーが閲覧できる店舗ID |

同じメールアドレスが複数行あります。これは「1人が複数店舗を担当する」ケースを表しています。

| ユーザー | 行数 | 意味 |
|---|---|---|
| tanaka@... | 1行（S001） | 新宿本店の店長 |
| area-kanto@... | 4行（S001〜S004） | 関東エリアマネージャ |
| exec@... | 14行（S001〜S014） | 経営層。全店舗 |

**1人が何行でも持てる**のが、この方式（動的RLS）の最大の利点です。

## ステップ1：権限テーブルを読み込む（5分）

1. **データを取得 → テキスト/CSV** で `security_users.csv` を選択
2. **データの変換** → クエリ名を `Dim_ユーザー権限` に変更
3. 両列をテキスト型に設定
4. `Email` 列を選択 → **変換 → 書式 → 小文字**（大文字小文字の揺れを吸収）
5. **ホーム → 閉じて適用**

> [!TRAP] メールアドレスの大文字小文字
> Power BI の文字列比較は大文字小文字を区別しませんが、実運用では前後の空白や全角文字が混ざります。**取り込み時に小文字化＋トリミング**しておくのが安全です。ステップ3のDAX式でも `LOWER()` で受けます。両側で揃えるのが定石です。

## ステップ2：リレーションシップを作る（5分）

モデルビューで、`Dim_ユーザー権限[StoreID]` から `Dim_店舗[StoreID]` へ線を引きます。

| 項目 | 設定 |
|---|---|
| 基数 | 多対1（`Dim_ユーザー権限` が多側、`Dim_店舗` が1側） |
| クロスフィルターの方向 | **両方** |
| セキュリティフィルターを両方向に適用 | オン |

> [!WARN] ここだけは双方向にする
> [双方向リレーションシップの罠](lesson.html?id=L1202) で「双方向は避ける」と学びましたが、**RLSのブリッジテーブルは正当な例外**です。`Dim_ユーザー権限` で絞った結果を `Dim_店舗` に渡し、そこから `Fact_売上` に流す必要があるためです。この1本以外を双方向にしてはいけません。

```figure
{ "type":"steps", "title":"フィルターが流れる順番", "caption":"3段階のうち1つでも切れると、行が0件になるか全件見えるかのどちらかになる",
  "items":[
    {"title":"ログイン情報を受け取る","text":"USERPRINCIPALNAME() が現在のユーザーのメールアドレスを返す","tone":"blue"},
    {"title":"権限テーブルを絞る","text":"ロールのDAX式が Dim_ユーザー権限 を該当行だけに絞る","tone":"green"},
    {"title":"店舗と売上へ伝播する","text":"双方向で Dim_店舗 へ、1対多で Fact_売上 へ流れる","tone":"amber"} ] }
```

## ステップ3：ロールを作成する（8分）

1. **モデリング → ロールの管理 → 作成**
2. ロール名を `店舗担当者` に変更
3. `Dim_ユーザー権限` テーブルを選択
4. DAX式に次を入力

```dax
[Email] = LOWER( USERPRINCIPALNAME() )
```

5. 保存

```figure
{ "type":"formula", "lang":"dax", "title":"ロールのフィルター式",
  "code":"[Email] = LOWER( USERPRINCIPALNAME() )",
  "caption":"この1行が「あなたの行だけ残す」を意味する。TRUE になる行だけが残る",
  "parts":[
    {"match":"[Email]","label":"Dim_ユーザー権限 の各行の値","tone":"blue"},
    {"match":"LOWER","label":"取り込み時に小文字化した値と揃える","tone":"green"},
    {"match":"USERPRINCIPALNAME()","label":"今ログインしている人のメールアドレスを返す","tone":"violet"} ] }
```

> [!EXAM] `USERNAME()` ではなく `USERPRINCIPALNAME()`
> `USERNAME()` は Desktop では `DOMAIN\user` 形式、Service では UPN を返します。**テストと本番で挙動が変わる**ため使いません。`USERPRINCIPALNAME()` はどちらでも UPN を返します。PL-300 の「2.6 行レベルセキュリティ」で頻出です。

## ステップ4：Desktop でテストする（8分）

1. **モデリング → 表示 → ロールとして表示**
2. `店舗担当者` にチェック
3. 「他のユーザー」にチェックを入れ、`tanaka@northstar-retail.example.com` と入力
4. **OK**

画面上部に黄色いバナーが表示され、そのユーザーの視点でレポートが表示されます。

### 確認すること

| ユーザー | 期待される表示 | 総売上の目安 |
|---|---|---|
| tanaka@northstar-retail.example.com | 新宿本店（S001）のみ | 全社の約1/14 |
| suzuki@northstar-retail.example.com | 横浜店（S003）のみ | 全社の約1/14 |
| area-kanto@northstar-retail.example.com | 関東4店舗（S001〜S004） | 全社の約4/14 |
| exec@northstar-retail.example.com | 全14店舗 | 全社と一致 |

5. バナーの「ロールの表示を停止」で通常表示に戻します

```figure
{ "type":"interactive", "widget":"rls-simulator", "title":"ユーザーを切り替えて見える行を確認する",
  "caption":"店長・エリアマネージャ・経営層で、同じレポートの数字がどう変わるか" }
```

> [!TRAP] 「ロールとして表示」で何も表示されないとき
> 次の順に確認してください。
> - `Dim_ユーザー権限 → Dim_店舗` のクロスフィルター方向が「両方」になっているか
> - 「セキュリティフィルターを両方向に適用」がオンか
> - 入力したメールアドレスが `security_users.csv` に存在するか（スペルミス・余分な空白）
> - `Email` 列を小文字化したか

> [!TRAP] 逆に「全部見えてしまう」とき
> ロールにチェックを入れずに「他のユーザー」だけ入力しています。**ロール名のチェックボックスが必須**です。

1. **ホーム → 発行**
2. 発行先のワークスペースを選択（共有ワークスペース。個人用ワークスペースでは共有できません）
3. 発行完了後、「Power BI で開く」をクリック

## ステップ6：Service でロールにユーザーを割り当てる（8分）

1. ワークスペースを開く
2. セマンティックモデルの「**…**」→ **セキュリティ**
3. 左側に `店舗担当者` ロールが表示される
4. 右側の入力欄に、ユーザーまたは**セキュリティグループ**を追加 → **追加** → **保存**

```figure
{ "type":"compare", "title":"Desktop と Service の役割分担", "caption":"この境界を間違えると「設定したのに効かない」が起きる",
  "panels":[
    {"title":"Power BI Desktop","tone":"blue",
     "items":["ロールを作る","DAXフィルター式を書く","ロールとして表示でテスト","ユーザーの割り当てはできない"],
```

> [!EXAM] 分担は頻出
> **ロールの定義は Desktop、ユーザーの割り当ては Service。** Desktop でユーザーを割り当てることはできず、Service でフィルター式を書き換えることもできません。式を直したら再発行が必要です。

### Service でのテスト

1. セキュリティ画面でロール名の「**…**」→ **ロールとしてテスト**
2. 特定のユーザーになりすまして表示を確認できます

> [!TIP] セキュリティグループを使う
> 個人のメールアドレスを直接割り当てると、異動のたびに Power BI 側の設定を直すことになります。Entra ID のセキュリティグループを割り当てておけば、人事側のグループ変更だけで完結します。運用が始まる前に決めておいてください。

1. ワークスペース右上の **アプリの作成**
2. **セットアップ**：アプリ名 `Northstar 売上ダッシュボード`、説明、テーマ色を設定
3. **コンテンツ**：作成したレポートを追加、表示順を調整
4. **対象ユーザー**：

   - アクセス権を付与するグループ/ユーザーを指定
   - **「ビルド権限を許可する」はオフ**（閲覧のみにする場合）

## ステップ8：権限の最終確認（5分）

配布先のユーザーには、次の権限になっている必要があります。

| 対象 | ワークスペースロール | 理由 |
|---|---|---|
| 閲覧者 | **ビューアー**（またはアプリの閲覧者） | RLSが適用されるのはビューアーのみ |
| レポート作成者 | 共同作成者 | 編集はできるがアプリ発行はできない |
| 配布責任者 | メンバー | アプリの発行・更新ができる |
| 全体責任者 | 管理者 | ワークスペースの削除・権限変更ができる |

> [!WARN] RLSを無効化してしまう権限
> **閲覧者に共同作成者以上の権限を与えると、RLSが効かず全データが見えます。** 管理者・メンバー・共同作成者はモデルを編集できる立場であり、RLSの対象外だからです。RLSを実装したら、必ず権限設定も併せて確認してください。「RLSを設定したから安全」は誤りです。

## トラブルシューティング

| 症状 | 原因 | 対処 |
|---|---|---|
| 何も表示されない | 双方向設定が漏れている | クロスフィルター方向を「両方」に |
| 何も表示されない | メールアドレスが権限表にない | `security_users.csv` を確認 |
| 全部見えてしまう | ロールのチェックを入れていない | ロール名にチェック |
| 全部見えてしまう（Service） | ユーザーが共同作成者以上 | ビューアーに変更 |
| 一部の店舗だけ見えない | 権限表の StoreID にスペースが混入 | トリミングを実施 |
| 数字は絞られるが商品一覧が全件 | 単一方向のため商品側に伝播しない | 仕様。必要なら商品側にもRLSを追加 |
| 発行後に式を直したい | Service では変更不可 | Desktop で修正して再発行 |
| 更新が失敗する | ゲートウェイまたは資格情報の設定漏れ | セマンティックモデルの設定を確認 |

## 発展課題

### 課題1：静的ロールを追加する（10分）

「関東エリアのデータだけを見せる」固定ロールを作ってください。

1. **ロールの管理 → 作成** → 名前 `関東限定`
2. `Dim_店舗` テーブルに次の式を設定

```dax
[Region] = "関東"
```

動的RLSと静的RLSの違いは「誰が見ているかを式が参照するかどうか」です。ユーザーが増えても式を直さなくてよいのが動的RLSの利点です。

### 課題2：複数ロールの合成を確かめる（10分）

1人のユーザーに `店舗担当者` と `関東限定` の両方を割り当てるとどうなるでしょうか。予想してから、「ロールとして表示」で両方にチェックを入れて確かめてください。

答え：**OR（和集合）** になります。片方でも見える行は見えます。「両方の条件を満たす行だけ」にはなりません。制限を強めたいときは、1つのロールの中に複数テーブルのフィルターを書きます（この場合は AND）。

### 課題3：オブジェクトレベルセキュリティを調べる（10分）

RLSは「行」を隠しますが、「列そのもの」を隠すにはオブジェクトレベルセキュリティ（OLS）を使います。Tabular Editor が必要です。どんな場面で必要になるか（例：給与列）を考えてみてください。

### 課題4：階層RLSに進む

「エリアマネージャは配下の全店舗を見られる」を組織階層として実装する方法があります。`PATH` と `PATHCONTAINS` を使います。

```dax
PATHCONTAINS(
    Dim_店舗[店舗パス],
    LOOKUPVALUE(
        Dim_ユーザー権限[StoreID],
        Dim_ユーザー権限[Email], LOWER( USERPRINCIPALNAME() )
    )
)
```

本格的な実装は [LAB10](lab.html?id=LAB10) で段階的に扱います。理論は [行レベルセキュリティ](lesson.html?id=L1204) を参照してください。
