ここからはティア4、プロの領域です。上級までは「自分が作るもの」の話でした。ここからは「組織が使い続けるもの」の話をします。

違いは一点に集約されます。**自分が作るものは自分が直せますが、組織が使うものは自分がいなくなっても動き続けなければならない。**この制約が、設計のすべてを変えます。

## なぜ全体像から始めるのか

BIの現場で起きる崩壊には、決まった順序があります。

```figure
{ "type":"timeline", "title":"設計のないBIが崩れる順序", "caption":"どの段階も「悪いこと」に見えないまま進むのが、この崩壊の厄介なところ",
  "items":[
    {"label":"0〜6か月","title":"最初の成功","text":"1人が1つのレポートを作る。速い。喜ばれる。","tone":"green"},
    {"label":"6〜18か月","title":"増殖","text":"部署ごとに似たレポートが増える。それぞれ別のExcelを読んでいる。","tone":"cyan"},
    {"label":"18〜30か月","title":"不一致","text":"会議で売上の数字が2つ出る。どちらが正しいか誰も証明できない。","tone":"amber"},
    {"label":"30か月〜","title":"凍結","text":"怖くて誰も直せない。作った人は異動済み。新規開発が止まる。","tone":"bad"} ] }
```

崩壊の原因は技術力の不足ではありません。**「どの処理をどこに置くか」という約束が組織になかったこと**です。その約束のことをアーキテクチャと呼びます。

> [!NOTE] 要点
> アーキテクチャとは「絵」ではなく「**責務の分担ルール**」です。誰が見ても同じ結論に至る配置の約束があれば、100人が別々に作っても基盤は一貫します。

## BI基盤の5層モデル

どんな規模のBI基盤も、次の5つの層に分解できます。層とは、**責務のまとまり**のことです。

```figure
{ "type":"stack", "title":"BIアーキテクチャの5層", "caption":"上の層は下の層にだけ依存する。逆流させないことが設計の第一原則",
  "layers":[
    {"label":"利用層","sub":"レポート / アプリ / Excel接続 / 埋め込み — 人が意思決定する場所","tone":"pink"},
    {"label":"セマンティック層","sub":"セマンティックモデル — 指標の定義とビジネス用語がある場所","tone":"violet"},
    {"label":"変換層","sub":"データフロー / Notebook / ストアドプロシージャ — 事実を分析可能な形に整える場所","tone":"green"},
    {"label":"保管層","sub":"レイクハウス / ウェアハウス / DWH — 整えたデータが再利用可能な形で置かれる場所","tone":"amber"},
    {"label":"ソース層","sub":"基幹システム / SaaS / ファイル — 事実が発生する場所","tone":"blue"} ] }
```

### 各層の責務を1文で言う

| 層 | 責務 | 置いてはいけないもの |
|---|---|---|
| ソース層 | 業務の事実を記録する | 分析用の加工 |
| 保管層 | 整えたデータを再利用可能な形で保持する | ビジネスルールの解釈 |
| 変換層 | 型・粒度・欠損・結合を整える | 見た目の都合の加工 |
| セマンティック層 | 指標の定義と関係性を持つ | 元データの掃除 |
| 利用層 | 見せ方と操作性 | 指標の再定義 |

この表の右列が重要です。**「置いてはいけないもの」を守れるかどうかが、設計の実力**です。

> [!TRAP] レポート側で指標を定義してしまう
> 「このレポートだけ税抜で見たい」と言われて、レポートのビジュアル上で `売上 * 0.9` のような計算を足す。これは利用層に指標の定義を持ち込んだ状態です。半年後、税率が変わったときに直す場所は誰も知りません。**指標はセマンティック層にしか置かない**。例外を作った瞬間、その基盤の一貫性は失われます。

> [!DS] データサイエンス視点：関心の分離
> 層に分けるという発想は、ソフトウェア工学の**関心の分離（Separation of Concerns）**そのものです。1つの変更理由につき1つの置き場所を用意すると、変更の影響範囲が予測可能になります。逆に、1つのファイルに接続・整形・計算・見た目が全部入っていると、どんな小さな変更もファイル全体の再検証を要求します。pbix 1本にすべてを入れた構成の本質的な問題はこれです。

> 近年よく聞く2語を整理します。**データメッシュ**は組織論で、「データを業務ドメインごとのチームが製品として所有し、責任を持って提供する」という考え方です。ハブアンドスポークの現場側を強化し、各ドメインが自分のゴールド層を持つ形に近い。**データファブリック**は技術論で、「散在するデータをメタデータとカタログで仮想的に統合し、どこにあっても同じように扱える層を作る」という考え方です。Fabric の OneLake やショートカットはこの発想の実装です。片方が正しいのではなく、**メッシュは誰が責任を持つかの話、ファブリックはどう繋ぐかの話**であり、両立します。

## 現行構成を診断する

新規設計より多いのは、既存の混乱を引き継ぐ仕事です。最初にやるべき診断項目を挙げます。

| 診断項目 | 健全 | 危険信号 |
|---|---|---|
| 基幹システムへの直接接続数 | 保管層経由に集約 | 各pbixが直接つないでいる |
| 同名指標の定義数 | 1つ | 「売上」が3種類 |
| 更新失敗の検知 | 自動通知がある | 利用者からの連絡で気づく |
| 所有者不明の資産 | 0件 | ワークスペースの半分 |
| 認定済みモデルの利用率 | 主要レポートの8割 | 認定を誰も使っていない |
| 変換ロジックの重複 | 共有データフロー | 同じMコードが20個 |

> [!TIP] 実務のコツ
> 診断は感想ではなく**件数**で出します。「モデルが多い気がする」ではなく「セマンティックモデル147件、うち90日間アクセス0が82件」。数字にすると経営に説明でき、片付ける予算が付きます。件数はアクティビティログとスキャンAPIから機械的に取れます（M18で扱います）。

## ワークスペース設計は層の写し絵

Power BI / Fabric では、層の分離を**ワークスペースの分け方**で物理的に表現します。ここが曖昧だと、いくら図がきれいでも運用は混ざります。

```figure
{ "type":"stack", "title":"層とワークスペースの対応", "caption":"アクセス権を層ごとに変えられることが、分ける最大の実益",
  "layers":[
    {"label":"WS-Sales-App（配信用）","sub":"アプリとして公開。閲覧者は Viewer のみ。編集者を置かない","tone":"pink"},
    {"label":"WS-Sales-Report（開発用）","sub":"レポート開発者が Contributor。共有モデルへ接続するシンレポート","tone":"violet"},
    {"label":"WS-Model-Certified（共有モデル）","sub":"BIチームのみ Member。認定済みセマンティックモデルを置く","tone":"amber"},
    {"label":"WS-Data-Gold（配信用データ）","sub":"データエンジニアが所有。レイクハウス／データフロー","tone":"green"},
    {"label":"WS-Data-Raw（取り込み）","sub":"人が触らない。パイプラインだけが書く","tone":"blue"} ] }
```

| 判断 | ワークスペースを分ける | 1つにまとめる |
|---|---|---|
| アクセス権が違う | 分ける | — |
| 更新スケジュールの責任者が違う | 分ける | — |
| ライフサイクル（開発／本番）が違う | 分ける | — |
| 同じチームが同時に触る少数の資産 | — | まとめる |
| 分けると相互参照が10本以上になる | — | まとめる |

> 「営業部WS」「経理部WS」という切り方は、最初は自然に見えます。しかし開発中のものと公開中のものが同じ箱に入るため、**未完成のレポートが利用者に見えてしまう**事故が起きます。切る軸は「部署 × ライフサイクル」の2次元です。営業部なら開発用と配信用の2つを持ちます。

③ は特に軽視されがちですが、**手入力データこそ統制対象**です。予算・目標値・組織マスタなどは基幹システムに存在せず、人が作ります。所在が個人のOneDriveのままだと、その人の退職時に基盤が止まります。

この構成の設計判断は3つです。

1. **MESは15分ごとに取り込むが、モデルの更新は1時間ごと**。保管層の鮮度とモデルの鮮度を分けることで、必要なときだけ細かい鮮度を使える。

> アーキテクチャとは責務の分担ルールである。5層に分け、上の層は下の層にだけ依存させ、「置いてはいけないもの」を守る。組織パターンは利用者数と統制要求の2軸で選び、100人規模ならハブアンドスポークが標準解になる。そして非機能要件、特に鮮度は、設計を始める前に数字で合意する。
