Fabric で「顧客マスタを整形してゴールド層に置く」処理を書く方法は、少なくとも4つあります。Dataflow Gen2、Notebook、Warehouse のストアドプロシージャ、そしてパイプラインのコピーアクティビティ＋変換。

**どれでも動きます。**だからこそ、選択の理由を言えないまま選ぶと、3年後に誰も読めない基盤ができあがります。このレッスンは、その選択理由を扱います。

> [!WARN] 執筆時点の情報
> 機能の対応範囲は更新が続いています。ここでは**選択の判断軸**を中心に扱います。個別機能の可否は公式ドキュメントで確認してください。

## ゴールド層の作り方

BI担当にとって最も関心が高いのは、ゴールド層をどう組むかです。ここで手を抜くと、モデル側の努力では取り返せません。

```figure
{ "type":"star", "title":"ゴールド層はスタースキーマで置く", "caption":"モデル側で組み直すのではなく、保管層の時点でこの形にしておく",
  "fact":{"label":"gold_fact_売上","lines":["日付キー / 商品キー / 顧客キー","数量 / 金額 / 原価"]},
  "dims":[
    {"label":"gold_dim_日付","lines":["年 / 四半期 / 月","会計年度 / 営業日フラグ"]},
    {"label":"gold_dim_商品","lines":["商品名 / カテゴリ","ブランド / 単位"]},
    {"label":"gold_dim_顧客","lines":["顧客名 / セグメント","地域 / 業種"]},
    {"label":"gold_dim_組織","lines":["部門 / 支店","階層レベル"]} ],
  "edgeLabel":"整数キーで結合" }
```

ゴールド層をこの形にしておく利点は3つです。

1. **モデル作成がほぼ自動になる** — テーブルを読み込むだけでスタースキーマになる
2. **複数モデルで同じ形を再利用できる** — 各モデルが独自に組み直さない
3. **Direct Lake の性能が出る** — 余計な変換なしで読める

| ゴールド層でやること | ゴールド層でやらないこと |
|---|---|
| ファクトとディメンションへの分解 | レポート固有の並び順の埋め込み |
| サロゲートキーの付与 | フィルターに依存する計算 |
| 業務語での列名付け | 特定部署だけの派生列 |
| 事前集計テーブルの作成 | 見た目のための書式文字列 |

> [!TRAP] ゴールド層に「あるレポート専用」の列を足す
> 「このレポートだけこの区分が欲しい」という要望に応えてゴールド層に列を足し続けると、**ゴールド層が特定レポートの都合で汚れていきます**。数年後には、誰も使っていない列が数十本残ります。判断基準は明確で、**2つ以上のモデルで使うならゴールド層、1つだけならモデル内**です。この線を最初に引いておいてください。

## オーケストレーションの設計

複数のパイプラインが増えてくると、全体の依存関係が見えなくなります。

```figure
{ "type":"stack", "title":"パイプラインの階層構成", "caption":"1つの巨大なパイプラインより、階層に分けたほうが再実行と保守がしやすい",
  "layers":[
    {"label":"マスターパイプライン","sub":"日次の全体制御。各ドメインのパイプラインを順に起動する","tone":"violet"},
    {"label":"ドメインパイプライン","sub":"販売 / 購買 / 生産。ドメイン内の処理順序を制御","tone":"amber"},
    {"label":"テーブル単位のパイプライン／Notebook","sub":"個々の変換処理。単体で再実行できる","tone":"green"} ] }
```

階層に分ける利点は**部分的な再実行ができること**です。販売ドメインだけ失敗したなら、その階層だけを再実行すればよい。1つの巨大なパイプラインでは、最初からやり直すことになります。

> [!DS] データサイエンス視点：ワークフロー管理の一般原則
> データパイプラインの設計原則は、Fabric に限らず共通です。(1) **DAG（有向非巡回グラフ）で依存を表現する** — 循環する依存は必ず破綻する。(2) **タスクは小さく、単一の責務にする** — 失敗の切り分けと部分再実行のため。(3) **状態を外部に持つ** — タスク自身が「どこまで処理したか」を覚えるのではなく、データ側にウォーターマークを持たせる。(4) **リトライは冪等性とセットで初めて安全** — 冪等でない処理のリトライは、重複を生む。この4原則は Airflow でも Fabric でも同じように効きます。

## 実行環境と性能

Notebook を使う場合、Spark の実行環境が性能とコストを決めます。

| 設定 | 意味 | 判断 |
|---|---|---|
| プールのサイズ | 実行に使うノードの規模 | 大きいほど速いがCU消費も増える |
| 起動時間 | セッションが立ち上がるまでの時間 | 小さい処理では起動時間が支配的になる |
| セッションの再利用 | 連続実行で同じセッションを使う | 多数の小処理では有効 |
| 同時実行数 | 並列して走るNotebook数 | 増やすと全体は速いが容量を圧迫する |

> [!TRAP] 小さい処理をNotebookで大量に走らせる
> Spark はセッションの起動に時間がかかります。**数千行の処理を100個のNotebookに分けて走らせると、処理時間の大半が起動待ちになります。**この場合、1つのNotebookでまとめて処理するか、Dataflow Gen2 やストアドプロシージャを使うほうが速く、CU消費も少なくて済みます。「分散処理だから速い」は、データが十分に大きい場合にのみ成り立ちます。

> [!NOTE] このレッスンのまとめ
> Lakehouse と Warehouse はどちらもOneLakeのDeltaテーブルに保存され、違いは操作方法とチームのスキル適合。変換の手段は4つあり、選択基準は性能より「3年後に誰が保守するか」。層ごとに手段を固定すると、構造が逆引きでき障害調査が速くなる。パイプラインはオーケストレーションを担当し、冪等性・失敗時の挙動・リトライ上限・通知・ログの5点を必ず設計する。そして分散処理が速いのは、データが十分に大きい場合だけである。
