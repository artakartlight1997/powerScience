モデルビューでテーブル間に線を引くと、リレーションシップができます。しかし**線を引いた時点で、あなたは3つの設定を同時に決めています**。既定値のまま進むと、意図しない挙動が後から表面化します。

```figure
  "caption": "線を1本引くたびに、この3つが決まっている",
```

> [!NOTE]
> リレーションシップとは、**フィルターが流れる配管**です。データを物理的に結合しているのではなく、「一方のテーブルの選択が、もう一方のテーブルの行をどう絞るか」を定義しています。この見方に切り替えると、以降の挙動がすべて説明できます。

## 基数 — どちらの側でキーが一意か

```figure
{ "type": "star", "title": "スタースキーマの基数はすべて1対多",
  "caption": "ディメンション側が「1」、ファクト側が「多」。矢印はディメンションからファクトへ",
  "fact": {"label": "Fact_売上（多側）", "lines": ["ProductID が何度も現れる", "6,948行"]},
  "dims": [
    {"label": "Dim_商品（1側）", "lines": ["ProductID が一意", "32行"]},
    {"label": "Dim_店舗（1側）", "lines": ["StoreID が一意", "14行"]},
    {"label": "Dim_顧客（1側）", "lines": ["CustomerID が一意", "600行"]} ],
  "edgeLabel": "1対多" }
```

| 基数 | 意味 | 実例 | 使用頻度 |
|---|---|---|---|
| 1対多（1:*） | 片方で一意、もう片方で重複 | Dim_商品 → Fact_売上 | ほぼすべて |
| 多対1（*:1） | 1対多を逆から見たもの | Fact_売上 → Dim_商品 | 同上（表記の違い） |
| 1対1（1:1） | 両方で一意 | 社員 ↔ 社員詳細 | まれ。統合を検討すべき |
| 多対多（*:*） | 両方で重複 | 顧客 ↔ 商品 | 例外的。慎重に扱う |

**スタースキーマが正しく組めていれば、基数は必ず1対多になります。** 逆に言えば、多対多や1対1が現れたら、モデルに問題があるサインです。

## 「多対多になってしまう」の正体

Power BI でリレーションシップを作ろうとして、意図せず多対多になることがあります。原因は1つしかありません。**1側にしたいテーブルのキーに重複がある**ことです。


> [!TRAP]

## クロスフィルターの方向

**フィルターは「1側」から「多側」へ流れます。既定では逆には流れません。**

```figure
{ "type": "pipeline", "title": "フィルターの流れる向き",
  "caption": "ディメンションで絞ると、ファクトの行が絞られる。これが集計の仕組み",
  "nodes": [
    {"id": "d", "label": "Dim_商品\nカテゴリ＝家電を選択", "tone": "green"},
    {"id": "f", "label": "Fact_売上\n家電の行だけに絞られる", "tone": "blue"},
    {"id": "d2", "label": "Dim_店舗\n絞られない", "tone": "gray"} ],
  "edges": [
    {"from": "d", "to": "f", "label": "フィルターが流れる（単一方向）"},
    {"from": "f", "to": "d2", "label": "流れない（既定）"} ] }
```

「カテゴリ別売上」が正しく出るのは、この一方向の流れがあるからです。方向を「両方」にすると、ファクトからディメンションへも流れるようになります。

| 方向 | 挙動 | 使いどころ |
|---|---|---|
| 単一 | 1側 → 多側 のみ | 既定。ほぼすべてのケースでこれ |
| 両方 | 双方向に流れる | 多対多の解決、ブリッジテーブル、一部のRLS |

> [!TRAP]
> 双方向クロスフィルターは、**問題を解決したように見えて、別の場所で新しい問題を作ります**。とくにディメンションが3つ以上あるモデルで双方向を1本入れると、フィルターの経路が複数になり、Power BI が「あいまいさ」を検出してリレーションシップを無効化することがあります。「スライサーが効かないから両方にした」という対処は、ほとんどの場合誤りです。まず `CROSSFILTER` 関数やメジャーでの解決を検討してください（L0604 で扱います）。

## アクティブと非アクティブ

**2つのテーブル間に持てるアクティブなリレーションシップは1本だけ**です。

`sales.csv` には `OrderDate` と `ShipDate` の2つの日付列があります。どちらも `Dim_日付` とつなぎたいところですが、2本目は自動的に非アクティブ（点線）になります。

```figure
  "root": {"label": "OrderDate と ShipDate の両方で分析したい"},
  "children": [

     "children": [

    {"label": "日付テーブルを2つ用意する", "sub": "Dim_受注日 と Dim_出荷日", "tone": "amber",
     "children": [{"label": "両方を同時にスライサーに出せる", "sub": "役割を持つ次元の複製。テーブルは増える"}]},
```

非アクティブなリレーションシップは、DAX で一時的に有効化します。

```dax
出荷日ベース売上 =
CALCULATE(
    SUM( Fact_売上[SalesAmount] ),
    USERELATIONSHIP( Fact_売上[ShipDate], Dim_日付[Date] )
)
```

`USERELATIONSHIP` は「この計算の間だけ、この線をアクティブにする」という指示です。アクティブな受注日のリレーションシップは、この計算の間だけ無効になります。

> [!EXAM]
> PL-300 の頻出パターンです。「受注日と出荷日の両方で売上を分析したい。どうするか」という設問に対し、正解は**非アクティブなリレーションシップを作成し、USERELATIONSHIP を使うメジャーを作る**です。「双方向にする」「リレーションシップを2本ともアクティブにする」は仕様上不可能なので誤りです。日付テーブルを2つ用意する選択肢も正解になり得るので、設問文の「テーブルを追加せずに」といった条件を読んでください。

## 参照整合性と空白行

ファクトに存在するキーが、ディメンションに存在しない場合はどうなるでしょうか。**Power BI はディメンション側に「空白」という架空の行を1行作り、そこに未一致のファクト行を集めます**。

```figure
{ "type": "tablediff", "arrowLabel": "未一致キーがあるときの表示",
  "before": {"title": "Fact_売上（P9999 はマスタにない）", "tone": "bad",
    "head": ["OrderID", "ProductID", "SalesAmount"],
    "rows": [["O000001", "P0027", "1580"], ["O009999", "!P9999", "!48000"]]},
  "after": {"title": "カテゴリ別売上の表示", "tone": "amber",
    "head": ["Category", "売上"],
    "rows": [["食品", "1580"], ["!（空白）", "!48000"]]} }
```

この「(空白)」という行は、**参照整合性が壊れていることを知らせる警告**です。金額は失われていないので合計は正しく出ますが、どのカテゴリにも属さない売上が存在することになります。

対処は、隠すのではなく直すことです。

1. L0505 の左反結合で、未一致のキーを洗い出す
2. マスタ側に登録を依頼する、または不明品として明示的にディメンションへ1行追加する
3. ディメンションに「不明」「未登録」という行を用意しておく設計は、実務で広く使われる

> [!TRAP]
> 「(空白) が出て見た目が悪いからビジュアルレベルでフィルターして消す」のは最悪の対処です。**数字が消えるだけで、問題は残ります**。合計が他のレポートと合わなくなり、原因調査に何日もかかります。空白行は必ず原因を追ってください。

## 1対1と多対多

**1対1**は、両方のテーブルでキーが一意な関係です。多くの場合、2つのテーブルを1つに統合すべきサインです。統合しない理由があるとすれば、機密列を分離してRLSを掛ける、といった特殊な要件のときだけです。

**多対多**は Power BI で直接作成できますが、慎重な扱いが必要です。典型例は「1つの顧客が複数のセグメントに属する」といった関係です。正しい解決は、間に **ブリッジテーブル**（両方のキーの組み合わせを持つ表）を置き、両側から1対多でつなぐことです。

```figure
{ "type": "pipeline", "title": "多対多をブリッジテーブルで解消する",
  "caption": "直接つながず、組み合わせの表を挟む。関係が明示的になる",
  "nodes": [
    {"id": "c", "label": "Dim_顧客\n（1側）", "tone": "green"},
    {"id": "b", "label": "Bridge_顧客セグメント\n（多側）", "tone": "amber"},
    {"id": "s", "label": "Dim_セグメント\n（1側）", "tone": "green"},
    {"id": "f", "label": "Fact_売上", "tone": "blue"} ],
  "edges": [
    {"from": "c", "to": "b", "label": "1対多"},
    {"from": "s", "to": "b", "label": "1対多"},
    {"from": "c", "to": "f", "label": "1対多"} ] }
```

> [!WARN]
> 多対多を使うと、**合計が単純な足し算にならなくなります**。1件の売上が複数のセグメントに数えられるため、セグメント別売上の合計が全体売上を上回ります。これは誤りではなく多対多の必然ですが、**レポートを見る人には必ず説明が必要**です。注釈なしに出すと「数字が合っていない」と受け取られます。

## リレーションシップかDAXか

「フィルターが届かない」問題に直面したとき、選択肢は2つあります。モデルを変えるか、DAX で解決するか。

```figure
{ "type": "compare", "title": "モデルで解決する vs メジャーで解決する",
  "caption": "モデルの変更は全レポートに影響する。メジャーの変更はその指標だけに閉じる",
  "panels": [
    {"title": "双方向にしてモデルで解決", "tone": "bad",
     "items": ["1本変えるだけで全ビジュアルに影響", "経路のあいまいさを生む可能性", "性能への影響が読みにくい", "影響範囲を検証しきれない"],
     "note": "影響が広い"},
    {"title": "メジャーで解決", "tone": "good",
     "items": ["影響がそのメジャーだけに閉じる", "CROSSFILTER で必要な時だけ双方向にできる", "意図がコードに残る", "後から取り消しやすい"],
     "note": "影響が局所的"} ] }
```

```dax
-- 売れた商品の数（双方向にせずファクト側から数える）
売れた商品数 =
CALCULATE(
    DISTINCTCOUNT( Fact_売上[ProductID] )
)
```

```dax
-- どうしても双方向が必要なときは、そのメジャーの中だけで有効化する
商品数_売上ありのみ =
CALCULATE(
    COUNTROWS( Dim_商品 ),
    CROSSFILTER( Dim_商品[ProductID], Fact_売上[ProductID], BOTH )
)
```

**原則は「モデルは単純に保ち、複雑さはメジャーに閉じ込める」**です。モデルは全員が使う共有物なので、変更のコストが高くつきます。

## リレーションシップ設計の点検表

モデルが完成したら、次の項目を1本ずつ確認してください。所要は数分ですが、これを飛ばすと数日を失います。

| 点検項目 | 合格 | 不合格のときの対処 |
|---|---|---|
| すべての線が1対多か | 1と*が表示されている | 1側の重複を解消する |
| 矢印がディメンション→ファクトか | 単一方向の矢印が下向き | 基数の設定を見直す |
| 双方向の線が0本か | 0本、または理由を説明できる | メジャーでの解決に置き換える |
| 非アクティブな線の用途が明確か | USERELATIONSHIP を使うメジャーがある | 不要なら削除する |
| ディメンション同士がつながっていないか | つながっていない | スノーフレークを解消する |
| ファクト同士がつながっていないか | つながっていない | 共有ディメンション経由に変える |
| 空白行が出ていないか | 出ていない | 左反結合で未一致キーを調査する |

## 型と結合キーの実務

リレーションシップは、両側のキー列の**型が一致していないと作成できません**。しかも、型が一致していても値の見た目が同じとは限りません。

| 状況 | 起きること | 対処 |
|---|---|---|
| 片方が text、片方が whole number | 線が引けない | Power Query 側で型を揃える |
| 前後に空白がある | 一致せず空白行が発生 | 両側にトリミングを適用する |
| 大文字小文字が違う | Power BI の照合は大文字小文字を区別しない | 通常は一致する。ただし表示は不安定になる |
| キーが日付型と日付時刻型 | 時刻部分があると一致しない | 日付テーブルとの結合では必ず date 型に揃える |

```figure
    {"label": "型の不一致", "sub": "text と number", "tone": "amber"},
```

> [!TRAP]
> 日付でのつまずきが最も多く発生します。ファクトの `OrderDate` が **日付時刻型で時刻に 09:15:00 が入っている**と、日付テーブルの 00:00:00 と一致せず、その行はすべて空白行に落ちます。合計金額は正しいのに、月別に分けると全部「(空白)」に集まる、という症状です。**日付テーブルとつなぐキーは、必ず時刻を落とした date 型にしてください**。Power Query で「日付」型に変換すれば時刻部分は切り捨てられます。

## 理解度チェック

2. カテゴリ別売上の表に「(空白)」という行が現れ、48,000円が計上されています。何が起きていますか。正しい対処と、やってはいけない対処をそれぞれ述べてください。

| 基数が多対多になる | 1側のキーに重複がある | 列の分布で重複を確認し、キーで重複削除するか粒度を見直す |
| リレーションシップが作れない | キーの型が違う | 両側の型を揃える（IDは text 型が安全） |
| 「(空白)」行が出る | ファクトのキーがディメンションにない | 左反結合で未一致キーを洗い出し、マスタを修正する |
| スライサーが一部のビジュアルに効かない | フィルターの向きが単一で届いていない | メジャー側で解決する。安易に双方向にしない |
| リレーションシップが勝手に無効化された | 経路のあいまいさが検出された | 双方向を単一に戻し、経路を1本に絞る |
| 2本目の日付の線が点線になる | アクティブは1本までの仕様 | USERELATIONSHIP を使うメジャーを作る |
| 合計が全体より大きい | 多対多で重複計上されている | 仕様であることを説明するか、粒度を見直す |
| 意図しない線が引かれている | 自動検出が有効 | オプションで自動検出を無効にし、手動で引き直す |
