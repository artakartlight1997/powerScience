## 計算列は「表に列が増える」

計算列は、Power Query で列を追加するのとよく似ています。違いは、計算するのが Power Query エンジンではなく DAX エンジンだという点です。

```dax
-- Fact_売上 に作る計算列
利益額 = Fact_売上[SalesAmount] - RELATED( Dim_商品[StandardCost] ) * Fact_売上[Quantity]
```

この式は、`Fact_売上` の **1行ごと** に評価されます。100万行あれば100万回計算され、100万個の結果が列として保存されます。

```figure
{ "type":"tablediff", "arrowLabel":"計算列を追加", "title":"計算列は表を横に太らせる",
  "caption":"データ更新のたびに全行ぶんが計算され、そのままモデルに保存される",
  "before":{"title":"元の Fact_売上","tone":"neutral",
    "head":["OrderDate","ProductID","Quantity","SalesAmount"],
    "rows":[["2024-04-01","P001","2","240000"],["2024-04-01","P042","5","15000"],["2024-04-02","P001","1","120000"]]},
  "after":{"title":"利益額 列が増えた","tone":"blue",
    "head":["OrderDate","ProductID","Quantity","SalesAmount","利益額"],
    "rows":[["2024-04-01","P001","2","240000","!60000"],["2024-04-01","P042","5","15000","!6750"],["2024-04-02","P001","1","120000","!30000"]]} }
```

計算列の中では、**その行の値をそのまま参照できます**。`Fact_売上[SalesAmount]` と書けば「いま処理している行のSalesAmount」を意味します。
これを可能にしているのが **行コンテキスト**（いまどの行を処理しているかという情報）です。L0802 で詳しく扱います。

## メジャーは「表に何も増えない」

メジャーは、式の定義だけがモデルに保存されます。表は1ミリも太りません。

```dax
売上合計 = SUM( Fact_売上[SalesAmount] )
利益額合計 =
SUMX( Fact_売上, Fact_売上[SalesAmount] - RELATED( Dim_商品[StandardCost] ) * Fact_売上[Quantity] )
```

> [!TRAP] メジャーの中で列を「直接」参照できない理由
> 次の式はエラーになります。
>
> ```dax
> -- ✗ エラー：1つの値が必要ですが、複数の値が見つかりました
> 売上NG = Fact_売上[SalesAmount]
> ```
>
> メジャーが評価されるとき、そこには「いま処理している行」が存在しません。あるのは**絞り込まれた表**だけです。
> 100万行の表に対して「SalesAmount列の値を出せ」と言われても、エンジンはどの行のことか決められません。
> だから **メジャーの中の列参照は、必ず集計関数で包む** 必要があります。これはDAX最初の関門であり、この一文で説明が尽きます。

## 決定的な違いが表に出る例：利益率

ここからが本題です。**利益率を計算列で作ると壊れます。** 数字で確認します。

商品カテゴリ別の売上と原価は次のとおりです。

| Category | 売上 | 原価 | 利益 | 利益率 |
|---|---|---|---|---|
| 家電 | 52,000,000 | 39,000,000 | 13,000,000 | 25.0% |
| 衣料 | 18,000,000 | 9,900,000 | 8,100,000 | 45.0% |
| 食品 | 30,000,000 | 24,000,000 | 6,000,000 | 20.0% |
| **合計** | **100,000,000** | **72,900,000** | **27,100,000** | **27.1%** |

もし各行で計算した利益率を「平均」してしまうと、`(25 + 45 + 20) / 3 = 30.0%` になります。
正解は **27.1%** です。3ポイントもずれました。

```figure
{ "type":"chart", "kind":"bar", "title":"利益率：正しい計算と誤った平均",
  "caption":"行ごとの比率を平均すると、規模の大きい家電の影響が過小評価される",
  "categories":["家電","衣料","食品","全体（正）","行平均（誤）"],
  "series":[{"name":"利益率","values":[25,45,20,27.1,30],"tone":"blue"}],
  "highlight":4, "unit":"%" }
```

> [!DS] 比率の平均は、平均の比率ではない
> 一般に、比率どうしを単純平均すると誤ります。正しくは **分子の合計 ÷ 分母の合計** です。
> 統計では前者を「マクロ平均」、後者を「マイクロ平均」と呼び分けることもあります。
> 売上規模が大きく違う集団を混ぜるほど、この差は開きます。**比率指標は、必ず分子と分母をそれぞれ集計してから割る。** これはDAXに限らず、あらゆる分析での鉄則です。

### 計算列で書くとどうなるか

```dax
-- ✗ アンチパターン：Fact_売上 の計算列
利益率列 = DIVIDE( Fact_売上[SalesAmount] - Fact_売上[原価額], Fact_売上[SalesAmount] )
```

この列を作ると、行ごとの利益率が保存されます。これをビジュアルに置くと、既定の集計は「合計」なので、
`25% + 45% + 20% = 90%` のような無意味な数字が出ます。集計を「平均」に変えても、上で見たとおり `30%` で誤りです。

### メジャーで書くと正しくなる

```dax
利益率 =
DIVIDE(
    [売上合計] - [原価合計],
    [売上合計]
)
```

```figure

  "code":"利益率 = DIVIDE( [売上合計] - [原価合計], [売上合計] )",
  "parts":[
    {"match":"DIVIDE","label":"ゼロ除算に強い割り算。分母が0やBLANKなら空を返す","tone":"violet"},

```

メジャーは各セルで再評価されるので、合計行では「合計の売上」と「合計の原価」で割り算が行われ、`27.1%` が出ます。
**集計してから割るのか、割ってから集計するのか。順序が結果を変えます。**

「行ごとの列がほしい」と決まったあと、もう一段の選択があります。

```figure

  "root":{"label":"行ごとの列が必要"},
```

> [!EXAM] PL-300で問われる
> 「レポート利用者がスライサーで絞り込めるようにしたい」→ **計算列**。
> 「複数のビジュアルで同じ集計を使い回したい」「モデルサイズを増やしたくない」→ **メジャー**。
> この対応関係は頻出です。設問文の「スライサー」「絞り込み」という語を目印にしてください。

## 実装して比べる

同じ「平均単価」を両方で作り、結果の違いを確認します。

```dax
-- 計算列（Fact_売上）
単価列 = DIVIDE( Fact_売上[SalesAmount], Fact_売上[Quantity] )

-- メジャー
平均単価 = DIVIDE( [売上合計], [数量合計] )
```

| Category | 単価列の平均（計算列） | 平均単価（メジャー） |
|---|---|---|
| 家電 | 43,500 | 41,600 |
| 衣料 | 4,120 | 3,600 |
| 食品 | 780 | 750 |
| **合計** | **9,800** | **2,500** |

合計行の差が極端です。計算列版は「全取引行の単価を単純平均した値」であり、
メジャー版は「総売上 ÷ 総数量」、つまり実際の平均単価です。
**顧客に説明できるのは後者だけです。**

## 理解度チェック

**問1.** 「販売単価が5,000円以上の取引だけをスライサーで選べるようにしたい」と依頼された。計算列とメジャーのどちらで実装するか。

<details><summary>答え</summary>
計算列。スライサーに置けるのは列だけであり、メジャーは置けない。`単価帯 = IF( DIVIDE(Fact_売上[SalesAmount], Fact_売上[Quantity]) >= 5000, "高単価", "通常" )` のような列を作る。
</details>

**問2.** 利益率を各行の計算列で求め、ビジュアルで「平均」集計にしたところ、全体の利益率と一致しなかった。原因を1文で説明せよ。

<details><summary>答え</summary>
比率を先に計算してから平均すると、金額規模の違いが無視されるため。正しくは分子（利益）と分母（売上）をそれぞれ集計してから割る（マイクロ平均）。
</details>

**問3.** `売上NG = Fact_売上[SalesAmount]` というメジャーがエラーになる理由を、行コンテキストという語を使って説明せよ。

<details><summary>答え</summary>
メジャーの評価時には行コンテキストが存在せず、対象は絞り込まれた複数行の集合であるため、どの行の値を返すべきか決定できない。集計関数で1つの値に潰す必要がある。
</details>

## よくあるエラーと原因

| 症状・エラー | 原因 | 対処 |
|---|---|---|
| 「1つの値が必要ですが、複数の値が…」 | メジャー内で列を直接参照した | `SUM` `MAX` などで包む、または `SUMX` を使う |
| 計算列がスライサーに反応しない | 計算列は更新時に確定するため仕様 | 動的にしたいならメジャーにする |
| 比率の合計行が明らかにおかしい | 比率を計算列で作って合計・平均している | メジャーで「集計してから割る」形に直す |
| ファイルサイズが急に膨らんだ | ファクトテーブルに計算列を追加した | Power Query 側へ移すか、メジャーで代替する |
| 計算列で `RELATED` がエラー | リレーションが無い、または多側から一側でない | リレーションを確認。逆方向なら `RELATEDTABLE` |
| メジャーがデータペインに見つからない | 別テーブルに作られている | メジャー専用テーブルに整理する（L0706） |

> [!NOTE] このレッスンのまとめ
> 計算列は**更新時に行ごと**に評価され、表に保存されます。メジャーは**集計時にセルごと**に評価され、何も保存しません。
> 比率・平均・割合の類は、例外なくメジャーで「集計してから割る」。
> 計算列を使うのは、スライサー・並べ替え・リレーションなど**列でなければならない理由**があるときだけです。
