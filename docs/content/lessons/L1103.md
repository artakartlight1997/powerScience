「更新に3時間かかる」という相談の原因は、ほとんどの場合1つです。**1億行のテーブルを全部Power BIに転送してから、Power Query側でフィルターしている**。同じ結果を、データベース側で先に絞ってから受け取れば、転送は数十万行で済み、更新は数分で終わります。

この違いを生む仕組みが **クエリ フォールディング（query folding）** です。Power Query が、あなたの書いた変換ステップを**データソースが理解できる言語（SQLなど）に翻訳し、ソース側で実行させる**動作を指します。

## 折りたたみが効くとき、効かないとき

同じフィルター、同じ結果、同じ行数。違うのは**どこで絞ったか**だけです。

> [!NOTE] 要点
> クエリ フォールディングとは、Power Query のステップをデータソースのネイティブ言語（SQL、OData のクエリ文字列など）に変換し、**ソース側に処理を押し付ける**仕組みです。折りたたまれたステップの分だけ、Power BI に転送されるデータが減ります。

> [!DS] データサイエンス視点
> データベースの世界で **述語プッシュダウン（predicate pushdown）** と呼ばれる最適化と同じ考え方です。「フィルター条件（述語）を、データに最も近い層まで押し下げる」ことで、読み取り量と転送量を減らします。Spark、BigQuery、Snowflake など現代の分散処理エンジンも同じ最適化を持っており、**「計算をデータのある場所へ動かす」** はデータ処理の基本原則です。データを計算のある場所へ動かすのが、最も高くつきます。

## `Table.Buffer` は最後の手段

`Table.Buffer` はテーブルをメモリに固定します。**実行されるたびにソースへ問い合わせに行くのを防ぐ**ために使いますが、副作用として**その時点で折りたたみが完全に切れます**。

```m
let
    Src = Sql.Database(pServer, pDatabase),
    Fact = Src{[Schema="dbo", Item="FactSales"]}[Data],
    絞り込み = Table.SelectRows(Fact, each [売上日] >= #date(2026,1,1)),
    // ここまでは折りたたまれる。次の行で切れる
    固定 = Table.Buffer(絞り込み),
    // 以降はメモリ上のテーブルに対する処理
    追加 = Table.AddColumn(固定, "四半期", each "Q" & Text.From(Date.QuarterOfYear([売上日])), type text)
in
    追加
```

`Table.Buffer` が有効な場面は限られます。

| 場面 | Buffer の効果 |
|---|---|
| 小さなマスタを、大きなテーブルの各行から参照する | 参照のたびのソースアクセスを防ぎ、劇的に速くなる |
| 同じ中間結果を複数のクエリが参照する | 再計算を防げることがある |
| ソースが更新中で結果が揺れる | 一貫したスナップショットを固定できる |
| 単に「速くなりそうだから」 | **遅くなる。折りたたみが切れて全件転送になる** |

> [!TRAP] つまずきポイント
> 「Table.Buffer を入れたら速くなると聞いた」で全クエリの先頭に入れる人がいます。**先頭に置くと、そのテーブルを全件メモリに読み込むという意味**になり、最悪の結果になります。Buffer は「小さいテーブル」に対して、「繰り返し参照される」場合にだけ使ってください。

## `Value.NativeQuery` — SQLを直接書く

折りたたみで表現できない処理（ウィンドウ関数、複雑な集計、ソース固有の関数）は、SQLを直接書いて渡せます。

```m
let
    Src = Sql.Database(pServer, pDatabase),
    // EnableFolding=true を付けると、この結果に対する後続ステップも折りたたまれる
    Q = Value.NativeQuery(
        Src,
        "SELECT 商品ID, CAST(売上日 AS date) AS 売上日, SUM(金額) AS 金額 " &
        "FROM dbo.FactSales " &
        "WHERE 売上日 >= @from AND 売上日 < @to " &
        "GROUP BY 商品ID, CAST(売上日 AS date)",
        [from = RangeStart, to = RangeEnd],
        [EnableFolding = true]
    )
in
    Q
```

3番目の引数がパラメータのレコードです。**文字列連結でSQLを組み立てるのではなく、パラメータとして渡すこと**。これはSQLインジェクション対策であると同時に、ソース側で実行計画が再利用される利点もあります。

> [!WARN] 注意
> `Sql.Database(server, db, [Query="SELECT ..."])` のようにネイティブSQLを接続時点で埋め込むと、**そこから先の折りたたみが原則として効かなくなり**、増分更新も動きません。同じことをするなら `Value.NativeQuery(..., [EnableFolding=true])` を使ってください。

> [!TRAP] つまずきポイント
> ネイティブSQLを埋め込んだクエリは、**Power BI Serviceでの更新時に「ネイティブ データベース クエリの承認」が必要**になったり、データソースの権限設定によっては拒否されたりします。ローカルでは動くのにService上で失敗する典型パターンです。発行前にゲートウェイ／クラウド接続の設定を確認してください。

## 見落としやすい折りたたみ阻害要因

| 要因 | なぜ切れるか | 対処 |
|---|---|---|
| 異なるソースのマージ | ソースをまたぐ翻訳ができない | 片方を先にDBへ取り込むか、ステージングする |
| プライバシー レベルの設定 | データ結合が禁止され、内部でバッファされる | 組織のポリシーに従いレベルを揃える |
| 「型の変更」で特殊な型を指定 | 翻訳先の型が存在しない | ソース側でCASTしておく |
| 条件付き列に複雑な入れ子 | M固有の評価になる | SQLのCASE式としてビューに持たせる |
| 列名に依存する動的な処理 | 実行時まで列が確定しない | 列構成を固定してから処理する |

> [!WARN] 注意
> **プライバシー レベル**（データソースの分離設定）が原因で折りたたみが切れるケースは、原因が非常に分かりにくいものの1つです。異なるソースを結合しているのに更新が異常に遅い場合、ファイル→オプションと設定→オプション→プライバシーで設定を確認してください。組織のセキュリティ方針と相談のうえで判断します。

> Power BI のインポートモデルは **列指向ストレージ（columnar storage）** です。行単位ではなく列単位でデータを並べて圧縮するため、**同じ値が繰り返される列ほど強く圧縮されます**。逆に、伝票番号やGUIDのような「ほぼ全行で異なる値」を持つ列（高カーディナリティ列）は、ほとんど圧縮が効かず、モデルサイズの大半を占めることがあります。「明細レベルの伝票番号列を外したらpbixが1.2GBから300MBになった」というのは典型的な結果です。分析に使わない識別子列は、モデルに入れないでください。

## ゲートウェイ経由での注意点

オンプレミスのデータベースを使う場合、更新は **オンプレミス データ ゲートウェイ**（社内ネットワークとPower BI Serviceを中継するソフトウェア）を通ります。ここでも折りたたみの有無が効きます。

| 状況 | ゲートウェイでの影響 |
|---|---|
| 折りたたみが効いている | ゲートウェイは絞られた結果だけを中継する。負荷が小さい |
| 折りたたみが切れている | 全件がゲートウェイのメモリを経由する。他の更新まで巻き添えで遅くなる |
| 複数モデルが同時更新 | ゲートウェイのCPU・メモリが枯渇し、タイムアウトが多発する |

> [!TRAP] つまずきポイント
> 「自分のレポートは軽いのに、朝9時だけ更新が失敗する」という現象は、**同じゲートウェイを使う別の重いモデルが同時刻に更新されている**ことが原因のケースが多いです。自分のクエリだけを見ても直りません。ゲートウェイのパフォーマンス ログを確認し、更新スケジュールを分散させてください。折りたたみを効かせて自分の負荷を減らすことは、他人への配慮でもあります。

## 折りたたみを維持したまま書くための書き換え例

M固有の関数に見える処理でも、書き方を変えれば折りたたまれることがあります。

```m
// 折りたたまれない書き方：M の Date 関数を条件に使っている
let
    Src = Sql.Database(pServer, pDatabase),
    Fact = Src{[Schema="dbo", Item="FactSales"]}[Data],
    悪い = Table.SelectRows(Fact, each Date.Year([売上日]) = 2026)
in
    悪い
```

```m
// 折りたたまれる書き方：範囲比較に直す
let
    Src = Sql.Database(pServer, pDatabase),
    Fact = Src{[Schema="dbo", Item="FactSales"]}[Data],
    良い = Table.SelectRows(Fact,
        each [売上日] >= #date(2026,1,1) and [売上日] < #date(2027,1,1))
in
    良い
```

**列に関数を適用した結果を条件にすると、多くの場合ソース側で索引が使えなくなり、折りたたみも切れます**。「列そのものを範囲で比較する」形に書き換えるのが定石です。これはSQLでの `WHERE YEAR(日付)=2026` を `WHERE 日付 >= '2026-01-01' AND 日付 < '2027-01-01'` に直すのと同じ話で、**サージ可能（SARGable）な条件にする**と呼ばれます。

> [!TIP] 実務のコツ
> 増分更新で使う `RangeStart` / `RangeEnd` によるフィルターも、まさにこの「日付列そのものを範囲比較する」形です。次のレッスンで、この形が必須である理由が分かります。

## 設計判断チェックリスト

- [ ] ソースは折りたたみに対応しているか（DBか、ファイルか）を最初に確認したか
- [ ] 最後のステップで「ネイティブ クエリの表示」が選択できるか確認したか
- [ ] 折りたたみが切れる境界のステップを特定したか
- [ ] フィルターとグループ化をクエリの先頭側に寄せたか
- [ ] 不要な列を最初のステップで削除しているか
- [ ] `Table.Buffer` を「なんとなく」入れていないか
- [ ] ネイティブSQLを使う場合、`Value.NativeQuery` に `EnableFolding=true` を指定したか
- [ ] Service上での更新（ゲートウェイ経由）でも同じ経路が成立するか確認したか
- [ ] ビューをDB側に作るという選択肢を検討したか

## 理解度チェック

1. クエリの2番目のステップでインデックス列を追加し、3番目で年によるフィルターをしています。このクエリで何行が転送されますか。改善方法とその理由を説明してください。
2. 「ネイティブ クエリの表示」がすべてのステップでグレーアウトしています。考えられる原因を2つ挙げ、それぞれの対処を述べてください。
3. `Table.Buffer` を使うべき場面と、使ってはいけない場面をそれぞれ1つずつ具体的に挙げてください。
