ピボット解除やマージを学ぶ前に、**そもそも何を目指して整形するのか**をはっきりさせます。ゴールが分かっていない整形は、ボタンを押す順番の暗記になってしまいます。

目指す形には名前があります。**整然データ（tidy data）** です。統計学者 Hadley Wickham が 2014 年の論文で定義した、分析しやすいデータの標準形です。


この2つは対立しません。**整然データを土台に置き、人が読む表はビジュアルとして出力する**のが Power BI の使い方です。順番を逆にすると、集計済みの表から元の数字を復元できず、行き詰まります。

```figure

  "items": [
    {"icon": "1️⃣", "title": "1つの列は1つの変数", "text": "列名は変数の名前であり、データの値ではない。「2025年1月」という列名は、月という変数の値が列名に化けている状態。", "tone": "blue"},
    {"icon": "2️⃣", "title": "1つの行は1つの観測", "text": "1行が1回の出来事（1件の受注、1日の在庫）に対応する。小計行は観測ではないので混ぜない。", "tone": "green"},
    {"icon": "3️⃣", "title": "1つの表は1つの観測単位", "text": "受注明細と商品マスタは観測単位が違うので、別テーブルにする。混ぜると同じ値が延々と繰り返される。", "tone": "amber"} ] }
```

> [!NOTE]
> 3つのルールは、覚えるものではなく**判定に使う道具**です。目の前の表を見て「列名に値が入っていないか」「1行は何の1件か」「この表に何種類の観測単位が混ざっているか」を順に聞けば、直すべき箇所が特定できます。

## ルール2違反 — 1行が1観測になっていない

`新宿本店 小計` の行は、何かの出来事を記録した行ではありません。**他の行を足した結果**です。これが混ざったまま合計すると、値が二重に数えられます。

```figure
{ "type": "chart", "kind": "bar", "title": "小計行を残したまま合計すると何が起きるか",
  "categories": ["正しい合計", "小計行を含む合計"],
  "series": [{"name": "売上", "values": [8.1, 16.2], "tone": "blue"}],
  "highlight": 1, "unit": "百万円" }
```

小計は**データではなく計算結果**です。整然データには結果を持ち込まず、必要なら Power BI 側で合計させます。同じ理由で、次のような行も観測ではありません。

- 「※この行は集計対象外」といった注釈行
- ヘッダーの繰り返し（複数シートを結合したときに紛れ込む）
- 空行（区切りとして入れられたもの）

> [!DS]
> 整然データの3ルールは、リレーショナルデータベースの**正規化**、とくに第3正規形と本質的に同じことを言っています。Wickham は 2014 年の論文 "Tidy Data"（Journal of Statistical Software）で、Codd の正規形を統計分析の文脈に翻訳しました。違いは目的です。データベースの正規化は更新時の矛盾を防ぐために行い、整然データは分析ツールに素直に食わせるために行います。結果として形はほぼ一致します。BI では、**取り込み時は整然データ（正規化寄り）、モデル上はスタースキーマ（ディメンションだけ非正規化）** という折衷が最適解になります。

## 粒度を1文で宣言する

整然データを作るとき、最初に決めるべきものが **粒度（グレイン）** です。粒度とは「この表の1行が何を表すか」の定義です。

```figure
{ "type": "steps", "title": "粒度を宣言する手順",
  "caption": "この1文が書けないテーブルは、必ず後でトラブルになる",
  "items": [
    {"title": "1行が何かを言葉にする", "text": "「1行は、1件の受注明細（受注1件の中の商品1つ）を表す」のように書く。", "tone": "blue"},
    {"title": "その粒度を決める列を挙げる", "text": "受注明細なら OrderID + ProductID。この組み合わせが表の中で一意になる。", "tone": "green"},
    {"title": "一意性を検証する", "text": "その列の組み合わせで重複がないか、列の分布や重複の削除で確認する。", "tone": "amber"},
    {"title": "粒度より細かい情報を持ち込まない", "text": "1受注に1つしかない情報（受注日）は持てるが、明細ごとに変わらない値を明細に散らかさない。", "tone": "violet"} ] }
```

`sales.csv` の粒度を宣言してみます。

> **`sales.csv` の1行は、1件の受注における1商品の販売を表す。粒度は OrderID × ProductID。**

この宣言があると、判断が自動的に決まります。`SalesAmount` は行ごとに意味を持つので置いてよい。`ProductName` は `ProductID` から一意に決まるので置く必要がない（商品テーブルに置く）。`CustomerName` も同様です。

> [!TRAP]
> 「粒度を細かくしておけば後から集計できるから、常に最も細かい粒度がよい」と考えるのは、半分だけ正しい判断です。確かに細かい粒度は情報を失いませんが、行数が増えれば更新も計算も重くなります。**分析で必要な最も細かい粒度**まで下げ、それ以上は下げないのが正解です。日次で十分な分析に、秒単位のログを丸ごと取り込む必要はありません。

## 整然データが Power BI で効く理由

```figure
{ "type": "flow", "title": "整然データが下流にもたらすもの",
  "caption": "上流の形が、下流のすべての作業のやりやすさを決める",
  "dir": "col",
  "items": [
    {"label": "整然データ", "sub": "1列1変数・1行1観測", "tone": "green"},
    {"label": "ビジュアルにそのまま乗る", "sub": "列をフィールドにドラッグするだけ", "tone": "blue"},
    {"label": "DAXが短くなる", "sub": "SUM(列) で済む。列を12本足す必要がない", "tone": "violet"},
    {"label": "列が増えないので壊れない", "sub": "月が増えても行が増えるだけ", "tone": "amber"},
    {"label": "圧縮が効いてモデルが軽い", "sub": "同じ値が縦に並ぶ列は強く圧縮される", "tone": "pink"} ] }
```

横持ちのまま「1〜4月の合計」を出そうとすると、DAX はこうなります。

```dax
売上合計_横持ち =
SUM( 売上[2025年1月] ) + SUM( 売上[2025年2月] )
    + SUM( 売上[2025年3月] ) + SUM( 売上[2025年4月] )
```

5月が来たら書き換えが必要です。縦持ちならこうです。

```dax
売上合計 = SUM( Fact_売上[SalesAmount] )
```

何月が増えても書き換えは不要で、月別の内訳も日付テーブルとの組み合わせで自動的に出ます。**式の短さは、設計の正しさの副産物です**。

> [!EXAM]
> PL-300 では「月ごとの列が横に並んだデータを Power BI で分析可能にするには、どの変換を使うか」という形で出ます。答えは**列のピボット解除**です。選択肢に「列のピボット」「転置」「グループ化」が混ざるので、それぞれが何をするかを区別しておいてください（L0504 で扱います）。

## 判定チェックリスト

新しいデータを受け取ったら、この6つを順に見ます。

| チェック | 違反していたら |
|---|---|
| 列名にデータの値（月・年・支店名）が入っていないか | 列のピボット解除（L0504） |
| 小計・合計・注釈の行が混ざっていないか | テキストフィルターで除外（L0502） |
| 1つのセルに2つの意味が入っていないか（`東京都/新宿本店`） | 列の分割（L0502） |
| 同じ実体の情報が複数の列に散っていないか | 観測単位ごとにテーブル分割（L0601） |
| 1行が何を表すか1文で言えるか | 粒度を決めてグループ化（L0506） |
| 同じ値が何百万回も繰り返されていないか | マスタに切り出す（L0601） |

## 整然データにしない場面

例外もあります。**最終的な出力（レポート）は、人が読む形にすべき**です。マトリクスビジュアルで月を横に並べるのは正しい設計です。

大事なのは順序です。**縦持ちで持ち、横持ちで見せる**。逆はできません。横持ちで持ってしまうと、縦持ちに戻す手間が毎回かかり、しかも情報が欠けていることがあります。

> [!TIP]
> 受け取ったファイルが横持ちだったとき、送り主に「縦持ちで出してもらえませんか」と依頼できるなら、それが最善の解決です。基幹システムからの出力形式を1回変えてもらえば、毎月のピボット解除が不要になります。**整形は上流でやるほど安い**というのは、データエンジニアリングの基本原則です。

## なぜ横持ちのファイルばかり届くのか

横持ちは、悪意でも無知でもなく、**人間の目にとって自然だから**生まれます。12か月を横に並べれば、増減が一目で追えます。手で入力するときも、月ごとに列を足すほうが早い。人が使う道具としては合理的です。

## 観測単位が混ざると集計が壊れる

ルール3の違反は、見た目には気づきにくく、集計の段階で牙をむきます。

受注明細と「その受注に付随する送料」を1枚の表に入れたとします。1受注に3明細あると、送料が3行に複製されます。この表で送料を合計すると、**実際の3倍**になります。


> 「合計すると多すぎる」という症状を見たら、まず**粒度の混在**を疑ってください。金額が正確に整数倍（2倍、3倍）になっているときは、ほぼ確実にこれです。DAX で `SUM` を書き換えて誤魔化す前に、テーブルの分け方を疑うのが正しい順序です。

| 新宿本店 | 家電 | 2025-02 | 2497347 |
| 新宿本店 | 衣料 | 2025-02 | 2714341 |
| 渋谷店 | 家電 | 2025-01 | 1257332 |

1行が「ある店舗の、あるカテゴリの、ある月の売上」を表しています。**粒度は 店舗 × カテゴリ × 月**。この1文が言えるので、これは整然データです。

> [!TRAP]
> 整然データにした結果、行数は必ず増えます。3店舗 × 3カテゴリ × 4か月 = 36 行のように、掛け算で膨らみます。「行が増えたから失敗した」と考えないでください。**列が減って行が増えるのは、ピボット解除が成功した証拠**です。Power BI の列指向エンジンは、縦に長い表を強く圧縮できるので、この形が性能面でも有利です。

## 理解度チェック

1. 整然データの3ルールを挙げ、`sales_dirty.csv` がそれぞれをどう違反しているか、具体的な列名・行を挙げて説明してください。
2. 「5月のデータが追加された」とき、横持ちのままだと何を直す必要がありますか。縦持ちだとどうですか。
3. `sales.csv` の粒度を1文で宣言してください。その粒度に照らして、`ProductName` 列をこの表に置くべきでない理由を説明してください。

## よくあるエラーと対処

| 症状 | 原因 | 対処 |
|---|---|---|
| 毎月ビジュアルのフィールドを追加している | データが横持ちのまま | 列のピボット解除で縦持ちにする |
| 合計が実際の2倍になる | 小計行が混ざっている | 「小計」を含む行を除外する |
| 同じ商品名が数万行繰り返されている | 観測単位が混ざっている | 商品マスタに切り出してリレーションシップで結ぶ |
| DAXが長大な足し算になる | 変数が列名に散っている | ピボット解除して1列にまとめる |
| 1行が何なのか説明できない | 粒度が未定義 | グループ化で粒度を明示的に決め直す |
| セルに `東京都/新宿本店` のような複合値がある | 1セル1値になっていない | 区切り文字で列を分割する |
