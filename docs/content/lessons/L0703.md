この一言に対して、DAXには少なくとも5つの答え方があります。そして**どれを選ぶかで数字が変わります**。
会議で数字が食い違う原因の多くは、集計関数の選び間違いです。

このレッスンでは、集計関数を「何を数えているのか」で整理し、迷わず選べるようにします。

## 列を集計する関数

もっとも基本的な形です。引数は **列を1つだけ** 取ります。

```dax
売上合計   = SUM( Fact_売上[SalesAmount] )
数量合計   = SUM( Fact_売上[Quantity] )
最高単価   = MAX( Fact_売上[UnitPrice] )
最安単価   = MIN( Fact_売上[UnitPrice] )
平均取引額 = AVERAGE( Fact_売上[SalesAmount] )
```

いずれも「フィルターで残った行の、その列の値」を対象にします。
`AVERAGE` は空白行を分母に含めません。ここは Excel の `AVERAGE` と同じ挙動です。

> [!WARN] SUM に式は書けない
> `SUM( Fact_売上[Quantity] * Fact_売上[UnitPrice] )` はエラーになります。
> `SUM` が受け取れるのは **列そのもの1つだけ** で、式は受け取れません。式を扱いたいときは後述の `SUMX` を使います。

ここで **反復関数** の出番です。名前の末尾に `X` が付く関数がそれです。

### SUM と SUMX を取り違えるとどうなるか

3行のデータで確かめます。

| 行 | Quantity | UnitPrice | 行ごとの積 |
|---|---|---|---|
| 1 | 2 | 120,000 | 240,000 |
| 2 | 5 | 3,000 | 15,000 |
| 3 | 1 | 120,000 | 120,000 |
| **合計** | **8** | **243,000** | **375,000** |

```dax
-- ✓ 正しい：行ごとに掛けてから足す
正しい売上 = SUMX( Fact_売上, Fact_売上[Quantity] * Fact_売上[UnitPrice] )   // 375,000

-- ✗ 誤り：先に足してから掛ける
誤った売上 = SUM( Fact_売上[Quantity] ) * SUM( Fact_売上[UnitPrice] )        // 1,944,000
```

```figure
{ "type":"chart", "kind":"bar", "title":"掛け算と足し算の順序で結果が5倍違う",
  "caption":"誤りの式は「全数量 × 全単価の合計」という意味のない値を計算している",
  "categories":["正しい（SUMX）","誤り（SUM×SUM）"],
  "series":[{"name":"金額","values":[375,1944],"tone":"blue"}],
  "highlight":1, "unit":"千円" }
```

> [!DS] 集計の順序が結果を変える
> 「合計してから掛ける」と「掛けてから合計する」は、数学的に別物です（`Σ(aᵢ·bᵢ) ≠ Σaᵢ · Σbᵢ`）。
> 同じことが平均・比率・分散でも起こります。指標を設計するときは必ず
> **「行の単位で何を計算し、そのあと何で集計するか」** を1文で書き出してください。
> この1文が書けない指標は、実装しても正しさを検証できません。

> `Fact_売上` に「利益額」の計算列を作れば `SUM` で足せます。しかしそれはモデルを太らせます。
> `SUMX` を使えば、同じ結果を**列を増やさずに**得られます。ファクトテーブルが大きいほど、この差が効きます。

## AVERAGEX と MAXX

反復関数は `SUMX` だけではありません。同じ考え方が平均・最大にも使えます。

```dax
-- 顧客1人あたりの平均購入金額
顧客あたり平均売上 =
AVERAGEX(
    VALUES( Fact_売上[CustomerID] ),
    [売上合計]
)

-- 最も売れた商品の売上
最大商品売上 =
MAXX(
    VALUES( Dim_商品[ProductName] ),
    [売上合計]
)
```

`VALUES( 列 )` は「いま見えている範囲に存在する、その列の異なる値」を1列の表として返します。
つまり上の式は「顧客の一覧を1人ずつ見て、その人の売上合計を求め、最後に平均する」という意味になります。

> [!TRAP] `[売上合計]` が顧客ごとの値になる理由
> `AVERAGEX` の中でメジャー `[売上合計]` を書くと、なぜか顧客1人ぶんの値になります。
> これは **コンテキスト遷移**（行コンテキストがフィルターコンテキストに変換される現象）が起きているためです。
> いまは「メジャーを反復関数の中で呼ぶと、その行の条件で絞り込まれる」とだけ覚えておけば十分です。仕組みは L0802・L0803 で完全に解きます。

## 加法性という視点で集計を整理する

指標には「足し算できるもの」と「できないもの」があります。この分類を持っておくと、合計行の挙動に驚かなくなります。

### 非加法性を数字で見る


`DISTINCTCOUNT` は非加法的です。だから合計行は各行の和より小さくなります。
これは **正しい挙動** であり、「重複顧客が存在する」という事実を正確に表しています。

> [!TIP] 説明できる形で報告する
> 非加法的な指標を表に載せるときは、合計行のラベルを「合計」ではなく「全体（重複除く）」にする、
> または注記を添えると、問い合わせが激減します。技術的な正しさと、伝わりやすさは別の仕事です。

### 半加法的な指標の例

在庫残高は、店舗をまたいで足すのは正しいですが、月をまたいで足すのは誤りです。

| | 4月 | 5月 | 6月 | 四半期 |
|---|---|---|---|---|
| 東京店 | 120 | 140 | 150 | 150 |
| 大阪店 | 80 | 75 | 90 | 90 |
| **合計** | **200** | **215** | **240** | **240** |

四半期の列は `120+140+150` ではなく、**期末（6月）の値** を使います。
このような指標には `LASTDATE` と `CALCULATE` を組み合わせますが、それは上級で扱います。
ここでは「時間軸だけ扱いが違う指標がある」ことを覚えてください。

**カーディナリティ**（列に含まれる異なる値の種類の数）が高い列ほど、`DISTINCTCOUNT` は重くなります。

> [!EXAM] PL-300で問われる
> 「注文件数を求めたい」という設問では、`DISTINCTCOUNT( Fact_売上[OrderID] )` と `COUNTROWS( Fact_売上 )` の
> どちらが適切かを、**ファクトの粒度**から判断させる問題が出ます。
> 1行＝1注文明細なら `COUNTROWS` は明細数であり、注文数ではありません。粒度を必ず確認してください。

## まとめ表

| やりたいこと | 使う関数 | 注意点 |
|---|---|---|
| 金額を足す | `SUM` | 列そのものしか渡せない |
| 行ごとに計算して足す | `SUMX` | 第1引数は表、第2引数は式 |
| 表の行数 | `COUNTROWS` | 最も速く、意図が明確 |
| 値のある行数 | `COUNT` / `COUNTA` | 空白は数えない |
| 空白の行数 | `COUNTBLANK` | データ品質チェックに便利 |
| 重複を除いた種類数 | `DISTINCTCOUNT` | 空白を1種類と数える／非加法的／重い |
| 空白を除く種類数 | `DISTINCTCOUNTNOBLANK` | 報告値ではこちらが自然なことが多い |
| 単位あたりの平均 | `DIVIDE([分子],[分母])` | `AVERAGE` では規模の重みが消える |

## 理解度チェック

**問1.** `Fact_売上` は1行が「注文明細1件」を表す。注文の件数を求めるメジャーを書け。

<details><summary>答え</summary>
`注文件数 = DISTINCTCOUNT( Fact_売上[OrderID] )`。`COUNTROWS( Fact_売上 )` は明細行数であり、1注文に複数明細があると過大になる。
</details>

**問2.** `売上 = SUM( Fact_売上[Quantity] ) * SUM( Fact_売上[UnitPrice] )` が誤りである理由を、行の単位という語を使って説明せよ。

<details><summary>答え</summary>
掛け算は行の単位で成立する演算であり、先に列ごとに合計してから掛けると、行の対応関係が失われるため。正しくは `SUMX` で行ごとに掛けてから合計する。
</details>

**問3.** 割引率の列に空白が含まれるとき、「実際に適用された割引率の種類数」を求めるにはどの関数を使うか。

<details><summary>答え</summary>
`DISTINCTCOUNTNOBLANK( Fact_売上[DiscountRate] )`。`DISTINCTCOUNT` は空白を1種類として数えるため、1多くなる。
</details>

## よくあるエラーと原因

| 症状・エラー | 原因 | 対処 |
|---|---|---|
| 「SUM 関数は列参照を必要とします」 | `SUM` に式を渡した | `SUMX( 表, 式 )` に置き換える |
| 金額が桁違いに大きい | `SUM × SUM` で計算した | `SUMX` で行ごとに計算する |
| 種類数が想定より1多い | `DISTINCTCOUNT` が空白を数えた | `DISTINCTCOUNTNOBLANK` を使う |
| 合計行が各行の和にならない | 非加法的な指標を使っている | 正常な挙動。ラベルや注記で説明する |
| ビジュアルが極端に遅い | 高カーディナリティ列の `DISTINCTCOUNT` | 粒度を上げた集計表を用意するか、指標を見直す |
| `AVERAGEX` の中でメジャーが全体値になる | 反復対象が1行の表になっている | `VALUES( 列 )` で反復対象を明示する |

> [!NOTE] このレッスンのまとめ
> 集計関数は「列を集計する」「行を反復する」「個数を数える」の3家族に分かれます。
> 「件数」という依頼は必ず**何を数えるか**まで確認し、`COUNTROWS` / `COUNT` / `DISTINCTCOUNT` を選び分けます。
> 行ごとの計算が必要なら `SUMX`。そして合計行の違和感は、**加法性**の観点で説明できます。
