1件の受注には、日付が3つあります。**受注日、出荷日、請求日**。営業は受注日で見たい、物流は出荷日で見たい、経理は請求日で見たい。3部門とも正しく、3つとも必要です。

素朴な対処は「日付テーブルを3つ作る」ですが、これをやると期間スライサーが3つ並び、どれを操作すればよいか誰も分からなくなります。**1つの日付テーブルで3つの役割を切り替える**のが正解です。

## `USERELATIONSHIP` の書き方

```figure
{ "type":"formula", "lang":"dax",
  "title":"USERELATIONSHIP の構造",
  "caption":"CALCULATE の修飾子として使い、その計算の間だけ関係を切り替える",
  "code":"CALCULATE( SUM( Fact_受注[金額] ), USERELATIONSHIP( Fact_受注[出荷日], Dim_日付[日付] ) )",
  "parts":[
    {"match":"CALCULATE","label":"フィルターコンテキストを変更する関数。この中でしか使えない","tone":"violet"},
    {"match":"SUM( Fact_受注[金額] )","label":"評価したい式","tone":"blue"},
    {"match":"USERELATIONSHIP","label":"非アクティブな関係を、この計算の間だけ有効にする","tone":"amber"},
    {"match":"Fact_受注[出荷日], Dim_日付[日付]","label":"多側の列, 1側の列 の順で指定する","tone":"green"}
  ] }
```

実際のメジャー群はこうなります。

```dax
-- 受注日ベース（アクティブな関係なので指定不要）
売上_受注ベース = SUM( Fact_受注[金額] )

-- 出荷日ベース
売上_出荷ベース =
CALCULATE(
    SUM( Fact_受注[金額] ),
    USERELATIONSHIP( Fact_受注[出荷日], Dim_日付[日付] )
)

-- 請求日ベース
売上_請求ベース =
CALCULATE(
    SUM( Fact_受注[金額] ),
    USERELATIONSHIP( Fact_受注[請求日], Dim_日付[日付] )
)
```

この3つを同じマトリクスに並べると、1つの月に対して「受注はいくら、出荷はいくら、請求はいくら」が横に並びます。**期間スライサーは1つのまま**です。

> [!TIP] 実務のコツ
> メジャー名には必ず**基準となる日付を明記**してください。`売上合計` という名前のメジャーが受注日ベースなのか出荷日ベースなのかは、名前からしか分かりません。経理と営業で数字が食い違う原因の多くは、この命名の曖昧さです。

## タイムインテリジェンスと組み合わせる

役割別の日付でも、前年同期比などは同じように書けます。

```dax
-- 出荷日ベースの前年同期
売上_出荷ベース_前年 =
CALCULATE(
    [売上_出荷ベース],
    DATEADD( Dim_日付[日付], -1, YEAR )
)
```

```dax
-- 出荷日ベースの年度累計。USERELATIONSHIP は内側のメジャーに含まれている
売上_出荷ベース_YTD =
CALCULATE(
    [売上_出荷ベース],
    DATESYTD( Dim_日付[日付], "3/31" )
)
```

> [!TRAP] つまずきポイント
> `USERELATIONSHIP` を**外側の `CALCULATE` に書き、内側で別のメジャーを呼ぶ**場合、内側のメジャーは暗黙の `CALCULATE` を持つため、関係の切り替えが正しく引き継がれないケースがあります。**基準日付を切り替えたベースメジャーを1本作り、それを他のメジャーから参照する**という上の書き方にしておけば、この問題は起きません。「切り替えは1箇所、参照は何度でも」が原則です。

> [!TRAP] つまずきポイント
> `USERELATIONSHIP` は **`CALCULATE` / `CALCULATETABLE` の中でしか使えません**。`SUMX` の中に直接書くとエラーになります。また、**同じテーブルペアに対して複数の `USERELATIONSHIP` を同時に指定することはできません**。「受注日と出荷日の両方で同時に絞る」は、この方法では実現できず、日付テーブルの複製が必要になります。

## リードタイム分析 — 日付が2つあるからできること

複数の日付を持つファクトの価値は、**日付同士の差**を分析できることにあります。

```figure
{ "type":"tablediff", "arrowLabel":"日数差の列を追加",
  "title":"受注から出荷までのリードタイム",
  "caption":"Power Query か計算列で日数差を持たせると、分布や平均を分析できる",
  "before":{"title":"元のファクト","tone":"neutral",
    "head":["受注番号","受注日","出荷日","金額"],
    "rows":[
      ["S-001","2026-02-01","2026-02-03","120,000"],
      ["S-002","2026-02-01","2026-02-09","80,000"],
      ["S-003","2026-02-02","(未出荷)","45,000"]]},
  "after":{"title":"リードタイム列を追加","tone":"good",
    "head":["受注番号","受注日","出荷日","リードタイム","状態"],
    "rows":[
      ["S-001","2026-02-01","2026-02-03","!2","出荷済"],
      ["S-002","2026-02-01","2026-02-09","!8","出荷済"],
      ["S-003","2026-02-02","(未出荷)","!null","!未出荷"]]} }
```

```m
// Power Query で計算する（更新時に1度だけ計算される。推奨）
let
    Src = Fact_受注,
    LT = Table.AddColumn(Src, "リードタイム日数",
        each if [出荷日] = null then null
             else Duration.Days([出荷日] - [受注日]), Int64.Type),
    状態 = Table.AddColumn(LT, "出荷状態",
        each if [出荷日] = null then "未出荷" else "出荷済", type text)
in
    状態
```

```dax
-- 平均リードタイム（未出荷を除外して集計する）
平均リードタイム =
AVERAGEX(
    FILTER( Fact_受注, NOT ISBLANK( Fact_受注[リードタイム日数] ) ),
    Fact_受注[リードタイム日数]
)

-- 5日以内出荷率（SLA達成率）
SLA達成率 =
VAR 出荷済 = CALCULATE( COUNTROWS( Fact_受注 ), Fact_受注[出荷状態] = "出荷済" )
VAR 期限内 = CALCULATE( COUNTROWS( Fact_受注 ), Fact_受注[リードタイム日数] <= 5 )
RETURN
    DIVIDE( 期限内, 出荷済 )
```

> [!TRAP] つまずきポイント
> **未出荷（出荷日がnull）の扱いを決めずに平均を出すと、必ず誤ります。** 未出荷を0日として集計すれば平均は短くなり、除外すれば「遅れている案件が見えない」ことになります。実務では「未出荷を除いた平均リードタイム」と「未出荷件数・最古の受注日」を**必ずセットで表示**してください。片方だけでは意思決定できません。

## 複数ファクトを1つのモデルに置く

売上と在庫、実績と予算のように、**粒度も行数も異なるファクトを同じモデルで扱う**ことは日常的にあります。鍵は**共有ディメンション**です。

```figure
{ "type":"star", "title":"共有ディメンションで複数ファクトを串刺しにする",

  "fact":{"label":"Dim_日付 / Dim_商品\n（共有ディメンション）","lines":["両ファクトから参照される","粒度を揃える基準になる"]},

    {"label":"Fact_売上","lines":["日付 / 商品ID / 顧客ID","金額（日次・商品単位）"]},
    {"label":"Fact_在庫","lines":["日付 / 商品ID / 倉庫ID","在庫数（日次スナップショット）"]},
    {"label":"Fact_予算","lines":["年月 / カテゴリ","予算金額（月次・カテゴリ単位）"]},
    {"label":"Dim_顧客","lines":["Fact_売上 のみが参照"]},
```

> [!DS] データサイエンス視点
> ここで使われている共有ディメンションを、次元モデリングでは **コンフォームド ディメンション（conformed dimension）** と呼びます。「複数のファクトが、まったく同じ定義・同じキー体系で参照するディメンション」のことです。これがあるからこそ、売上と在庫を同じ商品軸で並べられ、実績と予算を同じ日付軸で比べられます。逆に、部門ごとに独自の商品マスタを持っていると、いくらデータを集めても串刺しにできません。**コンフォームド ディメンションを揃えることは、データウェアハウス設計の中心的な作業**です。

## 粒度の違うファクトを並べるときの注意

`Fact_売上` は日次・商品単位、`Fact_予算` は月次・カテゴリ単位。この2つを同じ表に並べると、**予算が存在しない粒度で予算が繰り返し表示される**という問題が起きます。

```figure
{ "type":"compare", "title":"粒度が合わない表示の扱い",
  "caption":"存在しない粒度では BLANK にするのが正しい。繰り返し表示は誤読を生む",
  "panels":[
    {"title":"何もしない場合","tone":"bad",
     "items":[
       "商品単品の行に、カテゴリの予算がそのまま表示される",
       "商品Aの予算 1000万、商品Bの予算 1000万 …と同じ値が並ぶ",
       "利用者は「商品ごとの予算」だと誤解する",
       "予算の合計が実態の何倍にもなる",
       "指摘されるまで誰も気づかない"
     ],"note":"最も多い事故"},
    {"title":"粒度を判定して BLANK にする","tone":"good",
     "items":[
       "予算が定義されている粒度かを ISINSCOPE / HASONEVALUE で判定",
       "商品単品の行では予算を空白にする",
       "カテゴリの小計行では正しく表示される",
       "「ここには予算がない」ことが利用者に伝わる",

```

```dax
-- 予算が定義されているのはカテゴリ×年月の粒度だけ。
-- それより細かい粒度では BLANK を返す
予算額_安全 =
IF(
    -- 商品単品まで絞り込まれている場合は予算が存在しない
    ISINSCOPE( Dim_商品[商品名] ),
    BLANK(),
    CALCULATE(
        SUM( Fact_予算[予算金額] ),
        TREATAS( VALUES( Dim_商品[カテゴリ] ), Fact_予算[カテゴリ名] ),
        TREATAS( VALUES( Dim_日付[年月] ), Fact_予算[年月] )
    )
)

-- 達成率も、予算が無い粒度では空白になる
予算達成率 = DIVIDE( [売上_受注ベース], [予算額_安全] )
```

> [!TIP] 実務のコツ
> `ISINSCOPE( 列 )` は「そのビジュアルの現在の行が、その列で明示的にグループ化されているか」を判定します。`HASONEVALUE` と似ていますが、**スライサーによる単一選択と、行としてのグループ化を区別できる**点が違います。粒度判定には `ISINSCOPE` を使ってください。

「スライサーで基準を切り替える」パターンの実装も載せておきます。

```dax
-- 切断テーブル（どのテーブルとも関係を持たない）を作っておく
-- Dim_日付基準 = DATATABLE("基準", STRING, {{"受注日"},{"出荷日"},{"請求日"}})

売上_基準切替 =
SWITCH(
    SELECTEDVALUE( Dim_日付基準[基準], "受注日" ),
    "受注日", [売上_受注ベース],
    "出荷日", [売上_出荷ベース],
    "請求日", [売上_請求ベース]
)
```

> [!WARN] 注意
> 切断テーブル（どのテーブルともリレーションシップを持たないテーブル）を使う設計では、**選択されていないときの既定値**を必ず指定してください。`SELECTEDVALUE( 列, 既定値 )` の第2引数がそれです。指定しないと、スライサーで複数選択されたときにメジャーが空白になり、「グラフが真っ白になった」という問い合わせにつながります。

> [!EXAM] PL-300で問われる
> 「1つのファクトテーブルに複数の日付列がある場合の実装方法」は頻出です。**非アクティブなリレーションシップを作成し、`USERELATIONSHIP` を使用する**が正解になります。「日付テーブルを複製する」も選択肢に出ますが、通常は誤答（または次善）として扱われます。`USERELATIONSHIP` が `CALCULATE` の修飾子であることも確認されます。

## 設計判断チェックリスト

- [ ] 日付テーブルは1つに統一されているか。役割ごとに増やしていないか
- [ ] 非アクティブなリレーションシップを、モデル図で確認したか（破線）
- [ ] メジャー名に基準日付を明記したか（`売上_出荷ベース` など）
- [ ] タイムインテリジェンスは、基準を切り替えたベースメジャーを参照する形にしたか
- [ ] リードタイム計算で、未完了（null）の扱いを決めたか。件数も併せて表示するか
- [ ] 複数ファクトは共有ディメンション経由でのみ結んでいるか。ファクト同士を直接つないでいないか
- [ ] 粒度が異なるファクトを並べる場合、`ISINSCOPE` で存在しない粒度を BLANK にしたか
- [ ] 切断テーブルを使う場合、`SELECTEDVALUE` に既定値を指定したか
- [ ] 部門間で「どの日付基準を正とするか」の合意を取ったか

## 理解度チェック

1. `Fact_受注` に受注日・出荷日・請求日があります。同じマトリクスに3つの基準の売上を横に並べるための実装を、メジャー定義を含めて説明してください。
2. `USERELATIONSHIP` を `SUMX` の中に直接書くとエラーになります。正しい書き方に直し、なぜその形が必要かを説明してください。
3. 月次・カテゴリ別の予算を、商品単品まで展開したマトリクスに表示すると何が起きますか。防ぐためのDAXを書いてください。
