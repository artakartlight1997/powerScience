Power BI が「遅い」「数字が合わない」「欲しい切り口が出せない」と言われるとき、原因の大半はビジュアルでも DAX でもなく、**モデルの形**にあります。そして正しい形はほぼ1つに決まっています。**スタースキーマ**です。

> [!NOTE]
> スタースキーマとは、数値を持つ **ファクトテーブル** を中心に置き、その数値を切り分ける説明的な属性を持つ **ディメンションテーブル** を周囲に配置する設計です。Power BI の計算エンジンは、この形を前提に最適化されています。

## フラットテーブルの何が問題か

「1枚の表に全部入っていたほうが分かりやすい」と感じるのは自然です。しかし、フラットテーブル（1枚の巨大な表）には具体的な問題が4つあります。

```figure

  "caption": "見やすさではなく、動作と拡張性で選ぶ",

    {"title": "フラットテーブル（1枚表）", "tone": "bad",
     "items": ["同じ商品名が数百万回繰り返される", "売れていない商品が一覧に出てこない", "切り口を足すたびに列が増える", "重複排除のDAXが必要になる", "更新のたびに全体を作り直す"],
     "note": "アンチパターン"},
    {"title": "スタースキーマ", "tone": "good",
     "items": ["商品名は商品テーブルに1行だけ", "売上0の商品もスライサーに出る", "属性はディメンション側に足すだけ", "SUMだけで正しく集計できる", "ディメンションだけ更新できる"],
     "note": "推奨"} ] }
```

### 問題1 — 同じ値の繰り返しで容量が膨らむ

`sales.csv` の 6,948 行に商品名を持たせると、「せんべい詰合せ」という文字列が数百回繰り返されます。実務規模の 1,000 万行なら、繰り返しは数十万回になります。

```figure
{ "type": "chart", "kind": "hbar", "title": "モデルサイズの比較（1,000万行の売上を想定）",
  "categories": ["フラット1枚表", "スタースキーマ"],
  "series": [{"name": "モデルサイズ", "values": [820, 210], "tone": "blue"}],
  "highlight": 1, "unit": "MB" }
```

Power BI の格納エンジンは列単位で圧縮するため、値の種類が少ない列は強く圧縮されます。それでも、**文字列を持つ列を数千万行ぶん抱えるより、整数のIDだけを持つほうが圧倒的に小さくなります**。

### 問題2 — 売れていないものが見えない

これは容量より深刻な、**分析そのものが壊れる**問題です。

フラットテーブルは売上明細なので、**売上が1件もない商品は行として存在しません**。したがってスライサーにも一覧にも出てきません。「今期まったく売れなかった商品は？」という、小売業で最も重要な質問に答えられなくなります。

```figure
{ "type": "tablediff", "arrowLabel": "商品ディメンションを分けると何が変わるか",
  "before": {"title": "フラット表の商品一覧（売上のある商品だけ）", "tone": "bad",
    "head": ["Category", "ProductName", "売上"],
    "rows": [["家電", "ノートPC スタンダード", "1,280,000"], ["家電", "電気ケトル", "348,000"], ["!—", "!（売上0の商品は現れない）", "!—"]]},
  "after": {"title": "Dim_商品を分けた一覧（全32商品）", "tone": "good",
    "head": ["Category", "ProductName", "売上"],
    "rows": [["家電", "ノートPC スタンダード", "1,280,000"], ["家電", "電気ケトル", "348,000"], ["!家電", "!デスクトップPC", "!0"]]} }
```

ディメンションは「起きた事実」ではなく「存在するもの」の一覧です。**存在するものを一覧できることが、ディメンションを分ける最大の価値**です。

### 問題3 — 切り口を足すたびに作り直しになる

「商品の仕入先も分析軸にしたい」と言われたとき、フラットテーブルでは 1,000 万行すべてに仕入先の列を追加する必要があります。スタースキーマなら、商品ディメンションの 32 行に列を1本足すだけです。

### 問題4 — DAX が複雑になる

フラットテーブルで「商品数」を数えると、明細の行数が返ってしまいます。正しく数えるには重複排除が必要です。

```dax
-- フラットテーブルの場合：重複排除が要る
商品数_フラット = DISTINCTCOUNT( 売上[ProductName] )
```

```dax
-- スタースキーマの場合：素直に数えるだけ
商品数 = COUNTROWS( Dim_商品 )
```

しかも前者は「売れた商品の数」であって「取り扱い商品の数」ではありません。**式が複雑になるのは、たいていモデルが間違っているサインです**。

## なぜ Power BI はこの形を好むのか

```figure
{ "type": "stack", "title": "スタースキーマが効く3つの層",
  "caption": "格納・結合・フィルターのすべてがこの形に最適化されている",
  "layers": [
    {"label": "フィルターの流れ", "sub": "1側（ディメンション）から多側（ファクト）へ一方向に流れる。単純で予測できる", "tone": "pink"},
    {"label": "リレーションシップ", "sub": "すべて1対多。多対多や双方向の複雑さが発生しない", "tone": "amber"},
    {"label": "列指向の圧縮", "sub": "ファクトは整数のIDと数値だけ。値の種類が少なく圧縮が最大限効く", "tone": "blue"} ] }
```

Power BI の格納エンジン（VertiPaq）は列指向で、同じ値が並ぶ列を辞書に置き換えて圧縮します。ファクトテーブルから文字列を追い出し、整数のキーだけにすると、この圧縮が最大限効きます。さらに、リレーションシップがすべて1対多の単一方向であれば、フィルターの経路が一意に定まり、エンジンは最短経路で計算できます。

> [!DS]
> スタースキーマは、Ralph Kimball が体系化した **次元モデリング（dimensional modeling）** の中核概念です。データウェアハウス設計には2つの流派があり、Inmon は全社統合の正規化されたウェアハウスを先に作る手法、Kimball は業務プロセスごとにスタースキーマ（データマート）を作り、共通ディメンションで束ねる手法を提唱しました。BI ツールの分析層においては、Kimball 流のスタースキーマが事実上の標準です。理由は明快で、**分析クエリは「多くの行を集計し、少数の属性で切る」というパターンに集中する**からです。トランザクション処理（OLTP）が更新の整合性のために正規化を求めるのに対し、分析処理（OLAP）は読み取りの単純さのためにディメンションの非正規化を選びます。同じデータでも、目的が違えば最適な形が違うという良い例です。

実際にフラットな1枚表を受け取ったときの手順です。

```figure

  "items": [
    {"title": "測定値の列を特定する", "text": "数量・金額・原価など、足したり数えたりする列。これがファクトに残る。", "tone": "blue"},
    {"title": "属性列をグループに分ける", "text": "商品名・カテゴリ・原価は商品グループ、店舗名・県・地域は店舗グループ。同じIDから決まる列がひとまとまり。", "tone": "green"},
    {"title": "各グループを別クエリに切り出す", "text": "元クエリを参照して、必要な列だけ残し、キーで重複を削除する。", "tone": "amber"},

    {"title": "ファクトから属性列を削除する", "text": "ファクトにはキーと測定値だけを残す。ここで容量が劇的に減る。", "tone": "pink"},
    {"title": "リレーションシップを引く", "text": "モデルビューで各ディメンションのキーからファクトのキーへ。すべて1対多になる。", "tone": "cyan"} ] }
```

商品ディメンションを切り出す M は次のようになります。

```m
// フラット表から商品ディメンションを切り出す
let
    ソース = フラット売上,
    商品列だけ = Table.SelectColumns(
        ソース,
        {"ProductID", "ProductName", "Category", "SubCategory", "StandardCost", "ListPrice"}
    ),
    重複削除 = Table.Distinct(商品列だけ, {"ProductID"})
in
    重複削除
```

> [!TRAP]
> `Table.Distinct` にキー列を指定せず全列で重複削除すると、**同じ ProductID なのに商品名が微妙に違う行が2つ残ります**（表記ゆれや、途中で商品名が変更された場合）。キーで1行に絞るには、必ず `Table.Distinct(表, {"キー列"})` のようにキーを指定してください。指定しないままモデルに載せると、リレーションシップが多対多になり、集計が壊れます。

## スノーフレークにしない

ディメンションをさらに正規化して、`Dim_商品` から `Dim_カテゴリ` を分離した形を **スノーフレークスキーマ** と呼びます。

```figure
{ "type": "tree", "title": "ディメンションを分けるべきか",
  "caption": "分析用モデルでは、ディメンションは非正規化して1枚に保つのが原則",
  "root": {"label": "カテゴリを別テーブルにするか"},
  "children": [
    {"label": "スタースキーマのまま", "sub": "カテゴリは Dim_商品 の列として持つ", "tone": "good",
     "children": [
       {"label": "テーブル数が少ない", "sub": "利用者が迷わない"},
       {"label": "結合が1段で済む", "sub": "エンジンが速い", "tone": "good"} ]},
    {"label": "スノーフレークにする", "sub": "Dim_カテゴリ を分離する", "tone": "amber",
     "children": [
       {"label": "正当な例：ソースが巨大で共有される", "sub": "全社共通のマスタなど"},
       {"label": "多くの場合は不要", "sub": "結合が増えて遅く、使いにくくなる", "tone": "bad"} ]} ] }
```

分析モデルでは、**ディメンションは非正規化して1枚にまとめる**のが原則です。カテゴリ名が数十種類しかないなら、それを商品テーブルの列として持っても容量はほとんど増えません。テーブルが増えることによる使いにくさのほうが、はるかに高くつきます。

> [!TRAP]
> データベース設計の経験がある人ほど、正規化を良いことだと考えてスノーフレーク化してしまいます。**OLTP（業務システム）の正規化と、OLAP（分析）の非正規化は目的が違います**。分析モデルで正規化を進めると、テーブル数が増え、結合が深くなり、フィルターの経路が複雑になり、利用者は「どのテーブルに何があるか」を覚えられなくなります。

## ファクトが複数あるとき

売上と在庫、売上と予算のように、ファクトが複数あるモデルも普通に存在します。このとき重要な原則が1つあります。

```figure
{ "type": "pipeline", "title": "共有ディメンションで複数のファクトを束ねる",
  "caption": "ファクト同士は直接つながない。必ず共有ディメンションを経由させる",
  "nodes": [
    {"id": "d1", "label": "Dim_日付", "tone": "amber"},
    {"id": "d2", "label": "Dim_商品", "tone": "green"},
    {"id": "f1", "label": "Fact_売上", "tone": "blue"},
    {"id": "f2", "label": "Fact_予算", "tone": "violet"} ],
  "edges": [
    {"from": "d1", "to": "f1", "label": "1対多"},
    {"from": "d1", "to": "f2", "label": "1対多"},
    {"from": "d2", "to": "f1", "label": "1対多"},
    {"from": "d2", "to": "f2", "label": "1対多"} ] }
```

**ファクトテーブル同士を直接リレーションシップでつないではいけません。** 粒度が違うため、必ず重複や欠落が生じます。売上は明細の粒度、予算は月×カテゴリの粒度、といった具合に粒度が違うのが普通です。共有ディメンション（日付・商品）を経由すれば、それぞれの粒度のまま正しく比較できます。

この「共通のディメンションを複数のファクトで共有する」考え方を、Kimball は **バスアーキテクチャ（conformed dimensions）** と呼びました。全社で日付・商品・顧客の定義を1つに揃えれば、部門ごとに作られたモデルでも数字が突き合わせられます。

> [!EXAM]
> PL-300 では「推奨されるスキーマはどれか」という直球の設問が出ます。答えは常に**スタースキーマ**です。また「フラットテーブルをスタースキーマに変換する理由」として正しいのは、パフォーマンスの向上、モデルサイズの削減、DAXの単純化、ディメンション属性の一元管理です。「データの重複を完全になくすため」という選択肢は、ディメンションを非正規化する時点で誤りになるので選ばないでください。

## 完成形を確認する

分解が終わったら、モデルビューでこの5つを確認します。

| チェック | 合格の状態 |
|---|---|
| ファクトが中心にあるか | 矢印がすべてファクトに向かっている |
| 矢印の向きが揃っているか | すべてディメンション→ファクト |
| 基数がすべて1対多か | 多対多や1対1が混ざっていない |
| ファクトに文字列の属性が残っていないか | キーと数値だけになっている |
| ディメンション同士が直接つながっていないか | つながっていない（つなぐと経路が曖昧になる） |


テーブル名に `Fact_` と `Dim_` の接頭辞をつける流儀は、この自己説明性のためです。名前を見ただけで「これは数値の表」「これは切り口の表」と分かり、モデルビューを開かなくても構造が予測できます。組織のルールがあればそれに従い、なければこの流儀を採用してください。

> [!WARN]
> スタースキーマは「理論的に美しいから」採用するのではありません。**性能・拡張性・可読性という3つの実利があるから**採用します。逆に言えば、この3つを損なう「原理主義」は不要です。ディメンションが2行しかないなら、それを分ける価値はないかもしれません。判断基準は常に、実際に使う人にとって楽になるかどうかです。

## よくある「これはどっち？」

分解の途中で必ず迷うテーブルがあります。判断の型を先に見ておきます。

| 迷うテーブル | 判定 | 理由 |
|---|---|---|
| 為替レート（日付 × 通貨 × レート） | ファクト寄り | 日々発生する測定値。ただし集計はしないので「ファクトレステーブル」と呼ぶこともある |
| 予算（月 × 部門 × 金額） | ファクト | 金額という測定値を持つ。粒度が売上と違うだけ |
| 社員マスタ | ディメンション | 「存在するもの」の一覧。属性を持つ |
| 受注ヘッダー（受注日・顧客・送料） | ファクト | 受注という出来事の記録。明細とは粒度が違うので別ファクト |
| 都道府県マスタ | ディメンション候補 | ただし店舗ディメンションに列として持たせるほうが素直（非正規化） |

> [!TIP]
> 判断に迷ったときの質問は1つです。**「この表の行は、何かが起きたときに増えるか、それとも何かが登録されたときに増えるか」**。起きたときに増えるならファクト、登録されたときに増えるならディメンションです。売上は起きたときに増え、商品は登録されたときに増えます。この基準は L0602 でさらに詳しく扱います。

```figure

  "caption": "この順に目視するだけで、設計ミスのほとんどが見つかる",
  "dir": "row",
  "items": [
    {"label": "配置", "sub": "ファクトを中央下、ディメンションを上に並べる", "tone": "blue"},
    {"label": "向き", "sub": "矢印がすべて下向きになっているか", "tone": "green"},
    {"label": "基数", "sub": "1と*の表示を1本ずつ確認", "tone": "amber"},
```

## よくあるエラーと対処

| 症状 | 原因 | 対処 |
|---|---|---|
| モデルが重く更新が遅い | ファクトに文字列の属性列が残っている | 属性をディメンションに移し、ファクトはキーと数値だけにする |
| 売上0の商品が一覧に出ない | 商品情報をファクトから取っている | Dim_商品 を作り、ビジュアルの軸をディメンション側の列にする |
| リレーションシップが多対多になる | ディメンション側のキーに重複がある | キーで重複を削除する。または本当の粒度を見直す |
| テーブルが多すぎて使いにくい | スノーフレーク化しすぎ | ディメンションを非正規化して1枚にまとめる |
| ファクト同士をつなぐと数字が合わない | 粒度の異なる表を直結した | 共有ディメンション経由に変更する |
| 属性を追加するたびに全件更新が必要 | フラットテーブル設計のまま | ディメンションを分離し、そちらに列を足す |
