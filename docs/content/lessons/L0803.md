実務のDAXを開くと、そこには `CALCULATE` があります。前年比にも、構成比にも、条件付き集計にも。

理由は単純で、**DAXでフィルターコンテキストを変更できる関数は `CALCULATE` だけ** だからです。
（`CALCULATETABLE` は同じ仕組みでテーブルを返す兄弟関数です。）

裏を返せば、`CALCULATE` を制御できれば、DAXの表現力のほとんどが手に入ります。

## フィルター引数の3つの書き方

```figure
{ "type":"cards", "cols":3, "title":"フィルター引数に書けるもの", "caption":"実務では上2つで足りる。3つ目は L0805 で扱う",
  "items":[
    {"icon":"=","title":"ブール述語","text":"Dim_商品[Category] = \"家電\" のような単純な条件。内部でFILTERに変換される。最も読みやすい。","tone":"blue"},
    {"icon":"▦","title":"テーブル式","text":"ALL( Dim_商品 ) や VALUES( … ) など、表そのものを渡す。フィルターを外すときに使う。","tone":"green"},
    {"icon":"ƒ","title":"FILTER 関数","text":"FILTER( 表, 複雑な条件 ) を渡す。2つ以上の列にまたがる条件や、メジャーを含む条件で必要。","tone":"violet"} ] }
```

ブール述語には制限があります。

```dax
-- ✓ OK：1つの列に対する条件
CALCULATE( [売上合計], Dim_商品[Category] = "家電" )

-- ✓ OK：同じ列への複数値（IN で書く）
CALCULATE( [売上合計], Dim_商品[Category] IN { "家電", "食品" } )

-- ✓ OK：違う列への条件を複数引数で（AND になる）
CALCULATE( [売上合計], Dim_商品[Category] = "家電", Dim_日付[年] = 2024 )

-- ✗ NG：1つの述語の中で2つの列を参照
CALCULATE( [売上合計], Dim_商品[Category] = "家電" && Dim_店舗[Region] = "関東" )
```

最後の形は「述語には1つの列しか書けない」という制約に反します。
複数列にまたがる条件は、引数を分けるか `FILTER` を使います。

```dax
-- ✓ 引数を分ける（これが最も速い）
CALCULATE( [売上合計], Dim_商品[Category] = "家電", Dim_店舗[Region] = "関東" )

-- ✓ FILTER を使う（必要な場合のみ）
CALCULATE( [売上合計], FILTER( Fact_売上, Fact_売上[Quantity] * Fact_売上[UnitPrice] > 100000 ) )
```

> [!TIP] 引数を分けられるなら分ける
> `CALCULATE( 式, 条件A, 条件B )` は、内部で最適化されて速く動きます。
> `FILTER` は表を1行ずつ走査するため、**必要なときだけ**使ってください。判断基準は L0805 で扱います。

## 暗黙のCALCULATE

前のレッスンで触れた重要な性質を、ここで正式に確認します。

**メジャーを参照すると、その参照は自動的に `CALCULATE` で包まれます。**

```dax
-- あなたが書いた式
SUMX( VALUES( Dim_商品[ProductName] ), [売上合計] )

-- エンジンが実際に評価する式
SUMX( VALUES( Dim_商品[ProductName] ), CALCULATE( [売上合計] ) )
```

```figure
{ "type":"interactive", "widget":"context-transition", "title":"暗黙のCALCULATEによる遷移を確認する",
  "caption":"反復の中でメジャーを呼んだとき、行の値がどうフィルターに変わるかを見る" }
```

この仕様のおかげで、反復関数の中でメジャーを呼べば直感どおりに動きます。
一方で、**知らないと「なぜ勝手に絞り込まれるのか」が謎になります**。

> [!WARN] 遷移はコストが高い
> コンテキスト遷移は、行ごとにフィルターコンテキストを作り直します。
> 数百万行の表を `SUMX` で反復し、その中でメジャーを呼ぶと、非常に遅くなります。
> **反復対象は必ず小さくする**（`VALUES( Dim_商品[ProductName] )` のようにディメンションの値を使う）のが定石です。

## 実務で使う3つの型

```figure
{ "type":"cards", "cols":3, "title":"CALCULATE の3大用途", "caption":"実務で書くCALCULATEは、ほぼこの3つのどれか",
  "items":[
    {"icon":"🔍","title":"条件付き集計","text":"CALCULATE( [売上合計], Dim_顧客[Segment] = \"法人\" ) — 特定の部分集団だけを見る。","tone":"blue"},
    {"icon":"🌐","title":"フィルターを外す","text":"CALCULATE( [売上合計], REMOVEFILTERS( Dim_商品 ) ) — 全体と比較する。構成比の分母を作る。","tone":"green"},
    {"icon":"📅","title":"時間をずらす","text":"CALCULATE( [売上合計], SAMEPERIODLASTYEAR( Dim_日付[Date] ) ) — 前年・前月と比べる。","tone":"violet"} ] }
```

具体例です。

```dax
-- 1. 条件付き集計
法人売上 = CALCULATE( [売上合計], Dim_顧客[Segment] = "法人" )

-- 2. 構成比（分母を全体にする）
カテゴリ構成比 =
DIVIDE(
    [売上合計],
    CALCULATE( [売上合計], REMOVEFILTERS( Dim_商品[Category] ) )
)

-- 3. 前年同期
前年売上 = CALCULATE( [売上合計], SAMEPERIODLASTYEAR( Dim_日付[Date] ) )
```

構成比の結果を確認します。

| Category | 売上合計 | カテゴリ構成比 |
|---|---|---|
| 家電 | 52 | 52.0% |
| 衣料 | 18 | 18.0% |
| 食品 | 30 | 30.0% |
| **合計** | **100** | **100.0%** |

分子は各行のコンテキストで、分母は `Category` の条件を外して計算されるため、正しい構成比になります。

> [!DS] 部分集団の比較には母数を添える
> 「法人売上が1,000万円」だけでは評価できません。全体に占める割合、前年からの変化、顧客数——
> **比較対象（ベースライン）がない数字は、意思決定に使えません。**
> `CALCULATE` は部分集団を切り出す道具であると同時に、比較対象を作る道具でもあります。
> 指標を1つ作るたびに「これは何と比べる数字か」を自問してください。

## CALCULATE は行を「増やす」こともできる

よくある誤解は「`CALCULATE` は絞り込むだけ」というものです。実際には **広げる** こともできます。

```figure

  "panels":[
    {"title":"絞り込む","tone":"blue","items":[
      "CALCULATE( [売上合計], Dim_顧客[Segment] = \"法人\" )",
      "外側に条件がなければ、法人だけに絞られる",
      "対象行が減る",
      "条件付き集計の型"],
     "note":"範囲を狭める"},
    {"title":"広げる","tone":"green","items":[
      "CALCULATE( [売上合計], ALL( Dim_商品 ) )",
```

「上書き」という1つの動作が、外側の条件次第で絞り込みにも拡大にもなります。
**`CALCULATE` は絞り込み関数ではなく、置き換え関数** だと理解してください。

## 変数を渡してはいけない（再確認）

L0705 で扱った罠を、`CALCULATE` の文脈でもう一度確認します。

```dax
-- ✗ 前年売上が当年と同じになる
VAR 当年 = [売上合計]
VAR 前年 = CALCULATE( 当年, SAMEPERIODLASTYEAR( Dim_日付[Date] ) )

-- ✓ 正しい
VAR 当年 = [売上合計]
VAR 前年 = CALCULATE( [売上合計], SAMEPERIODLASTYEAR( Dim_日付[Date] ) )
```

`CALCULATE` はコンテキストを変えますが、**すでに確定した数値を変えることはできません**。
第1引数には必ず「式」を渡してください。

> [!EXAM] PL-300で問われる
> 「特定カテゴリの売上を、他のカテゴリ行でも同じ値として表示したい」→ `CALCULATE` の上書きを利用。
> 「各行のコンテキストを保ったまま追加条件を適用したい」→ `KEEPFILTERS`（L0805）。
> この2つの違いを問う問題が頻出です。

## 理解度チェック

**問1.** `CALCULATE( [売上合計], Dim_商品[Category] = "家電" )` をカテゴリ別テーブルに置くと、全カテゴリ行で同じ値が出る。理由を「上書き」という語を使って説明せよ。

<details><summary>答え</summary>
フィルター引数と行から来た条件が同じ列（Category）に対するものなので、行の条件が上書きされ、どの行でも Category = 家電 になるため。異なる列（例：年）への条件なら追加（AND）となり、行ごとに違う値になる。
</details>

**問2.** `CALCULATE( [売上合計], Dim_商品[Category] = "家電" && Dim_店舗[Region] = "関東" )` がエラーになる理由と、正しい書き方を述べよ。

<details><summary>答え</summary>
ブール述語には1つの列しか書けないため。正しくは引数を分けて `CALCULATE( [売上合計], Dim_商品[Category] = "家電", Dim_店舗[Region] = "関東" )` とする（複数引数はANDで合成される）。
</details>

**問3.** `CALCULATE` の評価順序において、フィルター引数と第1引数のどちらが先に評価されるか。またそれが重要な理由は。

<details><summary>答え</summary>
フィルター引数が先。フィルター引数は「変更前の外側のコンテキスト」で評価され、その結果で新しいコンテキストを組み立ててから第1引数が評価される。この順序を知らないと、フィルター引数の中でメジャーを使ったときの挙動が予測できない。
</details>

## よくあるエラーと原因

| 症状・エラー | 原因 | 対処 |
|---|---|---|
| 全行で同じ値になる | 同じ列への条件で上書きされた | 意図どおりなら正常。行の条件を残すなら `KEEPFILTERS` |
| 「単一の列を参照する必要があります」 | 述語で2つの列を参照した | 引数を分けるか `FILTER` を使う |
| 前年売上が当年と同じ | `CALCULATE` に変数を渡した | 変数ではなくメジャー・式を渡す |
| 構成比の合計が100%にならない | 分母のフィルター除去範囲が不適切 | `REMOVEFILTERS` の対象列を見直す |
| 極端に遅い | 大きな表を `FILTER` で反復している | 述語形式に書き換える／対象列だけを渡す |
| 反復の中の値が全体値になる | メジャーではなく式を直接書いた | メジャー参照にして暗黙のCALCULATEを効かせる |
| スライサーを外すと値が変わる | 外側の条件が残っている（AND） | `ALL` / `ALLSELECTED` で意図を明示する |

> [!NOTE] このレッスンのまとめ
> `CALCULATE` はフィルターコンテキストを変更できる唯一の関数で、動作の本質は **置き換え** です。
> 評価は「フィルター引数が先、式が後」。同じ列は上書き、違う列は追加。
> 行コンテキストがある場所では **コンテキスト遷移** も同時に起こし、メジャー参照には暗黙の `CALCULATE` が含まれます。
> 次のレッスンでは、この上書きを使って「フィルターを外す」技法を扱います。
