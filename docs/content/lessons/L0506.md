6,948 行の明細をそのまま Power BI に読み込むべきでしょうか。答えは「分析に必要な粒度なら読み込む、不要なら畳む」です。この判断と実装を担うのが **グループ化** です。

グループ化は、**粒度を意図的に決める操作**です。L0503 で「1行が何を表すか」を宣言しました。グループ化はその宣言を実装に落とす作業になります。


4行が3行になり、`OrderID` という列は消えました。**グループ化は必ず情報を捨てます**。何を捨てるかを意識して実行してください。

> [!NOTE]
> グループ化のダイアログには「基本」と「詳細設定」があります。基本はキー1列・集計1つだけ。実務ではほぼ常に詳細設定を使い、複数のキーと複数の集計を指定します。最初から詳細設定を開く習慣にしてください。

## 集計関数を使い分ける

```figure

  "caption": "「合計」と「行数のカウント」の使い分けが最も多い。個別のカウントは意味が違う",
  "items": [
    {"icon": "➕", "title": "合計 / 平均", "text": "数値列に対して List.Sum / List.Average を適用する。平均は null を無視するので、0 と欠測の違いに注意する。", "tone": "blue"},
    {"icon": "🔢", "title": "行数のカウント", "text": "グループ内の行数。明細件数を数えるときに使う。null の行も数える。", "tone": "green"},
    {"icon": "🎯", "title": "個別の行数のカウント", "text": "重複を除いた件数。「何件の受注があったか」を明細から数えるときはこちら。", "tone": "amber"},
    {"icon": "📉", "title": "最小 / 最大", "text": "日付列に使うと初回購入日・最終購入日が出せる。顧客分析の基本材料になる。", "tone": "violet"},
    {"icon": "📊", "title": "中央値", "text": "外れ値の影響を受けにくい代表値。単価の分布が偏っているときに平均と併記する。", "tone": "pink"},
    {"icon": "📦", "title": "すべての行", "text": "集計せずグループの明細をテーブルとして保持する。後述の応用で使う強力な機能。", "tone": "cyan"} ] }
```

生成される M は `Table.Group` です。

```m
// 店舗 × カテゴリで集計する
= Table.Group(
    前のステップ,
    {"StoreID", "Category"},
    {
        {"数量計", each List.Sum([Quantity]), Int64.Type},
        {"売上計", each List.Sum([SalesAmount]), Int64.Type},
        {"明細件数", each Table.RowCount(_), Int64.Type},
        {"受注件数", each List.Count( List.Distinct([OrderID]) ), Int64.Type},
        {"初回受注日", each List.Min([OrderDate]), type date},
        {"最終受注日", each List.Max([OrderDate]), type date}
    }
  )
```

読み方は単純です。第2引数がキー列の一覧、第3引数が `{新しい列名, 計算式, 型}` の並びです。`_` はグループのテーブル自身、`[列名]` はそのグループにおける列の値のリストを指します。

> [!TRAP]
> 「明細件数」と「受注件数」を混同しないでください。1つの受注に3商品が含まれていれば、明細件数は3、受注件数は1です。**「今月何件売れましたか」という質問は、ほぼ常に受注件数（個別のカウント）を指しています**。行数のカウントで答えると件数が水増しされます。日本語の「件数」は曖昧なので、必ず定義を確認してから実装してください。

## 「すべての行」で明細を保持する

集計せずにグループの明細を丸ごと保持するのが「すべての行」です。これを使うと、**各グループの中で条件に合う1行を取り出す**という処理が書けます。

```figure
{ "type": "steps", "title": "顧客ごとの最新受注を取り出す",
  "caption": "SQL のウィンドウ関数に相当する処理を、グループ化だけで実現できる",
  "items": [
    {"title": "CustomerID でグループ化する", "text": "集計は「すべての行」を選び、列名を「明細」とする。", "tone": "blue"},
    {"title": "入れ子テーブルが作られる", "text": "各行の「明細」列に、その顧客の全受注が1つのテーブルとして入る。", "tone": "green"},
    {"title": "カスタム列で最大行を取り出す", "text": "Table.Max([明細], \"OrderDate\") で、受注日が最大の行のレコードを得る。", "tone": "amber"},
    {"title": "必要なフィールドを展開する", "text": "レコードから OrderID や SalesAmount を取り出し、入れ子列を削除する。", "tone": "violet"} ] }
```

```m
// 顧客ごとの最新受注を1行だけ取り出す
let
    グループ化 = Table.Group(
        売上, {"CustomerID"},
        {{"明細", each _, type table}}
    ),
    最新受注 = Table.AddColumn(
        グループ化, "最新",
        each Table.Max([明細], "OrderDate")
    ),
    展開 = Table.ExpandRecordColumn(
        最新, "最新",
        {"OrderID", "OrderDate", "SalesAmount"},
        {"最新受注ID", "最終受注日", "最新受注金額"}
    ),
    整理 = Table.RemoveColumns(展開, {"明細"})
in
    整理
```

この型を覚えておくと、「各商品の最高単価の受注」「各店舗の最初の受注」といった要件がすべて同じ手順で書けます。

> [!WARN]
> 「すべての行」は、グループ内の明細をメモリ上に保持するため、**大きなテーブルでは非常に重くなります**。数十万行を超えるデータで使うときは、先に不要な列を削除してからグループ化してください。列を減らすだけで劇的に速くなります。

## 行と列の操作

グループ化と並んで、粒度と容量を制御する基本操作を整理します。

| 操作 | コマンド | 使いどころ |
|---|---|---|
| 列の削除 | 右クリック → 列の削除 | 不要な列を落とす。容量削減の最重要操作 |
| 他の列の削除 | 右クリック → 他の列の削除 | **推奨**。残す列を指定するので、列が増えても壊れない |
| 行のフィルター | 列見出しの▼ | 対象範囲を絞る。できるだけ前に置く |
| 上位N行の保持 | ホーム → 行の保持 | サンプル抽出、テスト用 |
| 重複の削除 | 右クリック → 重複の削除 | ディメンション候補を作る |
| 行の逆順 | 変換 → 行の反転 | 末尾N行を取るときに保持と組み合わせる |
| インデックス列の追加 | 列の追加 → インデックス列 | 順序を固定する。並べ替えの保持に使う |

> [!TIP]
> **「列の削除」より「他の列の削除」を使ってください**。理由は L0504 のピボット解除と同じです。「列の削除」は消す列を列挙するので、ソースに新しい列が増えたとき、その列が黙ってモデルに入り込みます。「他の列の削除」は残す列を列挙するので、想定外の列は自動的に除外されます。**将来の変更に対して壊れにくい書き方を選ぶ**という原則は、Power Query 全体を貫いています。

グループ化・フィルター・列の削除は、いずれも**データベース相手なら折りたたみ可能**な操作です。SQL の `GROUP BY`、`WHERE`、`SELECT` にそのまま翻訳されます。

グループ化を折りたたませたい場合、**カスタムの集計式を書くと折りたたみが切れます**。`List.Sum` や `Table.RowCount` のような標準の集計は翻訳できますが、複雑な式は翻訳できません。性能が問題になる場面では、標準の集計だけで済ませる工夫が効きます。

> [!EXAM]
> PL-300 では「更新時間を短縮したい」「セマンティックモデルのサイズを削減したい」という設問が頻出します。有効な答えは、(1) 不要な列を削除する、(2) 必要な粒度まで集計する、(3) 日時列を日付と時刻に分割してカーディナリティを下げる、(4) 行のフィルターで対象期間を絞る、の4つです。「ビジュアルを減らす」「レポートのページを分ける」はモデルサイズに影響しないので誤りです。

## Power Query で集計するか、DAX で集計するか

グループ化を覚えると、つい何でも Power Query で集計したくなります。しかし Power BI では、**集計はメジャー（DAX）で行うのが原則**です。

```figure

  "caption": "「取り込む粒度」は Power Query の仕事、「見せる集計」は DAX の仕事",
```

では Power Query のグループ化はいつ使うのか。判断は明快です。

| Power Query で集計してよい場面 | 理由 |
|---|---|
| ソースが巨大で、明細を取り込むと更新が終わらない | 物理的な制約。粒度を文書化したうえで畳む |
| 分析に必要な粒度が明確に決まっている | 月次予算のように、そもそも明細が存在しない |
| ディメンションを作るために重複を落とす | 集計というより一意化の作業 |
| データ品質の検査クエリを作る | モデルには載せない |

> [!TRAP]
> 「表示が遅いから Power Query で集計しておこう」は、多くの場合順序が違います。遅さの原因はモデル設計かDAXの書き方にあることが大半で、粒度を落とすのは最後の手段です。**先に列を削り、スタースキーマを組み、それでも足りなければ粒度を落とす**。この順序を守らないと、後から必要になった分析ができなくなります。

```m
let
    列を絞る = Table.SelectColumns(
        売上, {"StoreID", "OrderDate", "OrderID", "Quantity", "SalesAmount"}
    ),
    月キー = Table.AddColumn(
        列を絞る, "月初日",
        each Date.StartOfMonth([OrderDate]), type date
    ),
    サマリー = Table.Group(
        月キー,
        {"StoreID", "月初日"},
        {
            {"売上計", each List.Sum([SalesAmount]), Int64.Type},
            {"数量計", each List.Sum([Quantity]), Int64.Type},
            {"受注件数", each List.Count( List.Distinct([OrderID]) ), Int64.Type}
        }
    ),
    並べ替え = Table.Sort(サマリー, {{"StoreID", Order.Ascending}, {"月初日", Order.Ascending}})
in
    並べ替え
```

`Table.SelectColumns` が「他の列の削除」に対応します。グループ化の前に列を絞ると、入れ子の生成コストが下がって処理が明確に速くなります。

> [!TIP]
> グループ化した結果に **`Table.Sort` で並べ替えを付けても、Power BI に読み込んだ後の表示順は保証されません**。表示順はビジュアル側と「列で並べ替え」の設定で決まります（L0606 で扱います）。Power Query での並べ替えは、あくまで確認用と考えてください。順序に意味を持たせたいなら、インデックス列を明示的に作る必要があります。

2. 「顧客ごとの最終購入日と、そのときの購入金額」を1つのテーブルで出す手順を、使う集計オプションを挙げて説明してください。

## よくあるエラーと対処

| 症状 | 原因 | 対処 |
|---|---|---|
| グループ化後に必要な列が消えた | キーにも集計にも指定していない | キー列に加えるか、`List.Max` などで集計値として取り出す |
| 件数が実際より多い | 行数のカウントを使っている | 個別の行数のカウント（`List.Distinct`）に変更する |
| グループ化が終わらない | 「すべての行」で巨大な入れ子を作っている | 先に不要な列を削除する。または集計に置き換える |
| 平均が想定より高い | null が無視されて分母が小さい | 0 と null の扱いを決め、必要なら 0 埋めしてから平均する |
| 新しい列が勝手にモデルに入る | 「列の削除」で列挙していた | 「他の列の削除」に置き換える |
| 集計後の値をさらに平均して数字が合わない | 平均の平均は全体平均と一致しない | 合計と件数を保持し、割り算はメジャー側で行う |
| グループ化で折りたたみが切れた | カスタムの集計式を使っている | 標準の集計関数だけで書き直す |
