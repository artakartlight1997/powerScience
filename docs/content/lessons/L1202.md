リレーションシップの編集画面に「クロス フィルターの方向」という設定があり、「単一」を「両方」に変えると、動かなかったスライサーが動き出します。**この瞬間に問題は解決したように見えます。** そして、別のどこかで数字が壊れ始めます。

このレッスンでは、双方向フィルターが何をしているのかを正確に理解し、**同じ要件を副作用なしで満たす4つの代替手段**を身につけます。

## フィルターは既定で「1側から多側」へ流れる

スタースキーマでは、フィルターは常にディメンションからファクトへ流れます。これが単方向（単一）です。

```figure
{ "type":"pipeline", "title":"単方向フィルターの伝播",
  "caption":"ディメンションで絞ると、ファクトの行が絞られる。逆は起きない。この一方通行が予測可能性を生む",
  "nodes":[
    {"id":"d1","label":"Dim_商品\nカテゴリ=家電を選択","tone":"blue"},
    {"id":"f","label":"Fact_売上\n家電の行だけに絞られる","tone":"green"},
    {"id":"d2","label":"Dim_顧客\n何も起きない","tone":"gray"},
    {"id":"d3","label":"Dim_日付\n何も起きない","tone":"gray"}
  ],
  "edges":[
    {"from":"d1","to":"f","label":"1側 → 多側"},
    {"from":"d2","to":"f","label":"（伝播せず）"},
    {"from":"d3","to":"f","label":"（伝播せず）"}
  ] }
```

「両方」にすると、この矢印が逆向きにも流れます。ファクトが絞られると、そのファクトに関係する**すべてのディメンションが絞られる**ようになります。

## 双方向で起きること1：意図しない連鎖

```figure
{ "type":"pipeline", "title":"双方向にしたときの連鎖",
  "caption":"1本を双方向にすると、そのファクトを経由して他のディメンションまで絞られる。これは多くの場合、意図していない",
  "nodes":[
    {"id":"d1","label":"Dim_商品\nカテゴリ=家電","tone":"blue"},
    {"id":"f","label":"Fact_売上\n家電の行","tone":"green"},
    {"id":"d2","label":"Dim_顧客\n家電を買った顧客だけに絞られる","tone":"amber"},
    {"id":"f2","label":"Fact_問い合わせ\nその顧客の問い合わせだけ","tone":"pink"},
    {"id":"d3","label":"Dim_日付\n該当日だけに絞られる","tone":"bad"}
  ],
  "edges":[
    {"from":"d1","to":"f"},
    {"from":"f","to":"d2","label":"双方向で逆流"},
    {"from":"d2","to":"f2","label":"さらに伝播"},
    {"from":"f2","to":"d3","label":"連鎖は止まらない"}
  ] }
```

「家電カテゴリを選んだら、顧客スライサーに家電を買った人だけ出る」。これは望んだ動作かもしれません。しかし同時に、**「家電を1度も買っていない顧客が集計から消える」**、**「顧客が0人の日付が日付スライサーから消える」** という副作用が起きます。売上0の分析ができなくなります。

> [!TRAP] つまずきポイント
> 双方向フィルターの被害で最も多いのが、**「0件が見えなくなる」** です。「今月まったく売れなかった商品を洗い出したい」「一度も購買していない顧客に施策を打ちたい」という分析が、モデルの構造上できなくなります。しかも「消えている」ことは画面から分からないため、「該当なしだったんだな」と誤読されます。

## 双方向で起きること2：曖昧なパス

複数のテーブル間に2つ以上の経路ができると、Power BI はどちらを使うか決められません。

```figure
{ "type":"star", "title":"曖昧なパスが生まれるモデル",
  "caption":"Dim_日付 から Fact_売上 へ、直接の経路と Fact_在庫 経由の経路の2つができてしまう状態",
  "fact":{"label":"Fact_売上","lines":["日付 / 商品ID / 店舗ID","金額"]},
  "dims":[
    {"label":"Dim_日付","lines":["直接つながる","かつ Fact_在庫 経由でもつながる"]},
    {"label":"Fact_在庫","lines":["日付 / 商品ID","在庫数","双方向にすると経路になる"]},
    {"label":"Dim_商品","lines":["商品ID","両ファクトに接続"]},
    {"label":"Dim_店舗","lines":["店舗ID"]}
  ],
  "edgeLabel":"経路が2つ" }
```

このとき Power BI は、**リレーションシップを非アクティブにするか、作成そのものを拒否します**。「このリレーションシップを作成すると、テーブル間に曖昧性が生じます」というエラーは、この状態を指しています。

> [!WARN] 注意
> Power BI が拒否してくれるのは、まだ運がよいケースです。**拒否されず、しかし直感と異なる経路が選ばれる**ケースもあります。この場合はエラーが出ず、数字だけが説明のつかない値になります。モデル図で「関係が閉路（ループ）を作っていないか」を目視で確認する習慣をつけてください。

## 双方向で起きること3：性能劣化

双方向のリレーションシップは、クエリのたびに逆方向の伝播を計算します。ファクトが大きいほど、この計算は重くなります。

```figure
{ "type":"chart", "kind":"bar", "title":"同じビジュアルの応答時間（1億行のファクト）",
  "caption":"双方向は「ファクト全体を走査してディメンションの値を求める」ため、行数に比例して重くなる",
  "categories":["すべて単方向","1本だけ双方向","3本を双方向","双方向＋RLS"],
  "series":[{"name":"応答時間","values":[0.4,1.9,6.2,14.8],"tone":"blue"}],
  "highlight":3, "unit":"秒" }
```

> [!DS] データサイエンス視点
> グラフ理論の言葉で言えば、単方向のスタースキーマは**有向非巡回グラフ（DAG）** です。フィルターの伝播経路が一意に決まるため、エンジンは最短経路を静的に決められます。双方向にすると閉路が生まれる可能性があり、経路の一意性が失われます。**「関係を双方向にする」は、グラフの性質を根本から変える操作**であって、単なるオプション変更ではありません。リレーショナルモデルの正規化・非正規化と同じく、構造の選択です。

## 双方向で起きること4：RLSの穴

これが最も深刻です。**双方向フィルターは、行レベルセキュリティ（RLS）の制限を回り込んで、見えてはいけない情報を推測可能にすることがあります。**

```figure
{ "type":"pipeline", "title":"双方向による情報の逆流",
  "caption":"自分の支店の売上しか見えないはずのユーザーが、他支店が扱う商品の存在を推測できてしまう",
  "nodes":[
    {"id":"rls","label":"RLS\n支店=東京 のみ許可","tone":"pink"},
    {"id":"ds","label":"Dim_支店\n東京だけに絞られる","tone":"amber"},
    {"id":"f","label":"Fact_売上\n東京の行だけ","tone":"green"},
    {"id":"dp","label":"Dim_商品\n東京で扱う商品だけに絞られる","tone":"cyan"},
    {"id":"f2","label":"Fact_仕入\n双方向経由で\n他支店の情報が見える経路","tone":"bad"}
  ],
  "edges":[
    {"from":"rls","to":"ds"},
    {"from":"ds","to":"f"},
    {"from":"f","to":"dp","label":"双方向で逆流"},
    {"from":"dp","to":"f2","label":"意図しない伝播"}
  ] }
```

リレーションシップの詳細設定にある **「両方向にセキュリティ フィルターを適用する」** をオンにすると、RLSのフィルターも双方向に伝播します。便利に見えますが、伝播の経路を完全に把握していない限り、**どこまで見えるかを保証できなくなります**。

> [!TRAP] つまずきポイント
> RLSを設定したモデルで双方向フィルターを使うときは、**必ず「ロールとして表示」で全ロールを実際に検証してください**。「設定したから大丈夫」は通用しません。特に、RLSをかけたテーブルとは別のテーブルを経由する経路がないかを確認します。セキュリティは「たぶん大丈夫」では成立しません。

## 代替手段1：`CROSSFILTER` — メジャー単位で双方向にする

モデルの関係は単方向のままにして、**必要なメジャーの中でだけ**双方向にします。

```figure
{ "type":"compare", "title":"モデルで双方向 vs CROSSFILTER",
  "caption":"影響範囲が「モデル全体・全レポート・全ビジュアル」か「そのメジャーだけ」かの違い",
  "panels":[
    {"title":"リレーションシップを双方向にする","tone":"bad",
     "items":[
       "影響範囲：モデル全体。すべてのビジュアル・すべてのレポート",
       "他の作成者が作るレポートにも影響する",
       "曖昧経路が生まれる可能性がある",
       "RLSのセキュリティ境界が広がる",
       "後から外すと、既存レポートが壊れる可能性がある",
       "モデル図を見れば気づけるのが唯一の利点"
     ],"note":"影響を完全に把握できるときだけ"},
    {"title":"CROSSFILTER をメジャー内で使う","tone":"good",
     "items":[
       "影響範囲：そのメジャーが使われたときだけ",
       "他のメジャー・他のレポートに影響しない",
       "モデルの構造は単方向のまま保たれる",
       "RLSの経路は変わらない",
       "メジャー名で意図を表現できる",
       "DAXを読まないと気づけないのが欠点。コメントを書く"
     ],"note":"既定の選択肢にする"}
  ] }
```

```dax
-- 例：商品カテゴリごとに「購入したことのある顧客数」を出す。
-- Dim_顧客 → Fact_売上 は単方向のままだが、このメジャー内でだけ逆流させる
購入顧客数 =
CALCULATE(
    DISTINCTCOUNT( Dim_顧客[顧客ID] ),
    CROSSFILTER( Dim_顧客[顧客ID], Fact_売上[顧客ID], BOTH )
)
```

`CROSSFILTER` の第3引数は3種類です。

| 指定 | 意味 | 使いどころ |
|---|---|---|
| `BOTH` | 双方向にする | ファクトからディメンションへ絞りたいとき |
| `ONEWAY` | 単方向にする | モデルで双方向のものを、このメジャーでは単方向に戻す |
| `NONE` | 関係を無効にする | そのメジャーだけ関係を切りたいとき（全期間比較など） |

```dax
-- NONE の使用例：日付フィルターを無視した全期間の合計
全期間売上 =
CALCULATE(
    SUM( Fact_売上[金額] ),
    CROSSFILTER( Dim_日付[日付], Fact_売上[売上日], NONE )
)
```

## 代替手段2：`TREATAS` — 値をフィルターとして渡す

関係の向きを変えるのではなく、必要な値だけをフィルターとして送り込みます。

```dax
-- 売上のあった商品カテゴリだけを対象に、在庫を集計する
売れた商品の在庫 =
CALCULATE(
    SUM( Fact_在庫[在庫数] ),
    TREATAS(
        VALUES( Fact_売上[商品ID] ),
        Fact_在庫[商品ID]
    )
)
```

`CROSSFILTER` が「関係の向きを変える」のに対し、`TREATAS` は「関係を使わずに値を渡す」ものです。**中間テーブルを経由しないので、経路が長いモデルでは性能面でも有利になります**。

## 代替手段3：モデルをスター化する

そもそも双方向が必要になるのは、**モデルがスタースキーマになっていない**ことが原因である場合が多くあります。

## 代替手段4：メジャーで「存在」を判定する

「売上のある商品だけスライサーに出したい」という要件は、双方向ではなくビジュアル側で解けます。

```dax
-- 売上がある行だけを残すためのフラグメジャー
売上あり = IF( NOT ISBLANK( [売上合計] ), 1 )
```

このメジャーをビジュアルのフィルターペインに置き、「1に等しい」を指定すると、売上のない商品が非表示になります。**モデルには一切影響しません。** レポートごとに、出すか出さないかを選べるという利点もあります。

## 双方向が正当化される数少ないケース

  "root":{"label":"フィルターを逆向きに流したい"},
  "children":[
    {"label":"モデルがスノーフレークでは？","sub":"まず構造を疑う","tone":"good",
     "children":[
       {"label":"はい → ディメンションに畳む","sub":"双方向は不要になる","tone":"good"}
     ]},
    {"label":"1つのメジャーの話か？","sub":"特定の集計だけの要件","tone":"cyan",
     "children":[
       {"label":"はい → CROSSFILTER / TREATAS","sub":"モデルは触らない","tone":"good"}
     ]},
    {"label":"スライサーの見た目の話か？","sub":"選択肢を絞りたいだけ","tone":"amber",
     "children":[
       {"label":"はい → フラグメジャーでフィルター","sub":"レポート側で解決","tone":"good"}

     "children":[

正当化されるのは、実質的に次の2つだけです。

1. **多対多ブリッジテーブルとディメンションの間の1本**。しかもRLSが関わらないモデル。
2. **小さなディメンション同士を結ぶ、ファクトを経由しない関係**。伝播が波及しない構造であることが確認できている場合。

> [!EXAM] PL-300で問われる
> 「双方向のクロス フィルターを使用すべきでない理由」「曖昧なリレーションシップの回避方法」は出題範囲です。また、RLS と組み合わせた場合の**「両方向にセキュリティ フィルターを適用する」** の意味も問われます。正解の方向性は一貫して「**既定は単方向、必要な場合のみ DAX の `CROSSFILTER` で限定的に**」です。

## フィルターの伝播を自分の目で確かめる

理屈で理解するより、動かして確かめるほうが速く身につきます。次の3つの方法を使い分けてください。

```figure
{ "type":"cards", "cols":3, "title":"伝播を確認する3つの道具",
  "caption":"「たぶんこう伝わっている」を「こう伝わっていることを確認した」に変える",
  "items":[
    {"icon":"🔍","title":"モデル ビューの強調表示","text":"テーブルを選ぶと、関係する線が強調される。矢印の向きが視覚的に分かる","tone":"blue"},
    {"icon":"⏱","title":"パフォーマンス アナライザー","text":"表示タブから起動。各ビジュアルのDAXクエリと所要時間が取れる。双方向の重さがここに出る","tone":"green"},
    {"icon":"🧪","title":"検証用の行数メジャー","text":"COUNTROWS を各テーブルに1本ずつ作り、表に並べる。どのテーブルが絞られたか一目で分かる","tone":"violet"}
  ] }
```

```dax
-- 検証用メジャー：どのテーブルが何行に絞られているかを可視化する
行数_売上   = COUNTROWS( Fact_売上 )
行数_顧客   = COUNTROWS( Dim_顧客 )
行数_商品   = COUNTROWS( Dim_商品 )
行数_日付   = COUNTROWS( Dim_日付 )
```

この4つをカードビジュアルで並べ、スライサーを操作します。**商品カテゴリを選んだときに `行数_顧客` が減れば、双方向が効いている証拠**です。減らなければ単方向です。モデルを引き継いだ直後にこの検証ページを作っておくと、以後の調査が圧倒的に楽になります。

> [!TIP] 実務のコツ
> この検証ページは、レポートの「非表示ページ」として残しておいてください。数字がおかしいという問い合わせが来たとき、「どのテーブルが絞られているか」を最初に見るだけで、原因の半分は特定できます。

## 既存モデルの双方向を外す手順

すでに双方向だらけのモデルを引き継いだ場合の進め方です。

1. **モデル図で双方向のリレーションシップを列挙する**（矢印が両端に付いている線）。
2. 各リレーションシップについて、**外したときに壊れるビジュアルを特定する**。テスト用のページに、影響しそうなビジュアルを集めておく。
3. 1本ずつ単方向に戻し、**壊れたビジュアルだけ** `CROSSFILTER` を使ったメジャーに置き換える。
4. RLSがある場合は、各ロールで「ロールとして表示」を実行し、**見える行が変わっていないこと**を確認する。
5. 応答時間を計測し、改善を記録する（パフォーマンス アナライザー）。

> [!TRAP] つまずきポイント
> 一度に全部外すと、何が原因で壊れたか分からなくなります。**1本ずつ、必ず検証を挟んで**進めてください。また、外した結果として「今まで見えていなかった0件の行が見えるようになる」ことがあります。これは修正であって不具合ではありませんが、**利用者には事前に説明が必要です**。「先月から数字が変わった」というクレームを防ぐために、変更の告知は必ず行ってください。

## 設計判断チェックリスト

- [ ] モデル図で、双方向の矢印が何本あるか数えたか
- [ ] その双方向は、スノーフレークをスター化すれば不要にならないか
- [ ] 要件は1つのメジャーの話か。`CROSSFILTER` / `TREATAS` で代替できないか
- [ ] スライサーの選択肢を絞りたいだけなら、フラグメジャーで解けないか
- [ ] 双方向にした結果、「0件の行が見えなくなる」影響を確認したか
- [ ] リレーションシップに閉路（ループ）ができていないか
- [ ] RLSがある場合、全ロールで「ロールとして表示」を検証したか
- [ ] 「両方向にセキュリティ フィルターを適用する」の意味を理解したうえで設定したか
- [ ] 応答時間を、双方向の設定前後で計測したか
