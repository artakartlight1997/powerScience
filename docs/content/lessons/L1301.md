DAX の関数は、大きく2つに分かれます。**表全体を一気に集計する関数**と、**行を1つずつ見ながら計算する関数**です。後者を**イテレータ関数**と呼びます。名前の末尾に `X` が付くのが目印です。

この区別が分かっていないと、次の事故が起きます。

```figure
{ "type":"compare", "title":"同じ「売上金額」のつもりで書いた2つの式", "caption":"上は行ごとの掛け算を一切していない。単価の合計と数量の合計を掛けただけの、意味のない数字になる",
  "panels":[
    {"title":"SUM を使った式（誤り）","tone":"bad","items":["SUM( Fact_売上[UnitPrice] ) * SUM( Fact_売上[Quantity] )","単価の総和 × 数量の総和","3行のデータで 1,000万円 と表示される"],"note":"掛け算の順序が違う"},
    {"title":"SUMX を使った式（正しい）","tone":"good","items":["SUMX( Fact_売上, Fact_売上[UnitPrice] * Fact_売上[Quantity] )","行ごとに掛けてから足す","同じデータで 46万円 と表示される"],"note":"意図どおり"} ] }
```

数字が20倍違います。しかもエラーにはなりません。**静かに間違った数字を出す**——これがDAXで最も高くつく事故です。

## なぜ差が出るのか

具体的な数字で見ます。3行だけのデータです。

```figure
{ "type":"tablediff", "title":"SUM×SUM と SUMX の計算過程", "arrowLabel":"行ごとに計算してから合計する",
  "before":{"title":"SUM(単価) × SUM(数量)","tone":"bad","head":["処理","値"],
    "rows":[["SUM(UnitPrice)","1,000 + 2,000 + 500 = 3,500"],["SUM(Quantity)","10 + 5 + 20 = 35"],["最後に掛ける","!3,500 × 35 = 122,500"]]},
  "after":{"title":"SUMX(行ごとに単価×数量)","tone":"good","head":["行","単価 × 数量"],
    "rows":[["1行目","1,000 × 10 = 10,000"],["2行目","2,000 × 5 = 10,000"],["3行目","500 × 20 = 10,000"],["合計","!30,000"]]} }
```

SUM は**列を1本受け取って、その列の値を足すだけ**です。列と列を掛ける能力を持っていません。一方 SUMX は**表を受け取り、1行ずつ式を評価して、その結果を足します**。

> [!NOTE] 要点
> `SUM(列)` は列を集計する。`SUMX(表, 式)` は表を1行ずつ走査して式を評価し、その結果を集計する。**列と列の演算が必要なら、必ずイテレータを使う。**

## イテレータ関数の形

すべてのイテレータ関数は、引数を2つ取ります。

```figure
{ "type":"formula", "lang":"dax", "title":"SUMX の解剖",
  "code":"SUMX( Fact_売上, Fact_売上[UnitPrice] * Fact_売上[Quantity] )",
  "parts":[
    {"match":"SUMX","label":"第1引数の表を1行ずつ走査し、第2引数の結果を合計する","tone":"violet"},
    {"match":"Fact_売上,","label":"第1引数：走査する表。ここでフィルターコンテキストが効いた後の行だけが対象になる","tone":"blue"},
    {"match":"Fact_売上[UnitPrice] * Fact_売上[Quantity]","label":"第2引数：各行で評価される式。この中では「今の行」の値が参照できる","tone":"amber"} ] }
```

第2引数の式が「今の行の値」を参照できるのは、SUMX が**行コンテキスト**を作っているからです。

> [!NOTE] 用語
> **行コンテキスト**とは、「今どの行を処理しているか」という情報のことです。計算列を書くと自動的に作られ、イテレータ関数の第2引数の中でも作られます。行コンテキストがない場所で `Fact_売上[UnitPrice]` と裸で書くとエラーになります。

## SUM と SUMX が一致するとき、しないとき

すべてのケースで SUMX を使えばいい、という話ではありません。

```figure
{ "type":"matrix", "title":"SUM と SUMX の使い分け",
  "xLabel":"式の複雑さ", "yLabel":"性能への影響",
  "xLow":"単一列をそのまま","xHigh":"列同士の演算あり","yLow":"小","yHigh":"大",
  "quadrants":[
    {"title":"SUM を使う","text":"SUM( Fact_売上[SalesAmount] )。最速。迷う余地なし","tone":"good"},
    {"title":"SUMX が必須","text":"SUMX( Fact_売上, [UnitPrice] * [Quantity] )。SUMでは書けない","tone":"amber"},
    {"title":"SUMX でも同じ結果","text":"SUMX( Fact_売上, [SalesAmount] ) は SUM と同値。わざわざ書く理由はない","tone":"neutral"},
    {"title":"設計を疑う","text":"重い式を毎回イテレートしているなら、計算列やETLでの事前計算を検討する","tone":"bad"} ] }
```

**単一列をそのまま集計するだけなら SUM を使ってください。** `SUMX( Fact_売上, Fact_売上[SalesAmount] )` は SUM と全く同じ結果を返しますが、エンジンが**列そのものの集計**として最適化しやすいのは SUM のほうです。

> [!DS] データサイエンス視点
> これは**ベクトル化演算**の話とほぼ同じ構造です。NumPy や pandas で `df["a"].sum()` はCレベルで一括処理されますが、`df.apply(lambda r: r["a"]*r["b"], axis=1)` は行ごとにPythonの関数呼び出しが起きて桁違いに遅くなります。DAXも同じで、**列単位で完結する処理を列単位で書けるかどうか**が性能を決めます。ただしDAXのイテレータは、後で見るとおり多くの場合エンジン側で列演算に変換されるため、pandasほどの差にはなりません。

## SUMX が本当に必要になる場面

実務で SUMX を選ぶ理由は3つに集約されます。

```figure
{ "type":"cards", "cols":3, "title":"SUMX を使う3つの理由",
  "items":[
    {"icon":"✖","title":"列同士の演算","text":"単価×数量、金額−原価など、複数の列を使った計算を行ごとに行う必要がある","tone":"blue"},
    {"icon":"🔀","title":"行ごとの条件分岐","text":"IF で行ごとに違う計算をしたい。SUMX( Fact_売上, IF( [Quantity] > 10, [SalesAmount] * 0.9, [SalesAmount] ) )","tone":"green"},
    {"icon":"📊","title":"集計テーブルの上で集計","text":"顧客ごとの合計を出してから、その平均を取るなど、2段階の集計を行う","tone":"violet"} ] }
```

3つ目が上級の入口です。実例を見ます。

```dax
粗利 =
SUMX(
    Fact_売上,
    Fact_売上[SalesAmount]
        - Fact_売上[Quantity] * RELATED( Dim_商品[StandardCost] )
)
```

`RELATED` は行コンテキストがある場所でのみ使えます。「今の行の商品IDに対応する Dim_商品 の行から、StandardCost を持ってくる」という関数です。SUMX が行コンテキストを作っているので、この中で RELATED が動きます。

> [!TRAP] つまずきポイント
> `RELATED` はメジャーの中でいきなり書くとエラーになります。行コンテキストがないからです。`SUM( RELATED( Dim_商品[StandardCost] ) )` は書けません。**RELATED はイテレータの第2引数か、計算列の中でしか使えません。**

## AVERAGEX — 「平均」の落とし穴

「1件あたりの平均売上」と「1顧客あたりの平均売上」は別物です。

```figure
{ "type":"tablediff", "title":"何の平均か", "arrowLabel":"平均を取る対象の表を変える",
  "before":{"title":"AVERAGE( Fact_売上[SalesAmount] )","tone":"neutral","head":["対象","結果の意味"],
    "rows":[["売上明細 12,000行","1明細あたりの平均金額"],["結果","3,850円"]]},
  "after":{"title":"AVERAGEX( VALUES( Dim_顧客[CustomerID] ), [売上合計] )","tone":"good","head":["対象","結果の意味"],
    "rows":[["顧客 850人","1顧客あたりの平均金額"],["結果","!54,350円"]]} }
```

```dax
顧客あたり平均売上 =
AVERAGEX(
    VALUES( Dim_顧客[CustomerID] ),
    [売上合計]
)
```

この式は**イテレータの中でメジャーを呼んでいます**。そこで何が起きているのかが、次のレッスンの主題である**コンテキスト遷移**です。今は「顧客IDを1人ずつ走査して、その顧客の売上合計を出し、850個の値を平均している」と理解しておいてください。

> [!WARN] 注意
> `AVERAGEX` は式が BLANK を返した行を**平均の分母から除外します**。売上がゼロだった顧客を分母に含めたいなら、`AVERAGEX( VALUES( Dim_顧客[CustomerID] ), [売上合計] + 0 )` のように 0 を足して BLANK を潰す必要があります。この一手で平均値が大きく変わります。

## RANKX — ランキングの基本形

RANKX は引数が5つあり、最初は面食らいます。分解すれば単純です。

```figure
{ "type":"formula", "lang":"dax", "title":"RANKX の解剖",
  "code":"RANKX( ALL( Dim_商品[ProductName] ), [売上合計], , DESC, Dense )",
  "parts":[
    {"match":"RANKX","label":"第2引数の式を第1引数の各行で評価し、順位を返す","tone":"violet"},
    {"match":"ALL( Dim_商品[ProductName] )","label":"第1引数：順位を競わせる母集団。ALL を外すと「今の行だけ」の中で順位を付けるので全部1位になる","tone":"blue"},
    {"match":"[売上合計]","label":"第2引数：順位付けの基準となる式。母集団の各行で評価される","tone":"amber"},
    {"match":"DESC","label":"第4引数：降順。売上が大きいほど1位。省略時も DESC","tone":"green"},
    {"match":"Dense","label":"第5引数：同順位の次を詰める。1,2,2,3 となる。Skip なら 1,2,2,4","tone":"cyan"} ] }
```

第3引数は省略しています。ここには「順位を付ける対象の値」を明示できますが、省略すると**現在のフィルターコンテキストで第2引数を評価した値**が使われます。ほとんどの場合、省略で正解です。

```figure
{ "type":"tablediff", "title":"ALL の有無で結果が変わる", "arrowLabel":"母集団を ALL で解放する",
  "before":{"title":"RANKX( Dim_商品, [売上合計] )","tone":"bad","head":["商品","売上","順位"],
    "rows":[["ノートPC","4,200万","!1"],["タブレット","3,100万","!1"],["スマートフォン","2,800万","!1"]]},
  "after":{"title":"RANKX( ALL( Dim_商品[ProductName] ), [売上合計] )","tone":"good","head":["商品","売上","順位"],
    "rows":[["ノートPC","4,200万","!1"],["タブレット","3,100万","!2"],["スマートフォン","2,800万","!3"]]} }
```

左が全部1位になるのは、行見出しのフィルターコンテキストが `Dim_商品` に効いているためです。「ノートPC」の行では母集団が「ノートPC 1件」しかないので、その中では必ず1位になります。**ALL でフィルターを外して、母集団を全商品に戻す**必要があります。

> [!TRAP] つまずきポイント
> `ALL( Dim_商品 )` と `ALL( Dim_商品[ProductName] )` は違います。前者はテーブル全体のフィルターを外すので、カテゴリスライサーの選択まで無視されます。**順位を競わせたい列だけを ALL に渡す**のが基本です。カテゴリ内順位を出したいなら、まさに `ALL( Dim_商品[ProductName] )` が正解になります。

`CONCATENATEX` は動的タイトルの定番です。

## 性能の話 — イテレータは遅いのか

「X 系は遅い」と言われますが、正確ではありません。**エンジンが列演算に変換できる形なら速い**のです。

```figure
{ "type":"compare", "title":"同じ結果を返す2つの書き方の性能",
  "caption":"右は行ごとにフィルターコンテキストの再構築が必要になり、ストレージエンジンだけで完結しない",
  "panels":[
    {"title":"速い：単純な列演算","tone":"good",
     "items":["SUMX( Fact_売上, [UnitPrice] * [Quantity] )","ストレージエンジンが列同士の掛け算として一括処理","100万行で数ミリ秒","スキャン回数 1回"],
     "note":"エンジンに任せられる形"},
    {"title":"遅い：行ごとに複雑な判定","tone":"bad",
     "items":["SUMX( Fact_売上, IF( RELATED( Dim_商品[Category] ) = \"家電\", [SalesAmount] * 1.1, [SalesAmount] ) )","行ごとに数式エンジンへ制御が戻る","100万行で数百ミリ秒","CallbackDataID が発生"],
     "note":"書き換えの余地あり"} ] }
```

右の式は、`CALCULATE( SUMX(...) * 1.1, Dim_商品[Category] = "家電" ) + CALCULATE( SUMX(...), Dim_商品[Category] <> "家電" )` のようにフィルターで分割すれば、両方ともストレージエンジンだけで処理できます。この「CallbackDataID」という言葉は M14 のパフォーマンス編で正体を明かします。

> [!DS] データサイエンス視点
> イテレータの計算量は原則 O(n)、n は走査する表の行数です。問題は係数のほうです。1行あたりの処理が「列の値を掛ける」だけなら係数はごく小さく、「別テーブルを探しに行く」なら係数が跳ね上がります。**アルゴリズムの計算量ではなく、1ステップのコストを下げる**のがDAX最適化の主戦場です。

> [!EXAM] PL-300で問われる
> 「単価と数量から売上を計算するメジャーを作成する」という設問では、`SUM(単価) * SUM(数量)` は必ず誤答選択肢として出ます。**列同士の演算を含む集計はイテレータ関数**、と即答できるようにしてください。

## ネストしたイテレータに注意

イテレータの中でイテレータを回すと、行数が掛け算になります。

```dax
-- 危険：顧客850人 × 売上明細12,000行 の走査が発生しうる
悪い例 =
AVERAGEX(
    VALUES( Dim_顧客[CustomerID] ),
    MAXX( Fact_売上, Fact_売上[SalesAmount] )
)
```

内側の `Fact_売上` に外側のフィルターが効いていれば実害は小さいのですが、`ALL` などで解放してしまうと、850 × 12,000 = 1,020万回の評価になります。

> [!TIP] 実務のコツ
> ネストしたイテレータを書いたら、**外側の行数 × 内側の行数**を口に出して見積もってください。1万を超えたら設計を疑います。多くの場合、`SUMMARIZE` で一度集計テーブルを作ってから走査する形（L1303）に書き換えられます。

## 理解度チェック

**問1.** `Fact_売上` に `UnitPrice` と `Quantity` があり、割引率が行ごとに違います。割引後の売上合計を返すメジャーを書いてください。割引率は `Fact_売上[DiscountRate]` にあります。

<details>
<summary>解答</summary>

```dax
割引後売上 =
SUMX(
    Fact_売上,
    Fact_売上[UnitPrice] * Fact_売上[Quantity] * ( 1 - Fact_売上[DiscountRate] )
)
```

3つの列を行ごとに掛け合わせる必要があるため、SUM では表現できません。イテレータが必須です。
</details>

**問2.** `RANKX( ALL( Dim_商品 ), [売上合計] )` と `RANKX( ALL( Dim_商品[ProductName] ), [売上合計] )` は、カテゴリスライサーで「家電」を選んだとき、それぞれどう振る舞いますか。

<details>
<summary>解答</summary>

前者は `Dim_商品` テーブル全体のフィルターを外すため、**カテゴリスライサーの選択も無視され、全商品の中での順位**が返ります。後者は `ProductName` 列のフィルターだけを外すので、**家電の中での順位**が返ります。実務で欲しいのはたいてい後者です。
</details>

**問3.** `AVERAGEX( VALUES( Dim_顧客[CustomerID] ), [売上合計] )` の結果が、想定より高く出ています。原因として最も可能性が高いものは何ですか。

<details>
<summary>解答</summary>

**売上がなかった顧客が BLANK になり、平均の分母から除外されている**ためです。AVERAGEX は式が BLANK を返した行を無視します。全顧客を分母に入れたいなら `[売上合計] + 0` として BLANK を 0 に変えます。ただし「購入した顧客の平均」を出したいなら現状が正しいので、**どちらを求めているのか要件を確認する**のが先です。
</details>
