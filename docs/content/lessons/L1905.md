月曜の朝、全社のレポートが前日のデータのままでした。夜間の更新がすべて失敗しています。ログを見ると「リソースが不足しています」。

原因は更新処理ではありませんでした。金曜の夕方に誰かが数億行のNotebookを流し、その処理が土日を通して容量を占有していたのです。

**容量は共有資源です。**そして共有資源は、見える化していなければ必ず溢れます。このレッスンは、その見える化と制御を扱います。

> [!WARN] 執筆時点の情報
> SKU の種類、上限値、課金体系、スロットリングの挙動は変更されます。ここでは**消費の考え方と監視・是正の方法**を中心に扱います。具体的な数値は必ず公式ドキュメントで確認してください。

## CU という単位

Fabric の計算資源は **CU（Capacity Unit / 容量ユニット）**という単位で測られます。

```figure
{ "type":"stack", "title":"容量とCUの関係", "caption":"SKUが1秒あたりに使えるCUを決め、すべてのワークロードがそこから消費する",
  "layers":[
    {"label":"各操作の消費","sub":"クエリ / 更新 / Notebook実行 / パイプライン / Dataflow — すべてCUを消費する","tone":"pink"},
    {"label":"ワークスペースの割り当て","sub":"どのワークスペースがどの容量を使うか","tone":"violet"},
    {"label":"Fabric 容量（F SKU）","sub":"F2 / F4 / F8 … F64 … F2048。数字が1秒あたりのCU","tone":"amber"},
    {"label":"物理リソース","sub":"CPU / メモリ。CUはその抽象化された配給量","tone":"blue"} ] }
```

重要な性質は、**すべてのワークロードが同じCUプールを共有する**ことです。Power BI のクエリも、Sparkの処理も、パイプラインも、同じ財布から支払われます。だから「データエンジニアの重い処理」が「営業のレポート表示」を遅くします。

> [!NOTE] 要点
> 従来は、Power BI Premium 容量と Azure のデータ処理が別々の課金・別々の資源でした。Fabric では統合されています。**利点は柔軟性、欠点は干渉**です。この構造を理解していないと、原因不明の性能劣化に悩まされます。

## スムージングとバースト

Fabric の消費モデルには、2つの重要な仕組みがあります。

```figure
{ "type":"compare", "title":"バーストとスムージング",
  "panels":[
    {"title":"バースト（借りる）","tone":"blue",
     "items":["一時的にSKUの上限を超えて処理を実行できる","重い処理が待たされずに始まる","借りた分は後で返す必要がある","短時間のピークを吸収する仕組み"],
     "note":"処理を速く終わらせるための仕組み"},
    {"title":"スムージング（ならす）","tone":"good",
     "items":["消費を一定時間にわたって平準化して計上する","バックグラウンド処理は長い期間にならされる","対話操作は短い期間でならされる","瞬間的な超過で即座に止まらない"],
     "note":"消費を時間軸で平らにする仕組み"} ] }
```

この2つの結果として、**「重い処理を実行した瞬間」ではなく「その後しばらく」に影響が出ます**。これが容量トラブルの原因究明を難しくしています。

```figure
{ "type":"chart", "kind":"area", "title":"重い処理の後に消費が続くイメージ", "unit":"CU使用率%",
  "categories":["17:00","18:00","19:00","21:00","23:00","翌1:00","翌3:00","翌5:00"],
  "series":[{"name":"CU使用率","values":[35,180,120,105,98,95,92,88],"tone":"bad"}],
  "highlight":1 }
```

17時台の1回の重い実行が、翌朝まで容量を占有し続けます。**夜間更新が失敗した原因が前日夕方の操作である**という構図が、ここから生まれます。

> [!TRAP] 容量が逼迫して更新が失敗する
> このモジュールで繰り返し触れてきた事故の全体像がこれです。特徴は3つ。(1) **原因と結果に時間差がある**ため、直前の操作を見ても分からない。(2) **失敗するのは重い処理を実行した人ではなく、後から来た更新処理**。(3) **利用者は「更新されていない」としか報告しない**ため、容量が原因だと気づくのが遅れる。対策は監視しかありません。容量メトリックアプリを入れて、日常的に見る習慣を作ってください。

## スロットリングの3段階

容量を使いすぎると、段階的に制限がかかります。

```figure
{ "type":"timeline", "title":"スロットリングの進行", "caption":"利用者への影響が軽い順に発動する。最初の段階で気づければ被害は小さい",
  "items":[
    {"label":"第1段階","title":"対話操作の遅延","text":"レポートのクエリに人工的な遅延が入る。「なんとなく遅い」と感じる段階。","tone":"amber"},
    {"label":"第2段階","title":"対話操作の拒否","text":"レポートが開かない、クエリがエラーになる。利用者が明確に困る段階。","tone":"bad"},
    {"label":"第3段階","title":"バックグラウンド処理の拒否","text":"更新やパイプラインが実行されない。翌朝データが古いまま。","tone":"bad"} ] }
```

| 段階 | 誰が最初に気づくか | 望ましい対応 |
|---|---|---|
| 第1段階 | 熱心な利用者（報告されないことが多い） | 監視で自動検知する |
| 第2段階 | 多数の利用者から問い合わせ | 即座に原因アイテムを特定し停止 |
| 第3段階 | 翌朝の運用担当 | 容量の見直しと処理配置の再設計 |

> [!TIP] 実務のコツ
> **第1段階を検知できる仕組みを作ることが投資対効果として最も高い。**第2段階まで進むと問い合わせ対応に人手を取られ、信頼も損なわれます。容量メトリックアプリで「使用率が一定を超えたら通知」を設定しておけば、利用者が困る前に手を打てます。

Fabric Capacity Metrics アプリは、容量の状態を可視化する公式ツールです。見るべき順序があります。

```figure
{ "type":"steps", "title":"容量トラブルの調査手順",
  "items":[
    {"title":"タイムラインで全体を見る","text":"いつから使用率が上がったか。スロットリングが発生した時刻を特定する。","tone":"blue"},
```

最後の手順が肝心です。**その場で止めるだけでは、来週また同じことが起きます。**「重い処理は専用容量で」「実行時間帯を制限」「そもそも処理を軽くする」のいずれかまで踏み込みます。

### 消費が大きいアイテムの典型

| 消費源 | よくある原因 |

| Notebook | 過大なプールサイズ、小処理の大量並列実行 |
| Dataflow Gen2 | チェーンの深さ、フォールディング切れ |

| Excel からの接続 | ピボットの操作ごとにクエリが飛ぶ。利用者数が多いと侮れない |
| サブスクリプション配信 | 配信時刻にレポートの描画が集中する |

## 容量の分け方

1つの容量にすべてを載せるか、分けるか。設計判断です。

```figure
{ "type":"matrix", "title":"容量を分けるべきか", "xLabel":"ワークロードの性質の違い", "yLabel":"サービス水準の要求差",
  "xLow":"似ている","xHigh":"大きく違う（BIと重いETL）","yLow":"どれも同程度","yHigh":"止まってはいけないものがある",
  "quadrants":[
    {"title":"1つで足りる","text":"小〜中規模。分けると管理が煩雑になるだけ。","tone":"good"},
    {"title":"分ける","text":"重いデータ処理と対話利用を分離する。干渉を構造的に防ぐ。","tone":"violet"},
    {"title":"1つ＋監視","text":"分けるほどではないが、消費の内訳は見えるようにしておく。","tone":"cyan"},
    {"title":"必ず分ける","text":"経営が見るレポートが、誰かの実験で止まってはいけない。","tone":"bad"} ] }
```

分け方の実務的な選択肢を挙げます。

| 分け方 | 効果 | 注意 |
|---|---|---|
| 本番と開発を分ける | 開発の実験が本番を止めない | 開発容量は小さくてよい |
| 対話用とバッチ用を分ける | 更新が閲覧を邪魔しない | ワークスペース設計と連動させる |
| ドメインごとに分ける | 部門間の干渉がなくなり、コスト配賦も明確 | 容量数が増え管理コストが上がる |
| 重いモデル専用 | 大規模Direct Lakeが他を押し出さない | L1904参照 |

> [!TIP] 実務のコツ
> 最初に分けるべきは**開発と本番**です。最も安く、最も効果が確実です。開発容量はF2やF4といった小さいSKUで足り、それでも「開発中の実験が本番を止める」という最も痛い事故を構造的に防げます。ドメインごとの分割は、コスト配賦の要求が出てきてから検討すれば十分です。

## 消費を減らす設計上の打ち手

容量の議論は「増やすか」に流れがちですが、**消費そのものを減らす打ち手**のほうが安く確実です。効果の大きい順に挙げます。

```figure
{ "type":"chart", "kind":"hbar", "title":"消費削減施策の効果（ある組織での実測・相対値）", "unit":"削減CU（相対）",
  "categories":["未使用資産の更新停止","フルリフレッシュを増分更新に","1ページのビジュアル数を24→8に","Notebookのプールサイズ適正化","Dataflowのチェーン解消"],
  "series":[{"name":"削減効果","values":[100,86,54,41,28],"tone":"good"}],
  "highlight":0 }
```

| 施策 | 難易度 | 効果 | 副作用 |
|---|---|---|---|
| 未使用資産の更新停止 | 低 | 大 | なし（廃止プロセスは要る） |
| フルリフレッシュ→増分更新 | 中 | 大 | フォールディングの確認が必要 |
| ページのビジュアル数削減 | 低 | 中 | 利用者との合意が要る |
| プールサイズの適正化 | 中 | 中 | 処理時間が延びる場合がある |
| Dataflowのチェーン解消 | 中 | 中 | 構成の作り直し |

> [!TIP] 実務のコツ
> 一番上の「未使用資産の更新停止」は、**技術的には数クリックで終わる**のに効果が最大です。難しいのは技術ではなく「本当に使われていないと確信すること」。L1805の廃止プロセス（アクセス実績の確認→予告→アクセス停止→30日待つ→削除）をそのまま適用してください。更新の停止だけなら、削除より遥かに軽い判断で実行できます。

## 誰が容量を管理するのか

容量管理は、役割を決めないと誰もやりません。

```figure
{ "type":"cards", "cols":3, "title":"容量管理の役割分担",
  "items":[
    {"icon":"🛡","title":"容量管理者","text":"SKUの決定、ワークスペースの割り当て、スロットリング時の一次対応。1〜2名を指名する。","tone":"amber"},
    {"icon":"📊","title":"ワークスペース所有者","text":"自分のワークスペースの消費に責任を持つ。月次で自分の消費を確認する。","tone":"violet"},
    {"icon":"💰","title":"予算責任者","text":"容量の増減とコストの承認。実測データをもとに判断する。","tone":"green"} ] }
```

> [!TRAP] 容量管理を「誰かがやっているはず」の状態にする
> 最も多い失敗がこれです。容量は共有資源なので、**全員のものは誰のものでもない**という状態に陥りやすい。指名されていない限り、誰も日常的にメトリックを見ません。そして溢れてから初めて全員が慌てます。**名前を書いて役割を割り当ててください。**「BIチームで見ています」ではなく「○○さんが週次で確認し、閾値超過時に△△さんへエスカレーション」まで決めます。

## 消費の見える化を利用者にも広げる

容量意識は、管理者だけが持っていても限界があります。使う側にも見えるようにすると、行動が変わります。

| 見せる相手 | 見せるもの | 期待する行動変化 |
|---|---|---|
| レポート開発者 | 自分のレポートのクエリ消費 | ビジュアル数とDAXの見直し |
| データエンジニア | Notebook / パイプラインの消費 | プールサイズと実行時間帯の調整 |
| ワークスペース所有者 | ワークスペース単位の月次消費 | 不要資産の整理 |
| 部門長 | 部門への配賦額 | 優先度の判断 |

> [!TIP] 実務のコツ
> チャージバック（部門への費用配賦）は、実際に請求しなくても効果があります。**「もし配賦したらいくらか」を示すだけで、消費行動は変わります。**「うちの部門は月80万円分使っているのか」と認識されると、使われていないレポートの整理が自発的に進みます。数字を見せることは、指示するより強い。

## 容量計画の立て方

新規に容量を選ぶとき、あるいは増強を検討するときの手順です。

```figure
{ "type":"steps", "title":"容量サイズの決め方",
  "items":[
    {"title":"配信規模から下限を決める","text":"閲覧者が多数ならF64以上（Proライセンス不要になる境目）。ここで大枠が決まる。","tone":"blue"},
    {"title":"モデルのメモリ要件を積む","text":"Direct Lakeや大きなインポートモデルのメモリ消費を合計する。","tone":"green"},
    {"title":"ピーク時の同時実行を見積もる","text":"朝9時に何人が開くか。1人あたりのクエリ数（L1705）を掛ける。","tone":"amber"},
    {"title":"バッチ処理の消費を加える","text":"更新・Notebook・パイプラインの合計。実行時間帯も記録する。","tone":"violet"},
    {"title":"余裕率を確認する","text":"ピークで80%以下に収まるか。超えるなら設計改善かSKU見直し。","tone":"pink"},

```

> [!DS] データサイエンス視点：キャパシティプランニングの原則
> 容量計画には、他分野と共通する3つの原則があります。(1) **平均ではなくピークで設計する** — 平均使用率30%でも、月初9時に200%になるなら足りていない。(2) **余裕は無駄ではない** — L1705で見たとおり、利用率が高まるほど待ち時間は非線形に伸びる。(3) **測定なしの最適化は推測にすぎない** — 見積もりは必要だが、実測で補正しなければ意味を持たない。特に3つ目が重要で、**稼働後1か月の実測データこそが、次の判断の唯一の根拠**です。導入時の見積もりに固執せず、実測で修正してください。

> [!EXAM] PL-300で問われる
> 容量とライセンスは「4.3 データ更新の管理」「4.1 ワークスペースの管理」で問われます。押さえるべきは、(1) **共有容量（Pro）と専用容量では更新回数の上限が異なる**、(2) 大きなモデル・高頻度更新・XMLAエンドポイントには**容量が必要**、(3) 更新の失敗通知は**データセット所有者と指定した連絡先**に送られる、(4) ゲートウェイはオンプレミスデータへの接続に必要で、**容量とは別の要素**、の4点です。

## 監視の仕組み化

最後に、これを継続させる仕組みです。

| 頻度 | 見るもの | 判断 |
|---|---|---|
| 日次（自動） | スロットリングの発生有無 | 発生していれば当日中に原因特定 |
| 週次 | CU消費の上位10アイテム | 想定外のものがないか |
| 月次 | 使用率の推移とピーク | 増強・削減の要否 |
| 月次 | 未使用資産の更新スケジュール | 停止候補の抽出 |
| 四半期 | ワークスペース別の消費 | 配賦と容量分割の検討 |

> [!TIP] 実務のコツ
> 監視レポートは**BIチーム自身がPower BIで作ってください。**容量メトリックアプリのデータを使って、自組織の関心に合わせたページを作る。これには2つの意味があります。1つは、自分たちの基盤を自分たちの道具で見るという当然の姿勢。もう1つは、**経営に説明するときに数字とグラフで示せる**こと。「容量が足りません」ではなく「ピーク時使用率が3か月連続で90%を超え、待ち時間が2倍になっています」と示せれば、投資判断は速く進みます。

## 設計チェックリスト

- [ ] 監視の頻度と確認項目を日次・週次・月次・四半期で定めた
- [ ] 容量管理者・ワークスペース所有者・予算責任者の役割を名前入りで割り当てた
- [ ] 消費の見える化を利用者側にも広げた
- [ ] 消費削減の施策を効果順に計画した

## 理解度チェック

1. 夜間の更新が失敗しました。直前の時間帯の操作を見ても異常がありません。Fabric の消費モデルの観点から、どこを調べるべきか説明してください。
2. スロットリングの第1段階が「投資対効果として最も検知価値が高い」と言われる理由を述べてください。
3. 容量の使用率が高いという報告を受けました。SKUを上げる前に確認・実施すべきことを3つ挙げてください。
4. チャージバックを実際に請求しなくても効果がある、と言われる理由を説明してください。

> [!NOTE] このレッスンのまとめ
> Fabric ではすべてのワークロードが同じCUプールを共有するため、重いデータ処理がBIの表示を遅くする。バーストとスムージングにより原因と結果に時間差が生じ、夕方の1回の実行が翌朝の更新失敗を引き起こす。スロットリングは対話遅延→対話拒否→バックグラウンド拒否と進み、第1段階での検知が最も価値が高い。SKUを上げる前に、使われていない資産の更新停止・開発と本番の分離・設計改善を尽くす。そして容量計画は平均ではなくピークで立て、稼働後の実測で必ず補正する。
