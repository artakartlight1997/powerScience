DAX の学習には壁が1枚あります。それが**コンテキスト遷移**です。ここを越えた人と越えていない人では、書けるメジャーの範囲がまったく違います。

まず結論を1文で置きます。

> [!NOTE] 定義
> **コンテキスト遷移とは、CALCULATE が実行されるとき、その時点で有効なすべての行コンテキストが、同じ値へのフィルターコンテキストに変換される現象のことです。**

この1文をこれから丁寧に分解します。

```figure
  "caption":"行を選ぶと、その行の行コンテキストがどんなフィルターコンテキストに変わるかが並んで表示される" }
```

## 2つのコンテキストの復習

DAX には評価コンテキストが2種類しかありません。

```figure

  "panels":[

     "note":"1行を指差している状態"},
    {"title":"フィルターコンテキスト","tone":"violet",
     "items":["「どの行が集計対象か」という絞り込み","ビジュアルの行見出し・列見出し・スライサー・CALCULATE で作られる","SUM などの集計関数が見る範囲を決める","行を指差してはいない — 範囲を囲っている"],
```

> [!TRAP] つまずきポイント
> **行コンテキストは、集計関数に何の影響も与えません。** 計算列に `= SUM( Fact_売上[SalesAmount] )` と書くと、全行で同じ値（テーブル全体の合計）になります。「今の行」を処理中でも、SUM から見えるテーブルは全行のままだからです。これを「なぜ絞られないのか」と悩むのが第一の関門です。

## 遷移が起きる瞬間

では、行コンテキストをフィルターコンテキストに変えたいときはどうするか。**CALCULATE を呼びます。** それだけです。

```figure
{ "type":"formula", "lang":"dax", "title":"計算列でのコンテキスト遷移",
  "code":"顧客の累計購入額 = CALCULATE( SUM( Fact_売上[SalesAmount] ) )",
  "parts":[
    {"match":"CALCULATE","label":"フィルター引数がなくても、これを書いた瞬間に遷移が起きる","tone":"violet"},
    {"match":"SUM( Fact_売上[SalesAmount] )","label":"遷移後のフィルターコンテキストで評価される。今の行の全列値で絞られた範囲だけを合計する","tone":"blue"} ] }
```

`Dim_顧客` テーブルの計算列としてこれを書くと、**その顧客の売上合計**が返ります。CALCULATE を外すと、全顧客の合計が全行に並びます。フィルター引数を1つも渡していないのに挙動が変わる——これがコンテキスト遷移です。

## 暗黙の CALCULATE — 最大の罠

ここからが本番です。**メジャーを参照すると、そこには目に見えない CALCULATE が付いています。**

```figure
{ "type":"formula", "lang":"dax", "title":"メジャー参照は CALCULATE に包まれている",
  "code":"SUMX( VALUES( Dim_顧客[CustomerID] ), [売上合計] )",
  "parts":[
    {"match":"SUMX( VALUES( Dim_顧客[CustomerID] ),","label":"顧客IDを1つずつ走査する。ここで行コンテキストが作られる","tone":"blue"},
    {"match":"[売上合計]","label":"実体は CALCULATE( [売上合計] )。参照した瞬間に遷移が起きる","tone":"violet"} ] }
```

つまり、この式は次のように書いたのと**完全に同じ**です。

```dax
SUMX(
    VALUES( Dim_顧客[CustomerID] ),
    CALCULATE( [売上合計] )
)
```

だから顧客ごとの売上が正しく出ます。もしメジャーではなく式を直接展開して書くと、結果が変わります。

```figure
{ "type":"compare", "title":"メジャー参照と式の直書きは別物",
  "caption":"見た目は同じ「売上合計」でも、遷移の有無で結果が180度変わる",
  "panels":[
    {"title":"メジャーを参照する","tone":"good",
     "items":["SUMX( VALUES( Dim_顧客[CustomerID] ), [売上合計] )","暗黙の CALCULATE により遷移が起きる","顧客ごとの売上が計算され、それを合計する","結果：正しい総売上"],
     "note":"意図どおり"},
    {"title":"式を直接書く","tone":"bad",
     "items":["SUMX( VALUES( Dim_顧客[CustomerID] ), SUM( Fact_売上[SalesAmount] ) )","遷移が起きない。SUM は全体を見たまま","顧客数 × 総売上 になる","結果：850倍に膨らむ"],
     "note":"典型的な事故"} ] }
```

> [!TRAP] つまずきポイント
> 「メジャーを分解して直接書いたら数字が変わった」という相談は、9割がこれです。**メジャー名の角括弧参照は、単なるコピー＆ペーストではありません。** CALCULATE が1つ付いてきます。

> [!TIP] 実務のコツ
> 逆に言えば、**遷移させたくないときは明示的に式を書く**という選択肢があります。ただし可読性が落ちるので、意図をコメントで残してください。

## 遷移が「効かない」ように見えるケース

コンテキスト遷移には、初見では説明のつかない挙動が2つあります。

### ケース1：リレーションがない側

`Fact_売上` をイテレートしながら `[売上合計]` を呼ぶと、その行1つ分の売上になります。

```dax
-- Fact_売上 に一意な行IDがない場合、想定外の結果になりうる
明細ごと処理 =
SUMX(
    Fact_売上,
    IF( [売上合計] > 100000, [売上合計] * 0.95, [売上合計] )
)
```

`Fact_売上` に完全に同一内容の行が複数あると、遷移後もそれらが全部残り、`[売上合計]` はその複数行の合計を返します。**ファクトテーブルをイテレートしながらメジャーを呼ぶのは、意味を確認してから行ってください。**

### ケース2：ALL で解放されている列

遷移は「今の行の値でフィルターする」だけです。もし内側でその列が `ALL` されていれば、遷移で作ったフィルターは消えます。

```dax
-- 遷移で顧客が絞られるが、内側の ALL がそれを打ち消す
消える遷移 =
SUMX(
    VALUES( Dim_顧客[CustomerID] ),
    CALCULATE( [売上合計], ALL( Dim_顧客 ) )
)
```

これは「顧客数 × 全体売上」になります。CALCULATE のフィルター引数は、遷移で作られたフィルターより**後に**適用されるためです。

```figure
{ "type":"pipeline", "title":"CALCULATE 内部の適用順序",
  "caption":"遷移は最初に起き、その後でフィルター引数が上書きする。だから ALL が勝つ",
  "nodes":[
    {"id":"rc","label":"行コンテキスト\\nCustomerID=C003","tone":"blue"},
    {"id":"ct","label":"コンテキスト遷移\\n全列でフィルター化","tone":"violet"},
    {"id":"fa","label":"フィルター引数の適用\\nALL( Dim_顧客 )","tone":"amber"},
    {"id":"ev","label":"式の評価\\nSUM( SalesAmount )","tone":"green"}],
  "edges":[
    {"from":"rc","to":"ct","label":"CALCULATE 開始"},
    {"from":"ct","to":"fa","label":"上書きされる"},
    {"from":"fa","to":"ev","label":"最終コンテキスト"}] }
```

> [!NOTE] 要点
> CALCULATE の内部順序は、**(1) コンテキスト遷移 → (2) フィルター引数の適用 → (3) 式の評価** です。フィルター引数のほうが後なので、同じ列を触れば必ずフィルター引数が勝ちます。

## EARLIER は何だったのか

古いDAXの教材には `EARLIER` が出てきます。**入れ子になった行コンテキストの、1つ外側の行を参照する関数**です。

```dax
-- 旧来の書き方：自分より売上が大きい商品の数を数える
順位_旧 =
COUNTROWS(
    FILTER(
        Dim_商品,
        [売上合計] > EARLIER( [売上合計] )
    )
) + 1
```

現在は**変数を使うのが正解**です。読みやすく、間違いにくくなります。

```figure
{ "type":"compare", "title":"EARLIER と VAR",
  "caption":"VAR は宣言時点のコンテキストで一度だけ評価され、その値が固定される。これが EARLIER の代わりになる",
  "panels":[
    {"title":"EARLIER を使う（非推奨）","tone":"bad",
     "items":["EARLIER( [売上合計] )","何段目の行コンテキストか読み手に分からない","3段以上の入れ子で EARLIEST が必要になる","レビューで必ず質問される"],
     "note":"レガシー"},
    {"title":"VAR を使う（推奨）","tone":"good",
     "items":["VAR CurrentSales = [売上合計]","名前で意図が伝わる","評価タイミングが宣言位置で明確","入れ子が深くても混乱しない"],
     "note":"現代のDAX"} ] }
```

```dax
順位_現代 =
VAR CurrentSales = [売上合計]
RETURN
    COUNTROWS(
        FILTER(
            ALL( Dim_商品[ProductName] ),
            [売上合計] > CurrentSales
        )
    ) + 1
```

> [!NOTE] 要点
> **VAR は宣言された場所のコンテキストで、ただ一度評価されます。** その後どんなに CALCULATE や FILTER で内側に入っても、変数の値は変わりません。この性質が EARLIER の完全な代替になります。

## よくある実務パターン

コンテキスト遷移を使わないと書けない指標を3つ挙げます。

```figure
{ "type":"cards", "cols":3, "title":"遷移が必須になる指標",
  "items":[
    {"icon":"👤","title":"顧客あたり平均","text":"AVERAGEX( VALUES( Dim_顧客[CustomerID] ), [売上合計] )。顧客単位に集計してから平均する","tone":"blue"},
    {"icon":"🏅","title":"ランキング","text":"RANKX の第2引数でメジャーを評価する。母集団の各行で遷移が起きている","tone":"violet"},
    {"icon":"🎯","title":"条件を満たす顧客数","text":"COUNTROWS( FILTER( VALUES( Dim_顧客[CustomerID] ), [売上合計] > 100000 ) )","tone":"green"} ] }
```

3つ目を分解します。

```dax
優良顧客数 =
COUNTROWS(
    FILTER(
        VALUES( Dim_顧客[CustomerID] ),
        [売上合計] > 100000
    )
)
```

`FILTER` はイテレータです。顧客IDを1人ずつ走査し、行コンテキストを作ります。`[売上合計]` を参照した瞬間に暗黙の CALCULATE が働き、その顧客だけの売上が計算されます。10万円を超えた顧客だけが残り、それを数えます。**遷移がなければ、全顧客が同じ全体売上を返し、全員が残るか誰も残らないかの二択になります。**

> [!DS] データサイエンス視点
> コンテキスト遷移は、プログラミング言語の**変数束縛（binding）**と同じ話です。ループ変数がスコープ内でどう見えるかを決める仕組みで、DAX は「行を指す参照」を「値による絞り込み」へ変換します。SQL の相関サブクエリで外側のクエリの行を内側から参照する構造と対応づけると理解が速くなります。`WHERE c.CustomerID = outer.CustomerID` を自動でやってくれるのがコンテキスト遷移です。

> [!EXAM] PL-300で問われる
> 直接「コンテキスト遷移」という語で問われることは多くありませんが、「イテレータの中でメジャーを使ったときの結果」を選ばせる設問は出ます。**メジャー参照 = CALCULATE 付き**を機械的に適用すれば解けます。

## 理解度チェック

**問1.** `Dim_商品` の計算列に `= SUM( Fact_売上[SalesAmount] )` と書きました。全行に同じ値が並びます。なぜですか。また、商品ごとの売上にするにはどう直しますか。

<details>
<summary>解答</summary>

計算列には行コンテキストがありますが、**行コンテキストは集計関数のフィルターにならない**ためです。SUM から見える `Fact_売上` は全行のままです。`= CALCULATE( SUM( Fact_売上[SalesAmount] ) )` と CALCULATE で包むと、コンテキスト遷移が起きて商品ごとの売上になります。
</details>

**問2.** 次の2つの式は、同じ結果を返しますか。返さない場合、どちらがどう違いますか。

```dax
A = SUMX( VALUES( Dim_店舗[StoreID] ), [売上合計] )
B = SUMX( VALUES( Dim_店舗[StoreID] ), SUM( Fact_売上[SalesAmount] ) )
```

<details>
<summary>解答</summary>

**返しません。** A はメジャー参照なので暗黙の CALCULATE により遷移が起き、店舗ごとの売上を合計するため、結果は総売上と一致します。B は遷移が起きないため、各店舗の行で全体の総売上が返り、それを店舗数ぶん足します。**B は「店舗数 × 総売上」**になります。
</details>

**問3.** `CALCULATE( [売上合計], ALL( Dim_顧客 ) )` をイテレータの中で使うと、遷移で作られた顧客フィルターが消えます。この挙動が起きる理由を、CALCULATE の内部順序から説明してください。

<details>
<summary>解答</summary>

CALCULATE は **(1) コンテキスト遷移 → (2) フィルター引数の適用 → (3) 式の評価** の順で処理します。遷移は最初に起きて `Dim_顧客` にフィルターを置きますが、その後にフィルター引数の `ALL( Dim_顧客 )` が同じテーブルのフィルターを解除します。**後から適用されるフィルター引数が勝つ**ため、遷移の効果が打ち消されます。
</details>
