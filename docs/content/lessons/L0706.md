DAXが書けるようになると、次に来る問題は「**書いたものが増えすぎて管理できない**」です。

メジャーが50本を超えたモデルで、次のことが起きます。

- どのテーブルにどのメジャーがあるか分からない
- 「売上」「売上合計」「売上金額」「Sales」が全部存在する
- 半年前に自分が書いた式の意図が読み取れない
- 数値の桁区切りやパーセント表示がビジュアルごとにバラバラ

これは能力の問題ではなく、**規約を決めていない**という設計の問題です。
このレッスンで、最初に決めておくべきことを全部片づけます。

## 1. メジャー専用テーブルを作る

メジャーは、どのテーブルに置いても計算結果が変わりません。だからこそ、**置き場所を自分で決められます**。
実務の定石は「メジャーだけを入れる空のテーブル」を作ることです。

```figure
{ "type":"steps", "title":"メジャーテーブルの作り方", "caption":"5分で終わる。最初にやっておくと、後で並べ替える手間がゼロになる",
  "items":[
    {"title":"空のテーブルを作る","text":"ホーム → データの入力 → テーブル名を「_指標」などにして読み込む。列は1つだけ、値は空でよい。","tone":"blue"},
    {"title":"メジャーを移動する","text":"既存メジャーを選び、リボンの「ホームテーブル」を _指標 に変更する。ドラッグでも移動できる。","tone":"green"},
    {"title":"ダミー列を非表示にする","text":"作成時の Column1 を右クリックして「レポートビューで非表示にする」。","tone":"amber"},
    {"title":"表示フォルダーで分類する","text":"メジャーのプロパティで「表示フォルダー」に 売上 / 利益 / 比率 などを設定する。","tone":"violet"},
    {"title":"名前の先頭を _ にする","text":"アンダースコアで始まるテーブルはデータペインの先頭に並ぶ。毎回スクロールする手間が消える。","tone":"pink"} ] }
```

```figure
{ "type":"tree", "title":"表示フォルダーによる整理の例", "caption":"利用者はこの階層を見て指標を探す。分類がそのまま説明になる",
  "root":{"label":"_指標"},
  "children":[
    {"label":"01_売上","sub":"金額系","tone":"blue",
     "children":[{"label":"売上合計"},{"label":"数量合計"},{"label":"平均単価"}]},
    {"label":"02_利益","sub":"原価と利益","tone":"green",
     "children":[{"label":"原価合計"},{"label":"利益額合計"},{"label":"利益率"}]},
    {"label":"03_時間比較","sub":"前年比・累計","tone":"violet",
     "children":[{"label":"前年売上"},{"label":"前年比"},{"label":"売上YTD"}]},
    {"label":"99_内部","sub":"他メジャーから呼ぶ用","tone":"gray",
     "children":[{"label":"_基準日"}]} ] }
```

> [!TIP] 番号を前置きすると並び順を制御できる
> 表示フォルダー名は辞書順に並びます。`01_` `02_` のように番号を付けると、
> 「売上 → 利益 → 比率」という**業務上の理解の順**で並べられます。

> `Fact_売上[SalesAmount]` という列があるモデルで、`SalesAmount` というメジャーを作ってはいけません。
> どちらを参照しているのか式から判別できなくなり、**参照先が入れ替わるバグ**を生みます。
> 列は英語の物理名、メジャーは日本語の業務名、と使い分けるのが安全です。

## 3. 参照の書き方を統一する

L0701 で触れた規則を、あらためて規約として固定します。

```figure
{ "type":"formula", "lang":"dax", "title":"参照の書き分け規約",
  "caption":"この2つの形を見分けられれば、他人の式も読めるようになる",
  "code":"利益率 = DIVIDE( [売上合計] - SUM( Fact_売上[原価額] ), [売上合計] )",
  "parts":[
    {"match":"[売上合計] - ","label":"メジャー参照：角かっこのみ。テーブル名を書かない","tone":"violet"},
    {"match":"SUM( Fact_売上[原価額] )","label":"列参照：必ずテーブル名［列名］","tone":"blue"},
    {"match":"DIVIDE","label":"関数は大文字。変数・メジャーと視覚的に区別する","tone":"amber"} ] }
```

| 対象 | 書き方 | 理由 |
|---|---|---|
| 列 | `Fact_売上[SalesAmount]` | テーブル名を省略すると、同名列があるとき壊れる |
| メジャー | `[売上合計]` | テーブル名を付けると列に見えてしまう |
| 関数 | すべて大文字 | 業界標準。式の骨格が一目で分かる |
| 変数 | 意味のある名前 | `VAR 当年売上` のように、型と役割が伝わるもの |

## 4. 書式を整える

長いDAXは、改行とインデントで読みやすさが変わります。基本ルールは3つです。

```figure
{ "type":"compare", "title":"1行で書いた式と、整形した式", "caption":"内容は同一。読解にかかる時間だけが違う",
  "panels":[
    {"title":"整形前","tone":"bad","items":[
      "1行に全部詰め込む",
      "括弧の対応が数えられない",
      "どこがフィルター引数か分からない",
      "差分レビューで全体が1行の変更になる"],
     "note":"Gitでの比較も困難"},
    {"title":"整形後","tone":"good","items":[
      "関数ごとに改行する",
      "引数を1つずつ行に分ける",
      "カンマは行頭または行末で統一",
      "変更箇所だけが差分に出る"],
     "note":"レビューが成立する"} ] }
```

整形の実例です。

```dax
-- ✗ 整形前
売上構成比 = DIVIDE([売上合計],CALCULATE([売上合計],REMOVEFILTERS(Dim_商品[Category])))

-- ✓ 整形後
売上構成比 =
DIVIDE(
    [売上合計],
    CALCULATE(
        [売上合計],
        REMOVEFILTERS( Dim_商品[Category] )
    )
)
```

```figure
    {"title":"関数の開きかっこの後で改行する","text":"引数は1行に1つ。かっこの深さがインデントの深さと一致する。","tone":"green"},
```

## 5. 表示形式と説明を設定する

メジャーは、値そのものだけでなく **見え方** もモデル側で決められます。
ビジュアルごとに設定するのは間違いです。1か所で決めれば全ビジュアルに反映されます。

```figure
{ "type":"tablediff", "arrowLabel":"表示形式を設定", "title":"同じ値でも、伝わり方が変わる",
  "caption":"モデル側で設定すれば、どのビジュアルに置いても同じ見え方になる",
  "before":{"title":"既定のまま","tone":"bad",
    "head":["指標","表示"],
    "rows":[["売上合計","100000000"],["利益率","0.271"],["前年比","0.136"],["顧客数","800"]]},
  "after":{"title":"表示形式を設定後","tone":"good",
    "head":["指標","表示","設定内容"],
    "rows":[["売上合計","!¥100,000,000","通貨・桁区切り・小数0桁"],["利益率","!27.1%","パーセンテージ・小数1桁"],["前年比","!+13.6%","パーセンテージ・正数に+"],["顧客数","!800 人","10進数・カスタム書式 #,0\" 人\""]]} }
```

設定手順は、メジャーを選択 → 「メジャーツール」タブ → 書式・小数点以下の桁数・通貨記号を指定するだけです。

さらに **説明（Description）** を書いておくと、データペインでホバーしたときに表示されます。

```dax
-- 説明欄に書く内容の例
-- 「税抜の売上金額。返品行（Quantity < 0）を含む。会計側の売上とは返品計上時期が異なる。」
```

> [!DS] メトリクス定義の一元管理
> 同じ「売上」でも、税抜／税込、返品込み／除く、計上基準の違いで数字は変わります。
> 組織で数字が食い違う原因の大半は、計算ミスではなく **定義の不一致** です。
> メジャーの説明欄は、その定義を置く最も近い場所です。
> ここに定義を書いておくと、モデルが「計算エンジン」から「**合意された指標の辞書**」に変わります。
> これは再現性（同じ問いに同じ答えが返る性質）を担保する、分析基盤の基本要件です。

## 計算グループという先の話

指標が増えると、「売上合計・利益額合計・数量合計」それぞれに
「前年」「前年比」「YTD」を作ることになり、メジャー数が掛け算で増えます。

```figure
{ "type":"chart", "kind":"bar", "title":"指標×時間軸でメジャーが爆発する",
  "caption":"基本指標が増えるほど、時間軸のバリエーションで本数が跳ね上がる",
  "categories":["基本指標3本","×前年","×前年比","×YTD"],
  "series":[{"name":"メジャー本数","values":[3,6,9,12],"tone":"amber"}],
  "highlight":3, "unit":"本" }
```

この爆発を止める仕組みが **計算グループ** です。
「前年」「YTD」といった時間軸の変換を1度だけ定義し、あらゆる指標に適用できます。
ただし作成には Tabular Editor などの外部ツールが必要で、扱いも上級者向けです。

> [!NOTE] いまは「規約」で十分
> 計算グループは上級ティアで扱います。中級の段階では、
> **命名規則と表示フォルダーで秩序を保つ**ことが現実的で、効果も十分です。
> 「メジャーが増えすぎたら計算グループという解決策がある」とだけ覚えておいてください。

```figure
    {"title":"優先度低","text":"表示フォルダーの細分化","tone":"gray"} ] }
```

| 項目 | 確認内容 |
|---|---|
| 置き場所 | メジャーが `_指標` などの専用テーブルに集約されているか |
| 命名 | 集計方法が名前から分かるか（「売上」ではなく「売上合計」） |
| 参照 | 列は `テーブル[列]`、メジャーは `[名前]` で統一されているか |
| 書式 | 3行を超える式が整形されているか |
| 表示形式 | 通貨・パーセント・桁区切りが設定されているか |
| 説明 | 主要メジャーに定義が書かれているか |
| 非表示 | ID列・材料列が隠されているか |
| 重複 | 同じ計算をする別名メジャーが存在しないか |

> [!EXAM] PL-300で問われる
> 「レポート利用者が指標を見つけやすくするには」→ **表示フォルダーと説明の設定**。
> 「誤った集計を防ぐには」→ **数値列を非表示にし、メジャーを提供する**。
> どちらもモデルの使いやすさに関する定番出題です。

## 理解度チェック

**問1.** メジャーを `_指標` という専用テーブルに集める利点を2つ挙げよ。

<details><summary>答え</summary>
(1) すべての指標が1か所に集まり、データペインで探しやすくなる。(2) 表示フォルダーで業務的に分類でき、利用者が意味の単位で指標を選べる。加えて、先頭のアンダースコアでペインの最上部に固定できる。
</details>

**問2.** `Fact_売上[SalesAmount]` 列を非表示にし、`[売上合計]` メジャーだけを公開する設計の狙いは何か。

<details><summary>答え</summary>
利用者が列を直接ビジュアルに置けなくなるため、既定の集計（合計・平均）が意図せず適用される事故を防げる。指標の定義を一元化し、どのビジュアルでも同じ計算が使われることを保証できる。
</details>

**問3.** メジャーの説明欄に書くべき内容として、最も価値が高いのは何か。

<details><summary>答え</summary>
計算方法そのものではなく、**業務上の定義と前提**。税抜か税込か、返品を含むか、他システムの数字と何が違うか、といった「式を見ても分からない情報」を書く。
</details>

## よくあるエラーと原因

| 症状 | 原因 | 対処 |
|---|---|---|
| メジャーが見つからない | 作成時に選んでいたテーブルに置かれた | ホームテーブルを `_指標` に変更する |
| 「メジャー 'X' はテーブルの一部ではありません」 | メジャー参照にテーブル名を付けた | `[X]` の形に直す |
| 数値の見た目がビジュアルごとに違う | 表示形式をビジュアル側で設定した | モデル側のメジャーで設定し直す |
| 利用者が誤って列を合計している | 数値列が公開されたまま | 列を非表示にし、メジャーを提供する |
| 同じ指標が複数ある | 命名規則がなく重複作成された | 定義を突き合わせて統合し、旧名は削除する |
| 式を開くと1行で読めない | 整形していない | DAX Formatter などで整形する |

> [!NOTE] このレッスンのまとめ
> DAXは書けるだけでは足りません。**置き場所・名前・書式・メタデータ**の4点を決めることで、
> 式は「動くコード」から「引き継げる資産」になります。
> 特に効果が大きいのは、メジャーテーブルへの集約・表示形式の設定・数値列の非表示の3つです。
> ここまでで M07 は完了です。次のモジュールで、DAXの心臓部である**コンテキスト**に入ります。
