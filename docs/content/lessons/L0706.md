## レビューのチェックリスト

| 項目 | 確認内容 |
|---|---|
| 置き場所 | メジャーが `_指標` などの専用テーブルに集約されているか |
| 命名 | 集計方法が名前から分かるか（「売上」ではなく「売上合計」） |
| 参照 | 列は `テーブル[列]`、メジャーは `[名前]` で統一されているか |
| 書式 | 3行を超える式が整形されているか |
| 表示形式 | 通貨・パーセント・桁区切りが設定されているか |
| 説明 | 主要メジャーに業務上の定義が書かれているか |
| 非表示 | ID列・材料列が隠されているか |
| 重複 | 同じ計算をする別名メジャーが存在しないか |

> [!WARN] 列名とメジャー名を同じにしない
> `SalesAmount` 列があるモデルで同名メジャーを作ると、参照先が入れ替わるバグを生みます。
> 列は英語の物理名、メジャーは日本語の業務名で分けるのが安全です。

> [!DS] メトリクス定義の一元管理
> 数字が食い違う原因の大半は計算ミスではなく **定義の不一致**（税抜／税込、返品込み）。
> 説明欄に定義を書くと、モデルが「合意された指標の辞書」に変わります。

> [!EXAM] PL-300で問われる
> 「指標を見つけやすくする」→ **表示フォルダーと説明**。
> 「誤った集計を防ぐ」→ **数値列を非表示にしメジャーを提供する**。

## 理解度チェック

**問1.** メジャーを `_指標` に集める利点を2つ挙げよ。

<details><summary>答え</summary>
指標が1か所に集まり探しやすい。表示フォルダーで業務的に分類でき先頭に固定できる。
</details>

**問2.** `SalesAmount` 列を隠し `[売上合計]` だけ公開する狙いは。

<details><summary>答え</summary>
既定の集計が意図せず適用される事故を防ぎ、指標の定義を一元化できるため。
</details>

**問3.** メジャーの説明欄に書く価値が最も高い内容は。

<details><summary>答え</summary>
計算方法ではなく業務上の定義と前提。税抜か、返品を含むかなど式に現れない情報。
</details>

## よくあるエラーと原因

| 症状 | 原因 | 対処 |
|---|---|---|
| メジャーが見つからない | 作成時のテーブルに置かれた | ホームテーブルを `_指標` に変更 |
| メジャー 'X' はテーブルの一部では… | 参照にテーブル名を付けた | `[X]` の形に直す |
| 見た目がビジュアルごとに違う | 表示形式をビジュアル側で設定 | モデル側のメジャーで設定する |
| 利用者が誤って列を合計している | 数値列が公開されたまま | 列を非表示にしメジャーを提供 |
| 同じ指標が複数ある | 命名規則がなく重複作成された | 定義を突き合わせ統合し旧名を削除 |
| 式を開くと1行で読めない | 整形していない | DAX Formatter などで整形する |
