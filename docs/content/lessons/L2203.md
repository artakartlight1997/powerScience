経営会議で提示した数字が、たった一度間違っていた。それだけで、そのレポートは二度と信用されません。以後1年間、会議のたびに「この数字、本当に合ってる？」と聞かれ続けます。

**信頼は非対称です。** 積み上げるのに1年、失うのに1日。だからデータ品質は、気合いや注意力ではなく、**定義・測定・契約**という仕組みで守ります。

## データ品質の6次元

品質は漠然と語らず、6つの次元に分解して測ります。**測れない品質は改善できません。**

```figure
{ "type":"cards", "cols":3, "title":"データ品質の6次元", "caption":"それぞれに測定方法があり、SQLやDAXで数値化できる",
  "items":[
    {"icon":"🧩","title":"完全性 Completeness","text":"必要なデータが欠けていないか。欠損率、想定行数との差","tone":"blue"},
    {"icon":"🎯","title":"正確性 Accuracy","text":"値が現実と一致しているか。基幹システムや実地との突合で測る","tone":"green"},
    {"icon":"🔗","title":"一貫性 Consistency","text":"システム間・期間内で矛盾がないか。合計の突合、参照整合性","tone":"amber"},
    {"icon":"⏰","title":"適時性 Timeliness","text":"必要な時刻までに揃っているか。更新完了時刻、データの鮮度","tone":"violet"},
    {"icon":"🆔","title":"一意性 Uniqueness","text":"重複がないか。キーの重複件数、名寄せ後の重複率","tone":"pink"},
    {"icon":"✅","title":"妥当性 Validity","text":"取りうる値の範囲・形式に収まっているか。型、コード値、範囲外検出","tone":"cyan"} ] }
```

| 次元 | 測定式の例 | 目標値の例 |
|---|---|---|
| 完全性 | 必須項目の非空白率 = 非空白行数 ÷ 全行数 | 顧客の業種コード ≥ 95% |
| 正確性 | 基幹システム月次合計との差異率 | 絶対差異 ≤ 0.1% |
| 一貫性 | 参照整合性違反件数（Dimに存在しないキー） | 0件 |
| 適時性 | 更新完了時刻 － 期限時刻 | 6:00 までに完了、遅延0回/月 |
| 一意性 | 主キーの重複件数 | 0件 |
| 妥当性 | 範囲外・不正コード件数 ÷ 全行数 | ≤ 0.05% |

> [!TRAP] つまずきポイント
> 品質問題で最も多いのは、**エラーで止まる問題ではなく、静かに間違う問題**です。更新は成功し、レポートは表示され、数字だけがおかしい。たとえば上流システムでコード体系が変わり、リレーションが繋がらなくなった行が「(空白)」に集約される。合計は減るのに、エラーは1つも出ません。**「エラーが出ていない」は品質の証明になりません。**

## 品質ルールをデータとして実装する

目視確認は続きません。ルールを実装し、**品質そのものを指標として可視化**します。

```dax
-- 完全性：必須項目の充足率
業種コード充足率 =
DIVIDE(
    CALCULATE( COUNTROWS( Dim_顧客 ), NOT ISBLANK( Dim_顧客[業種コード] ) ),
    COUNTROWS( Dim_顧客 )
)

-- 一貫性：ディメンションに存在しないキーを持つファクト行（参照整合性違反）
孤立行数 =
CALCULATE(
    COUNTROWS( Fact_売上 ),
    ISBLANK( RELATED( Dim_顧客[顧客SK] ) )
)

-- 妥当性：値が想定範囲外の行
範囲外金額件数 =
CALCULATE(
    COUNTROWS( Fact_売上 ),
    OR( Fact_売上[売上金額] < 0, Fact_売上[売上金額] > 100000000 )
)

-- 適時性：最新データの鮮度（時間単位）
データ鮮度_時間 =
DATEDIFF( MAX( Fact_売上[更新日時] ), NOW(), HOUR )

-- 総合スコア（各次元を0〜1で評価し加重平均）
品質スコア =
VAR 完全性 = [業種コード充足率]
VAR 一貫性 = IF( [孤立行数] = 0, 1, 0 )
VAR 妥当性 = 1 - DIVIDE( [範囲外金額件数], COUNTROWS( Fact_売上 ) )
VAR 適時性 = IF( [データ鮮度_時間] <= 24, 1, 0 )
RETURN
DIVIDE( 完全性 + 一貫性 + 妥当性 + 適時性, 4 )
```

Power Query 側では、**変換の途中で行数を記録**しておくと、どのステップで行が消えたかを追跡できます。

```m
// 各ステップの行数を記録するパターン
let
    ソース = Sql.Database("server", "db"),
    元データ = ソース{[Schema="dbo",Item="Sales"]}[Data],
    行数_元 = Table.RowCount(元データ),

    型変換 = Table.TransformColumnTypes(元データ, {{"売上日", type date}, {"金額", type number}}),
    エラー行 = Table.SelectRowsWithErrors(型変換),
    行数_エラー = Table.RowCount(エラー行),

    結合 = Table.NestedJoin(型変換, {"顧客ID"}, 顧客マスタ, {"顧客ID"}, "顧客", JoinKind.LeftOuter),
    未一致 = Table.SelectRows(結合, each Table.IsEmpty([顧客])),
    行数_未一致 = Table.RowCount(未一致),

    // 監査テーブルとして出力する
    監査 = Table.FromRecords({[
        検査日時 = DateTime.LocalNow(),
        元行数 = 行数_元,
        エラー行数 = 行数_エラー,
        顧客未一致行数 = 行数_未一致
    ]})
in
    監査
```

> [!TIP] 実務のコツ
> **「顧客マスタに存在しない顧客IDが何件あったか」を毎回記録**してください。この数値が突然増えたときは、上流でマスタ登録の運用が変わったサインです。数字がおかしくなってから調べるのではなく、**行数の変化を先行指標として監視**するのが、データオブザーバビリティの基本です。

Power BI Service では、系譜ビューで「このデータフロー → このセマンティックモデル → このレポート」という依存関係を確認できます。上流を変更する前に必ず系譜を見て、**影響を受けるレポートの所有者に事前連絡**してください。

> [!TIP] 実務のコツ
> **「このモデルを消したら、何が壊れますか」に即答できない状態は危険です。** 系譜ビューを定期的に確認し、依存の多いモデル（=組織の基幹資産）を特定してください。そのモデルには、他より厳しい品質基準・変更手続き・監視を適用します。すべてを同じ水準で守る必要はなく、**重要度に応じて守り方を変える**のが現実的な運用です。

## 品質を文化にする

```figure
{ "type":"compare", "title":"品質が守られない組織／守られる組織", "caption":"仕組みだけでなく、扱い方が違う",
  "panels":[
    {"title":"守られない組織","tone":"bad",
     "items":["数字の誤りを見つけた人が責められる","「誰のミスか」が最初の議題になる","品質チェックは余裕があるときにやる作業","定義の質問をすると「そんなことも知らないのか」と言われる"],
     "note":"問題が隠される"},
    {"title":"守られる組織","tone":"good",
     "items":["誤りの報告に感謝が返る","「どの仕組みが検知できなかったか」を議論する","品質チェックが作業手順に組み込まれている","定義の質問が歓迎され、その場で用語集に追記される"],
     "note":"問題が早期に表面化する"} ] }
```

> [!NOTE] 要点
> 品質問題を報告した人を責める組織では、次から誰も報告しなくなります。問題は消えるのではなく、**見えなくなるだけ**です。「発見してくれてありがとう。この検知漏れをどう塞ぐか考えよう」という反応を、最初の1回で示せるかどうかが分かれ目です。

## まとめ：品質を守る3層

```figure
{ "type":"stack", "title":"データ品質を守る3層構造", "caption":"下の層ほど根本的で、上の層ほど即効性がある",
  "layers":[
    {"label":"③ 検知と通知","sub":"品質監視レポート、アラート、鮮度バナー。利用者より先に気づく","tone":"pink"},
    {"label":"② 測定","sub":"6次元の数値化、監査テーブル、プロファイリングの記録","tone":"amber"},
    {"label":"① 契約と定義","sub":"データ契約、指標定義書、変更管理の合意。ここが根本","tone":"blue"} ] }
```

多くの組織は③だけをやろうとします。しかし①がなければ、③は無限に鳴り続けるアラートになります。**契約 → 測定 → 検知の順に整備する**のが正しい順序です。

## 理解度チェック

1. 「更新は成功しているのに、売上が先月より2億円少ない」という報告を受けました。原因の候補を3つ挙げ、確認する順番を答えてください。
2. データ品質の6次元のうち、「更新は成功するが数字が静かに間違う」タイプの事故に最も関係する次元を2つ挙げ、それぞれの測定方法を述べてください。
3. データ提供元にデータ契約を提案したところ「今まで通りでいいのでは」と言われました。契約が双方にとって有益である理由を説明してください。
