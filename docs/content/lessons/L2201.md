「営業向けのダッシュボードを作ってほしい」

この一言を受けて、そのまま作り始めた人のレポートは、ほぼ確実に使われません。理由は単純です。依頼者が口にした**要求**と、組織が本当に必要としている**要件**は、まったく別物だからです。

要件定義は、作る前の準備作業ではありません。**プロジェクトの成否がほぼ決まる工程**です。

```figure
{ "type":"compare", "title":"要求と要件は違う", "caption":"要求を聞いて、要件に翻訳するのが設計者の仕事",
  "panels":[
    {"title":"要求（依頼者が言うこと）","tone":"amber",
     "items":["「ダッシュボードが欲しい」","「全部の数字を見たい」","「Excelと同じ形式で」","「リアルタイムで更新して」"],
     "note":"手段が語られている"},
    {"title":"要件（本当に必要なこと）","tone":"good",
     "items":["「週次会議で支援先を決める判断材料が欲しい」","「目標未達の営業所を素早く特定したい」","「今の集計作業2時間をゼロにしたい」","「朝会の8:30時点で前日実績が見たい」"],
     "note":"目的と判断が語られている"} ] }
```

> [!NOTE] 要点
> 依頼者は**解決策の形**で要望を語ります。「ダッシュボードが欲しい」は解決策であって、問題ではありません。問題は必ずその手前にあります。**「それができると、何が良くなりますか」**——この質問1つで、対話は要求から要件に移ります。


### 深掘りの質問リスト

そのまま印刷して持っていけるリストです。

```text
【BI要件ヒアリング質問リスト】

■ 目的・背景
  1. このレポートで解決したい問題は何ですか
  2. それができると、何が良くなりますか（金額・時間・品質で）
  3. なぜ今、必要なのですか（きっかけとなった出来事は）
  4. これがない場合、何が起き続けますか

■ 現状（最重要。可能なら画面を見せてもらう）
  5. 今はどうやってその情報を得ていますか
  6. その作業に、誰が、どれくらい時間を使っていますか
  7. 今のやり方で、一番困っているのはどこですか
  8. 使っている既存の資料を見せてもらえますか
  9. その資料で、実際に見ている箇所はどこですか（見ていない箇所は何ですか）

■ 意思決定
 10. その数字を見て、どんな判断をしますか
 11. その判断は、誰が、いつ行いますか
 12. 判断の結果、何が変わりますか（誰が何をしますか）
 13. 判断を間違えると、どんな損失が出ますか

■ 利用シーン
 14. いつ見ますか（頻度・曜日・時刻）
 15. どこで見ますか（PC / 会議室の投影 / スマホ）
 16. 何分見ますか
 17. 誰が見ますか（人数、役職、データの慣れ）
 18. 見た内容を誰かに共有しますか（その方法は）

■ データ
 19. 必要なデータはどこにありますか
 20. そのデータの正しさは、誰が保証していますか
 21. いつ時点のデータが必要ですか（前日でよいか、リアルタイムが必要か）
 22. 見てはいけない人がいますか（部門・役職による制限）
 23. 数字の定義で、部署によって解釈が違うものはありますか

■ 成功基準・制約
 24. どうなったら「成功」と言えますか（数字で）
 25. いつまでに必要ですか。その日付の理由は何ですか
 26. 今回のスコープに入れないものは何ですか
 27. 過去に似た取り組みはありましたか。うまくいかなかった理由は
```

> [!TIP] 実務のコツ
> 質問9「**見ていない箇所は何ですか**」は、既存帳票の移植依頼で決定的に効きます。20列ある帳票のうち、実際に見ているのは5列——これが普通です。この質問なしに移植すると、誰も見ない15列の維持コストを未来永劫背負うことになります。

## ステークホルダーを整理する

関係者は依頼者だけではありません。整理せずに進めると、完成直前に別の部署から反対が出ます。

```figure
{ "type":"matrix", "title":"ステークホルダー分析", "caption":"影響力の高い人を早期に巻き込むかどうかで、後半の難易度が変わる",
  "xLabel":"関心の高さ", "yLabel":"影響力（決定権）",
  "xLow":"低い","xHigh":"高い","yLow":"小さい","yHigh":"大きい",
  "quadrants":[
    {"title":"満足させる","text":"関心は低いが決定権がある。経営層・情シス部門長。要点だけ定期報告し、反対されない状態を作る","tone":"amber"},
    {"title":"密接に協働する","text":"キーパーソン。要件定義・レビュー・パイロットに必ず巻き込む","tone":"good"},
    {"title":"監視する","text":"影響も関心も低い。最小限の情報共有にとどめる","tone":"gray"},
    {"title":"情報提供する","text":"関心は高いが決定権はない。現場担当・データ提供部門。実務の情報源として重要","tone":"blue"} ] }
```

| 見落とされがちな関係者 | 巻き込まないと起きること |
|---|---|
| データ提供元の部署 | 「そのデータは公開できない」と後から言われる |
| 情報システム部門 | ゲートウェイ・権限・セキュリティ要件で止まる |
| 経理・管理会計 | 「その数字は公式の数字と違う」と会議で否定される |
| 実際の利用者（現場） | 完成後に「これは使えない」と言われる |
| 既存レポートの所有者 | 重複と縄張り争いが発生する |

> [!DS] データサイエンス視点：ジョブ理論と 5 Whys
> **ジョブ理論**（Jobs to be Done）は、「顧客は製品が欲しいのではなく、片づけたい用事のために製品を雇う」という考え方です。BI に当てはめれば、**利用者はダッシュボードが欲しいのではなく、「上司に説明する」「支援先を決める」という用事を片づけたい**だけです。用事が特定できれば、必ずしもダッシュボードが最適解とは限りません（メール1通の自動配信で済むこともあります）。用事にたどり着く手法が **5 Whys**——「なぜ」を5回繰り返して真因まで降りる技法です。ただし機械的に5回聞くと尋問になるので、「それができると何が良くなりますか」という肯定形に言い換えて使ってください。

## ユーザーストーリーと受け入れ基準

要件は、実装可能で検証可能な形式に落とします。

```figure
{ "type":"formula", "lang":"text", "title":"ユーザーストーリーの形式",
  "code":"[誰として] [何をしたい] [なぜなら]",
  "parts":[
    {"match":"[誰として]","label":"営業所長として","tone":"blue"},
    {"match":"[何をしたい]","label":"担当エリアの目標未達店舗を一覧したい","tone":"green"},
    {"match":"[なぜなら]","label":"週次で訪問先を決める必要があるから","tone":"amber"} ] }
```

各ストーリーには**受け入れ基準**をつけます。「できたかどうか」を誰が見ても判定できる形にすることが目的です。

```text
【ユーザーストーリーと受け入れ基準の例】

ストーリー:
  営業所長として、担当エリアの目標未達店舗を一覧したい。
  なぜなら、週次で訪問先を決める必要があるから。

受け入れ基準:
  □ 自分の担当エリアの店舗のみが表示される（RLS適用）
  □ 達成率の低い順に並んでいる
  □ 各店舗について「達成率」「未達額」「前週からの変化」が見える
  □ 月曜8:00時点で、前週日曜までの実績が反映されている
  □ スマートフォンで表示でき、文字が読める
  □ 表示完了まで3秒以内

完了の定義:
  所長3名がテスト環境で実際に訪問先を選定でき、
  かつ現行のExcel作業（週2時間）を行わずに済むことを確認できた状態
```

> [!TIP] 実務のコツ
> 受け入れ基準に**性能要件（3秒以内）と鮮度要件（月曜8:00時点）を必ず入れてください**。この2つは後から追加すると、モデル設計をやり直すことになります。最初に書いておけば、インポートかDirectQueryか、増分更新が必要かといった技術判断が自動的に決まります。

```figure
{ "type":"compare", "title":"スコープの管理", "caption":"断るのではなく、置き場所を作る",
  "panels":[

     "items":["「できますよ」と全部受ける","口頭で合意し、記録を残さない","追加要望のたびに納期を延ばす","断ると関係が悪くなると思っている"],

```

> [!TRAP] つまずきポイント
> **「ついでにこれも」を断れずに全部受ける**のは、優しさではありません。納期遅延と品質低下を招き、最終的に全員が損をします。ただし、**単に断るのは最悪の対応**です。要望を可視化されたリストに載せ、「優先度を一緒に決めましょう」と持ちかけてください。依頼者は無視されることを嫌うだけで、順番待ちには納得します。

## ヒアリングの実技

質問リストがあっても、聞き方を誤ると本音は出てきません。実技として押さえるべき点があります。


## 要件定義の成果物を、次の工程に渡す

要件定義書は、書いて終わりではありません。次の3つの工程に直接つながります。


## 理解度チェック

1. 「全社の売上ダッシュボードが欲しい」という役員からの依頼に対し、最初に投げるべき質問を3つ、その意図とともに述べてください。
2. 依頼者（部長）と利用者（現場40名）が異なる案件で、要件定義の進め方をどう変えますか。
3. 要件合意後に「顧客の業種データが60%欠損している」と判明しました。この事態を防ぐために要件定義のどの工程が必要だったか、また現時点で取るべき対応を述べてください。
