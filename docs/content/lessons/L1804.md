情報漏えいが起きたとき、最初に聞かれるのは「**誰が何を見ましたか**」です。

このとき「分かりません」と答える基盤は、組織を守れません。BIは組織で最も機密データが集まる場所です。基幹システムの明細も、人事の情報も、顧客の個人情報も、分析のために1か所に集まります。**BIは分析基盤であると同時に、最も守るべき資産の集積地**です。

## 秘密度ラベル

**秘密度ラベル**とは、Microsoft Purview 情報保護で定義された分類のことで、「社外秘」「機密」などのラベルを資産に付与します。ラベルは単なる表示ではなく、**暗号化とアクセス制御の設定を伴います**。

```figure
{ "type":"pipeline", "title":"秘密度ラベルの継承", "caption":"ラベルは資産から資産へ、そしてエクスポートされたファイルへも引き継がれる",
  "nodes":[
    {"id":"src","label":"ソース\n（ラベル付き）","tone":"blue"},
    {"id":"sm","label":"セマンティックモデル\n「社外秘」","tone":"violet"},
    {"id":"rp","label":"レポート\n「社外秘」を継承","tone":"pink"},
    {"id":"xl","label":"エクスポートしたExcel\n「社外秘」を保持","tone":"green"},
    {"id":"pp","label":"PowerPoint / PDF\n「社外秘」を保持","tone":"amber"},
    {"id":"out","label":"社外へ送信\n→ 開けない","tone":"bad"}],
  "edges":[
    {"from":"src","to":"sm","label":"継承"},
    {"from":"sm","to":"rp","label":"継承"},
    {"from":"rp","to":"xl","label":"エクスポート"},
    {"from":"rp","to":"pp","label":"エクスポート"},
    {"from":"xl","to":"out","label":"権限がなければ"} ] }
```

ラベルの価値は**下流への保護の継承**にあります。レポートからExcelにエクスポートされたファイルにもラベルが引き継がれ、そのファイルが社外に送られても、権限のない人は開けません。**アクセス制御が「基盤の中」でしか効かないのに対し、ラベルは「基盤の外」でも効きます。**

### ラベルの設計

```figure
{ "type":"tree", "title":"ラベル体系の設計", "caption":"多すぎると誰も正しく選べない。4段階が実用上の上限",
  "root":{"label":"ラベルを何段階にするか"},
  "children":[
    {"label":"公開","sub":"社外に出してよい情報","tone":"good",
     "children":[{"label":"保護なし","sub":"IR資料、公開済みの統計"}]},
    {"label":"社内限定","sub":"組織内のみ","tone":"cyan",
     "children":[{"label":"組織内ユーザーのみ閲覧可","sub":"大半の業務データはここ"}]},
    {"label":"社外秘","sub":"限定された部門のみ","tone":"amber",
     "children":[{"label":"指定グループのみ／透かし表示","sub":"原価、与信、未公表の業績"}]},
    {"label":"極秘","sub":"個人情報・法規制対象","tone":"bad",
     "children":[{"label":"暗号化＋エクスポート禁止＋監査強化","sub":"人事情報、医療情報、決済情報"}]} ] }
```

> [!TIP] 実務のコツ
> ラベル体系を設計するとき、**既存の社内文書分類に合わせる**のが鉄則です。BIだけ独自の4段階を作ると、利用者は「Wordの『社外秘』とPower BIの『社外秘』は同じか」で混乱します。ラベルはPurviewでテナント全体に定義されるものなので、情報セキュリティ部門が既に持っている分類をそのまま使ってください。**BIチームが独自にラベル体系を作る場面は、基本的にありません。**

> [!WARN] 注意
> 秘密度ラベルは**アクセス制御を置き換えません**。「極秘」ラベルを付けても、そのワークスペースに閲覧権限を持つ人は見られます。ラベルが制御するのは主に「基盤の外に出た後」です。**まずアクセス権を正しく設定し、その上でラベルを付ける**。順序を守ってください。

## DLP（データ損失防止）ポリシー

秘密度ラベルや機密情報の種類を条件に、**その資産が扱われたときに自動でアクションを取る**仕組みです。

| 検出条件 | アクション例 |
|---|---|
| マイナンバーらしき文字列を含む | 所有者に通知、管理者にアラート |
| クレジットカード番号のパターンを含む | 共有をブロック |
| 「極秘」ラベルの資産が外部共有された | ブロックして理由を表示 |

> [!DS] データサイエンス視点：データ分類は自動化と人手の組み合わせ
> データ分類（どのデータが機密か決めること）は、完全自動でも完全手動でも失敗します。自動検出は**パターンで見つかるもの**（カード番号、マイナンバー、メールアドレス）には強いが、**文脈に依存する機密**（未公表の組織再編、特定顧客の与信判断）は見つけられません。逆に人手だけでは網羅できません。**自動検出で候補を出し、データスチュワードが確定する**という2段階が現実解です。この考え方はDMBOKのデータセキュリティ管理でも中核に置かれています。

## 監視すべき異常のパターン

ログを取っても、何を見るかが決まっていなければ意味がありません。

| 異常パターン | 何を疑うか |
|---|---|
| 特定ユーザーのエクスポートが急増 | 退職前の持ち出し |
| 通常アクセスしない部門の資産への閲覧 | 権限設定の誤り |
| 深夜・休日の大量アクセス | 認証情報の不正利用 |
| 「Webに公開」の新規発生 | 誤操作による情報公開 |
| ワークスペース権限の一括変更 | 誤操作または内部不正 |
| 外部ユーザーの追加 | 共有ポリシーの逸脱 |
| 個人ワークスペースへの大量アップロード | 統制外への資産の退避 |
| 同一アカウントの複数拠点からのアクセス | 認証情報の共有または漏えい |

> [!TIP] 実務のコツ
> 上の6項目のうち、**最初に監視すべきは「Webに公開」の新規発生**です。影響が最も大きく、検知が容易で、誤操作で起きやすいからです。1つのアラートを作るなら、まずこれ。すべてを完璧に監視しようとして何も作らないより、1つ作って動かすほうが遥かに価値があります。

## RLSとOLSの守備範囲

行レベル・列レベルのセキュリティも、データ保護の一部です。それぞれ守れる範囲が違います。

```figure
{ "type":"matrix", "title":"RLS・OLS・モデル分離の使い分け", "xLabel":"隠したい単位", "yLabel":"機密度",
  "xLow":"行（一部のレコード）","xHigh":"列・テーブル（項目そのもの）","yLow":"中","yHigh":"高",
  "quadrants":[
    {"title":"RLS","text":"営業担当が自分の担当顧客だけ見る。標準的な用途。","tone":"good"},
    {"title":"OLS（オブジェクトレベルセキュリティ）","text":"給与額の列を一部のロールから隠す。列の存在自体が見えなくなる。","tone":"amber"},
    {"title":"RLS＋監査","text":"機密度が高い行の制御。設定ミスの影響が大きいため、テストとログ監視をセットにする。","tone":"violet"},
    {"title":"モデルを分離する","text":"最も機密度が高い領域は、そもそも別モデル・別ワークスペースにする。","tone":"bad"} ] }
```

右上、機密度が最も高い領域では**RLSやOLSに頼らず、モデルごと分離する**のが正解です。理由は、設定ミスの影響が非対称だからです。RLSの設定を1つ間違えると、見えてはいけない人に見えます。モデルが分かれていれば、そもそも到達できません。

> [!WARN] 注意
> OLSで列を隠した場合、**その列を参照するメジャーやビジュアルはエラーになります**。「見えない」ではなく「壊れる」挙動になるため、レポート側の設計と合わせて検討する必要があります。ロールごとに別のレポートページを用意する、といった対応が必要になることがあります。

## 保持期間と削除

データ保護には「守る」だけでなく「捨てる」設計も含まれます。

| 対象 | 保持期間の考え方 | 設計への影響 |
|---|---|---|
| 分析用のファクト | 業務要件（3年・5年・7年） | 増分更新のアーカイブ期間 |
| 個人を特定できる項目 | 目的達成後は速やかに削除 | 仮名化のタイミング設計 |
| アクティビティログ | 監査要件（多くは1〜3年） | 外部保存先の容量計画 |
| 開発・テスト環境のデータ | 必要最小限 | 定期的な洗い替え |

> [!TRAP] 「全期間のデータを持っておく」を無条件に選ぶ
> 保持期間を決めないと、データは増え続けます。増えると、(1) モデルが重くなり、(2) コストが増え、(3) 漏えい時の被害が拡大し、(4) 削除要請への対応が困難になります。**保持期間は「長ければ長いほどよい」ものではありません。**業務上の必要性から決め、超過分はアーカイブに移すか削除する設計を、最初に入れておきます。

> [!DS] データサイエンス視点：最小権限の原則
> **最小権限の原則（Principle of Least Privilege）**とは、「業務の遂行に必要な最小限の権限だけを与える」という情報セキュリティの基本原則です。BIで守るのが難しい理由は、**分析という業務が「何が必要か事前に分からない」性質を持つ**からです。だからこそ、(1) 既定は最小、(2) 必要になったら追加、(3) 追加した権限は期限付きにするか定期棚卸しで回収、という運用が要ります。「とりあえず全部見せて、問題があったら絞る」は、順序が逆であり、一度広げた権限は回収が非常に困難です。

## セキュリティ設計を先送りしない

最後に、進め方の話をします。データ保護は「動くものができてから」やる作業だと思われがちですが、後回しにすると必ず作り直しになります。

```figure
{ "type":"timeline", "title":"プロジェクトのどこでセキュリティを決めるか", "caption":"×印の位置で決めると、その前の設計をやり直すことになる",
  "items":[
    {"label":"要件定義","title":"○ ここで決める","text":"機密度の分類、閲覧範囲、個人情報の要否、監査要件。構成の前提になる。","tone":"good"},
    {"label":"設計","title":"○ 構成に反映する","text":"モデル分離の要否、ワークスペース構成、RLS方式。ここまでが本来の判断点。","tone":"green"},
    {"label":"実装","title":"△ 実装だけ","text":"決まった方針を形にする。ここで方針を考え始めると手戻りする。","tone":"amber"},
    {"label":"公開直前","title":"× 手遅れ","text":"「個人情報が入っていた」「外部共有が必要だった」が発覚。構成から作り直し。","tone":"bad"} ] }
```

要件定義の段階で聞くべきことは3つだけです。**「このデータに個人情報や法規制対象は含まれますか」「見てはいけない人は誰ですか」「誰が見たかの記録は必要ですか」。**この3問で、構成の大枠が決まります。

> [!TIP] 実務のコツ
> セキュリティ部門を「止める人」ではなく「先に相談する相手」として扱うと、案件は速く進みます。公開直前に相談すると必ず止められますが、要件定義の段階で相談すれば、彼らは代替案を出してくれます。**「この構成なら承認できる」を早く聞き出すことが、結果的に最短経路です。**

> [!DS] データサイエンス視点：セキュリティは確率ではなく被害額で考える
> 「そんな事故は起きないだろう」という判断は、発生確率だけを見ています。リスクの評価は**発生確率 × 被害額**であり、確率が低くても被害が壊滅的なものは対策すべきです。「Webに公開」による顧客情報の流出は、確率は低くても被害額は事業継続に関わります。逆に、社内の誰かが権限外のレポートを見る事象は、確率は高くても被害は限定的です。**この2つに同じ労力をかけるのは、資源配分として誤り**です。守る順序を被害額で決めてください。

## 設計チェックリスト

- [ ] アクセス制御・ラベル・監査の3層のうち、まずアクセス制御を固めた
- [ ] テナント設定で「Webに公開」を既定で無効にした
- [ ] エクスポート・外部共有・外部サブスクリプションの方針を決めた
- [ ] 秘密度ラベル体系を、社内の既存文書分類に合わせて定義した
- [ ] ラベルがアクセス制御の代替ではないことをチームで共有した
- [ ] アクティビティログの日次取得と長期保存を自動化した
- [ ] 監視すべき異常パターンを定め、最低1つのアラートを稼働させた
- [ ] 使用状況メトリックとアクティビティログの用途を使い分けた
- [ ] 最も機密度が高い領域はRLSではなくモデル分離で守った
- [ ] 権限棚卸しのサイクル（月次・四半期・半期・年次）を定めた
- [ ] 権限は個人ではなくセキュリティグループに付与した
- [ ] 個人情報について「取り込まない／集計する／仮名化する」の判断を先に行った
- [ ] データの保持期間を対象ごとに定め、超過分の扱いを決めた
- [ ] 監査で聞かれる6項目に、日常運用の記録だけで答えられる状態にした
- [ ] セキュリティ要件を要件定義の段階で3問（個人情報・閲覧制限・監査要否）確認した

## 理解度チェック

1. 秘密度ラベルとワークスペースのアクセス権は、それぞれどの範囲を守るものか。違いを説明してください。
2. 「必要になったらアクティビティログを取ればよい」という考えの誤りを指摘してください。
3. 極めて機密度の高いデータについて、RLSで制御するのではなくモデルを分離すべき理由を、設定ミスの影響という観点から述べてください。
4. 「念のため個人情報の列も取り込んでおく」という判断が、なぜ最悪の選択なのかを3つの観点から説明してください。

> [!NOTE] このレッスンのまとめ
> データ保護はアクセス制御・ラベル・監査の3層で構成され、最優先は到達させないこと。テナント設定で危険な経路（特に「Webに公開」）を先に閉じる。秘密度ラベルは基盤の外に出た後も保護を継続させる仕組みで、アクセス制御の代替ではない。アクティビティログは事故の後では取れないため、日次取得と長期保存を事前に仕組み化する。そして最も機密度が高い領域は、設定ミスの影響が非対称であるがゆえに、RLSではなくモデルごと分離する。
