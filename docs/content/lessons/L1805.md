検索窓に「売上」と入れたら、47件出てきました。どれが正しいのか、利用者には分かりません。

この状況で多くの組織が最初にやろうとするのは**削除**です。しかしそれは失敗します。46件を消そうとすると、それぞれに使っている人がいて、それぞれに事情があり、政治的な抵抗に遭います。

正しい打ち手は削除ではなく、**「これが正です」という表示を1件に付けること**です。47件を46件にするより、47件の中から1件を光らせるほうが、遥かに速く、遥かに効果があります。

## 認定のプロセス

```figure
{ "type":"steps", "title":"認定の申請から付与まで",

    {"title":"技術レビューを行う","text":"BIチームが構造・性能・命名を確認。機械で判定できる項目は自動化済みであること。","tone":"green"},
    {"title":"業務レビューを行う","text":"指標の定義が業務的に正しいか、業務所有者が確認する。ここが本質。","tone":"amber"},
    {"title":"認定を付与し、記録する","text":"付与日・付与者・根拠を台帳に残す。付けっぱなしにしない。","tone":"violet"},
```

最後の「取り消し」を運用に入れている組織は稀ですが、**取り消せない認定は劣化します**。所有者が異動し、更新が失敗し続け、それでも認定済みのまま残る。その状態が続くと、組織は認定を信じなくなります。

> 認定の対象を最初から広げないでください。**まず3〜5個**。全社が使う主要ドメインのモデルだけを認定し、それが機能することを見せる。「認定済みを選べば間違いない」という経験を利用者が持ってから、対象を広げます。最初に30個認定すると、レビューが形骸化し、認定の価値が生まれる前に薄まります。

## 指標定義をカタログ化する

エンドースメントは資産（モデル・レポート）に対する保証ですが、利用者が本当に知りたいのは**指標の定義**です。

```figure
{ "type":"compare", "title":"指標カタログがある組織とない組織",
  "panels":[
    {"title":"ない","tone":"bad",
     "items":["「純売上って値引後ですか」を毎回聞く","部署ごとに解釈が違う","定義変更が誰にも伝わらない","新任者が理解するのに数か月かかる"],
     "note":"知識が個人に閉じている"},
    {"title":"ある","tone":"good",
     "items":["指標名・定義・計算式・除外条件・所有者が一覧できる","どのモデルで実装されているかが分かる","定義変更の履歴が残る","新任者が自分で調べられる"],
     "note":"知識が組織の資産になる"} ] }
```

指標カタログに載せる項目を定めます。

| 項目 | 例 |
|---|---|
| 指標名 | 純売上高 |
| 一文定義 | 値引・返品を控除した後の外部顧客向け売上 |
| 計算の要点 | 総売上 − 値引 − 返品。社内取引を除外 |
| 対象範囲 | 連結全社。2019年4月以降 |
| 基準となる日付 | 出荷日（会計計上日ではない） |
| 実装場所 | 販売ドメイン共有モデル `売上金額（純額）` |
| 所有者 | 経営企画部 |
| 最終変更 | 2026-03-15（子会社Aを対象に追加） |

> [!TIP] 実務のコツ
> 「基準となる日付」の欄は必ず入れてください。**数字が合わない原因の上位が、日付基準の違い**です。会計は計上日、販売は出荷日、契約は締結日。同じ「1月の売上」でも、基準が違えば数字は違います。カタログにこの欄があるだけで、突合の議論が数十分短縮されます。

> **DMBOK（Data Management Body of Knowledge）**は、データマネジメントの知識体系です。11の知識領域を定義しており、その中心に**データガバナンス**を置いています。重要な主張は「**ガバナンスは技術ではなく、意思決定の権限と責任の配置である**」という点です。誰がデータの定義を決めるのか、誰が品質に責任を持つのか、誰が公開を承認するのか。この配置が決まっていない組織では、どんなツールを導入しても状況は改善しません。エンドースメント機能もカタログも、**「誰が決めるか」が決まっていて初めて意味を持つ道具**です。

## 資産の廃止プロセス

第5段階の「廃止」は、慎重にやらないと反発を生みます。手順を固定しておきます。

```figure
{ "type":"steps", "title":"資産を安全に廃止する5段階",
  "items":[
    {"title":"利用実績を確認する","text":"直近90日のユニーク利用者数とアクセス日。0件でも、四半期に1回使う資産かもしれない。1年分を見る。","tone":"blue"},
    {"title":"所有者と利用者に予告する","text":"「30日後に廃止します。必要なら申し出てください」。反応がなければ次へ。","tone":"green"},
    {"title":"アクセスを止める（削除しない）","text":"権限を外す、またはアプリから除外する。ここで問い合わせが来れば復旧できる。","tone":"amber"},
    {"title":"30日待つ","text":"月次業務で使われていた場合、この期間に必ず気づかれる。","tone":"violet"},
    {"title":"バックアップを取って削除する","text":"pbix/pbipをアーカイブ保管し、資産を削除する。台帳に廃止日を記録。","tone":"pink"} ] }
```

3段階目の「アクセスを止めるが削除しない」が要です。**削除は取り消せませんが、権限は戻せます。**この1段階を挟むだけで、廃止の失敗が事故ではなくなります。

| 状況 | 廃止の判断 |
|---|---|
| 90日アクセス0・所有者不明 | 廃止（予告のみ） |
| 90日アクセス0・所有者あり | 所有者に確認して判断 |
| 月次で数名が利用 | 廃止しない。共有モデルへの付け替えを検討 |
| 認定済みだが利用者0 | 認定を取り消してから廃止判断 |

> [!TRAP] 誰も管理していないレポートが増殖する
> 廃止プロセスを持たない組織では、資産は増える一方です。5年運用すれば数百件になり、そのうち半分以上は誰も見ていません。問題は容量ではなく、**探せなくなること**です。検索結果に死んだ資産が並ぶと、認定済みの資産まで埋もれます。**廃止は掃除ではなく、生きている資産を見つけやすくするための作業**だと理解してください。

## 効果を数字で示す

ガバナンスの取り組みは「成果が見えない」と言われがちです。測定可能な指標を持っておきます。

```figure
{ "type":"chart", "kind":"line", "title":"ガバナンス施策の効果（導入からの推移）", "unit":"件",
  "categories":["開始時","3か月","6か月","12か月","18か月"],
  "series":[
    {"name":"「売上」を含む重複資産数","values":[47,44,31,18,11],"tone":"bad"},
    {"name":"認定済み資産の利用者数（十人単位）","values":[0,8,24,51,78],"tone":"good"}],
  "highlight":4 }
```

重要なのは2本の線の関係です。**重複が減るより先に、認定済みの利用が伸びています。**これが正しい順序であることの証拠です。認定済みが使われ始めてから、重複資産の廃止が受け入れられるようになります。逆順で進めた組織——先に削除しようとした組織——では、両方の線が動きません。

| 測定指標 | 意味 |
|---|---|
| 認定済み資産の利用者数 | 信頼の仕組みが機能しているか |
| 同名指標の定義数 | 数字の統一が進んでいるか |
| 所有者不明の資産数 | 管理の空白が減っているか |
| 廃止した資産数 | 掃除が進んでいるか |
| 「この数字は何ですか」問い合わせ件数 | カタログが機能しているか |

## Microsoft Purview との関係

執筆時点では、Fabric の資産は Microsoft Purview のデータカタログに統合されつつあります。

| レイヤー | 役割 |
|---|---|
| Fabric / Power BI 内のデータハブ | Fabric 内の資産を探す。エンドースメントが効く |
| OneLake カタログ | OneLake 上のデータ資産の探索とガバナンス |
| Microsoft Purview | Fabric 外（オンプレDB、他クラウド、SaaS）を含む全社カタログ |

> [!WARN] 執筆時点の情報
> このあたりの製品構成と名称は特に変化が速い領域です。「Fabric内で完結する範囲」と「全社カタログが必要な範囲」を分けて考えるという**設計の考え方**は安定していますが、機能名と統合の度合いは変わります。導入検討時には必ず公式ドキュメントで現状を確認してください。

> [!EXAM] PL-300で問われる
> エンドースメントは「4.5 ガバナンスとライフサイクル」の定番論点です。押さえるべきは、(1) **昇格済みは誰でも付与できる**（そのアイテムに書き込み権限があれば）、(2) **認定済みはテナント管理者が指定した人だけが付与できる**、(3) エンドースメントは**検索とデータハブでの表示順**に影響する、(4) エンドースメント自体は**アクセス権を変えない**、の4点です。「認定済みにすれば全員が見られるようになる」は誤りです。


第2段階が最も難しく、最も価値があります。**これは技術の仕事ではなく、合意形成の仕事**です。BI担当ができるのは、事実（何種類の定義が存在し、それぞれ何億円の差になるか）を示して、決める場を作ることです。決めるのは業務側です。

> [!TRAP] 技術で数字を統一しようとする
> 「共有モデルを作れば数字が統一される」という期待は外れます。定義の合意がないまま共有モデルを作れば、**使われないだけ**です。各部署は自分の定義で自分のモデルを使い続けます。順序は必ず「合意 → 実装 → 付け替え → 廃止」。技術は3番目に来ます。

## 設計チェックリスト

- [ ] エンドースメントの3段階の意味と、付与できる人の範囲を設定した
- [ ] 認定の必須条件を6項目以上、明文化した
- [ ] 認定プロセスに技術レビューと業務レビューの両方を入れた
- [ ] 認定の年次再確認と取り消しの運用を定めた
- [ ] 最初の認定対象を3〜5個に絞った
- [ ] カタログの「人が書く欄」を認定の条件にした
- [ ] 変更前に影響分析を実施する運用を定めた
- [ ] 系列ビューに出ない依存（Excel接続など）をログで補完した
- [ ] 指標カタログを作り、基準となる日付の欄を設けた
- [ ] ドメインごとにデータスチュワードを任命した
- [ ] 数字の統一を「合意 → 実装 → 付け替え → 廃止」の順で計画した
- [ ] 廃止プロセスに「アクセスを止めるが削除しない」段階を入れた
- [ ] 廃止前の予告期間（30日）を定めた
- [ ] ガバナンスの効果を測る指標を5つ決め、定期的に測定している
- [ ] Fabric内で完結する範囲と全社カタログが必要な範囲を切り分けた

## 理解度チェック

1. 「昇格済み」と「認定済み」の違いを、付与する人の観点から説明してください。
2. モデルの列を削除する前に影響分析を行いましたが、系列ビューには何も表示されませんでした。それでも確認すべきことがあります。何か、なぜか説明してください。
3. 似たレポートが47件ある状況で、「46件を削除する」という進め方が失敗する理由と、代わりに取るべき最初の一手を述べてください。
4. 資産の廃止手順で「アクセスを止めるが削除はしない」という段階を挟む理由を説明してください。

> [!NOTE] このレッスンのまとめ
> 重複した資産は削除ではなく、正を1つ光らせることから片付ける。エンドースメントは昇格済み（自己申告）と認定済み（第三者承認）に分かれ、認定は組織の保証であるため維持責任を伴う。カタログの「人が書く欄」は認定の条件にして初めて埋まる。影響分析は系列ビューに出ない依存をログで補完する。そして数字の統一は合意が先で技術は後——共有モデルを作れば統一されるという期待は、必ず外れる。
