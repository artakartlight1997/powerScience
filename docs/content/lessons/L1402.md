### 4. 小数点の多い数値

> [!TIP] 実務のコツ
> 金額列は「**10進数**」ではなく「**固定小数点数（通貨）**」型にしてください。固定小数点数は内部的に小数第4位までの整数として扱われるため、値符号化が効きます。為替換算などで小数第10位まで出ている列は、業務上必要な桁で `Number.Round` してから取り込みます。**小数第2位で足りるなら、それ以上は情報ではなくノイズです。**

> [!TRAP] つまずきポイント
> 複合キーでリレーションを張るために連結キーを作るのは、よくある手ですが**モデルサイズを大きく押し上げます**。しかもDAXの計算列は Power Query の列より圧縮が効きにくいため、二重に不利です。可能なら Power Query 側で作り、さらに可能なら**整数のサロゲートキーに置き換えて**ください。

> カーディナリティを下げる作業は、**次元削減**と同じ発想です。情報を捨てることで表現を小さくし、扱いやすくします。違いは、分析における次元削減が「分散を保ちながら次元を減らす」のに対し、モデル最適化は「**分析要件を満たしながら情報量を減らす**」点です。どちらも「何を捨てても目的を達成できるか」という問いが本質で、技術的な操作より要件定義のほうが難しいところも共通しています。

> [!EXAM] PL-300で問われる
> 「自動の日付/時刻を無効にする理由」も出題されます。**独自の日付テーブルがある場合、自動生成された非表示テーブルは無駄なだけでなく、タイムインテリジェンス関数の対象を紛らわしくする**——これが答えです。

## 理解度チェック

**問1.** 500万行のファクトテーブルに、カーディナリティ10の列とカーディナリティ500万の列があります。どちらがモデルサイズに与える影響が大きいですか。定量的に説明してください。

<details>
<summary>解答</summary>

**カーディナリティ500万の列**が圧倒的に大きくなります。本体サイズは `行数 × log2(カーディナリティ)` なので、前者は 500万 × 4ビット、後者は 500万 × 23ビット と6倍弱の差にとどまります。しかし辞書サイズはカーディナリティに正比例するため、10エントリと500万エントリで50万倍の差になります。**辞書が支配的**というのが要点です。
</details>

**問2.** 秒単位の `OrderDateTime` 列を日付と時刻の2列に分けると、なぜ大幅にサイズが減るのですか。

<details>
<summary>解答</summary>

1つの列で「日付 × 時刻」の全組み合わせを保持していたのが、2つの列で「日付」と「時刻」を別々に保持する形になるためです。3年分・秒単位なら 1,095 × 86,400 = 約9,460万通りが、1,095 + 86,400 = 87,495通りに減ります。さらに時刻を分単位に丸めれば 1,095 + 1,440 = 2,535通りです。**積が和になる**のが本質です。
</details>

**問3.** DAXの計算列でカテゴリ判定を作るのと、Power Query のカスタム列で作るのでは、どちらがモデルサイズ的に有利ですか。理由も答えてください。

<details>
<summary>解答</summary>

**Power Query のカスタム列**が有利です。Power Query で作った列は他の列と同じタイミングでエンコードされ、セグメント内の並べ替え最適化の対象になります。DAXの計算列は全列のロード後に評価されるため、この最適化の恩恵を受けにくく、圧縮率が落ちます。**上流でできることは上流でやる**という原則がここでも当てはまります。
</details>
