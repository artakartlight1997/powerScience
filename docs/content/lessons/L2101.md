「営業のダッシュボードを作ってほしい。とりあえず全部の数字が見たい」

この依頼をそのまま実装すると、指標が40個並んだ画面ができあがり、3週間後には誰も開かなくなります。全部見たいという要望は**要望ではなく、思考の放棄**です。設計者の仕事は、それを具体的な意思決定に翻訳することです。

```figure
{ "type":"compare", "title":"同じデータから作られる2つのレポート", "caption":"情報量は後者の方が少ない。しかし価値は比較にならない",
  "panels":[
    {"title":"全部載せレポート","tone":"bad",
     "items":["KPIカードが12枚","グラフが9個、表が3つ","スライサーが8個","どこを見るべきか分からない","結局Excelにエクスポートされる"],
     "note":"3週間で閲覧ゼロ"},
    {"title":"意思決定志向レポート","tone":"good",
     "items":["主要指標は3つ","「目標との差」が最上部","差の要因が下に1段","次の行動が明示される","深掘りはドリルスルー"],
     "note":"毎週の会議で使われる"} ] }
```

## 設計は3つの問いから始まる

レポート設計の出発点は、画面でもデータでもありません。次の3つです。

```figure
{ "type":"formula", "lang":"text", "title":"設計の3点セット",
  "code":"[誰が] [どんな判断を] [どう変えるために] このレポートを見るのか",
  "parts":[
    {"match":"[誰が]","label":"役職・人数・データリテラシー・見る場所（会議室/スマホ）","tone":"blue"},
    {"match":"[どんな判断を]","label":"具体的な意思決定。「把握する」は判断ではない","tone":"amber"},
    {"match":"[どう変えるために]","label":"見た結果、何が変わるか。変わらないなら作らない","tone":"pink"} ] }
```

> [!NOTE] 要点
> **「把握する」「モニタリングする」は意思決定ではありません。** 「予算未達の営業所に対し、今週どこへ支援を投入するかを決める」が意思決定です。この粒度まで書けたとき、初めて必要な指標と粒度が確定します。

```figure
{ "type":"tree", "title":"依頼から設計への分岐", "caption":"同じ「売上ダッシュボード」でも、判断が違えば設計は全く別物になる",
  "root":{"label":"「売上ダッシュボードが欲しい」"},
  "children":[
    {"label":"経営会議で使う","sub":"月次・全社","tone":"violet",
     "children":[
       {"label":"判断：予算修正・投資配分","sub":"必要：目標差、トレンド、構成比","tone":"violet"},
       {"label":"粒度：月×事業部","sub":"明細は不要","tone":"gray"}]},
    {"label":"営業部長が使う","sub":"週次・部門","tone":"amber",
     "children":[
       {"label":"判断：どの案件に人を割くか","sub":"必要：案件別進捗、確度、失注リスク","tone":"amber"},
       {"label":"粒度：案件×担当","sub":"明細が必要","tone":"gray"}]},
    {"label":"営業担当が使う","sub":"日次・個人","tone":"green",
     "children":[
       {"label":"判断：今日誰に連絡するか","sub":"必要：訪問予定、放置期間、次アクション","tone":"green"},
       {"label":"粒度：顧客1件","sub":"スマホで見る","tone":"gray"}]} ] }
```

この3つを1画面に詰め込もうとするのが、失敗の始まりです。**読者が違えば、レポートは分ける。** これが情報設計の第一原則です。

## 3層モデル：戦略・戦術・運用

組織のレポートは、意思決定の周期と粒度で3層に整理できます。

```figure
{ "type":"stack", "title":"レポートの3層構造", "caption":"上ほど少数・低頻度・粗い粒度。下ほど多数・高頻度・細かい粒度",
  "layers":[
    {"label":"戦略レイヤー（経営）","sub":"月次・四半期／全社・事業部／指標5個以内／「方向は正しいか」","tone":"pink"},
    {"label":"戦術レイヤー（部門管理）","sub":"週次／部門・チーム／指標10個以内／「どこに手を打つか」","tone":"amber"},
    {"label":"運用レイヤー（現場）","sub":"日次・リアルタイム／案件・顧客単位／「今日何をするか」","tone":"green"} ] }
```

| 層 | 主な利用者 | 見る頻度 | 指標数の目安 | 求められる粒度 |
|---|---|---|---|---|
| 戦略 | 役員・事業責任者 | 月次 | 3〜5 | 集計値と傾向。明細は不要 |
| 戦術 | 部長・マネージャー | 週次 | 5〜10 | セグメント別。要因が追える |
| 運用 | 担当者 | 日次 | 1〜3 + リスト | 行単位。アクション可能 |

> [!TRAP] つまずきポイント
> **役員向けレポートに明細テーブルを載せる**——非常によくある失敗です。「念のため」と置かれた明細は、会議で細部の議論を誘発し、本来決めるべき戦略的判断の時間を奪います。明細が必要なら**ドリルスルーの先**に置いてください。見えないことにも設計上の意味があります。

## 1画面に載せられる指標の数

人が同時に把握できる情報量には限界があります。短期記憶が保持できる情報の塊は概ね4〜7個とされ、それを超えた瞬間、比較や判断の質が落ちます。

```figure
{ "type":"chart", "kind":"bar", "title":"画面上の指標数と「見て判断できた人」の割合", "caption":"指標数が増えるほど判断率は落ちる。多いことは親切ではない",
  "categories":["3個","5個","8個","12個","20個"],
  "series":[{"name":"判断できた割合","values":[92,85,61,34,12],"tone":"blue"}],
  "highlight":4, "unit":"%" }
```

> [!DS] データサイエンス視点：認知の制約は設計の前提条件
> 短期記憶の容量には限界があり（いわゆるマジカルナンバー4±1）、選択肢が増えるほど意思決定は遅く質が下がることが知られています（選択のパラドックス）。これは根性や訓練で克服できるものではなく、**設計の前提として扱うべき物理的制約**です。「情報を絞る」のは手抜きではなく、認知科学に基づいた設計判断です。この根拠を持っておくと、「もっと載せて」という要望に対して、感覚ではなく理由で応答できます。

```text
読者B: 営業企画（3名）

  見る頻度: 随時
```

> [!TIP] 実務のコツ
> **「現在の代替手段」を必ず書いてください。** 人は既存のやり方を捨てるとき、必ず比較します。「今Excelで2時間かかっている作業が3分になる」と示せれば定着します。逆に、現在の手段より不便な点が1つでもあると、そこを理由に戻られます。

## 1画面1メッセージ

優れたレポートページには、**一言で言える主張**があります。それを言えないページは、たいてい何も伝えていません。

```figure
{ "type":"compare", "title":"ページタイトルの書き方", "caption":"タイトルは分類ラベルではなく、主張を書く場所",
  "panels":[
    {"title":"分類ラベル型","tone":"bad",
     "items":["「売上分析」","「営業ダッシュボード」","「月次レポート」"],
     "note":"何も伝えていない"},
    {"title":"メッセージ型","tone":"good",
     "items":["「売上は目標比 -6%。要因は国内直営の客数」","「西日本エリアの粗利率が3期連続で低下」","「今週の重点フォロー：滞留案件18件」"],
     "note":"読む前に結論が伝わる"} ] }
```

タイトルを動的にすることもできます。DAX で作った文字列をタイトルに設定すれば、フィルターに応じて主張が変わります。

```dax
ページタイトル =
VAR 差 = [売上合計] - [売上目標]
VAR 率 = DIVIDE( 差, [売上目標] )
RETURN
"売上は目標比 " & FORMAT( 率, "+0.0%;-0.0%" ) &
"（" & FORMAT( ABS( 差 ) / 1000000, "#,0" ) & "百万円の" &
IF( 差 >= 0, "超過", "不足" ) & "）"
```

> [!WARN] 注意
> 動的タイトルは強力ですが、**フィルターで対象が0行になったときの表示**を必ず確認してください。「売上は目標比 -100.0%（0百万円の不足）」のような表示が出ると、読み手は混乱します。`ISBLANK` での分岐を必ず入れます。

## スコープと非スコープを書く

設計書には「作らないもの」を明記します。これが後半戦を守ります。

```text
【スコープ定義】営業所長向け週次レポート v1.0

含むもの:
  - 所属営業所の週次売上・粗利・案件進捗
  - 前年同週比、目標比
  - 滞留案件リスト（14日以上動きのない案件）
  - 担当者別の活動件数

含まないもの（v1では対応しない）:
  - 個人の評価に使える指標（人事利用は別途協議）
  - 見込み顧客のスコアリング（データ未整備のため v2 で検討）
  - リアルタイム更新（日次更新とする。理由：基幹システムの連携が日次）
  - Excelエクスポート機能（定着まで意図的に制限し、要望を蓄積する）

前提:
  - データは基幹システムから毎日 6:00 に更新される
  - 所長は自分の営業所のデータのみ閲覧可（RLS適用）
```

> [!TRAP] つまずきポイント
> スコープを書かないと、開発中に要望が無限に増えます（スコープクリープ）。「ついでにこれも」を断る根拠は、**最初に合意した文書だけ**です。断るのではなく「v2の候補リストに入れます」と受け止め、**リストを見える場所に置く**のが実務的です。要望が消えたわけではないと分かれば、依頼者は待てます。

> [!EXAM] PL-300で問われる
> 直接的な出題は少ないですが、**「特定の対象者向けにレポートを配布する方法」**（アプリ、ワークスペースロール、RLS）や、**「モバイルレイアウトの構成」**は情報設計と密接に関係します。「営業担当がスマホで見る」という要件が出たら、モバイルレイアウトの作成が正解になる、という形で問われます。

現場で繰り返し目にする失敗には、はっきりした型があります。自分の設計がどれに当てはまるか、着手前に確認してください。

```figure
{ "type":"cards", "cols":2, "title":"失敗の5類型と処方箋", "caption":"どれも「設計を飛ばした」ことが原因",

    {"icon":"📦","title":"御用聞き型","text":"依頼された指標をそのまま全部載せた。処方：意思決定から逆算して削る","tone":"bad"},
    {"icon":"🪞","title":"データ構造の写し型","text":"テーブルの構造がそのまま画面になっている。処方：読者の問いの順に並べ替える","tone":"bad"},
    {"icon":"🎨","title":"見た目優先型","text":"きれいだが何を見ればいいか分からない。処方：1画面1メッセージに戻す","tone":"amber"},
    {"icon":"🧮","title":"分析者の自己満足型","text":"高度な分析を見せたいだけ。処方：読者が行動できる形に翻訳する","tone":"amber"},
```

5番目は特に議論を呼びます。「今の帳票と同じものを作ってほしい」という要望は正当に見えますが、その帳票は10年前の業務のために作られ、以後誰も見直していないことがほとんどです。**「この列は何の判断に使いますか」を1列ずつ聞く**と、半分が「昔からあるから」に行き着きます。

> 既存帳票の移植依頼では、**移植版と設計版の2つを作って並べて見せる**のが最も効きます。議論で説得するより、実物を比べさせる方が速い。移植版は1時間で作れます（そして、たいてい誰も選びません）。

## 複数の読者をどう扱うか

読者が違えばレポートを分ける、と述べました。しかし現実には「1つのレポートで全員に対応してほしい」と言われます。手段は3つあります。

```figure
{ "type":"compare", "title":"複数読者への3つの対処", "caption":"どれを選ぶかは、読者間の差の大きさで決める",
  "panels":[
    {"title":"ページで分ける","tone":"good",
     "items":["1ファイル内でページを分割","ナビゲーションボタンで移動","読者ごとに入口ページを指定できる"],
     "note":"最も一般的"},
    {"title":"ロールで出し分ける","tone":"amber",
     "items":["RLSで行を絞る","ブックマーク＋条件付き表示で要素を切替","保守が複雑になりやすい"],
     "note":"データの範囲が違うとき"},
    {"title":"レポートごと分ける","tone":"good",
     "items":["同じモデルにライブ接続","レポートは読者ごとに独立","数字の一貫性は保たれる"],
     "note":"読者の差が大きいとき"} ] }
```

3番目が実は最も筋が良い場面が多いです。**セマンティックモデルは1つ、レポートは複数**。これなら数字の定義は統一されたまま、それぞれの読者に最適化した画面を提供できます。T3 で学んだ共有データセットの構成が、ここで効いてきます。

```figure
{ "type":"stack", "title":"1モデル・多レポート構成", "caption":"定義の一貫性と、読者ごとの最適化を両立する",
  "layers":[
    {"label":"レポート層","sub":"経営用 / 部門用 / 現場用 / モバイル用（それぞれ独立）","tone":"pink"},
    {"label":"共有セマンティックモデル","sub":"指標の定義はここ1か所。RLSもここ","tone":"amber"},
    {"label":"データソース","sub":"基幹システム / DWH","tone":"blue"} ] }
```

> [!NOTE] 要点
> 情報設計の目的は「情報を減らすこと」ではなく、**「読者ごとに、その人が決めるために必要な情報だけを届けること」**です。全社で見れば情報は減っていません。宛先ごとに仕分けているだけです。

### 次のレッスンへの橋

ここまでで「誰の何のために作るか」が決まりました。次のレッスンでは、**その情報をどう見せれば人の目と脳に正しく届くか**——可視化の理論に入ります。棒グラフを選ぶか円グラフを選ぶかは、好みの問題ではなく、知覚精度という測定された事実に基づく判断です。
