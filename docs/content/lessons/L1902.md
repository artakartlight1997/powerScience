分析基盤の費用を分解すると、驚くほど多くが**同じデータを何度もコピーすること**に消えています。

基幹システムからDWHへコピー。DWHからデータマートへコピー。データマートからPower BIへインポート。さらに部署が独自にExcelへ抽出。同じ売上明細が、4か所に4つの形で存在します。それぞれに保管費用、更新処理、そして「どれが最新か」という問題が付いてきます。

OneLake の設計思想は、この前提を変えることにあります。

> [!WARN] 執筆時点の情報
> 本レッスンは執筆時点（2026年）の構成を前提としています。機能名や制限は変わりうるため、実装前に公式ドキュメントを確認してください。**「コピーせずに参照する」という設計思想**は変わりません。

## OneLake とは何か

**OneLake は、Fabric テナントに1つだけ存在するデータレイク**です。「OneDrive for data」と説明されます。

```figure
{ "type":"stack", "title":"OneLake の論理構造", "caption":"テナントに1つ。ワークスペースがフォルダー、アイテムがサブフォルダーに対応する",
  "layers":[
    {"label":"ファイル / テーブル","sub":"Delta Parquet 形式のテーブル、または任意形式のファイル","tone":"green"},
    {"label":"アイテム（Lakehouse / Warehouse など）","sub":"サブフォルダーに相当","tone":"amber"},
    {"label":"ワークスペース","sub":"フォルダーに相当","tone":"violet"},
    {"label":"OneLake（テナントに1つ）","sub":"組織全体で共有される単一のストレージ基盤","tone":"blue"} ] }
```

重要な性質が3つあります。

1. **テナントに1つ** — 作成も削除もしない。最初から存在する
2. **すべてのワークロードが同じ場所を読み書きする** — Spark も T-SQL も Power BI も同じファイルを見る
3. **オープンな形式で保存される** — Delta Lake（Parquet）形式。他のツールからも読める

> [!NOTE] 要点
> OneLakeの本質は**「1つの物理コピーを、複数のエンジンから読む」**ことです。従来はエンジンごとにデータを持っていました。SparkにはParquet、SQLにはテーブル、Power BIにはインポート済みのモデル。OneLakeでは、同じDeltaテーブルをすべてが読みます。

## Delta Lake という形式

OneLakeのテーブルは **Delta Lake** 形式で保存されます。これは Parquet ファイル群にトランザクションログを添えたオープンフォーマットです。

```figure
{ "type":"compare", "title":"素のParquetと Delta Lake",
  "panels":[
    {"title":"素の Parquet","tone":"gray",
     "items":["列指向で圧縮が効く","読み取りは速い","更新・削除ができない","書き込み中の読み取りで不整合が起きうる","スキーマの変更履歴がない"],
     "note":"ファイルとしては優秀"},
    {"title":"Delta Lake","tone":"good",
     "items":["Parquet + トランザクションログ","ACIDトランザクションが効く","UPDATE / DELETE / MERGE ができる","読み取りが書き込みに邪魔されない","過去のバージョンを参照できる（time travel）"],
     "note":"データウェアハウス並みの信頼性"} ] }
```

BI担当が知っておくべき実務上の意味は3つです。

| 性質 | 実務での意味 |
|---|---|
| ACIDトランザクション | 更新の途中でレポートを開いても、中途半端なデータが見えない |
| MERGE が使える | 冪等な取り込み（L1703）が自然に書ける |
| time travel | 「先週時点のデータで再計算する」ができる。障害調査に強い |

### V-Order

Fabric では、Delta テーブルの書き込み時に **V-Order** という最適化が適用されます。Power BI のエンジン（VertiPaq）が読みやすい順序と圧縮でParquetを書く仕組みです。

> [!TIP] 実務のコツ
> V-Order は Direct Lake の性能に直結します。既定では有効ですが、**大量書き込みの処理では、書き込み速度を優先して無効化されている場合があります**。Direct Lake で使うテーブルの性能が出ないとき、確認すべき項目の1つです。「書き込みを速くする設定」と「読み取りを速くする設定」はトレードオフの関係にある、と理解しておいてください。

## Lakehouse の構造

**Lakehouse** は、OneLake上にデータを置くためのアイテムです。2つの領域を持ちます。

```figure
{ "type":"pipeline", "title":"Lakehouse の Files と Tables", "caption":"Files は何でも置ける置き場、Tables は構造化された分析対象",
  "nodes":[
    {"id":"src","label":"外部ソース\nCSV / JSON / API","tone":"gray"},
    {"id":"f","label":"Files\n生ファイルの置き場","tone":"cyan"},
    {"id":"nb","label":"Notebook / Dataflow\n変換","tone":"green"},
    {"id":"t","label":"Tables\nDelta テーブル","tone":"amber"},
    {"id":"sql","label":"SQL分析エンドポイント\n読み取り専用T-SQL","tone":"blue"},
    {"id":"sm","label":"セマンティックモデル\nDirect Lake","tone":"violet"}],
  "edges":[
    {"from":"src","to":"f","label":"取り込み"},
    {"from":"f","to":"nb","label":"読む"},
    {"from":"nb","to":"t","label":"書く"},
    {"from":"t","to":"sql","label":"自動で公開"},
    {"from":"t","to":"sm","label":"直接読む"} ] }
```

| 領域 | 何を置くか | アクセス方法 |
|---|---|---|
| Files | CSV、JSON、画像、ログ、任意の形式。ブロンズ層に相当 | Notebook（Spark）、パイプライン |
| Tables | Delta テーブル。シルバー・ゴールド層に相当 | Notebook、SQL分析エンドポイント、Direct Lake |

**SQL分析エンドポイント**は、Lakehouse の Tables に対して自動的に提供される読み取り専用のT-SQLインターフェースです。SQLしか書けない人でも、Lakehouseのデータを読めます。ただし**書き込みはできません**。書き込むにはNotebookかパイプライン、あるいはWarehouseを使います。

> [!TRAP] SQL分析エンドポイントに書き込もうとする
> 「LakehouseにSQLで接続できる」と聞くと、`INSERT` や `UPDATE` ができると思いがちですが、**読み取り専用**です。T-SQLで書き込みたい場合は Warehouse を使います。この違いが、次のレッスンで扱う「LakehouseとWarehouseのどちらを選ぶか」の判断軸の1つになります。

## ショートカット

OneLake の設計思想が最も現れているのが**ショートカット**です。**データを物理的にコピーせず、別の場所のデータを自分のLakehouseの中にあるかのように見せる**機能です。

```figure
{ "type":"compare", "title":"コピーとショートカット",
  "panels":[
    {"title":"コピー（従来）","tone":"bad",
     "items":["データを物理的に複製する","保管費用が二重にかかる","同期の仕組みが必要","同期の遅延と失敗が起きる","どちらが最新か問題が生じる"],
     "note":"コピー元が変わるたびに追従が要る"},
    {"title":"ショートカット","tone":"good",
     "items":["参照するだけ。実体は元の場所","保管費用は元の1か所分","常に元データと一致する","権限は元の場所の設定に従う","作成が数分で終わる"],
     "note":"『まず繋いでみる』が低リスクでできる"} ] }
```

ショートカットで参照できる先は、執筆時点で次のようなものがあります。

| 参照先 | 用途 |
|---|---|
| 他のワークスペースのLakehouse | ドメイン間でのデータ共有 |
| ADLS Gen2 | 既存のAzureデータレイク資産の活用 |
| Amazon S3 / Google Cloud Storage | マルチクラウド環境での統合 |
| 他のFabricアイテム（Warehouse等） | Fabric内での相互参照 |
| Dataverse | 業務アプリのデータを分析基盤に取り込む |

どの参照先でも共通するのは、**実体は元の場所にあり続ける**という点です。参照先の変更・削除は、こちら側の資産を壊します。ショートカットを作った時点で、その参照先の変更管理に依存する関係が生まれる、と理解してください。

> [!TIP] 実務のコツ
> ショートカットは**共有ディメンション（L1702）の配布に非常に有効**です。中央のBIチームが1か所で `Dim_日付` `Dim_組織` `Dim_商品` を管理し、各ドメインのLakehouseからショートカットで参照する。コピーがないので、中央が更新すれば全ドメインに即座に反映されます。「共通マスタは1か所、参照は各所から」という理想形が、追加の同期処理なしに実現できます。

### ショートカットの注意点

```figure
{ "type":"tree", "title":"ショートカットを使う前の確認", "caption":"便利だが万能ではない。特に権限と性能に注意",
  "root":{"label":"ショートカットを作りたい"},
  "children":[
    {"label":"権限はどうなる？","sub":"参照先の権限が効く","tone":"amber",
     "children":[{"label":"→ 参照先に権限がない人は読めない","sub":"「ショートカットを作れば見せられる」ではない"}]},
    {"label":"性能は？","sub":"元の場所の性能とネットワークに依存","tone":"blue",
     "children":[{"label":"→ 別クラウド参照は遅くなりうる","sub":"頻繁に読むならコピーのほうが速い場合もある"}]},
    {"label":"元が消えたら？","sub":"参照が壊れる","tone":"bad",

    {"label":"形式は合う？","sub":"Deltaテーブルとして読めるか","tone":"green",

```

> [!TRAP] ショートカットで権限問題が解決すると思う
> 「あの部署のデータをショートカットで持ってくれば、うちのメンバーが見られる」——これは成立しません。**ショートカットは参照であり、権限の委譲ではありません。**参照先のデータに対する権限がなければ読めません。データを共有したいなら、参照先の権限設定が必要です。この誤解は設計レビューで頻繁に見つかります。

## ミラーリング

**ミラーリング**は、外部データベースの内容をOneLake上にほぼリアルタイムで複製し続ける機能です。ショートカットとは性質が異なります。

```figure
{ "type":"matrix", "title":"ショートカットとミラーリングの使い分け", "xLabel":"参照先の種類", "yLabel":"必要な鮮度",
  "xLow":"オブジェクトストレージ","xHigh":"運用データベース","yLow":"日次で足りる","yHigh":"数分以内",
  "quadrants":[
    {"title":"ショートカット","text":"ADLS / S3 上のファイルを参照。コピーなし。最も軽量。","tone":"good"},
    {"title":"ミラーリング","text":"SQL Database / Cosmos DB などをOneLakeへ継続複製。ソースに負荷をかけずに分析できる。","tone":"violet"},
    {"title":"ショートカット","text":"同上。鮮度要求が低ければ最も安い。","tone":"good"},
    {"title":"ミラーリング","text":"運用DBを直接分析クエリで叩かずに済む。基幹への負荷を避けたい場合の答え。","tone":"amber"} ] }
```

ミラーリングの実務的な価値は、**基幹システムに分析クエリの負荷をかけないこと**です。従来はDirectQueryで基幹を直接叩くか、夜間バッチでコピーするかの2択でした。ミラーリングは第3の選択肢になります。

OneLake上にゴールド層のテーブルを作るとき、Power BI から使うことを前提にした設計上の注意があります。

```figure
{ "type":"cards", "cols":3, "title":"Direct Lake を見据えたテーブル設計", "caption":"ここを外すと、後でモデル側の工夫では取り返せない",
  "items":[
    {"icon":"🔢","title":"キーは整数にする","text":"文字列のサロゲートキーは結合も圧縮も不利。整数に統一する。","tone":"blue"},
    {"icon":"📅","title":"日付列を明示的に持つ","text":"タイムスタンプ1本ではなく、日付列を別に持つ。カーディナリティが桁で変わる。","tone":"green"},
    {"icon":"🧹","title":"不要な列を落としておく","text":"モデル側で非表示にしても、Direct Lakeでは読み込みの対象になりうる。上流で落とす。","tone":"amber"},
    {"icon":"📐","title":"スタースキーマの形で置く","text":"ゴールド層をファクトとディメンションに分けておく。モデル側の作業がほぼ不要になる。","tone":"violet"},

    {"icon":"📄","title":"小さいファイルを作らない","text":"Deltaは小ファイルが増えると読み取りが遅くなる。定期的に最適化する。","tone":"cyan"} ] }
```

最後の項目は運用上とても重要です。Delta テーブルは追記のたびに新しいParquetファイルが増えます。数千個の小さいファイルになると、読み取りのオーバーヘッドが無視できなくなります。**定期的なテーブル最適化（コンパクション）を運用に組み込んでください。**

| 症状 | 疑うこと |
|---|---|
| Direct Lake の初回応答が遅い | 小ファイルの多さ、V-Order未適用 |
| 特定の期間だけ遅い | パーティションの偏り |
| モデルサイズが想定より大きい | 不要列、高カーディナリティ列 |
| 頻繁にDirectQueryへ落ちる | 容量のメモリ上限、非対応の機能 |
| 更新直後だけ遅い | 再フレーミング後の初回読み込み（ウォームアップ前） |
| 一部の列だけ極端に重い | 高カーディナリティの文字列列が残っている |

> データ基盤の設計には「**データ重力（Data Gravity）**」という考え方があります。データは大きくなるほど動かしにくくなり、アプリケーションや処理のほうがデータの近くに引き寄せられる、という比喩です。従来のアーキテクチャは、データをエンジンのところへ運ぶ設計でした。レイクハウスの発想は逆で、**データは1か所に置き、複数のエンジンをそこへ連れてくる**。ショートカットもミラーリングも、この転換の実装です。設計判断として覚えておくべきは、**「このデータを動かす必要が本当にあるか」を常に問う**ことです。多くの場合、答えは「ない」になります。

## time travel を運用に使う

Delta の「過去バージョンを参照できる」性質は、BI運用で具体的に役立ちます。使いどころを挙げます。

> time travel の保持期間には上限があり、また保持期間中は古いファイルが残るためストレージを消費します。**「無制限に過去へ戻れる」わけではありません。**どのテーブルをどれだけ保持するかは、障害調査に必要な期間と保管コストのバランスで決めます。多くの現場では、ゴールド層は数週間、ブロンズ層は再取り込みできるので短め、という設計になります。

> [!NOTE] 覚えておく一文
> **OneLake は「置き場所」であり、Lakehouse は「その上の作業場」である。**この区別が付いていれば、Fabric のドキュメントを読むときに迷いません。


この手順の要点は、**既存基盤に一切変更を加えずに効果を測れる**ことです。ショートカットは参照するだけなので、失敗しても削除すれば元に戻ります。**低リスクで試せることは、必ず試してから判断する。**これは技術選定の基本姿勢です。

> [!TRAP] 検証なしで全面移行を決める
> 製品資料の性能数値は、理想的な条件での測定値です。自組織のデータ（列数、カーディナリティ、更新頻度、クエリの形）で同じ結果が出るとは限りません。**必ず自分のデータで測ってください。**ショートカットを使えば、この検証は数時間で終わります。数時間の検証を惜しんで数か月の移行を決めるのは、最も高くつく判断です。

> [!EXAM] PL-300で問われる
> PL-300 では OneLake の内部構造までは問われませんが、「1.1 データソースへの接続」の文脈で**Lakehouse への接続方法**が問われることがあります。押さえるべきは、(1) Lakehouse の Tables には**SQL分析エンドポイント経由でも Direct Lake でも接続できる**、(2) **ショートカットはデータをコピーしない**、(3) 接続方式の選択は**鮮度・データ量・変換の必要性**で決まる、の3点です。

## 設計チェックリスト

- [ ] OneLake がテナントに1つであり、ワークスペースがフォルダーに対応することを理解した
- [ ] Delta Lake 形式の3つの利点（ACID・MERGE・time travel）を説明できる
- [ ] Lakehouse の Files と Tables の使い分けを決めた
- [ ] SQL分析エンドポイントが読み取り専用であることを踏まえて設計した
- [ ] コピーとショートカットの判断基準を定めた
- [ ] ショートカットが権限の委譲ではないことをチームで共有した
- [ ] 共有ディメンションをショートカットで配布する構成を検討した
- [ ] ミラーリングとショートカットを、鮮度と参照先で使い分けた
- [ ] メダリオンの層ごとにワークスペースを分け、アクセス権を層別に設計した
- [ ] 既存基盤にショートカットを張って、自組織のデータで効果を実測した
- [ ] ゴールド層のテーブルをスタースキーマの形で、整数キー・明示的な日付列で設計した
- [ ] Delta テーブルの定期最適化（小ファイルのコンパクション）を運用に入れた
- [ ] time travel の保持期間を、障害調査の必要期間とコストから決めた
- [ ] 手入力データの投入経路（OneLake file explorer 等）を用意した

## 理解度チェック

1. 同じデータをコピーせずに複数のワークスペースから使いたい場合、どの機能を使うか。またその際、権限について注意すべきことを述べてください。
2. Lakehouse の SQL分析エンドポイントでデータを更新しようとしたところ、できませんでした。理由と、T-SQLで書き込みたい場合の選択肢を説明してください。
3. Delta Lake が素のParquetに対して持つ利点を3つ挙げ、それぞれがBI運用でどう役立つか説明してください。
4. Direct Lake の初回応答が遅いとき、Lakehouse 側で確認すべきことを2つ挙げてください。

> [!NOTE] このレッスンのまとめ
> OneLake はテナントに1つのデータレイクで、すべてのワークロードが同じDeltaテーブルを読む。Lakehouse は Files（任意形式）と Tables（Delta）を持ち、Tables には読み取り専用のSQL分析エンドポイントが自動で付く。ショートカットはコピーせずに参照する仕組みで、共有ディメンションの配布に特に有効だが、権限の委譲ではない。ミラーリングは運用DBを継続複製し、基幹に分析負荷をかけずに済ませる。そして技術選定は、必ず自組織のデータで実測してから決める。
