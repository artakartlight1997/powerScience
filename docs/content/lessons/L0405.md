Power Query エディタは、Power BI で最も時間を過ごすことになる画面です。そしてここで行った作業は**手順として記録され、毎回自動で再現されます。**

この「記録される」という一点が、Excelの手作業との決定的な違いです。今日1時間かけた整形が、来月からは更新ボタン1回になります。M04の締めくくりとして、エディタの基本操作を身につけます。

## ピボット解除 — 最も重要な変換

実務のExcelは、ほぼ必ず**横持ち**（月が列に並ぶ形）で作られています。これは人が読むには良いのですが、分析にはまったく向きません。

```figure
{ "type": "tablediff", "arrowLabel": "ピボット解除（列のピボット解除）",
  "before": {"title":"横持ち（人が読む形）","tone":"bad",
    "head":["商品","1月","2月","3月","4月"],
    "rows":[
      ["ノートPC","120","135","150","142"],
      ["タブレット","80","95","88","91"]]},
  "after": {"title":"縦持ち（機械が扱う形＝整然データ）","tone":"good",
    "head":["商品","月","数量"],
    "rows":[
      ["ノートPC","1月","120"],["ノートPC","2月","135"],
      ["ノートPC","3月","150"],["ノートPC","4月","142"],
      ["タブレット","1月","80"],["タブレット","2月","95"]]} }
```

操作は簡単です。**保持したい列（商品）を選択 → 右クリック →「その他の列のピボット解除」**。「その他の列」を選ぶのがコツで、こうしておけば5月・6月と列が増えても手順が壊れません。

> [!DS] 整然データ（Tidy Data）の3原則
> 統計学者ハドリー・ウィッカムが提唱した**整然データ**の定義は3つの原則からなります。**① 1つの列は1つの変数を表す。② 1つの行は1つの観測を表す。③ 1つの表は1つの観測単位を表す。** 横持ちの表は「1月」「2月」という列が実は「月」という1つの変数の値であるため、原則①に違反しています。整然データにすると、集計・フィルター・可視化のすべてが同じ操作でできるようになります。これはPower BIに限らず、R・Python・SQLのすべてに共通する考え方です。**分析しやすいデータの形には正解がある**という事実は、覚えておく価値があります。

> [!TRAP] 「その他の列のピボット解除」を選ぶ理由
> 単なる「列のピボット解除」で1月〜4月を選ぶと、その4列がステップに固定されます。翌月に5月の列が増えると、その列は変換されず取り残されます。**「その他の列のピボット解除」なら、キー列以外はすべて対象になるため、列が増えても自動的に処理されます。** 実務で壊れないクエリを書くための重要な作法です。

## M言語を読む

すべての操作は **M言語** のコードとして記録されています。書けるようになる必要はありませんが、**読めると原因究明が速くなります。**

```figure
{ "type": "formula", "lang": "m",
  "code": "= Table.SelectRows( 変更された型, each [SalesAmount] > 0 )",
  "parts": [
    {"match":"Table.SelectRows","label":"行を絞り込む関数。フィルター操作がこれになる","tone":"violet"},
    {"match":"変更された型","label":"前のステップの名前。ここが入力になる","tone":"blue"},
    {"match":"each [SalesAmount] > 0","label":"各行に適用する条件式","tone":"amber"} ] }
```

M言語には3つの特徴があります。**① 大文字小文字を厳密に区別する**（`Table.SelectRows` を `table.selectrows` と書くとエラー）。**② 各ステップが前のステップを入力として受け取る**。**③ `let 〜 in` という構造で全体が1つの式になっている**。

```figure
{ "type": "formula", "lang": "m",
  "code": "let ソース = Csv.Document(...), 型変更 = Table.TransformColumnTypes(ソース,...) in 型変更",
  "parts": [
    {"match":"let","label":"ここからステップの定義が始まる","tone":"green"},
    {"match":"ソース = Csv.Document(...)","label":"最初のステップ。変数名＝ステップ名","tone":"blue"},
    {"match":"Table.TransformColumnTypes(ソース,...)","label":"前のステップ「ソース」を入力にしている","tone":"amber"},
    {"match":"in 型変更","label":"最終的に返すステップを指定する","tone":"violet"} ] }
```

コード全体は**ホーム → 詳細エディタ**で確認できます。ステップを削除したときにエラーが出る理由も、このコードを見れば分かります。後続のステップが、削除したステップの名前を参照しているからです。

> 大きなデータでは「閉じて適用」に数分かかることがあります。この間、全ステップが実際に実行されています。**エディタ上のプレビューは一部の行だけを処理した結果**であり、適用時に初めて全行が処理されます。プレビューでは出なかったエラーが適用時に出るのは、このためです。

> データ分析の実務では、**作業時間の6〜8割が前処理**に費やされると言われます。モデルを作る時間より、データを使える形にする時間のほうがはるかに長いのです。そしてこの前処理は、分析結果の正しさを決定づけます。どんな高度な手法も、間違って整形されたデータの上では意味を持ちません。**前処理を「作業」ではなく「記録すべき手順」として扱う**こと。Power Query の適用したステップは、その思想を体現した機能です。同じ発想が、SQLのビュー、Pythonのスクリプト、dbtのモデルなど、あらゆるデータ基盤に共通しています。

## まとめ

- 適用したステップは手順の記録。順序に意味があり、後から編集・並べ替えができる
- ステップ名は「なぜそうしたか」が分かる名前に変える。将来の自分と同僚のため
- 基本の変換8つ（列削除・行フィルター・ヘッダー昇格・値の置換・列の分割・列の追加・グループ化・ピボット解除）で実務の7割をカバーできる
- 横持ちは「その他の列のピボット解除」で縦持ちにする。列が増えても壊れない
- 整然データの3原則（1列1変数・1行1観測・1表1観測単位）が、扱いやすいデータの定義
- M言語は読めれば十分。大文字小文字を区別し、各ステップが前のステップを参照する
- 参照は連動、複製は独立。共通処理は参照でまとめ、中間クエリは読み込みを無効にする
- **削る操作を先に、増やす操作を後に。** フォールディングを維持すると更新が速い
- 前処理を「記録すべき手順」として扱うことが、再現可能な分析の土台になる
