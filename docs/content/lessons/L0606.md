## 書式を設定する

書式はモデル側で設定します。ビジュアルごとに設定すると、作るたびに設定し直すことになります。

| 対象 | 書式 | 設定例 |
|---|---|---|
| 売上金額 | 通貨または10進数 | `¥#,0` / 小数点以下0桁 |
| 数量 | 整数 | 桁区切りあり |
| 割引率 | パーセンテージ | 小数点以下1桁 |
| 日付 | 短い日付 | `yyyy/MM/dd` |
| 構成比のメジャー | パーセンテージ | 小数点以下1桁 |

> [!TIP]
> 金額の桁が大きいと、`12,400,000` のような数字が並んで読みにくくなります。カスタム書式 `#,0,,"百万"` を使うと `12百万` と表示できます（カンマ2つで百万単位に丸める指定です）。**書式は「正確さ」ではなく「読みやすさ」のための設定**なので、意思決定に必要な桁数まで落として構いません。

## データカテゴリを設定する

列に「これは地理情報である」「これはURLである」と教えると、Power BI の挙動が変わります。

| データカテゴリ | 設定する列 | 効果 |
|---|---|---|
| 都道府県 / 市区町村 | `Prefecture` | マップビジュアルが正しい場所を表示する |
| Web URL | 商品ページのURL | クリック可能なリンクになる |
| 画像 URL | 商品画像のURL | テーブルに画像が表示される |
| 電子メールアドレス | `ManagerEmail` | メールリンクとして扱われる |
| バーコード | 商品コード | 対応ビジュアルで利用できる |

> [!TRAP]
> 地理データのカテゴリを設定しないと、マップが「東京都」を海外の別の地名として解釈することがあります。とくに「一般的な地名」に見える文字列で誤認識が起きます。**マップを使うなら、都道府県・国・市区町村のカテゴリ設定は必須**だと考えてください。

## 命名規則

| 対象 | 規則 | 例 |
|---|---|---|
| ファクトテーブル | `Fact_` + 業務プロセス | `Fact_売上`、`Fact_在庫` |
| ディメンション | `Dim_` + 対象 | `Dim_商品`、`Dim_日付` |
| 列 | 業務の言葉。単数形 | `カテゴリ`、`都道府県` |
| メジャー | 何を表すかを名詞で | `売上合計`、`粗利率`、`前年同月比` |
| 内部用テーブル | `_` で始める | `_メジャー`、`_パラメーター` |

> [!DS]
> 整えられたモデルは、データ活用の文脈で **セマンティックレイヤー（意味の層）** と呼ばれます。生のデータベースの列名（`SLS_AMT_JPY`）を、業務の言葉（`売上金額`）に翻訳し、指標の定義（`粗利率 = 粗利 ÷ 売上`）を1箇所に集約する層です。この層があると、部署ごとに違う「売上」の定義が乱立する事態を防げます。組織のデータ活用が成熟するかどうかは、ダッシュボードの数ではなく、**指標の定義が1箇所に集約されているか**で決まります。Power BI のセマンティックモデルは、まさにその集約点です。書式や説明を整える作業は、見た目の話ではなく、組織の共通言語を整える作業だと理解してください。

> [!EXAM]
> PL-300 では、(1)「月が正しい順序で並ばない。どうするか」→ **列で並べ替え**、(2)「マップが正しい場所を表示しない」→ **データカテゴリの設定**、(3)「利用者に不要な列を見せたくない」→ **非表示**、(4)「ドリルダウンできるようにしたい」→ **階層の作成**、という4パターンが繰り返し出題されます。いずれもモデルビュー／テーブルビューでの設定であり、ビジュアル側の設定ではない点が問われます。

## モデルサイズを仕上げで減らす

磨く工程は、性能改善の最後の機会でもあります。不要なものを落とすだけで、モデルは目に見えて軽くなります。

```figure
{ "type": "chart", "kind": "hbar", "title": "仕上げで効く削減策（効果の目安）",
  "categories": ["伝票番号など一意な列の削除", "日時列を日付に丸める", "使わない列の一括削除", "小数点以下の桁数を減らす", "行数を1割減らす"],
  "series": [{"name": "サイズ削減効果", "values": [35, 22, 18, 9, 3], "tone": "blue"}],
  "highlight": 0, "unit": "%" }
```

効果の大小は、**その列に何種類の値があるか（カーディナリティ）**でほぼ決まります。一意に近い列は圧縮がまったく効かないため、削除の効果が最も大きくなります。逆に、カテゴリのように値の種類が少ない列は、削除してもサイズはほとんど変わりません。

| 施策 | 具体的な操作 |
|---|---|
| 使わない列を削除 | Power Query の「他の列の削除」で残す列を指定する |
| 日時を分割 | 日付列と時刻列に分け、時刻が不要なら落とす |
| 小数の精度を落とす | 金額を整数に、率を小数2桁に丸める |
| 高カーディナリティ列を隠すのではなく消す | 非表示にしてもサイズは減らない |

> [!WARN]
> **列を非表示にしてもモデルサイズは1バイトも減りません。** 非表示は利用者向けの整理であって、性能施策ではありません。サイズを減らしたいなら、Power Query の段階で列そのものを削除する必要があります。この2つを混同すると、「整理したのに軽くならない」という結果になります。

## よくあるエラーと対処

| 症状 | 原因 | 対処 |
|---|---|---|
| 月が文字コード順に並ぶ | 並べ替え列が未設定 | 列で並べ替えに月番号を指定する |
| 「複数の値が含まれています」エラー | 並べ替え列が1対1でない | 対応関係を確認し、粒度の合う番号列を作る |
| 循環依存のエラーが出る | 2つの列が互いを並べ替え列にしている | 片方の設定を解除する |
| 階層に列が追加できない | 別テーブルの列を入れようとしている | 階層はテーブル内で完結させる。属性の配置を見直す |
| マップが海外を指す | データカテゴリが未設定 | 都道府県などのカテゴリを設定する |
| 列を隠したら階層から消えた | 階層の構成列を非表示にした | 階層で使う列は表示のままにする |
| 数値の書式がビジュアルごとに違う | ビジュアル側で個別設定している | モデル側で書式を設定し直す |
| 同じ指標のメジャーが複数ある | 定義が集約されていない | 正のメジャーを1つ決め、他を削除して説明を付ける |
