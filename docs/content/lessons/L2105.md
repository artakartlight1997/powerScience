## ユーザビリティテスト — 3人で十分

本格的な調査は不要です。**想定利用者3〜5人**に実際に触ってもらえば、重大な問題の大半が見つかります。

```figure
{ "type":"steps", "title":"思考発話法によるテスト（1人20分）", "caption":"「どう思いますか」ではなく「やってみてください」と頼む",
  "items":[
    {"title":"1. タスクを与える","text":"「先月、最も粗利率が低かった営業所を調べてください」と具体的な作業を依頼する","tone":"blue"},
    {"title":"2. 考えていることを声に出してもらう","text":"「今、何を探していますか」と促す。沈黙は迷いのサイン","tone":"green"},
    {"title":"3. 助けない","text":"詰まっても教えない。詰まった箇所こそが設計の欠陥","tone":"amber"},
    {"title":"4. 時間と誤りを記録する","text":"完了までの秒数、誤ったクリック、諦めた箇所を記録","tone":"violet"},
    {"title":"5. 最後に感想を聞く","text":"順序が逆にならないこと。先に感想を聞くと行動が変わる","tone":"pink"} ] }
```

> [!DS] データサイエンス視点：なぜ5人で足りるのか
> ユーザビリティ工学では、**5人のテストで問題の約8割が発見される**という経験則が知られています（Nielsen）。理由は単純で、重大な問題ほど多くの人が遭遇するためです。10人、20人と増やしても、同じ問題を繰り返し確認するだけで新しい発見は逓減します。**5人テストして直し、また5人テストする**方が、20人に一度テストするより効率的です。これは A/Bテストのような定量評価とは目的が異なります。定性テストは「なぜ詰まるか」を、定量テストは「どちらが良いか」を答えます。両方が必要です。

> [!TRAP] つまずきポイント
> **指標の定義変更を黙って実施する**のは、BIで最も信頼を失う行為です。先月「粗利率 32%」だった数字が、今月同じ期間を見たら「29%」になっていたら、利用者は全ての数字を疑い始めます。定義変更は必ず、(1) 事前告知、(2) 変更日の明示、(3) 過去数値の扱いの説明、(4) 新旧の差異の提示、の4点をセットで行ってください。

適用日: 2026年5月1日の更新分から
過去分の扱い: 2025年4月分まで遡って再計算します
影響: 粗利率は概ね +2.5pt 程度、見かけ上上昇します
   （例：4月実績 旧定義 29.4% → 新定義 31.9%）
問い合わせ先: BI推進チーム（担当: ______）
```

    {"from":"a","to":"d","label":""},
    {"from":"b","to":"d","label":""},
    {"from":"c","to":"d","label":""},
    {"from":"d","to":"e","label":"閾値を超えたら通知"} ] }
```

| 監視項目 | 閾値の例 | 検知したときの行動 |
|---|---|---|
| 90日間の閲覧ゼロ | 0人 | 所有者に継続要否を確認、アーカイブ候補に |
| 更新失敗の連続 | 2日連続 | 即時調査。利用者へ状況を通知 |

| 認定レポートの重複 | 同名2件以上 | どちらが正かを確定し、片方を廃止 |

> [!NOTE] 要点
> **更新が止まっても誰も気づかないレポート**が、組織で最も危険な資産です。古い数字が正しい数字として使われ、誤った意思決定を生みます。「更新失敗を検知して通知する」仕組みは、どんな機能追加よりも優先して作るべきものです。

### レビュー文化を根づかせる

最後に、仕組みより難しい話をします。レビューは、指摘される側にとって気持ちの良いものではありません。文化として定着させるには工夫が要ります。

| やること | 理由 |
|---|---|
| レビュー対象を「人」でなく「レポート」と呼ぶ | 人格ではなく成果物への指摘だと明確にする |
| 指摘は必ず原則と根拠を添える | 「好みです」を排除し、学習の機会に変える |
| 良かった点も1つは挙げる | 続けるべき設計が共有される |
| 全員が同じチェックリストを使う | 属人的な基準を排除する |
| リーダーが自分のレポートを最初にレビューさせる | 心理的安全性は、上から順に作られる |

## 理解度チェック

1. 公開3週間後に閲覧数が急落したレポートについて、原因を特定するために取る行動を、順序をつけて3つ挙げてください。
2. ユーザビリティテストで「作成者が説明してはいけない」理由を説明してください。
3. 「この表に列を5本追加してほしい」という要望を受けました。そのまま実装する前に確認すべきことと、想定される代替案を2つ述べてください。
