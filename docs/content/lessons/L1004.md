会議で 3 つの部署がそれぞれ「今期の売上」を出し、3 つとも違う数字だった — この光景は、BI が普及した組織で必ず一度は起きます。

原因はデータではなく、**モデルが分裂していること**です。部署ごとに自分の pbix を作れば、売上の定義も、除外条件も、税の扱いも少しずつ違います。このレッスンでは、モデルを 1 つに集約して共有資産にする方法を扱います。

```figure
{ "type":"compare", "title":"メジャーをどこに書くか",
  "caption":"レポート側のローカルメジャーは便利だが、定義分裂の入口になる",
  "panels":[
    {"title":"レポートごとにメジャーを書く","tone":"bad",
     "items":["同じ『売上合計』が5つのレポートに別々に存在する","1つを直しても他は古いまま","レポート作成者ごとに解釈が入る"],
     "note":"数字が合わなくなる"},
    {"title":"共有モデルにメジャーを集約","tone":"good",
     "items":["定義は1か所。全レポートが同じ結果になる","修正すると全レポートに即反映される","説明文（description）を付ければ利用者が意味を確認できる"],

```

```text
// モデル側に置くメジャー（説明文も必ず付ける）
売上合計 =
SUM( Fact_売上[売上金額] )
-- 説明：返品を含む税抜の売上。計上基準は出荷日。

売上合計_返品除外 =
CALCULATE( [売上合計], Fact_売上[取引種別] <> "返品" )
-- 説明：返品を除いた売上。経営会議の標準指標。
```

> [!DS] データサイエンス視点：単一の真実の源とメトリクス層
> 「同じ指標が組織内で 1 つの定義しか持たない」状態を **単一の真実の源（single source of truth）** と呼びます。データ基盤の議論では長く目標とされてきた概念ですが、実際に難しいのはデータの一元化ではなく**定義の一元化**です。売上、稼働率、アクティブユーザー数 — これらは技術的な計算式である前に、業務上の合意です。
>
> 近年のデータ基盤では、この合意を保持する層を **メトリクス層（metrics layer / semantic layer）** と呼び、独立したコンポーネントとして設計します。Power BI のセマンティックモデルは、まさにこのメトリクス層に相当します。レポートを増やすのは自由でよく、**増やしてはいけないのはメトリクス層**である、という原則は、ツールを問わず成立します。

「モデルが増えすぎている」は感覚ではなく、測れます。


集約作業でやることは単純です。**同じソースを参照し、同じ粒度のモデル**を洗い出し、機能の和集合を持つ 1 つのモデルに統合します。統合したら旧モデルを削除し、レポートを新モデルへ接続し直します。

> [!TIP] 実務のコツ
> 洗い出しには**系列（リネージ）ビュー**が使えます。ワークスペースの表示を系列ビューに切り替えると、データソース → モデル → レポート → アプリ の依存関係が図で表示されます。同じデータソースから複数のモデルが伸びていれば、それが集約の候補です。

## 理解度チェック

1. 部署ごとに独自の pbix で「売上」を集計しており、会議で数字が食い違う。この状況を解消する構成を述べ、各部署のレポート作成者が失う自由と得る利点を説明せよ。
2. ライブ接続したレポートで「取得データに独自の分類列を足したい」と言われた。どう対応すべきか。
3. 認定済みモデルの制度を導入したが、3 年後に「認定済みだが更新が止まっているモデル」が増えた。制度設計に何が欠けていたか。

<details>
<summary>解答の要点</summary>

1. 構成：**共有セマンティックモデルを 1 つ作り、各部署はライブ接続でレポートだけを作る**。売上のメジャー定義はモデル側に集約し、説明文を付ける。失う自由は、Power Query による独自のデータ変換・テーブル追加ができないこと、そして自分に都合のよい売上定義を作れないこと。得る利点は、数字が組織全体で一致すること、モデリングの知識がなくてもレポートが作れること、更新が 1 回で済みソース負荷も減ること、定義の修正が全レポートへ即座に波及すること。
2. 原則は**モデル側で対応する**。共有モデルのディメンションに分類列を追加し、全レポートで使えるようにする。その分類がその部署固有で他部署には無意味な場合でも、非表示や表示フォルダーで整理すれば共存できる。どうしてもモデルに入れられない場合は複合モデル（DirectQuery for Power BI semantic models）でローカルテーブルを結合する手があるが、定義分裂とパフォーマンス劣化のリスクがあるため最終手段とする。
3. 欠けていたのは「**認定を外す運用**」と「**定期的な再確認**」。認定を付与するプロセスだけを作り、有効期限や責任者の在籍確認を制度化していなかった。対策は、年 1 回の再確認（責任者の在籍・更新の稼働・利用実績）を運用カレンダーに組み込み、条件を満たさないモデルの認定を外すこと。使用状況メトリクス（L1005）で利用ゼロのモデルを機械的に洗い出せる。

</details>

- [ ] メジャーの定義をモデル側に集約した（レポートローカルを乱用していない）
- [ ] 主要メジャーに説明文を書いた
- [ ] 列名を業務の言葉にし、作業列を非表示にした
- [ ] モデルの説明欄に用途・粒度・更新頻度・責任者・制約を書いた
- [ ] ビルド権限を渡す前に RLS を検証した

- [ ] 系列（リネージ）ビューで重複モデルの候補を確認した
- [ ] モデルの責任者を明記し、変更ワークフローを決めた
