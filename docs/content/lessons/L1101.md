GUIのボタンだけでPower Queryを使っていると、あるところで必ず壁に当たります。「この変換、ボタンにない」「他人が作ったクエリが何をしているか読めない」「更新が失敗するが、どのステップが原因か分からない」。この壁の向こう側にあるのが **M言語** です。

M言語は、Power Query が内部で使っている変換言語です。GUIで押したボタンは、すべてMのコードに翻訳されて保存されています。つまりあなたはすでにMを書いてきました。読めないだけです。

このレッスンでは、Mの構造そのものを扱います。関数を丸暗記するのではなく、**「どういう文法の言語か」** を掴むことが目的です。文法さえ掴めば、あとは関数リファレンスを引きながら書けるようになります。

## GUI操作とMコードは1対1で対応している

まず、いま自分が書いているものを見ます。Power Query エディターの「ホーム」→「詳細エディター」を開いてください。適用したステップの一覧が、そのままコードになっています。

## let ... in — Mの心臓部

典型的なクエリは、次の形をしています。

```m
let
    ソース = Csv.Document(File.Contents("C:\data\sales.csv"), [Delimiter=",", Encoding=65001]),
    昇格されたヘッダー数 = Table.PromoteHeaders(ソース, [PromoteAllScalars=true]),
    変更された型 = Table.TransformColumnTypes(昇格されたヘッダー数, {{"売上日", type date}, {"金額", Int64.Type}}),
    フィルターされた行 = Table.SelectRows(変更された型, each [金額] > 0)
in
    フィルターされた行
```

この形を分解します。

```figure
{ "type":"formula", "lang":"m",
  "title":"let 式の構造",
  "caption":"let のあとに名前付きの計算をいくつも並べ、in のあとに「最終的に返す1つの値」を書く",
  "code":"let ステップ名1 = 式1, ステップ名2 = 式2 in 返す値",
  "parts":[
    {"match":"let","label":"ここから名前付きの計算を並べる宣言","tone":"violet"},
    {"match":"ステップ名1 = 式1","label":"1つ目の中間結果に名前をつける","tone":"blue"},
    {"match":"ステップ名2 = 式2","label":"前のステップを参照して次を作る","tone":"cyan"},
    {"match":"in","label":"ここから先が「このクエリの答え」","tone":"amber"},
    {"match":"返す値","label":"通常は最後のステップ名。1つの値しか返せない","tone":"green"}
  ] }
```

押さえるべき点は4つです。

1. **ステップは変数である。** `変更された型` は「変数名」であり、その中身は1つのテーブルです。
2. **各ステップは前のステップを引数として受け取る。** 引数に何を書くかで、参照するステップを変えられます。
3. **`in` の後に書いた値だけが、クエリの結果になる。** 途中のステップは中間結果です。
4. **カンマ区切り、最後のステップの後にカンマは付けない。** ここが構文エラーの最多発地点です。

> [!TRAP] つまずきポイント
> ステップを削除したとき、次のステップは削除された名前を参照したままになり「ステップ 'xxx' が見つかりません」というエラーになります。GUIの「×」で削除すると自動で繋ぎ直してくれることが多いのですが、繋ぎ直せない場合（列参照が消える等）は手で直す必要があります。**エラーメッセージに出るステップ名でコード内を検索する**のが最短ルートです。

## 順番は「上から下」ではなく「依存関係」で決まる

Mは宣言型に近い言語です。ステップは書いた順に実行されるのではなく、**`in` で要求された値から逆にたどって、必要なものだけが評価されます**（遅延評価）。

```figure
{ "type":"pipeline", "title":"評価は in から逆向きにたどられる",
  "caption":"どこからも参照されないステップは評価されない。これがMの遅延評価",
  "nodes":[
    {"id":"s","label":"ソース","tone":"blue"},
    {"id":"h","label":"ヘッダー昇格","tone":"cyan"},
    {"id":"t","label":"型変更","tone":"green"},
    {"id":"f","label":"行フィルター","tone":"amber"},
    {"id":"x","label":"使われない\n中間ステップ","tone":"gray"},
    {"id":"o","label":"in（結果）","tone":"violet"}
  ],
  "edges":[
    {"from":"s","to":"h"},
    {"from":"h","to":"t"},
    {"from":"t","to":"f"},
    {"from":"f","to":"o","label":"ここが要求される"},
    {"from":"h","to":"x","label":"参照されないので評価されない"}
  ] }
```

> [!DS] データサイエンス視点
> 手続き型（Pythonのスクリプトのように上から順に実行）と宣言型（結果から必要な計算を逆算）の違いです。SQLも宣言型で、「どう計算するか」ではなく「何が欲しいか」を書きます。Mが宣言型に寄っていることは、後で学ぶ**クエリ フォールディング**（Mの式をSQLに翻訳してデータソース側で実行させる仕組み）が成立する理由でもあります。式が「手順」ではなく「意味」で書かれているから、別の言語に翻訳できるのです。

## 識別子とクォート記法 `#"..."`

Mの変数名（識別子）に空白や記号を含めたいときは、`#"..."` で囲みます。

```m
let
    ソース = Excel.Workbook(File.Contents("C:\data\売上.xlsx"), null, true),
    #"売上 Sheet" = ソース{[Item="売上",Kind="Sheet"]}[Data],
    #"昇格されたヘッダー" = Table.PromoteHeaders(#"売上 Sheet", [PromoteAllScalars=true])
in
    #"昇格されたヘッダー"
```

GUIが生成するステップ名は日本語で空白を含むことが多いため、`#"変更された型"` のような形が大量に出てきます。**`#"` は特別な意味を持つ記号ではなく、単に「ここから識別子です」という囲みです**。読むときは中身だけ見れば十分です。

> [!TIP] 実務のコツ
> ステップ名は英数字のみの短い名前に付け替えると、コードが劇的に読みやすくなります。`Src`, `Head`, `Typed`, `Filtered` のような命名にしておくと、詳細エディターでの編集速度が上がります。名前の変更は「適用したステップ」で右クリック→名前の変更で行えば、参照も自動で追随します。

## Mが扱う値の種類

Mの値は数種類しかありません。ここを押さえると、「なぜこの関数はこれを返すのか」が読めるようになります。

```figure
{ "type":"cards", "cols":3, "title":"Mの主な値の型",
  "caption":"テーブルは「レコードのリスト」。この入れ子構造が Power Query の柔軟さの正体",
  "items":[
    {"icon":"📋","title":"リスト list","text":"順序のある値の並び。{1, 2, 3} と書く。0始まりの位置で {0} のように取り出す","tone":"blue"},
    {"icon":"🗂","title":"レコード record","text":"項目名と値の組。[名前=\"佐藤\", 年齢=30] と書く。[名前] で取り出す","tone":"green"},
    {"icon":"▦","title":"テーブル table","text":"同じ項目名を持つレコードのリスト。行と列に見えているもの","tone":"violet"},
    {"icon":"🔤","title":"プリミティブ","text":"text / number / date / datetime / logical / duration / binary","tone":"cyan"},
    {"icon":"⚙","title":"関数 function","text":"(x) => x * 2 のような値。変数に入れて渡せる","tone":"amber"},

```

取り出し方の記号は3つだけ覚えます。

| 記号 | 対象 | 例 | 結果 |
|---|---|---|---|
| `{ }` | リスト・テーブルの**行** | `ソース{0}` | 先頭行（レコード） |
| `[ ]` | レコードの**項目** | `行[金額]` | その項目の値 |
| `{[ ]}` | 条件に合う行の抽出 | `ソース{[Item="売上"]}` | 条件に一致するレコード |

```m
// Excelブックから「売上」シートのデータだけ取り出す典型パターン
let
    Book = Excel.Workbook(File.Contents("C:\data\売上.xlsx"), null, true),
    // {[...]} で Item が "売上" かつ Kind が "Sheet" の行を1件取り、その [Data] 列を取り出す
    Sheet = Book{[Item="売上", Kind="Sheet"]}[Data]
in
    Sheet
```

## `each` と `_` は省略記法である

`Table.SelectRows(前ステップ, each [金額] > 0)` の `each` に戸惑う人は多いのですが、正体は単純です。

```figure
{ "type":"compare", "title":"each は「1引数の無名関数」の略記",
  "caption":"どちらも同じ動作。each は _ を省略できるだけ",
  "panels":[
    {"title":"略記（GUIが生成する形）","tone":"neutral",
     "items":[
       "each [金額] > 0",
       "each _[金額] > 0",
       "_ は「いま処理している1行のレコード」",
       "_ が1つだけなら省略できる"
     ],"note":"読みやすいが、入れ子になると _ がどれを指すか曖昧になる"},
    {"title":"明示形（自分で書くならこちら）","tone":"good",
     "items":[
       "(row) => row[金額] > 0",
       "引数に名前がつくので入れ子でも迷わない",
       "2つのテーブルを入れ子で扱うときは必須",
       "他人が読んだときに意図が伝わる"
     ],"note":"入れ子の each で詰まったら、こう書き換えると解決する"}
  ] }
```

```m
// 同じ処理を3通りで書く
let
    T = #table({"商品","金額"}, {{"A", 100}, {"B", -50}, {"C", 300}}),
    方法1 = Table.SelectRows(T, each [金額] > 0),
    方法2 = Table.SelectRows(T, each _[金額] > 0),
    方法3 = Table.SelectRows(T, (row) => row[金額] > 0)
in
    方法3
```

> [!TRAP] つまずきポイント
> `Table.AddColumn` の中でさらに `Table.SelectRows` を呼ぶと、内側の `_` が内側の行を指すため、外側の行の値が参照できなくなります。**入れ子になった瞬間に `each` をやめて `(outer) => ...` と名前を付ける**のが唯一の確実な解決策です。以下は「各行について、日付が自分以下の行の金額を合計する（累計）」の例です。

```m
let
    T = #table(type table[日付=date, 金額=number],
        {{#date(2026,1,1), 100}, {#date(2026,1,2), 200}, {#date(2026,1,3), 50}}),
    // (outer) と名前を付けたので、内側の each と混ざらない
    累計付き = Table.AddColumn(T, "累計", (outer) =>
        List.Sum(
            Table.SelectRows(T, each [日付] <= outer[日付])[金額]
        ), type number)
in
    累計付き
```

## 型を明示する — `type` と `Table.TransformColumnTypes`

Mは動的に型を推論しますが、**推論に任せると更新のたびに型が変わり、リレーションシップやDAXが壊れます**。列の型は必ず明示してください。

```m
let
    ソース = Csv.Document(File.Contents("C:\data\sales.csv"), [Delimiter=",", Encoding=65001, QuoteStyle=QuoteStyle.Csv]),
    Head = Table.PromoteHeaders(ソース, [PromoteAllScalars=true]),
    Typed = Table.TransformColumnTypes(Head, {
        {"売上日", type date},
        {"顧客ID", type text},
        {"数量", Int64.Type},
        {"金額", Currency.Type}
    })
in
    Typed
```

| 書き方 | 意味 | 使いどころ |
|---|---|---|
| `type text` | テキスト | ID・コードは必ずテキストに |
| `Int64.Type` | 64ビット整数 | 数量・件数 |
| `Currency.Type` | 固定小数点（10進4桁） | 金額。丸め誤差を避けたいとき |
| `type number` | 倍精度浮動小数点 | 比率・単価 |
| `type date` / `type datetime` | 日付 / 日時 | 時刻が不要なら date にする |

> [!WARN] 注意
> `type number` は浮動小数点なので、金額の合計で 0.000000001 のような誤差が出ることがあります。**金額列は `Currency.Type`（固定小数点数）** を使ってください。Power BI 側では「固定小数点数」と表示されます。

## エラーは値である — `try ... otherwise`

Mでは、変換に失敗したセルに **error という値** が入ります。行は消えず、その位置にエラーが残ります。

```figure
{ "type":"tablediff", "arrowLabel":"try ... otherwise で受け止める",
  "title":"エラー行を消さずに記録する",
  "caption":"エラーを黙って除去すると、データが減ったことに誰も気づかない。理由を列に残す",
  "before":{"title":"型変換に失敗した状態","tone":"bad",
    "head":["伝票番号","金額","変換後金額"],
    "rows":[["A-001","1200","1200"],["A-002","!不明","!Error"],["A-003","950","950"]]},
  "after":{"title":"エラー内容を列に退避","tone":"good",
    "head":["伝票番号","金額","変換後金額","エラー理由"],
    "rows":[["A-001","1200","1200",""],["A-002","不明","!null","!DataFormat.Error: 数値に変換できません"],["A-003","950","950",""]]} }
```

```m
let
    T = #table({"伝票番号","金額"}, {{"A-001","1200"},{"A-002","不明"},{"A-003","950"}}),
    // try は「成功したか」を持つレコード [HasError, Value, Error] を返す
    試行 = Table.AddColumn(T, "試行", each try Number.From([金額])),
    金額列 = Table.AddColumn(試行, "変換後金額", each if [試行][HasError] then null else [試行][Value], type number),
    理由列 = Table.AddColumn(金額列, "エラー理由", each if [試行][HasError] then [試行][Error][Message] else null, type text),
    整理 = Table.RemoveColumns(理由列, {"試行"})
in
    整理
```

短く書きたい場合は `try ... otherwise` を使います。

```m
// 失敗したら 0 にする（ただし「なぜ失敗したか」は失われる）
Table.AddColumn(T, "金額", each try Number.From([金額]) otherwise 0, type number)
```

> [!TRAP] つまずきポイント
> `try ... otherwise 0` は便利ですが、**「変換できなかった行」と「本当に0円だった行」が区別できなくなります**。実務では `otherwise null` にして、後段で「null が何件あるか」を必ずチェックしてください。エラーを握りつぶした結果、合計が毎月少しずつ減っていくのに誰も気づかない、という事故は珍しくありません。

## クエリ同士を参照する

1つの巨大なクエリを書くより、小さなクエリに分けて参照し合うほうが保守できます。他のクエリは**クエリ名をそのまま識別子として書く**だけで参照できます。

```m
// クエリ名: 売上明細
let
    Src = Sql.Database("srv01", "SalesDW"),
    T = Src{[Schema="dbo", Item="FactSales"]}[Data]
in
    T

// クエリ名: 当年売上（上のクエリを参照）
let
    Base = 売上明細,
    当年 = Table.SelectRows(Base, each Date.Year([売上日]) = Date.Year(DateTime.LocalNow()))
in
    当年
```

## 手でステップを書き足す練習

GUIにないことをやるときの手順です。ここでは「列名の先頭と末尾の空白を、全列まとめて除去する」を書きます。GUIには「選択した列のトリミング」しかなく、**列名**のトリミングはボタンがありません。

```figure
{ "type":"steps", "title":"Mを手書きするときの型",
  "caption":"いきなり完成形を書かない。前ステップ名を確認し、1ステップずつ足して結果を見る",
  "items":[
    {"title":"直前のステップ名を確認する","text":"詳細エディターを開き、最後のステップ名を控える（例：変更された型）","tone":"blue"},
    {"title":"新しい行を追加してカンマを打つ","text":"直前の行の末尾にカンマを付け、新しい行に「新ステップ名 = 」を書く","tone":"cyan"},
    {"title":"前ステップを第1引数に渡す","text":"Table.XXX(変更された型, ...) の形にする。ここが依存関係の宣言になる","tone":"green"},
    {"title":"in の値を新ステップ名に変える","text":"最後の行を書き換え忘れると、追加したステップは評価されない","tone":"amber"},
    {"title":"プレビューで確認し、名前を整える","text":"意図した結果になったらステップ名を分かりやすい名前に変更する","tone":"violet"}
  ] }
```

```m
let
    Src = Csv.Document(File.Contents("C:\data\sales.csv"), [Delimiter=",", Encoding=65001]),
    Head = Table.PromoteHeaders(Src, [PromoteAllScalars=true]),
    Typed = Table.TransformColumnTypes(Head, {{"売上日", type date}, {"金額", Currency.Type}}),
    // ここから手書き：列名をすべてトリムする
    列名リスト = Table.ColumnNames(Typed),
    リネーム対応表 = List.Transform(列名リスト, (c) => {c, Text.Trim(c)}),
    列名トリム済み = Table.RenameColumns(Typed, リネーム対応表)
in
    列名トリム済み
```

`List.Transform` は「リストの各要素に関数を適用して新しいリストを作る」関数です。ここでは列名のリストから `{元の名前, 新しい名前}` のペアのリストを作り、`Table.RenameColumns` に渡しています。**「リストを作って関数に渡す」がMの基本形**で、この形を覚えると多くの一括処理が書けます。

> [!EXAM] PL-300で問われる
> PL-300では、詳細エディターのコードを見せて「このクエリは何をしているか」「エラーの原因はどのステップか」を問う問題が出ます。全関数の暗記は不要ですが、**`let ... in` の構造、ステップ間の参照、`each` の意味、`Table.SelectRows` / `Table.AddColumn` / `Table.TransformColumnTypes` / `Table.PromoteHeaders` の役割**は読めるようにしておいてください。

## デバッグの実務テクニック

| 症状 | 確認する場所 | 対処 |
|---|---|---|
| 「トークン 'in' が必要です」 | 直前の行の末尾カンマ | カンマの過不足を直す |
| 「ステップ 'xxx' が見つかりません」 | 参照しているステップ名 | 削除・改名されたステップを特定して繋ぎ直す |
| 「列 'xxx' が見つかりません」 | ソース側の列名変更 | 列名をハードコードしている箇所を可変にする |
| プレビューは出るが更新で失敗 | データソースの権限・データ量 | 資格情報とプライバシーレベルを確認 |
| 途中結果が見たい | `in` の値 | 一時的に `in 途中のステップ名` に書き換える |

> [!TIP] 実務のコツ
> **`in` の値を途中のステップ名に書き換える**のが、Mで最も使うデバッグ手法です。どのステップで壊れたかを二分探索で特定できます。確認が終わったら戻すのを忘れないでください。

## 設計判断チェックリスト
