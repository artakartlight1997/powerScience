Q&A は「自然言語で質問できる機能」ではありません。正確には、**あなたが整備した語彙の範囲内でだけ質問できる機能**です。素のモデルに Q&A を置くと、「今月の粗利は？」と聞いても答えが返らず、利用者は二度と使いません。

逆に、語彙を整備したモデルは強力です。レポートを開かない層——役員、営業所長、現場のリーダー——が、自分の言葉で数字を取りに来られるようになります。

```figure
{ "type":"pipeline", "title":"Q&Aが質問を答えに変える経路", "caption":"③で失敗すると「その質問は理解できません」になる",
  "nodes":[
    {"id":"q","label":"「今月の粗利は？」","tone":"blue"},
    {"id":"t","label":"① 語に分割","tone":"gray"},
    {"id":"m","label":"② モデル語彙と照合","tone":"amber"},
    {"id":"d","label":"③ DAXクエリを生成","tone":"violet"},
    {"id":"v","label":"④ ビジュアルを選択","tone":"green"},
    {"id":"a","label":"答え","tone":"good"} ],
  "edges":[
    {"from":"q","to":"t","label":""},
    {"from":"t","to":"m","label":"同義語辞書"},
    {"from":"m","to":"d","label":"テーブル/列/メジャー"},
    {"from":"d","to":"v","label":"型から判断"},

```

> [!NOTE] 要点
> Q&A が参照するのは**モデルのメタデータ**（テーブル名・列名・メジャー名・データ型・リレーションシップ・同義語）です。**データの中身の値も一部インデックス化されます**が、基本は名前で解決します。だから「名前の整備」が Q&A 対応の本体になります。

## 準備なしの Q&A が失敗する理由

現場の言葉とモデルの名前は、ほぼ必ずずれています。

```figure
{ "type":"tablediff", "title":"現場語とモデル語のずれ", "arrowLabel":"同義語登録で橋を架ける",
  "before":{"title":"利用者が使う言葉","tone":"bad","head":["言い方","モデルには…"],
    "rows":[["粗利","!存在しない（[売上総利益] がある）"],["得意先","!Dim_顧客[顧客名]"],["今月","!日付の解釈が必要"],["ヨコハマ支店","!Dim_店舗[店舗名]='横浜'"]]},
  "after":{"title":"整備後にできること","tone":"good","head":["質問","解決先"],
    "rows":[["今月の粗利","[売上総利益] × 当月フィルター"],["得意先別の粗利トップ10","Dim_顧客[顧客名] で降順10件"],["ヨコハマ支店の売上推移","Dim_店舗[店舗名] × 月次折れ線"]]} }
```

> [!TRAP] つまずきポイント
> 「Q&Aを試したら変な答えが返ってきた」という報告のうち、**本当にAIが間違っているケースはごくわずか**です。ほとんどは (1) 同義語が無い、(2) 同じ意味のメジャーが3本あってどれが選ばれるか不定、(3) 使ってはいけない技術列（IDやフラグ）が公開されたまま、のいずれかです。原因はモデル側にあります。

## Q&A セットアップの6つの仕事

Q&A の整備画面（Q&Aセットアップ）で行う作業は、次の6つに分類できます。上から順に効果が大きい順です。

```figure
{ "type":"steps", "title":"Q&A整備の優先順位", "caption":"上の3つを終えるだけで、回答成功率は大きく変わる",
  "items":[
    {"title":"1. 不要なフィールドを隠す","text":"サロゲートキー、内部フラグ、作業列をQ&Aから除外する。候補が減るほど正解率は上がる","tone":"blue"},
    {"title":"2. 表示名を業務語にする","text":"SLS_AMT → 売上金額。列名の変更はQ&A以外にも効く","tone":"green"},
    {"title":"3. 同義語を登録する","text":"1フィールドにつき現場語を2〜4個。方言・略語・英語表記も入れる","tone":"amber"},
    {"title":"4. 用語（線形化用語）を定義する","text":"「優良顧客」「重点商品」のような、複数条件の塊に名前をつける","tone":"violet"},
    {"title":"5. 質問候補を登録する","text":"利用者が最初に押せる例を5〜8本。使い方の教育を兼ねる","tone":"pink"},
    {"title":"6. レビューして教える","text":"実際に来た質問のログを見て、外した質問に正解を教え込む","tone":"cyan"} ] }
```

### 除外がいちばん効く

Q&A の精度は、**候補が少ないほど上がります**。モデルに200列あって、そのうち業務的に意味があるのが40列なら、残り160列は徹底的に除外します。

```figure
{ "type":"compare", "title":"除外の有無で何が変わるか", "caption":"「隠す」はレポート作成にも効く。Q&A整備はモデル整備そのもの",
  "panels":[
    {"title":"全部公開したまま","tone":"bad","items":["「売上」に反応する列が7本ある","内部コード列が答えに出る","同じ数字が微妙に違う複数の経路で返る"],"note":"利用者は信用しなくなる"},
    {"title":"公開を40列に絞る","tone":"good","items":["曖昧さがほぼ消える","答えが常に同じメジャーに解決する","レポート作成者の迷いも減る"],"note":"整備の第一歩"} ] }
```

> [!TIP] 実務のコツ
> 除外の判断に迷ったら「**この列名だけを見て、営業所長が意味を言えるか**」を基準にします。言えないなら除外です。列を隠す操作は、モデルビューで対象を選び「レポートビューで非表示」＋ Q&A セットアップの「フィールドを管理」で対応します。

### 同義語の書き方

同義語は「1つ登録すれば十分」ではありません。実際の発話は割れます。

| フィールド | 登録すべき同義語の例 |
|---|---|
| `[売上総利益]` | 粗利、粗利益、あらり、GP、gross profit |
| `Dim_顧客[顧客名]` | 得意先、取引先、客先、アカウント、顧客 |
| `Dim_商品[カテゴリ]` | 商品カテゴリ、商品分類、カテゴリー、品目区分 |
| `[受注件数]` | 件数、オーダー数、受注数、注文件数 |

> [!WARN] 注意
> 同義語を**複数のフィールドに重複して登録しない**でください。「件数」を `[受注件数]` と `[出荷件数]` の両方に登録すると、どちらが選ばれるかが不定になり、数字が日によって変わったように見えます。重複が避けられないときは、片方を「受注の件数」のように修飾した語にします。

### 用語（線形化用語）で業務概念を教える

「優良顧客の今期売上」と聞かれたとき、モデルに「優良顧客」という概念が無ければ答えられません。Q&A の**用語**機能では、`優良顧客 = 年間購入額が100万円以上の顧客` のような定義を登録できます。

```figure
{ "type":"tree", "title":"業務語をモデル語に落とす", "caption":"曖昧な業務語を放置すると、部署ごとに違う数字が生まれる",
  "root":{"label":"「優良顧客」を定義する"},
  "children":[
    {"label":"金額基準","sub":"年間購入額 ≥ 100万円","tone":"green",
     "children":[{"label":"期間は？","sub":"直近12か月／会計年度を明示"}]},
    {"label":"頻度基準","sub":"年間購入回数 ≥ 6回","tone":"amber",
     "children":[{"label":"併用か択一か","sub":"AND / OR を決めて文書化"}]},
    {"label":"利益基準","sub":"粗利貢献 ≥ 30万円","tone":"violet"} ] }
```

用語を定義する作業は、実は Q&A のためだけの作業ではありません。**組織の言葉を1つに揃える作業**です。定義した内容は用語集にも書き出し、レポートの説明文にも載せてください。

> [!DS] データサイエンス視点：セマンティックレイヤー
> データベースの物理構造と、人間が使う業務概念のあいだに置く「意味の層」を**セマンティックレイヤー**と呼びます。Power BI のセマンティックモデルはまさにこれです。Q&A の同義語・用語の整備は、セマンティックレイヤーに**オントロジー**（概念とその関係の定義）を追加する行為にあたります。生成AI時代には、この層の整備品質がそのままAIの回答品質になります。整備は無駄になりません。

## Q&A の答えを固定する：レビューと「教える」

Power BI Service では、実際に投げられた質問のログを確認できます。答えられなかった質問には、その場で正解を教え込めます。

```figure
{ "type":"flow", "dir":"col", "title":"Q&A改善のループ", "caption":"最初の1か月は週次で回す",
  "items":[
    {"label":"質問ログを見る","sub":"どんな言葉で聞かれたか","tone":"blue"},
    {"label":"外した質問を抽出","sub":"「理解できません」の一覧","tone":"amber"},
    {"label":"原因を分類","sub":"語彙不足／曖昧／モデルに無い","tone":"violet"},
    {"label":"同義語・用語を追加","sub":"またはメジャーを新設","tone":"green"},
    {"label":"再テスト","sub":"同じ質問で確認","tone":"good"} ] }
```

「モデルに無い」に分類された質問は、**Q&Aの問題ではなくモデル設計の宿題**です。たとえば「粗利率の前年差は？」が繰り返し来るなら、そのメジャーを作るべきだという需要のシグナルです。Q&Aのログは、**利用者が本当に知りたいことの一次データ**として読んでください。

> [!TIP] 実務のコツ
> Q&A を公開する前に、想定利用者に**「この画面に聞きたいことを10個書いてください」**と依頼し、その10問が全部通るまで整備します。これだけで公開後の失望をほぼ防げます。

## スマートナラティブ — 自動要約を信用できる文章にする

スマートナラティブ（Smart Narrative）は、ページやビジュアルの内容を自然言語の要約テキストにするビジュアルです。そのままでは冗長で当たり障りのない文章になりますが、**編集して自分の言葉と動的値を混ぜる**と実用になります。

```figure
{ "type":"compare", "title":"自動生成のまま vs 編集後", "caption":"編集して初めて、読む価値のある文章になる",
  "panels":[
    {"title":"自動生成のまま","tone":"bad",
     "items":["「売上は1,240百万円でした。最も高いのは家電で、520百万円でした。」","事実の羅列で、判断がない","毎月同じ構文で読み飛ばされる"],"note":"情報量ゼロ"},
    {"title":"人が構成を決めて動的値を埋める","tone":"good",
     "items":["「今月の売上は◯◯（前年比 △△%）。目標に対して ×× 不足。","最大要因は □□ カテゴリの客数減。」","毎月、同じ観点で比較できる"],"note":"意思決定に効く"} ] }
```

スマートナラティブのテキストボックスには、`+値` から**動的な値**を挿入できます。挿入されるのはメジャーやビジュアルの集計値で、フィルターに追従します。

```figure
{ "type":"formula", "lang":"text", "title":"動的値を織り込んだ文章の設計",
  "code":"今月の売上は {売上合計} で、前年同月比 {売上YoY%} です。目標比では {目標差額} 不足しています。",
  "parts":[
    {"match":"{売上合計}","label":"実績。フィルターに追従して変わる","tone":"blue"},
    {"match":"{売上YoY%}","label":"変化。「良い/悪い」の判断材料","tone":"amber"},
    {"match":"{目標差額}","label":"ギャップ。ここが行動につながる","tone":"pink"} ] }
```

> [!WARN] 注意
> 動的値の書式（小数桁、単位、％）は**メジャー側の書式設定に従います**。ナラティブ内で個別に整形するより、メジャーの書式を正しく設定するのが正解です。また、**フィルターで対象が0行になったときの文章**を必ず確認してください。「売上は（空白）でした」という文章が経営会議に出ると、その場で信用を失います。

### 条件で文章を切り替える

「良い/悪い」で文言を変えたいときは、**判定文言そのものをDAXメジャーで作る**のが最も確実です。

```dax
売上コメント =
VAR YoY = DIVIDE( [売上合計] - [売上合計_前年同月], [売上合計_前年同月] )
RETURN
SWITCH(
    TRUE(),
    ISBLANK( [売上合計] ), "対象期間のデータがありません",
    YoY >= 0.05,  "前年を大きく上回っています（+" & FORMAT( YoY, "0.0%" ) & "）",
    YoY >= 0,     "前年並みで推移しています（+" & FORMAT( YoY, "0.0%" ) & "）",
    YoY >= -0.05, "やや前年割れです（" & FORMAT( YoY, "0.0%" ) & "）",
    "前年を大きく下回っています（" & FORMAT( YoY, "0.0%" ) & "）"
)
```

このメジャーをカードビジュアルやナラティブに置けば、フィルターに応じて文章が変わります。**判定ロジックがモデル側にある**ため、複数のレポートで同じ言い回しを再利用でき、レビューもしやすくなります。

```figure
{ "type":"cards", "cols":3, "title":"文章生成の3方式", "caption":"用途に応じて選ぶ。混在させてもよい",
  "items":[
    {"icon":"🤖","title":"スマートナラティブ自動","text":"探索中の速報向け。公開レポートには原則そのまま出さない","tone":"gray"},
    {"icon":"✍","title":"ナラティブ＋動的値","text":"構成は人が決め、数値だけ自動。定例レポートの標準形","tone":"green"},
    {"icon":"🧮","title":"DAXで文章を組む","text":"条件分岐や複数レポートでの再利用が必要なとき","tone":"violet"} ] }
```

## アクセシビリティと多言語

Q&A とナラティブは、**視覚に頼らない情報取得の手段**としても価値があります。スクリーンリーダー利用者にとって、20個のビジュアルを読み上げるより、要約文1つのほうがはるかに速く要点に届きます。

| 論点 | 対応 |
|---|---|
| 読み上げ | ナラティブのテキストは読み上げ対象になる。要点を先頭に置く |
| 言語 | Q&A は日本語に対応するが、同義語は言語ごとに登録が必要 |
| 用語の一貫性 | レポートのタイトル・列名・ナラティブで表記を統一する |
| 代替テキスト | 主要ビジュアルには代替テキストを設定し、要点を1文で書く |

> [!EXAM] PL-300で問われる
> 出題ポイントは3つです。**(1) Q&Aの精度を上げる操作＝同義語の追加・フィールドの除外・用語の定義**、**(2) スマートナラティブは動的値を挿入して編集できる**、**(3) Q&Aビジュアルで作った結果は標準ビジュアルに変換できる**。「Q&Aで正しい答えが出ないときにまず何をするか」という問い方が頻出で、正解はほぼ「同義語を追加する／不要フィールドを非表示にする」です。

## Q&A をどこに置くか

Q&A には複数の登場場所があり、それぞれ利用者と目的が違います。置き場所を間違えると、整備しても使われません。

```figure
{ "type":"stack", "title":"Q&Aの3つの入口", "caption":"下ほど利用者が多く、上ほど自由度が高い",
  "layers":[
    {"label":"Q&Aビジュアル（レポート内）","sub":"作成者が配置。文脈のあるページで自由質問","tone":"violet"},
    {"label":"ダッシュボードの質問バー","sub":"経営層の入口。まず数字を取りに来る場所","tone":"amber"},
    {"label":"提案された質問ボタン","sub":"クリックだけで使える。導入初期はこれが主役","tone":"blue"} ] }
```

導入初期に最も効くのは**提案された質問**です。自由入力は「何を聞けばいいか分からない」という壁で止まります。よく使われる質問を5〜8本ボタン化しておき、慣れた人だけが自由入力に進む——この段差を設計してください。

```figure

  "xLabel":"質問の多様性", "yLabel":"利用者数",
  "xLow":"定型（数種類）","xHigh":"多様（予測不能）","yLow":"少ない","yHigh":"多い",

    {"title":"定型レポートで足りる","text":"聞かれる内容が決まっているなら、ページを作った方が速い","tone":"gray"},
    {"title":"Q&Aの本命","text":"多数の人が思い思いに聞く。整備コストを回収できる","tone":"good"},
    {"title":"不要","text":"少人数×定型。個別に答えた方が早い","tone":"gray"},
    {"title":"要注意","text":"少数のパワーユーザーが多様に聞く。Q&Aより自分でモデルを触ってもらう方が速い","tone":"amber"} ] }
```

> [!TRAP] つまずきポイント
> 「とりあえず全レポートにQ&Aビジュアルを置く」は失敗パターンです。整備されていないQ&Aは、**間違った答えを堂々と返します**。答えられないより、間違った答えを返す方が有害です。整備が終わったモデルにだけ置いてください。

## よくある失敗と原因の対応表

| 症状 | 主な原因 | 対処 |
|---|---|---|
| 「質問を理解できません」が多い | 同義語が未登録／技術的な列名のまま | 表示名の変更と同義語の一括登録 |
| 数字がレポートと合わない | Q&Aが別のメジャーや列を選んでいる | 重複メジャーの整理、不要フィールドの除外 |
| 「今月」が正しく解釈されない | 日付テーブルが無い、または日付としてマークされていない | 日付テーブルを作成し、リレーションを設定 |
| 変なビジュアルで返る | データ型が不適切（数値が文字列） | モデルの型を修正 |
| 人によって答えが違う | RLS が効いている（正常動作） | 仕様として説明し、RLS前提でテストする |
| 集計が意図と違う（合計か平均か） | メジャーではなく列を集計している | 明示的にメジャーを作り、列の既定集計を「なし」にする |

> [!TIP] 実務のコツ
> **「暗黙のメジャー」を無くす**——列を直接ドラッグして自動集計させるのをやめ、必要な集計はすべて名前付きメジャーとして定義する。この方針を徹底したモデルは、Q&A の回答が劇的に安定します。Copilot にも同じ効果があります。

## ケーススタディ：営業所長40人にQ&Aを配る

全国40営業所の所長に、月次の数字を自分で取ってもらう取り組みを想定します。

```figure
{ "type":"timeline", "title":"4週間の整備計画", "caption":"整備は1日では終わらない。しかし4週間あれば十分に届く",
  "items":[
    {"label":"Week 1","title":"語彙の棚卸し","text":"所長5人にヒアリングし、実際に使う言葉を80語収集する","tone":"blue"},
    {"label":"Week 2","title":"モデル整備","text":"表示名を業務語に変更、技術列を非表示、重複メジャーを1本に統合","tone":"green"},
    {"label":"Week 3","title":"同義語・用語登録","text":"収集した80語を割り当て、「優良顧客」など5つの用語を定義","tone":"amber"},
    {"label":"Week 4","title":"パイロットと修正","text":"所長5人に1週間使ってもらい、外した質問をログから拾って教え込む","tone":"violet"},
    {"label":"Week 5〜","title":"全体展開と月次改善","text":"40人に展開。月次で質問ログをレビューし、需要の高い指標をメジャー化","tone":"good"} ] }
```

この取り組みで最も価値が出たのは、実は Q&A そのものではなく、**Week 2 のモデル整備**でした。名前が業務語に揃い、重複メジャーが消えたことで、レポート作成者の生産性も上がります。Q&A の整備は、モデル品質向上の口実として使えます。

> [!NOTE] 要点
> Q&A 対応のためにやることは、**良いセマンティックモデルの条件そのもの**です。業務語の名前、隠された技術列、一意なメジャー定義、正しい日付テーブル。整備は Q&A のためだけの投資ではありません。

## 整備コストを説明する言葉を持つ

「同義語の登録に3日かかります」と言うと、上司は投資を渋ります。次のように翻訳してください。

```figure
{ "type":"compare", "title":"同じ作業の2つの説明", "caption":"効果の単位を、相手の関心事に合わせる",
  "panels":[
    {"title":"作業として説明する","tone":"bad",
     "items":["「Q&Aの同義語を80語登録します」","「フィールドを非表示にします」","「用語を定義します」"],
     "note":"承認されにくい"},
    {"title":"成果として説明する","tone":"good",
     "items":["「所長40人が、月次数字の問い合わせを自分で解決できるようになります」","「現在、月120件ある数字の問い合わせ対応（約30時間）を削減できます」","「『優良顧客』の定義が部署間で統一されます」"],
     "note":"投資判断ができる"} ] }
```

> [!DS] データサイエンス視点：セルフサービスBIの効果は「待ち時間」で測る
> セルフサービス化の効果は、作った本数ではなく**質問から回答までのリードタイム**で測るのが定石です。「依頼→分析担当が対応→回答」で平均2日かかっていたものが、Q&Aで30秒になれば、意思決定の回転数そのものが変わります。効果測定の指標は「問い合わせ件数の減少」と「回答リードタイムの短縮」の2本を用意してください。

## 理解度チェック

1. 営業部から「Q&Aで『粗利』と聞いても答えが返ってこない」と言われました。原因として考えられることを3つ挙げ、確認する順番を答えてください。
2. 「件数」という同義語を `[受注件数]` と `[出荷件数]` の両方に登録するとどうなりますか。回避策とあわせて説明してください。
3. スマートナラティブの自動生成文をそのまま経営向けレポートに載せてはいけない理由を述べ、代わりに取るべき方法を2つ挙げてください。
