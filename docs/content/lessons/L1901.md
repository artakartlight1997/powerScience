Power BI は、単体の製品から **Microsoft Fabric という基盤の1ワークロード**になりました。

この変化を「名前が変わっただけ」と受け取ると、設計の選択肢を大きく取り逃します。逆に「全部Fabricにすべきだ」と受け取ると、必要のない複雑さを抱え込みます。**正しい理解は、地図を持つことです。**どこに何があり、自分の課題はどの領域にあるのか。

> [!WARN] 執筆時点の情報
> Fabric は変化の速い製品です。本モジュールは執筆時点（2026年）の構成を前提に、**概念と設計判断**を中心に扱います。機能名・上限値・課金体系は変わりうるため、実際の設計時には Microsoft Learn の公式ドキュメントで最新情報を確認してください。ここで学ぶべきは「どの判断軸で選ぶか」であり、その骨格は製品の更新では変わりません。

## アイテムという統一概念

Fabricでは、すべての成果物が**アイテム（Item）**として扱われます。

| 種別 | 例 |
|---|---|
| データ保管 | Lakehouse / Warehouse / KQL Database / Mirrored Database |
| データ処理 | Pipeline / Dataflow Gen2 / Notebook / Spark Job Definition |
| セマンティック | Semantic Model |

## ドメインという概念

Fabric には、ワークスペースをより大きな単位でまとめる**ドメイン**という機能があります。

| 階層 | 単位 | 例 |
|---|---|---|
| テナント | 組織全体 | Contoso 株式会社 |
| ドメイン | 業務領域 | 販売 / 生産 / 人事 |
| ワークスペース | プロジェクト・環境 | 販売-開発 / 販売-本番 |
| アイテム | 個々の成果物 | 販売セマンティックモデル |

ドメインは、**データメッシュ的な組織設計を製品側で支える仕組み**です（L1701参照）。ドメインごとに管理者を置き、ドメイン内のガバナンス設定を委任できます。中央がすべてを見るのではなく、各業務領域が自分の責任範囲を持つ形です。

> [!DS] データサイエンス視点：統合基盤の利点と危うさ
> すべてを1つの基盤に集めることには、明確な利点があります。**データの移動が減り、権限が統一され、系列が追える**。一方で危うさもあります。1つの容量にすべてが乗るということは、**1つの重い処理が全社に影響する**ということでもあります。分散していた頃は、DWHが重くてもBIは動きました。統合された基盤では、そうはいきません。だからFabricでは、容量の設計と監視（L1905）が、以前より重要になります。**統合はリスクの集中でもある**という認識を持って設計してください。

## 用語の整理

Fabric を学ぶときの障害の1つは、似た名前の概念が多いことです。混同しやすいものを整理します。

| 混同しやすい組 | 違い |
|---|---|
| OneLake と Lakehouse | OneLake は組織に1つのストレージ基盤。Lakehouse はその上に作るアイテム |
| Lakehouse と Warehouse | 前者はSparkとファイル中心、後者はT-SQLとテーブル中心 |
| Dataflow Gen2 と Pipeline | 前者は変換（何をするか）、後者は制御（いつ何を動かすか） |
| セマンティックモデル と データセット | 同じもの。名称が変更された |
| ワークスペース と ドメイン | 前者はプロジェクト単位の箱、後者は業務領域単位のまとまり |
| 容量 と ライセンス | 前者は計算資源、後者は人の利用権 |

> [!TIP] 実務のコツ
> 会話で混乱が起きたときは、**「それは置き場所の話ですか、処理の話ですか、権限の話ですか」**と聞き返すと整理できます。Fabricの議論が噛み合わないときの原因は、ほぼこの3つの軸が混ざっていることです。

## Fabric の権限モデル

Fabricでは、権限が2つの経路で効きます。この二重構造の理解が実務では重要です。

```figure
{ "type":"stack", "title":"Fabric の権限の重なり", "caption":"上の層で許可しても、下の層で拒否されていればアクセスできない",
```

> [!TRAP] ワークスペース権限だけを見て安心する
> Fabricでは、**ワークスペースのViewerでも、Lakehouseの SQL 分析エンドポイント経由でデータに到達できる場合があります**。「レポートで見せていない列だから安全」という判断は成り立ちません。Power BI 単体の時代は、セマンティックモデルが実質的な境界でした。Fabricでは保管層に直接到達する経路が増えているため、**保管層のアクセス制御を必ず別途設計してください。**RLSも同様で、セマンティックモデルのRLSは、SQL経由の直接アクセスには効きません。

> [!DS] データサイエンス視点：統合基盤とレイクハウスアーキテクチャ
> Fabric の設計思想は、業界で**レイクハウス（Lakehouse）アーキテクチャ**と呼ばれる潮流の上にあります。従来は、柔軟だが構造が緩い「データレイク」と、構造は厳密だが硬い「データウェアハウス」が別々に存在し、両方を持つ組織はデータを二重に保管していました。レイクハウスは、**レイクの安価で柔軟なストレージの上に、ウェアハウス並みの信頼性（トランザクション、スキーマ管理、時間旅行）を載せる**という発想です。これを可能にしたのが Delta Lake や Apache Iceberg といったオープンテーブルフォーマットで、OneLake もこの系譜にあります。**「1か所に置いて、複数のエンジンから読む」**が、この10年の分析基盤設計の中心的な答えになりました。

## この先の4レッスンの読み方

このモジュールの残りは、Fabric の構成要素を1つずつ掘り下げます。読む順序には理由があります。

| レッスン | 扱うもの | なぜこの順か |
|---|---|---|
| L1902 | OneLake と Lakehouse | すべての土台。ここが分からないと他が理解できない |
| L1903 | Warehouse・Notebook・パイプライン | 変換層の選択肢。手段の使い分け |
| L1904 | Direct Lake | 保管層とセマンティック層の接続方法。前2つが前提 |
| L1905 | 容量管理とコスト | 全体を動かす資源。最後に全体を見渡す |

L1902 から L1904 までが「何をどう作るか」、L1905 が「それを回し続けられるか」です。**設計できることと運用し続けられることは別の能力**であり、プロに求められるのは両方です。

> [!NOTE] このレッスンのまとめ
> Fabric は分析に必要な機能を1つのSaaSに統合し、OneLake・容量・ワークスペース・ガバナンスを共通化した基盤である。Power BI はその中で出口（セマンティック層と利用層）を担当する。5層モデルは置き換わらず、そのまま適用できる。Fabricは良い設計を実現しやすくする道具であって、設計の不備を直す道具ではない。そして統合はリスクの集中でもあるため、容量の設計と監視が以前より重要になる。
