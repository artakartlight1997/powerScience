Power BI を「グラフを作るツール」だと思って使い始めると、必ず途中で迷子になります。実際には5つの異なる工程が1つのアプリに同居しており、それぞれ**別の言語・別のエンジン・別の考え方**で動いているからです。

この地図を最初に持つかどうかで、その後の学習効率が数倍変わります。「今つまずいているのはどの工程か」が言えるようになれば、調べるべきキーワードも自動的に決まります。

**DAX**（Data Analysis Expressions。Power BI の計算式言語）は、この工程で使います。Excelの数式に似た見た目ですが、動作原理は根本的に違います。Excelの数式は「このセル」を計算しますが、DAXのメジャーは**「今画面に表示されているフィルターの下で」計算します。** だから同じ「売上合計」というメジャーが、店舗別の表では店舗ごとの値になり、合計行では全体の値になります。

> [!NOTE] Power Query と DAX の使い分け
> 「この処理はどっちでやるべきか」は初心者最大の疑問です。原則はこうです。**行や列を増減させる処理はPower Query、集計して数字を出す処理はDAX。** データを取り込む前に確定できるもの（不要列の削除、型変換、結合）はPower Query。見る切り口によって値が変わるもの（売上合計、達成率、前年比）はDAX。この線引きはティア2で詳しく扱います。

## 2つのエンジンが同居している

Power BI が難しく感じられる根本原因は、**性質の異なる2つのエンジンが1つのアプリに入っている**ことです。

```figure
{ "type": "compare", "title": "2つのエンジンの違い",
  "caption": "この2つを混同すると、どこで何をすべきかが分からなくなる",
  "panels": [
    {"title":"Power Query（Mエンジン）","tone":"blue","items":[
      "言語：M（大文字小文字を区別する）",
      "タイミング：データ更新時に1回だけ実行",
      "対象：行と列そのもの",
      "結果：モデルに保存される固定のデータ",
      "画面：Power Queryエディタ"],
     "note":"取り込む前の世界"},
    {"title":"モデル（DAX / VertiPaq）","tone":"violet","items":[
      "言語：DAX",
      "タイミング：グラフを見るたびに毎回実行",
      "対象：フィルターと集計",
      "結果：見るたびに変わる動的な数値",
      "画面：レポートビュー / モデルビュー"],
```

境界線は明確です。**Power Queryエディタを閉じて「閉じて適用」を押した瞬間**に、Mの世界は終わり、DAXの世界が始まります。

> [!DS] 列指向ストレージという設計思想
> Power BI の内部エンジン **VertiPaq** は、データを行ではなく**列ごと**に保存します。列単位に保存すると、同じ値が繰り返される列（例：Category列に「家電」が数千回）を「家電 × 3,200件」のように圧縮できるため、元データの5分の1〜10分の1のサイズになります。集計時も必要な列だけを読むため高速です。この設計のおかげで、数千万行のデータでもノートPCで集計できます。裏を返せば、**値の種類が多い列（カーディナリティが高い列）は圧縮が効かずモデルを重くする**ということでもあります。この知識はティア3の性能改善で決定的に効いてきます。

## まとめ

- Power BI は「取得 → 整形 → モデル化 → 可視化 → 共有」の5工程からなる
- 実務のトラブルは②整形と③モデル化に集中する。上流が正しければ下流は素直に動く
- Power Query（M言語）は更新時に1回だけ動き、行と列を作る。DAXは表示のたびに動き、集計値を出す
- 「閉じて適用」がMの世界とDAXの世界の境界線
- 内部エンジン VertiPaq は列指向で圧縮するため高速。値の種類が多い列は圧縮が効かない
- 症状を工程名で言えるようになると、調べるべきキーワードが一意に決まる
- 学習コストが最も高いのはモデル化。ここを飛ばすと後で必ず戻ることになる
