「自分のPCでは更新できるのに、発行したらエラーになる」。Power BI を使い始めた人が最初にぶつかる壁です。原因はほぼ例外なく、**Desktop と Service の役割の違いを知らないこと**にあります。

Power BI は3つの製品で1つの仕組みを作っています。それぞれ何ができて何ができないかを、最初に線引きしておきます。

## 機能の担当表

どちらでできるかを覚えるのではなく、**「なぜそちらなのか」の理由**とセットで覚えると忘れません。

| やりたいこと | Desktop | Service | 理由 |
|---|---|---|---|
| データソースへの接続 | ○ | △ | 複雑な接続・整形はDesktopの領域 |
| Power Queryでの整形 | ○ | △（データフロー） | Mエンジンの完全な機能はDesktopのみ |
| リレーションシップの作成 | ○ | × | モデル構造の編集はDesktopで行う |
| DAXメジャーの作成 | ○ | △ | Service上でも編集可能だが実務ではDesktop |
| レポートの作成・編集 | ○ | ○ | どちらでも可。原本管理の観点でDesktop推奨 |
| ダッシュボードの作成 | × | ○ | ダッシュボードはService固有の機能 |
| スケジュール更新の設定 | × | ○ | クラウド側でしか自動実行できない |
| 他ユーザーへの共有 | × | ○ | 権限はクラウドで管理される |
| 行レベルセキュリティの定義 | ○ | — | 定義はDesktop、ユーザー割り当てはService |
| アラート・サブスクリプション | × | ○ | 通知はクラウドの機能 |

> [!NOTE] 迷ったときの原則
> **モデルの構造を変える作業はDesktop、人に届ける作業はService。** この一言で大半の判断がつきます。Service でもレポートを編集できますが、Desktopのpbixファイルが原本である以上、Service で直接編集すると原本と乖離します。実務では「編集はDesktop、配布はService」と決めておくのが安全です。

## ワークスペースという場所

**ワークスペース**とは、Service上のフォルダのようなもので、レポートやセマンティックモデルを置く共同作業の場所です。ただの入れ物ではなく、**権限の単位**でもあります。

```figure
{ "type": "stack", "title": "Serviceの階層構造",
  "caption": "上から下へ、テナント → ワークスペース → アイテム",
  "layers": [
    {"label":"テナント","sub":"組織全体。会社に1つ。管理者が全体設定を行う","tone":"gray"},
    {"label":"ワークスペース","sub":"チーム単位の作業場。ここに権限を設定する","tone":"violet"},
    {"label":"アイテム","sub":"レポート / セマンティックモデル / ダッシュボード / データフロー","tone":"amber"},
    {"label":"アプリ","sub":"ワークスペースの中身を整えて閲覧者に配る「published版」","tone":"blue"} ] }
```

ワークスペースには4つのロール（役割）があり、できることが違います。

| ロール | 主にできること | 想定する人 |
|---|---|---|
| 管理者 Admin | 削除・権限変更を含むすべて | ワークスペースの責任者 |
| メンバー Member | 発行・編集・アプリの公開 | 開発メンバー |
| 共同作成者 Contributor | 発行・編集（アプリ公開は不可） | 開発を手伝う人 |
| 閲覧者 Viewer | 閲覧のみ | レポートを見る人 |

> [!TRAP] 「マイワークスペース」で作業しない
> 個人用の**マイワークスペース**は自分だけの領域です。ここに置いたレポートは他人と共有しにくく、あなたが退職すると誰もアクセスできなくなります。**業務で使うものは必ずチーム用のワークスペースに置く。** これは組織で最も多い運用事故の1つです。

## Serviceにしかない機能

Service は「Desktopの閲覧専用版」ではありません。クラウドだからこそできる機能があります。

```figure
{ "type": "cards", "cols": 4, "title": "Service固有の機能",
  "caption": "これらはDesktopには存在しない。共有を前提とした機能ばかり",
  "items": [
    {"icon":"📌","title":"ダッシュボード","text":"複数レポートのビジュアルをタイルとしてピン留めした1画面。Service専用","tone":"violet"},
    {"icon":"⏰","title":"スケジュール更新","text":"毎日決まった時刻に自動でデータを取り直す。Proなら1日8回まで","tone":"green"},
    {"icon":"📧","title":"サブスクリプション","text":"レポートのスナップショットを定期的にメール送信する","tone":"blue"},
    {"icon":"📈","title":"使用状況メトリック","text":"誰がどのレポートを何回見たかを計測する。不要レポートの棚卸しに使う","tone":"amber"} ] }
```

**使用状況メトリック**は運用フェーズで極めて重要です。作ったレポートが実際に見られているかを数字で確認できます。半年間アクセス0のレポートは、維持コストだけが発生している資産です。定期的に棚卸しをすると、更新エラーの調査対象も減ります。

> [!TIP] 作る前に「誰が何回見るか」を見積もる
> 月1回しか見ないレポートに、日次自動更新は不要です。逆に毎朝見られるレポートなら、更新が朝7時に完了している必要があります。**利用頻度から更新頻度を決める**という順序で考えると、無駄な設定と無駄な負荷が減ります。

## チームで作るときの現実

Power BI の pbix ファイルは、テキストではなくバイナリです。そのため複数人が同時に編集して後からマージする、という開発ができません。

> [!EXAM] PL-300で頻出の切り分け
> 試験では「この操作はどこで行うか」が繰り返し問われます。**ダッシュボードの作成・スケジュール更新・アプリの公開・アラートの設定はService**、**リレーションシップの作成・計算列の追加・RLSロールの定義・モバイルレイアウトの作成はDesktop**。RLSは「ロールの定義はDesktop、メンバーの割り当てはService」という分割になっている点が特に狙われます。

## まとめ

- Desktopで作り、Serviceで配り、Mobileで見る。役割は明確に分かれている
- モデルの構造を変える作業はDesktop、人に届ける作業はService
- 発行すると1つのpbixが「レポート」と「セマンティックモデル」の2アイテムに分かれる
- ワークスペースは権限の単位。業務用のものをマイワークスペースに置かない
- ワークスペースは作る人の場所、アプリは見る人の場所。閲覧者が多いならアプリで配る
- 社内データをクラウドから更新するにはオンプレミスデータゲートウェイが必要
- Desktopの資格情報はServiceに引き継がれない。これが更新失敗の最大の原因

## 理解度チェック（自分に説明してみる）

1. 「リレーションシップを1本追加したい」「更新時刻を朝7時に変えたい」「レポートを営業部20人に配りたい」。それぞれDesktopとServiceのどちらで行いますか。理由も説明してください。
2. 発行したレポートが Service で更新に失敗しています。確認すべきことを、優先度の高い順に3つ挙げてください。
3. ワークスペースで直接共有するのと、アプリとして配布するのとでは、どんな場面でどちらが有利ですか。閲覧者の人数と更新頻度の観点から説明してください。
