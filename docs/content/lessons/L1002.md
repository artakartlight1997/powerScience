レポートが完成し、ワークスペースの器も用意できました。次は「届ける」工程です。

ここで多くの組織が同じ失敗をします。**1 人ずつ共有リンクを送る**という方法です。20 人までは何とかなりますが、その先は「誰が何を見られるのか」を誰も把握できなくなります。このレッスンでは、100 人規模へ安全に配布する正しい方法を扱います。

## 共有リンクのスコープ

個別のレポートを共有する場合、リンクには 3 種類のスコープがあります。

```figure
{ "type":"cards", "cols":3, "title":"共有リンクの3スコープ",
  "caption":"既定のスコープはテナント設定に依存する。送る前に必ず確認する",
  "items":[
    {"icon":"🏢","title":"組織内の全員","text":"社内の誰でもリンクを開ける。社内公開情報向け。機密データでは使わない","tone":"amber"},
    {"icon":"👤","title":"既存アクセス権を持つ人","text":"すでに権限がある人だけ。新たな権限は付与されない。安全だが、相手に権限が無いと開けない","tone":"green"},
    {"icon":"✉","title":"特定のユーザー","text":"指定した人にだけ権限を付与する。最小権限に近い。人数が増えると管理不能になる","tone":"blue"} ] }
```

> [!TRAP] つまずきポイント
> 共有リンクの既定が「**組織内の全員**」になっているテナントは珍しくありません。機密性の高いレポートのリンクを何気なく作ると、社内全員が閲覧可能になります。共有ダイアログでは必ずスコープ表示を確認し、必要なら「特定のユーザー」に変更してください。また共有時の「**受信者がこのレポートを共有できるようにする（再共有）**」のチェックも既定でオンになりがちです。

> [!EXAM] PL-300で問われる
> 「多数のユーザーに一貫した方法でコンテンツを配布したい」→ **アプリ**。「特定の 1 人に一時的に見せたい」→ **共有リンク（特定のユーザー）**。「同じレポートでユーザーごとに見える行を変えたい」→ **RLS**。「アプリ内で部門ごとに見えるレポートを変えたい」→ **対象ユーザー（Audience）**。この 4 択の区別が典型的な出題です。

> 「まず 3 人に見せて、良ければ全体へ」という段階的な公開をしたい場合も、**最初からアプリを作り、対象ユーザーを 3 人のグループにしておく**のが得策です。全体公開のときはグループの中身を差し替えるだけで済みます。個別共有から始めると、あとでアプリに移行する際に旧共有の解除作業が発生します。

## 理解度チェック

1. ワークスペースでレポートを修正したのに、読み手から「古いまま」と言われた。原因と対処を述べよ。
2. 営業部門 40 名に、それぞれ自分の担当地域のデータだけを見せたい。アプリの対象ユーザー機能だけで実現できるか。できない場合、何が必要か。
3. 「組織内の全員」スコープの共有リンクを使うべきでない場面と、その代替手段を述べよ。

<details>
<summary>解答の要点</summary>

1. 原因は、**アプリを更新していない**こと。アプリは公開時点のスナップショットを配布する仕組みで、ワークスペース側の変更は自動反映されない。対処は、ワークスペース右上の「アプリの更新」を押して再公開すること。この仕様は「作業中の変更が読み手に漏れない」という利点でもあるため、更新作業を公開手順に組み込む。
2. **実現できない**。対象ユーザー（Audience）が制御するのは「アプリ内でどのレポートが見えるか」だけで、同一レポート内の行の可視性は制御しない。必要なのは **RLS（行レベルセキュリティ）**。モデル側にロールと DAX フィルター（例：`Dim_担当[メール] = USERPRINCIPALNAME()`）を定義し、サービス側でロールにグループを割り当てる。加えて、読み手をワークスペースの編集ロールに入れないこと（編集権限保持者には RLS が適用されない）。
3. 機密性のあるデータ（個人情報、人事、原価、未公表の業績など）を含むレポート。「組織内の全員」は社内の誰でもリンクを開けるため、意図しない範囲に情報が広がる。代替は、**アプリ＋対象ユーザーで配布**（管理可能で監査しやすい）、または少人数なら共有リンクのスコープを「特定のユーザー」に変更し、再共有のチェックを外す。

</details>
