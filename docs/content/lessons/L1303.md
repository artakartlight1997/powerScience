DAX の関数は、返り値で2種類に分かれます。**1つの値を返すスカラー関数**と、**表を返すテーブル関数**です。

初級では前者しか使いません。上級のDAXは、**まずテーブルを組み立て、そのテーブルの上で集計する**という二段構えで書きます。この発想が身につくと、複雑な要件を1本の巨大な式に押し込む苦しみから解放されます。

```figure

  "caption":"テーブル関数の返り値はモデルに保存されない。式の途中にだけ存在する「仮想テーブル」である",
  "panels":[
    {"title":"スカラー関数","tone":"blue",
     "items":["SUM / AVERAGE / COUNTROWS / MAX","返り値は1つの値","メジャーの最終的な返り値はこれでなければならない","ビジュアルに直接表示できる"],
     "note":"値を返す"},

     "note":"表を返す"} ] }
```

## 仮想テーブルという考え方

`SUMX( VALUES( Dim_顧客[CustomerID] ), [売上合計] )` の `VALUES(...)` は、モデルのどこにも存在しない表です。式が評価されている一瞬だけメモリ上に作られ、使い終わったら消えます。これを**仮想テーブル**と呼びます。

```figure

  "caption":"仮想テーブルはクエリのたびに作られ、クエリが終われば消える。モデルサイズには影響しない",
  "nodes":[
    {"id":"m","label":"モデルの実テーブル\\nFact_売上 / Dim_顧客","tone":"blue"},

    {"id":"v","label":"仮想テーブル\\nSUMMARIZE の結果","tone":"violet"},
    {"id":"s","label":"スカラー値\\nビジュアルに表示","tone":"green"}],
  "edges":[
    {"from":"m","to":"f","label":"絞り込まれる"},

```

> [!NOTE] 要点
> テーブル関数は**メジャーの最終返り値にはできません**。必ず `SUMX` `COUNTROWS` `AVERAGEX` などのスカラー関数で包むか、`CALCULATE` のフィルター引数として使います。テーブルを返したまま置くと「メジャーの結果はスカラーである必要があります」というエラーになります。

最も使うテーブル関数です。1列を渡すと、その列の一意な値のリストを1列の表として返します。


> [!TRAP] つまずきポイント
> `Fact_売上` に `Dim_商品` に存在しない商品IDがあると、Power BI は自動的に**空白行（不明メンバー）**を `Dim_商品` に追加します。`VALUES( Dim_商品[ProductName] )` はこの空白行を返し、`DISTINCT` は返しません。「明細の合計と総計が合わない」ときは、この差が原因であることがあります。

VALUES にはもう1つ重要な使い方があります。**1列の表を渡すとスカラーとして評価される**という性質です。

```dax
選択中の店舗名 =
IF( HASONEVALUE( Dim_店舗[StoreName] ), VALUES( Dim_店舗[StoreName] ), "複数店舗" )
```

`VALUES` の結果がちょうど1行1列なら、DAX はそれをスカラーとして扱います。2行以上あるとエラーになるため、`HASONEVALUE` で守ります。`SELECTEDVALUE` はこのパターンを1関数にまとめたものです。

```dax
-- 上と同じ意味。こちらを使う
選択中の店舗名 = SELECTEDVALUE( Dim_店舗[StoreName], "複数店舗" )
```

## ADDCOLUMNS — 表に列を足す

既存のテーブルに計算列を追加した新しいテーブルを返します。**元のテーブルは変わりません。**

```dax
カテゴリ別集計 =
ADDCOLUMNS(
    SUMMARIZE( Fact_売上, Dim_商品[Category] ),
    "売上", [売上合計],
    "数量", SUM( Fact_売上[Quantity] ),
    "粗利率", DIVIDE( [粗利], [売上合計] )
)
```

```figure
{ "type":"tablediff", "title":"ADDCOLUMNS が返す表", "arrowLabel":"3つの列を追加",
  "before":{"title":"SUMMARIZE( Fact_売上, Dim_商品[Category] )","tone":"blue","head":["Category"],
    "rows":[["家電"],["衣料"],["食品"]]},
  "after":{"title":"ADDCOLUMNS( … , \"売上\", [売上合計], \"数量\", …, \"粗利率\", … )","tone":"good","head":["Category","売上","数量","粗利率"],
    "rows":[["家電","!28,800","!142","!0.31"],["衣料","!27,100","!310","!0.44"],["食品","!12,100","!980","!0.22"]]} }
```

ADDCOLUMNS はイテレータです。第1引数のテーブルを1行ずつ走査し、各行で式を評価します。したがって**行コンテキストが作られ、メジャー参照でコンテキスト遷移が起きます**。だから「家電」の行では家電だけの売上が計算されます。

> [!NOTE] 要点
> `ADDCOLUMNS( SUMMARIZE( ... ), "名前", 式 )` は上級DAXの基本形です。この形を指が覚えるまで書いてください。追加する列名は**必ずダブルクォートで囲みます**。

> [!TRAP] つまずきポイント
> ADDCOLUMNS の中で `SUM( Fact_売上[SalesAmount] )` と直接書くと、遷移が起きないため全行が同じ総計になります。メジャー参照 `[売上合計]` にするか、`CALCULATE( SUM( Fact_売上[SalesAmount] ) )` と包んでください。L1302 で扱ったとおりです。

## SELECTCOLUMNS — 列を選び直す

ADDCOLUMNS が「足す」のに対し、SELECTCOLUMNS は「選んで名前を付け直す」関数です。

```dax
顧客リスト =
SELECTCOLUMNS(
    Dim_顧客,
    "顧客ID", Dim_顧客[CustomerID],
    "区分", Dim_顧客[Segment]
)
```

元の列は含まれず、指定した列だけが指定した名前で返ります。**集合演算で列を揃えるときに必須**になります（L1304）。

`FILTER` はテーブル関数でありイテレータでもあります。第1引数のテーブルを1行ずつ走査し、第2引数が TRUE になる行だけを残した表を返します。

### CALCULATE のフィルター引数としてのテーブル

テーブル関数のもう1つの用途が、CALCULATE のフィルター引数です。

```dax
-- 売上10万円超の顧客に限定した売上合計
優良顧客の売上 =
CALCULATE(
    [売上合計],
    FILTER( VALUES( Dim_顧客[CustomerID] ), [売上合計] > 100000 )
)
```

CALCULATE のフィルター引数は、内部的にはすべてテーブルです。`Dim_商品[Category] = "家電"` という簡易構文も、エンジンは `FILTER( ALL( Dim_商品[Category] ), Dim_商品[Category] = "家電" )` に展開しています。**簡易構文で書けるものは簡易構文で書く**ほうが速く、ALL の範囲も限定されて安全です。

## 変数にテーブルを入れる

VAR にはテーブルも格納できます。上級のメジャーはこの形で読みやすくなります。

```dax
売上上位顧客の売上 =
VAR TopCustomers =
    TOPN(
        10,
        ADDCOLUMNS( VALUES( Dim_顧客[CustomerID] ), "@売上", [売上合計] ),
        [@売上], DESC
    )
VAR Result =
    SUMX( TopCustomers, [@売上] )
RETURN
    Result
```

```figure
  "items":[

    {"title":"3. 売上の降順で上位10行を取る","text":"TOPN が並べ替えて切り出す。同点なら10件を超えることがある","tone":"amber"},

```

> [!TIP] 実務のコツ
> ADDCOLUMNS で追加する列名の先頭に `@` を付けるのは、モデルの実列と区別するための慣習です。`[@売上]` と書けば「これは仮想テーブルの列だ」と一目で分かります。必須ではありませんが、チームで書くなら統一してください。

> [!DS] データサイエンス視点
> テーブル関数の組み合わせは、**リレーショナル代数**そのものです。`SUMMARIZE` は射影 + グループ化、`FILTER` は選択、`SELECTCOLUMNS` は射影とリネーム、`CROSSJOIN` は直積に対応します。SQL を書ける人は、頭の中でSQLに翻訳しながら読むと理解が速くなります。ただしDAXには「フィルターコンテキスト」というSQLにない層があるので、そこだけは別に考える必要があります。

## 理解度チェック

**問1.** 次の式が全カテゴリで同じ値を返してしまいます。原因と修正方法を答えてください。

```dax
ADDCOLUMNS(
    SUMMARIZE( Fact_売上, Dim_商品[Category] ),
    "売上", SUM( Fact_売上[SalesAmount] )
)
```

<details>
<summary>解答</summary>

`SUM( Fact_売上[SalesAmount] )` は式の直書きなので**コンテキスト遷移が起きません**。ADDCOLUMNS が作る行コンテキストは集計関数に影響しないため、全行で総計が返ります。`"売上", [売上合計]` とメジャー参照にするか、`"売上", CALCULATE( SUM( Fact_売上[SalesAmount] ) )` と CALCULATE で包みます。
</details>

**問2.** `VALUES( Dim_商品[ProductName] )` と `DISTINCT( Dim_商品[ProductName] )` で結果の行数が1行違いました。何が起きていますか。

<details>
<summary>解答</summary>

`Fact_売上` に、`Dim_商品` に存在しない商品IDの行が含まれています。Power BI が**不明メンバーの空白行**を `Dim_商品` に自動追加しており、`VALUES` はこれを含め、`DISTINCT` は含めません。データ品質の問題なので、Power Query 側でマスタ未登録の商品IDを洗い出して対処してください。
</details>

**問3.** メジャーの中で `SUMMARIZECOLUMNS` を使おうとしてエラーになりました。代わりにどう書きますか。

<details>
<summary>解答</summary>

`ADDCOLUMNS( SUMMARIZE( 起点テーブル, グループ化列 ), "名前", メジャー )` に書き換えます。SUMMARIZECOLUMNS はフィルターコンテキストが既に存在する状態での呼び出しに制約があり、メジャー内での利用は避けるのが安全です。
</details>
