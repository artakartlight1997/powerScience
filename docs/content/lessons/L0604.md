## 総計行が合わない理由

マトリクスの各行の合計と、総計行が一致しないことがあります。これはバグではなく、**総計行は各行の足し算ではなく、独立に再計算されている**からです。

総計行には「店舗＝新宿本店」というフィルターが効いていません。したがって全店舗の行に対して式が評価されます。`SUM` のような単純な集計なら結果は一致しますが、`DISTINCTCOUNT` や比率のメジャーでは一致しません。

| メジャー | 各行の合計 | 総計行 | 一致するか |
|---|---|---|---|
| 売上合計（SUM） | 各店舗の合計を足す | 全店舗を合計 | 一致する |
| 顧客数（DISTINCTCOUNT） | 各店舗の顧客数を足す | 全店舗の重複を除いた顧客数 | **一致しない** |
| 平均単価（割り算） | 各店舗の平均を足す | 全体の合計 ÷ 全体の件数 | **一致しない** |

> [!TRAP]
> 「総計が合わない」という指摘を受けたとき、**多くの場合は総計のほうが正しい**です。3店舗で買った顧客は、店舗別では3回数えられますが、全体では1人です。これは重複排除が正しく効いている証拠です。レポートを見る人にこの説明ができないと、モデルへの信頼が失われます。**同じ顧客が複数店舗で購入している場合、店舗別顧客数の合計は全体顧客数を上回ります**、と明記しておくのが実務的な対処です。

双方向は問題を解決するように見えますが、3つの副作用があります。

```figure

  "caption": "「動くようになった」の裏で、何が起きているかを知っておく",
  "panels": [
    {"title": "得られるもの", "tone": "neutral",
     "items": ["ファクト側から1側へフィルターが流れる", "スライサーに実績のある値だけ出せる", "多対多の解決に使える"],

     "note": "影響範囲が読めない"} ] }
```

とくに危険なのが RLS（行レベルセキュリティ）との組み合わせです。双方向のリレーションシップがあると、**あるテーブルに掛けた行フィルターが、意図しない別のテーブルにも波及します**。セキュリティ設定は「見えるべきものが見えない」より「見えてはいけないものが見える」ほうが深刻なので、双方向は慎重に扱ってください。

```dax
-- モデルは単一方向のまま、このメジャーの中だけ双方向にする
売上のあった店舗数 =
CALCULATE(
    DISTINCTCOUNT( Fact_売上[StoreID] )
)
```

このように、多くの場合は**ファクト側の列を直接数える**だけで双方向を回避できます。「ファクトに答えがあるなら、ファクトに聞く」というのが原則です。

## 経路のあいまいさ

リレーションシップの経路が2つ以上存在すると、Power BI は「どちらの経路でフィルターを流すべきか決められない」と判断します。

```figure

  "caption": "Dim_日付 から Fact_売上 へ、直接と Fact_予算 経由の2経路ができている",
  "nodes": [
    {"id": "d", "label": "Dim_日付", "tone": "amber"},

  "edges": [

    {"from": "p", "to": "f", "label": "経路2：商品経由"} ] }
```

この状態になると、Power BI はリレーションシップの作成を拒否するか、既存の線を非アクティブにします。**原因はほぼ常に、どこかに入れた双方向**です。単一方向に戻せば経路は一意に定まります。

> [!DS]
> フィルター伝播は、リレーショナル代数でいう **セミジョイン（semi-join）による絞り込み**の連鎖として理解できます。ディメンションで絞られたキーの集合が、ファクトの行を選択する条件になる、という構造です。スタースキーマでは経路が木構造（サイクルなし）になるため、伝播の順序が一意に決まり、エンジンは最適な実行計画を立てられます。双方向を入れると、この木にサイクルが生まれ、一意な実行計画が立てられなくなります。**「スタースキーマは速い」という主張の技術的根拠がここにあります**。グラフ理論の言葉でいえば、モデルは有向非巡回グラフであるべき、ということです。

> [!EXAM]
> PL-300 では、モデル図を見せて「スライサーAを操作したとき、ビジュアルBの値は変わるか」という形で問われます。判断手順は、(1) スライサーの列があるテーブルを特定する、(2) そこからビジュアルが参照するテーブルまでの経路があるか確認する、(3) 経路上の矢印の向きがすべて順方向か確認する。1つでも逆向きがあれば「変わらない」が答えです。また「双方向クロスフィルターを使うべきでない理由」として、あいまいさ・性能低下・RLSへの影響が正解になります。

## 空白と0の違い

フィルターの結果、該当する行が1行もない場合、メジャーは **空白（BLANK）** を返します。0 ではありません。

| 状態 | 表示 | 意味 |
|---|---|---|
| 該当行なし | （空白） | その組み合わせの取引が存在しない |
| 該当行があり合計が0 | 0 | 取引はあったが金額が0だった |

Power BI は既定で、空白になる行や列をビジュアルから除外します。「家電を扱っていない店舗が表に出てこない」のはこの仕様によるものです。全行を出したい場合は `+0` を付けるか、`SHOWALLSELECTED` などを使います。

```dax
-- 売上のない組み合わせも0として表示する
売上合計_ゼロ表示 = SUM( Fact_売上[SalesAmount] ) + 0
```

> [!WARN]
> `+0` を安易に使うと、**すべての組み合わせが行として出現し、表が巨大になります**。600顧客 × 32商品 × 730日の全組み合わせが表示されれば、ビジュアルは実用に耐えません。「空白を0で表示したい」という要望には、どの範囲で表示したいのかを必ず確認してください。

次のモデルを前提に、3つの問いに答えてください。答えは「経路があるか」「向きが揃っているか」の2点だけで決まります。

```figure
{ "type": "star", "title": "演習用のモデル",
  "caption": "すべて1対多・単一方向。矢印はディメンションからファクトへ",
  "fact": {"label": "Fact_売上", "lines": ["OrderDate / ProductID", "StoreID / CustomerID", "Quantity / SalesAmount"]},
  "dims": [

    {"label": "Dim_顧客", "lines": ["CustomerID が一意", "セグメント / 地域"]} ],

```

**問1：`Dim_日付` のスライサーで 2024 年を選ぶと、`COUNTROWS(Dim_商品)` の値は変わるか。**

変わりません。`Dim_日付` から `Fact_売上` へは流れますが、`Fact_売上` から `Dim_商品` へは流れないためです。商品テーブルは 32 行のまま数えられます。

**問2：`Dim_商品` のスライサーで「家電」を選ぶと、`SUM(Fact_売上[SalesAmount])` は変わるか。**

変わります。1側から多側への正方向なので、フィルターは届きます。

**問3：`Dim_店舗` で「関東」を選び、同時に `Dim_顧客` で「近畿」を選ぶと、売上はどうなるか。**

「関東の店舗で、近畿の顧客が買った売上」になります。2つのフィルターは AND で重なるためです。この組み合わせに該当する行がなければ、結果は空白になります。

> [!TIP]
> この読み方は、モデルが複雑になるほど価値が上がります。**モデル図を見て伝播を追える人は、DAX を1行も書かずに「その指標は今のモデルでは出せません」と判断できます**。設計レビューで最も重要な能力がこれです。

## フィルターに関する言葉を整理する

議論のときに用語が混ざると話が通じなくなるので、整理しておきます。

| 用語 | 意味 |
|---|---|
| フィルターコンテキスト | ある式が評価される時点で効いている、すべてのフィルターの集合 |
| フィルター伝播 | リレーションシップを通じて、あるテーブルのフィルターが別のテーブルへ伝わること |
| クロスフィルター方向 | 伝播が許される向きの設定（単一 / 両方） |
| 行コンテキスト | 「今どの行を処理しているか」という別の概念。計算列や反復関数で発生する |
| コンテキスト遷移 | 行コンテキストがフィルターコンテキストに変換されること。CALCULATE で起きる |

このレッスンで扱ったのはフィルターコンテキストと伝播です。行コンテキストとコンテキスト遷移は DAX のモジュールで扱いますが、**土台にあるのは同じ「どの行が対象か」という問い**です。

## RLS とフィルターの流れ

行レベルセキュリティ（RLS）は、**ユーザーに応じてテーブルに自動的なフィルターを掛ける仕組み**です。掛かったフィルターは、通常のフィルターと同じようにリレーションシップを通って伝播します。

```figure
{ "type": "pipeline", "title": "RLSのフィルターも同じ配管を流れる",
  "caption": "Dim_店舗 に掛けたフィルターが、ファクトへ、さらに先へ伝わる",
  "nodes": [
    {"id": "u", "label": "ログインユーザー\n関東エリア担当", "tone": "violet"},
    {"id": "s", "label": "Dim_店舗\n関東の4店舗に絞られる", "tone": "green"},
    {"id": "f", "label": "Fact_売上\n関東の売上だけ", "tone": "blue"},
    {"id": "c", "label": "Dim_顧客\n絞られない（単一方向）", "tone": "gray"} ],
  "edges": [
    {"from": "u", "to": "s", "label": "RLSのフィルター"},
    {"from": "s", "to": "f", "label": "伝播する"},
    {"from": "f", "to": "c", "label": "伝播しない"} ] }
```

ここで双方向のリレーションシップが1本でもあると、RLS のフィルターが顧客テーブルにも波及し、**設計者が意図していない絞り込みが発生します**。逆に、意図的にディメンションへ波及させたい場合は、リレーションシップの詳細設定にある「両方向にセキュリティフィルターを適用する」を使います。いずれにせよ、**RLS を使うモデルでは伝播経路を完全に把握しておく必要があります**。

モデルの伝播とは別に、レポート上でもフィルターは流れます。**あるビジュアルをクリックすると、同じページの他のビジュアルが絞られる**動作です。


> 「スライサーを操作したのに、このカードだけ数字が変わらない」という相談の原因は、モデルではなく**相互作用が「なし」に設定されている**ことが多くあります。モデルの伝播を延々と調べる前に、レポート側の設定を確認してください。**モデル起因かレポート起因かを切り分ける**のが、調査の最初の一歩です。


> [!NOTE]
> フィルターの出どころは大きく3層に分かれます。**モデル層**（リレーションシップとRLS）、**レポート層**（スライサー・相互作用・各種フィルターペイン）、**メジャー層**（CALCULATE によるフィルターの追加や除去）。数字が合わないときは、この3層のどこで起きているかを最初に切り分けてください。切り分けができれば、調査範囲は3分の1になります。

3. 「双方向クロスフィルターにしたらリレーションシップが非アクティブになった」と相談されました。何が起きた可能性が高いですか。どう直しますか。

## よくあるエラーと対処

| 症状 | 原因 | 対処 |
|---|---|---|
| スライサーが特定のビジュアルに効かない | 経路がない、または向きが逆 | モデル図で経路と矢印の向きを確認する。メジャーで解決を検討 |
| 総計が各行の合計と一致しない | DISTINCTCOUNT や比率は再計算される | 仕様。レポートに注釈を入れて説明する |
| リレーションシップが非アクティブになった | 双方向により経路があいまい | 双方向を単一に戻す |
| 売上0の組み合わせが表示されない | メジャーが空白を返している | 必要なら `+0`。ただし行数の爆発に注意 |
| RLSで見えてはいけない行が見える | 双方向により行フィルターが波及 | 双方向を外し、RLSの経路を単一方向で設計する |
| 数字が想定と違う | 効いているフィルターを把握していない | 7種類のフィルター源をすべて列挙してから調査する |
| 双方向にしたら急に遅くなった | 実行計画が最適化されない | 単一方向に戻し、CROSSFILTER で局所化する |
