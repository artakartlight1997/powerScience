顧客A社は、2025年まではランクB、2026年1月にランクAへ昇格しました。ここで質問です。**2025年の売上は、ランクAとランクBのどちらで集計すべきでしょうか。**

「今のランクで見たい」も「当時のランクで見たい」も、どちらも正当な業務要求です。問題は、**どちらかを選ばずにモデルを作ると、勝手に「今のランク」になる**ことです。その結果、去年のレポートを今年印刷し直すと数字が変わる、という状態が生まれます。

**SCD（Slowly Changing Dimension：緩やかに変化する次元）** は、この問題に対する定型的な設計手法です。

## 何が問題なのか

```figure
{ "type":"tablediff", "arrowLabel":"ランクが B → A に変更",
  "title":"上書きすると、過去のレポートが変わる",
  "caption":"ディメンションを上書きした瞬間、過去に出した集計結果が再現できなくなる",
  "before":{"title":"2025年12月時点の集計","tone":"neutral",
    "head":["ランク","2025年売上"],
    "rows":[["A","4,200万"],["B","!3,100万"],["C","900万"]]},
  "after":{"title":"2026年2月に同じレポートを再表示","tone":"bad",
    "head":["ランク","2025年売上"],
    "rows":[["A","!5,000万"],["B","!2,300万"],["C","900万"]]} }
```

売上データは1行も変わっていません。変わったのは顧客マスタのランク列だけです。それでも過去の集計が変わります。**これを「バグ」と呼ぶか「仕様」と呼ぶかを、設計時に決めておく必要があります。**

## SCDのタイプ

> [!DS] データサイエンス視点
> SCD は Ralph Kimball による次元モデリングの中心概念の1つです。本質は**「時間軸を2つ持つかどうか」**にあります。ファクトが持つ「事象が起きた時刻」に加えて、ディメンションが「その属性値が有効だった期間」を持つ設計を **バイテンポラル モデル**（2つの時間軸を持つモデル）と呼びます。金融や保険の分野では、さらに「システムに記録された時刻」を加えた設計が監査要件として求められます。「いつ起きたか」「いつそう認識していたか」「いつ記録したか」は別物です。

Type2 のポイントは3つです。

1. **顧客キー（サロゲートキー）は行ごとに一意。** 顧客ID（ナチュラルキー）は複数行で重複する
2. **有効期間で、どの時点の姿かを表す。** 現行行の終了日は `9999-12-31` などの番兵値にする
3. **ファクトは「その時点のサロゲートキー」を持つ。** これが履歴参照の要

## サロゲートキーとナチュラルキー

```figure
{ "type":"star", "title":"Type2 ディメンションを含むモデル",
  "caption":"ファクトが持つのはサロゲートキー。ナチュラルキーは属性として保持し、両方で分析できるようにする",
  "fact":{"label":"Fact_売上","lines":["売上日","顧客キー（サロゲート）","商品キー / 金額","※ 顧客IDは持たせてもよいが結合には使わない"]},
  "dims":[
    {"label":"Dim_顧客（Type2）","lines":["顧客キー（一意・サロゲート）","顧客ID（ナチュラル・重複あり）","ランク / 有効開始 / 有効終了 / 現在フラグ"]},
    {"label":"Dim_日付","lines":["年 / 月 / 四半期"]},
    {"label":"Dim_商品","lines":["商品キー / カテゴリ"]},
    {"label":"Dim_顧客現在（ビュー）","lines":["現在フラグ = Yes の行のみ","「今の姿」で分析したいとき用"]}
  ],
  "edgeLabel":"1対多" }
```

| キーの種類 | 例 | 性質 |
|---|---|---|
| ナチュラルキー（自然キー・業務キー） | 顧客ID `C001` | 業務側で決まる。意味を持つ。体系が変わることがある |
| サロゲートキー（代理キー） | 顧客キー `1`, `4` | システムが振る連番。意味を持たない。**Type2 では行ごとに一意** |

> [!TRAP] つまずきポイント
> **ファクトにナチュラルキー（顧客ID）だけを持たせると、Type2 は成立しません。** 顧客ID `C001` はディメンションに2行あるので、リレーションシップが「多対多」になり、1つの売上に対してランクAとランクBの両方が対応してしまいます。**ETL の段階で、売上日に対応する有効なサロゲートキーを引き当てて、ファクトに埋め込む**必要があります。この処理を「サロゲートキー ルックアップ」と呼びます。

```sql
-- ETL：売上日時点で有効な顧客キーを引き当てる
SELECT
    f.伝票番号,
    f.売上日,
    d.顧客キー,           -- 当時のサロゲートキーを埋め込む
    f.金額
FROM  stg.売上明細 AS f
LEFT JOIN dw.Dim_顧客 AS d
       ON  d.顧客ID   = f.顧客ID
       AND f.売上日  >= d.有効開始
       AND f.売上日  <  d.有効終了;
```

> [!TIP] 実務のコツ
> この引き当ては **ソース側（DWHのETL）で行うのが本来の姿**です。Power Query でも書けますが、ファクトが大きいと折りたたみが切れて更新が重くなります。**SCDは、Power BI が引き受けるべき仕事ではなくデータウェアハウス側の仕事**、というのが基本的な立場です。ただし現実にはDWHがない現場も多いので、次に Power Query での実装も示します。

## Power Query で Type2 を組む

ソースが「現在の姿」しか持たない場合、履歴は自分で蓄積するしかありません。**スナップショット方式**が最も単純で確実です。

```figure
{ "type":"pipeline", "title":"スナップショット方式で履歴を作る",
  "caption":"毎日のマスタの姿を保存し続け、そこから変化点を検出して有効期間に変換する",
  "nodes":[
    {"id":"src","label":"ソースの顧客マスタ\n（現在の姿のみ）","tone":"blue"},
    {"id":"snap","label":"日次スナップショット\n日付 + 全件を追記","tone":"cyan"},
    {"id":"chg","label":"変化点の検出\n前日と属性を比較","tone":"amber"},
    {"id":"scd","label":"Type2 ディメンション\n有効開始 / 有効終了","tone":"good"},
    {"id":"model","label":"セマンティックモデル","tone":"violet"}
  ],
  "edges":[
    {"from":"src","to":"snap","label":"毎日保存"},
    {"from":"snap","to":"chg","label":"差分を取る"},
    {"from":"chg","to":"scd","label":"期間に変換"},
    {"from":"scd","to":"model"}
  ] }
```

```m
// スナップショットから Type2 を組み立てる
let
    Snap = スナップショット履歴,   // 列: スナップ日, 顧客ID, 顧客名, ランク

    // 1) 顧客IDごとに日付順で並べる
    並べ替え = Table.Sort(Snap, {{"顧客ID", Order.Ascending}, {"スナップ日", Order.Ascending}}),

    // 2) 属性をひとまとめのハッシュにする。比較対象の列を明示するのが重要
    ハッシュ付き = Table.AddColumn(並べ替え, "属性ハッシュ",
        each Text.Combine({[顧客名], [ランク]}, "|"), type text),

    // 3) 顧客IDでグループ化し、グループ内で変化点だけを残す
    グループ化 = Table.Group(ハッシュ付き, {"顧客ID"}, {
        {"明細", each
            let
                idx = Table.AddIndexColumn(_, "i", 0, 1, Int64.Type),
                前行 = Table.AddColumn(idx, "前ハッシュ",
                    (r) => if r[i] = 0 then null
                           else Table.SelectRows(idx, each [i] = r[i] - 1){0}[属性ハッシュ], type text),
                変化点 = Table.SelectRows(前行, each [前ハッシュ] = null or [前ハッシュ] <> [属性ハッシュ])
            in
                変化点, type table}
    }),
    展開 = Table.ExpandTableColumn(グループ化, "明細",
        {"スナップ日", "顧客名", "ランク", "属性ハッシュ"}),

    // 4) 有効開始 = その変化点の日、有効終了 = 次の変化点の前日
    並べ2 = Table.Sort(展開, {{"顧客ID", Order.Ascending}, {"スナップ日", Order.Ascending}}),
    Idx = Table.AddIndexColumn(並べ2, "行番号", 0, 1, Int64.Type),
    有効終了 = Table.AddColumn(Idx, "有効終了", (r) =>
        let
            次 = Table.SelectRows(Idx, each [顧客ID] = r[顧客ID] and [行番号] = r[行番号] + 1)
        in
            if Table.IsEmpty(次) then #date(9999,12,31)
            else Date.AddDays(次{0}[スナップ日], -1), type date),

    // 5) 有効開始の改名とサロゲートキー付与
    改名 = Table.RenameColumns(有効終了, {{"スナップ日", "有効開始"}}),
    現在 = Table.AddColumn(改名, "現在フラグ",
        each if [有効終了] = #date(9999,12,31) then "Yes" else "No", type text),
    SK = Table.AddIndexColumn(現在, "顧客キー", 1, 1, Int64.Type),
    整理 = Table.SelectColumns(SK,
        {"顧客キー", "顧客ID", "顧客名", "ランク", "有効開始", "有効終了", "現在フラグ"})
in
    整理
```

> [!TRAP] つまずきポイント
> このコードは、**行数が多いと極端に遅くなります**。`Table.SelectRows` を各行から呼んでいるため、計算量が行数の2乗に比例するからです。数千行のマスタなら問題ありませんが、数十万行では実用になりません。大規模な場合は、**必ずソース側（SQL の `LAG` / `LEAD` ウィンドウ関数）で処理してください**。Power Query での SCD 構築は「小さなマスタの応急処置」と位置づけるべきです。

> [!TRAP] つまずきポイント
> **どの列の変化を「履歴を残すべき変化」とみなすか**を決めずに実装すると、住所の表記ゆれや電話番号の更新のたびに新しい行が生まれ、ディメンションが爆発します。上のコードで属性ハッシュに含めた列（顧客名・ランク）だけが変化点の判定対象です。**履歴を残す列と、上書きでよい列を明示的に分ける**のが Type6 の考え方であり、実務ではこれが最も現実的です。

## 時点参照のDAX

サロゲートキーがファクトに埋め込まれていれば、DAXは何も特別なことをしません。普通に集計するだけで「当時の姿」で集計されます。

```dax
-- 当時のランクで集計（サロゲートキー結合なので、これだけで正しい）
売上合計 = SUM( Fact_売上[金額] )
```

「今のランクで見たい」場合は、現在フラグでフィルターした別のディメンション（またはメジャー）を用意します。

```dax
-- 現在のランクで集計する（顧客IDで対応付け直す）
売上合計_現在ランク基準 =
CALCULATE(
    SUM( Fact_売上[金額] ),
    TREATAS(
        VALUES( Dim_顧客現在[顧客ID] ),
        Dim_顧客[顧客ID]
    )
)
```

サロゲートキーがファクトに無く、顧客IDしか持っていない場合は、DAXで時点判定します（**ファクトが小さい場合の応急処置**です）。

```dax
-- 売上日時点で有効な行を引き当てて集計する（重い。小規模向け）
売上_時点参照 =
SUMX(
    Fact_売上,
    VAR 日 = Fact_売上[売上日]
    VAR 顧客 = Fact_売上[顧客ID]
    VAR 該当ランク =
        CALCULATE(
            SELECTEDVALUE( Dim_顧客[ランク] ),
            REMOVEFILTERS( Dim_顧客 ),
            Dim_顧客[顧客ID] = 顧客,
            Dim_顧客[有効開始] <= 日,
            Dim_顧客[有効終了] >= 日
        )
    RETURN
        IF( 該当ランク = SELECTEDVALUE( Dim_ランク[ランク] ), Fact_売上[金額] )
)
```

> [!WARN] 注意
> 上のような行ごとの時点判定は、**ファクトが数十万行を超えると実用的な速度になりません**。「DAXで解ける」ことと「DAXで解くべき」ことは別です。**時点の解決は取り込み時に1度だけ行い、結果をキーとして保存する**のが正しい設計です。

## Type6 — 両方の見方を1つのディメンションで

実務で最も便利なのが Type6（ハイブリッド）です。Type2 の行に、Type1 の「現在の値」列も持たせます。

| 顧客キー | 顧客ID | ランク（当時） | 現在ランク | 有効開始 | 有効終了 |
|---|---|---|---|---|---|
| 1 | C001 | B | **A** | 2020-04-01 | 2025-12-31 |
| 4 | C001 | A | **A** | 2026-01-01 | 9999-12-31 |
| 2 | C002 | B | **B** | 2021-06-01 | 9999-12-31 |

`ランク（当時）` で集計すれば当時の姿、`現在ランク` で集計すれば今の姿。**同じテーブル・同じリレーションシップのまま、列を選ぶだけで切り替えられます。** レポート作成者にとって最も分かりやすい形です。

> [!TIP] 実務のコツ
> 列名には必ず「当時」「現在」を明記してください。`ランク` と `顧客ランク` のような区別のつかない名前にすると、必ず取り違えられます。**列名は仕様書です。**

## 実装後の検証

| 検証項目 | 方法 | 期待結果 |
|---|---|---|
| 期間の重複 | 同じ顧客IDで、有効期間が重なる行がないか | 0件 |
| 期間の欠落 | 前行の有効終了 + 1日 = 次行の有効開始 か | すべて連続 |
| 現在行の一意性 | 顧客IDごとに現在フラグ = Yes が1件か | すべて1件 |
| サロゲートキーの一意性 | 顧客キーの重複 | 0件 |
| ファクトの引き当て漏れ | 顧客キーが null または不明キーの行数 | 0件、または既知の件数 |
| 総計の一致 | Type2導入前後で、全期間の売上合計 | 完全に一致する |

> [!TRAP] つまずきポイント
> **総計が一致しないなら、必ずどこかが壊れています。** 履歴を持たせても、売上金額の総和は変わらないはずです。変わる場合は、引き当て漏れ（不明キー）か、期間の重複による二重計上です。この検証を最初に行ってください。

> [!EXAM] PL-300で問われる
> PL-300 では SCD そのものを深く問う設問は多くありませんが、**サロゲートキーの役割**、**ディメンションの履歴管理**、**一意でないキーでのリレーションシップの問題**として関連論点が出題されます。「ディメンションテーブルの主キーが一意でない場合の対処」という設問には、**サロゲートキーを追加する**が正解になります。

## 設計判断チェックリスト

- [ ] 属性ごとに、履歴を残すか上書きするかを決めたか。一律で決めていないか
- [ ] 「当時の姿」と「今の姿」のどちらが業務上の既定かを、利用部門と合意したか
- [ ] ディメンションのキーはサロゲートキーにしたか
- [ ] ファクトはサロゲートキーを持っているか。ナチュラルキーで結合していないか
- [ ] サロゲートキーの引き当ては、取り込み時に1度だけ行っているか
- [ ] 有効期間に重複・欠落がないことを検証したか
- [ ] 現在フラグが顧客IDごとに1件だけであることを検証したか
