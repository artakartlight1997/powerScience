「売上はいくらか」「利益率は何％か」「去年より伸びたか」——
この問いに答える言語が **DAX**（Data Analysis Expressions）です。

## DAXはExcelの数式ではない

DAXの関数名は Excel とよく似ています。`SUM`、`IF`、`AVERAGE`。
だから多くの人が「Excelの延長」だと思って書き始め、そして最初の10分でつまずきます。

**似ているのは名前だけで、計算の単位がまったく違うからです。**

Excelの数式は **セル** を計算します。`=B2*C2` は「2行目のB列と、2行目のC列」という座標の掛け算です。
DAXには座標がありません。DAXが扱うのは **列** と **表** と **フィルター** の3つだけです。

```figure

  "panels":[
    {"title":"Excelの数式","tone":"neutral","items":[
      "計算の単位は「セル」",
      "=B2*C2 のように座標で指定する",
      "1つの行に1つの数式を書き、下にコピーする",
      "数式は結果と同じ場所に置かれる",
      "どのセルを見ても、答えは1つに決まっている"],
     "note":"座標の世界"},
    {"title":"DAX","tone":"violet","items":[
      "計算の単位は「列」と「表」",
      "Fact_売上[SalesAmount] のように名前で指定する",

      "同じ式が、置かれたセルごとに違う答えを返す"],
     "note":"名前とフィルターの世界"} ] }
```

> [!NOTE] 要点
> DAXの1行目の心構えは「セルを忘れる」ことです。あなたが書くのは**1つの定義**であり、その定義が何百万行にどう適用されるかはエンジンが決めます。

## 最初のメジャーを書いてみる

いきなり理屈から入っても身につきません。まず1本書きます。

```dax
売上合計 = SUM( Fact_売上[SalesAmount] )
```

これだけです。この1行が意味するのは「**いま見えている範囲の** `SalesAmount` 列を全部足す」。
太字にした部分が、Excelとの違いの核心です。範囲は式の中に書かれていません。

## 同じ式が違う答えを返す理由

メジャーは、置かれた場所ごとに **フィルターコンテキスト**（そのセルに効いている絞り込み条件の集まり）を受け取ります。
式の中には範囲が書かれていないので、範囲は外から与えられます。

```figure
{ "type":"pipeline", "title":"セルに値が入るまで", "caption":"エンジンは「セルごとに」この流れを最初からやり直す",
  "nodes":[
    {"id":"a","label":"セルの位置","tone":"blue"},
    {"id":"b","label":"フィルターが決まる\nCategory = \"家電\"","tone":"amber"},
    {"id":"c","label":"Fact_売上 が絞られる\n該当行だけ残る","tone":"cyan"},
    {"id":"d","label":"SUM が実行される","tone":"violet"},
    {"id":"e","label":"52,000,000","tone":"good"} ],
  "edges":[
    {"from":"a","to":"b","label":"行・列・スライサー"},
    {"from":"b","to":"c","label":"リレーションで伝播"},
    {"from":"c","to":"d","label":"残った行に対して"},
    {"from":"d","to":"e","label":"1つの数値"} ] }
```

合計行のセルには `Category` の絞り込みがありません。だから全行が対象になり、`100,000,000` が出ます。
**合計行は「上の3行を足したもの」ではなく、「絞り込みなしでもう一度計算し直したもの」です。**

この違いは、いまは「同じことでは？」と感じるかもしれません。`SUM` なら確かに同じ結果になります。
しかし次のような指標では、結果が食い違います。

| Category | 売上合計 | 顧客数（重複なし） |
|---|---|---|
| 家電 | 52,000,000 | 320 |
| 衣料 | 18,000,000 | 210 |
| 食品 | 30,000,000 | 480 |
| **合計** | **100,000,000** | **800** |

顧客数の列を縦に足すと `320 + 210 + 480 = 1,010` ですが、合計行は `800` です。
間違いではありません。3カテゴリすべてを買った人が重複して数えられていないだけです。

> [!DS] 加法性という考え方
> 「行の値を足すと合計になる」性質を **加法性** といいます。売上金額や数量は加法的です。
> 一方、重複を除いた人数・在庫残高・比率は加法的ではありません。
> BIの数字が合わないと言われる原因の多くは、**非加法的な指標を足し算できると誤解している**ことにあります。この性質は M07 のこの後のレッスンで繰り返し登場します。

> [!TRAP] 「合計行がおかしい」は、たいてい正しい
> ユーザーから「合計が合わない」と言われたとき、まず疑うのはバグではなく**指標の性質**です。
> 合計行は独立して評価されるという原則を知っていれば、その場で説明できます。

DAXの関数は、必ず次のどちらかを返します。ここを最初に分類しておくと、後で関数を覚える負担が激減します。

## DAXはどこで動いているのか

DAXの式は、Power BI のファイルの中の **セマンティックモデル**（データと指標定義を持つ層）で評価されます。
レポートは、そのモデルに「この条件でこの指標をください」と問い合わせているだけです。

```figure
{ "type":"stack", "title":"DAXが評価される層", "caption":"レポートは問い合わせるだけ。答えを作るのはモデル層",
  "layers":[
    {"label":"レポート","sub":"ビジュアルが「条件＋指標」を要求する","tone":"pink"},
    {"label":"DAXクエリ","sub":"ビジュアルごとに自動生成される問い合わせ","tone":"amber"},
    {"label":"セマンティックモデル","sub":"メジャー定義・リレーション・列がある層","tone":"violet"},
    {"label":"列指向ストレージ","sub":"圧縮されたデータ本体","tone":"blue"} ] }
```

だから **メジャーを1本直せば、それを使っている全ビジュアルが同時に直ります**。
Excelのように、シートごとに数式を貼り直す必要はありません。これがDAXの最大の利点です。

> [!EXAM] PL-300で問われる
> 「同じ計算を複数のビジュアルで使い回すにはどうするか」という問題では、答えはほぼ常に**メジャーを作る**です。
> 計算列や、ビジュアル側の「クイックメジャー」を選ばせる選択肢は、たいていダミーです。

## DAXを書ける場所は3か所ある

同じDAXという言語を、Power BI は3つの用途で使います。名前が似ているので、最初に整理しておきます。

```figure
{ "type":"cards", "cols":3, "title":"DAXの3つの置き場所", "caption":"文法は共通だが、評価されるタイミングと結果の形が違う",
  "items":[
    {"icon":"Σ","title":"メジャー","text":"集計時に、ビジュアルのセルごとに評価される。結果はスカラー。実務のDAXの大半はこれ。","tone":"violet"},
    {"icon":"▤","title":"計算列","text":"データ更新時に、行ごとに一度だけ評価される。結果は表に実体として保存される。","tone":"blue"},
    {"icon":"▦","title":"計算テーブル","text":"データ更新時に評価され、新しい表そのものを作る。日付テーブルの生成などに使う。","tone":"green"} ] }
```

たとえば日付テーブルは、計算テーブルとして1行で作れます。

```dax
Dim_日付 = CALENDAR( DATE(2022,1,1), DATE(2025,12,31) )
```

この式は `CALENDAR` がテーブルを返すので、メジャーには使えません。計算テーブルだからこそ成立します。
**「どこに置くか」で、使える関数の戻り値の型が決まる** ということです。

> [!WARN] 名前だけで判断しない
> データペインでは、メジャーには計算機のアイコン、計算列には表アイコンが付きます。
> このアイコンを毎回確認する癖をつけてください。名前が同じでも、挙動はまったく違います。

## 理解度チェック

**問1.** `売上合計 = SUM( Fact_売上[SalesAmount] )` というメジャーを、カテゴリ別のテーブルと、スライサーで「2024年」を選んだカードの両方に置いた。式は1つなのに値が違うのはなぜか。

<details><summary>答え</summary>
メジャーの式には対象範囲が書かれておらず、範囲は置かれた場所のフィルターコンテキストから与えられるため。テーブルの各行では `Category` の条件が、カードでは `Dim_日付` の年の条件が効いている。
</details>

**問2.** `顧客数 = DISTINCTCOUNT( Fact_売上[CustomerID] )` をカテゴリ別に表示したら、各行の合計（1,010）と合計行の値（800）が一致しなかった。バグか。

<details><summary>答え</summary>
バグではない。合計行は各行の和ではなく、フィルターなしで独立に再計算された結果。重複顧客が一度しか数えられないため、合計行は各行の和より小さくなる。重複を除いた人数は非加法的な指標である。
</details>

**問3.** `売上明細 = FILTER( Fact_売上, Fact_売上[Quantity] > 10 )` をメジャーとして作ろうとしたらエラーになった。理由は何か。

<details><summary>答え</summary>
`FILTER` はテーブルを返す関数であり、メジャーは必ずスカラー（単一の値）を返さなければならないため。`COUNTROWS` や `SUMX` などのスカラー関数で包む必要がある。
</details>

## よくあるエラーと原因

| エラーメッセージ | 原因 | 対処 |
|---|---|---|
| 「1つの値が必要ですが、複数の値が…」 | メジャーの中で列を直接参照した | 集計関数で包む（`SUM(...)` など） |
| 「テーブル式は…に変換できません」 | メジャーの最外側がテーブル関数 | `COUNTROWS` `SUMX` などスカラー関数で包む |
| 「列 'X' が見つかりません」 | 列名の変更、または全角の角かっこ | 半角 `[ ]` を使い、列名を再確認する |
| 「メジャー 'X' はテーブルの一部ではありません」 | メジャー参照にテーブル名を付けた | `Dim_商品[売上合計]` → `[売上合計]` |
| 数字は出るがすべて同じ値 | ビジュアルにディメンション列を置いていない | 行に `Dim_商品[Category]` などを追加する |

> [!NOTE] このレッスンのまとめ
> DAXは「セル」ではなく「列・表・フィルター」の言語です。式は1つだけ書き、その式が置かれた場所ごとに違う答えを返します。
> 関数の戻り値はスカラーかテーブルのどちらかで、メジャーの最外側は必ずスカラーです。
> そして合計行は、各行の和ではなく**独立した再計算**です。この3つを持って、次のレッスンへ進みます。
