## 01. 列同士の掛け算を SUM で書く

**症状**：売上金額が実際の数十倍〜数百倍になる。エラーは出ない。

**原因**：`SUM` は列を1本しか受け取れず、列同士の演算ができない。

```dax
-- 誤り
売上 = SUM( Fact_売上[UnitPrice] ) * SUM( Fact_売上[Quantity] )

-- 正しい
売上 = SUMX( Fact_売上, Fact_売上[UnitPrice] * Fact_売上[Quantity] )
```

**なぜそうなるのか**：前者は「単価の総和 × 数量の総和」を計算しています。数学的には `(Σa)(Σb)` であり、求めたい `Σ(a·b)` とは別物です。両者が一致するのは全行が同じ値のときだけです。

## 02. イテレータの中でメジャーを式に展開する

**症状**：メジャーを分解して直接書いたら、結果が行数倍に膨らんだ。

**原因**：メジャー参照には暗黙の `CALCULATE` が付いており、展開するとコンテキスト遷移が消える。

```dax
-- 誤り：遷移が起きず、全行で総売上が返る
X = SUMX( VALUES( Dim_顧客[CustomerID] ), SUM( Fact_売上[SalesAmount] ) )

-- 正しい
X = SUMX( VALUES( Dim_顧客[CustomerID] ), [売上合計] )
-- または
X = SUMX( VALUES( Dim_顧客[CustomerID] ), CALCULATE( SUM( Fact_売上[SalesAmount] ) ) )
```

**なぜそうなるのか**：行コンテキストは集計関数のフィルターになりません。CALCULATE がそれをフィルターコンテキストに変換して初めて、顧客ごとの絞り込みが起きます。

## 03. 平均の平均を取る

**症状**：全体の平均が、明細の平均と一致しない。

**原因**：小計の平均を平均しても、全体の平均にはならない。

```dax
-- 誤り：店舗ごとの平均単価を平均している
平均単価 = AVERAGEX( VALUES( Dim_店舗[StoreID] ), AVERAGE( Fact_売上[UnitPrice] ) )

-- 正しい：全体の加重平均
平均単価 = DIVIDE( SUM( Fact_売上[SalesAmount] ), SUM( Fact_売上[Quantity] ) )
```

**なぜそうなるのか**：平均は加算的ではありません。1,000件の店舗と10件の店舗の平均を単純平均すると、小さい店舗が過剰に効きます。**加重平均は「合計 ÷ 合計」で書く**のが原則です。

## 04. DISTINCTCOUNT を足し算する

**症状**：地域別の顧客数を足すと、総計と合わない。

**原因**：重複のある集合を数える指標は加算的でない（非加法的指標）。

```dax
-- 総計は各行の和にならない。これは正常な挙動
顧客数 = DISTINCTCOUNT( Fact_売上[CustomerID] )
```

**なぜそうなるのか**：同じ顧客が関東と関西の両方で買っていれば、両方の行で1人として数えられます。総計では1人です。**バグではないので、レポートに注記を添えてユーザーに説明してください。** 「合計を足しても総計にならない」ことを事前に伝えるのがプロの仕事です。

## 05. FILTER でテーブル全体を渡す

**症状**：メジャーが遅い。数百ミリ秒〜数秒かかる。

**原因**：`FILTER( Fact_売上, ... )` は全列を持った巨大な表を数式エンジンで走査する。

```dax
-- 遅い
売上_家電 = CALCULATE( [売上合計], FILTER( Fact_売上, RELATED( Dim_商品[Category] ) = "家電" ) )

-- 速い
売上_家電 = CALCULATE( [売上合計], Dim_商品[Category] = "家電" )
```

**なぜそうなるのか**：簡易構文 `列 = 値` は、エンジンが `FILTER( ALL( Dim_商品[Category] ), ... )` に展開します。走査対象が「カテゴリの一意値8件」だけになり、ストレージエンジンだけで完結します。**FILTER に渡すのは、判定に必要な最小の列**が鉄則です。

## 06. ALL と ALLSELECTED を取り違える

**症状**：スライサーで絞ったのに、構成比の合計が100%にならない。

**原因**：`ALL` はスライサーの選択まで無視する。

```dax
-- 誤り：スライサーを無視した分母
構成比 = DIVIDE( [売上合計], CALCULATE( [売上合計], ALL( Dim_商品 ) ) )

-- 正しい：表示中の合計を分母にする
構成比 = DIVIDE( [売上合計], CALCULATE( [売上合計], ALLSELECTED( Dim_商品 ) ) )
```

**なぜそうなるのか**：`ALL` はモデル全体のフィルターを外し、`ALLSELECTED` は「ビジュアルの外側から来たフィルター（スライサーやページフィルター）」を残して、ビジュアル内の行列見出しだけを外します。**ユーザーが見ている表の中での割合が欲しいなら ALLSELECTED**です。

## 07. ALL にテーブル全体を渡してしまう

**症状**：カテゴリスライサーを選んでも、ランキングが全商品の中での順位のまま。

**原因**：`ALL( Dim_商品 )` はカテゴリ列のフィルターまで解除する。

```dax
-- 誤り
ランク = RANKX( ALL( Dim_商品 ), [売上合計] )

-- 正しい：順位を競わせたい列だけを解放する
ランク = RANKX( ALLSELECTED( Dim_商品[ProductName] ), [売上合計] )
```

**なぜそうなるのか**：`ALL( テーブル )` はそのテーブルの**全列**のフィルターを外します。`ALL( テーブル[列] )` はその列だけです。カテゴリ内順位が欲しいなら、商品名列だけを解放します。

## 08. ALLEXCEPT の引数の順序を間違える

**症状**：`ALLEXCEPT` を使ったのにフィルターが残らない、または全部残る。

**原因**：第1引数はテーブル、第2引数以降は「**残したい**列」である。

```dax
-- 正しい：カテゴリだけを残し、他は解除する
カテゴリ内構成比 =
DIVIDE( [売上合計], CALCULATE( [売上合計], ALLEXCEPT( Dim_商品, Dim_商品[Category] ) ) )
```

**なぜそうなるのか**：名前が「ALL、ただし EXCEPT（除く）」なので「除外する列」と誤読されがちですが、意味は「**列挙した列以外のすべてを ALL する**」です。列挙した列のフィルターは保持されます。

## 10. 非アクティブリレーションを使い忘れる

**症状**：出荷日ベースの売上を出したいのに、注文日ベースの数字が返る。

**原因**：アクティブなリレーションだけが自動的に使われる。

```dax
-- 正しい
出荷日ベース売上 =
CALCULATE( [売上合計], USERELATIONSHIP( Fact_売上[ShipDate], Dim_日付[Date] ) )
```

**なぜそうなるのか**：2つのテーブル間で有効になるリレーションは常に1本だけです。`USERELATIONSHIP` は「この式の評価中だけ、このリレーションをアクティブにする」という指定で、CALCULATE の中でのみ使えます。

## 11. 割り算に DIVIDE を使わない

**症状**：無限大の記号が表示される、またはビジュアル全体がエラーになる。

**原因**：分母がゼロや BLANK になるケースを想定していない。

```dax
-- 誤り
達成率 = [売上合計] / [目標額]

-- 正しい
達成率 = DIVIDE( [売上合計], [目標額] )
達成率 = DIVIDE( [売上合計], [目標額], 0 )   -- ゼロを返したい場合
```

**なぜそうなるのか**：`DIVIDE` はゼロ除算を検出して第3引数（省略時は BLANK）を返します。さらに、内部的に最適化されているため性能面でも `/` より有利です。**DAXの除算はすべて DIVIDE で書く**と決めてしまってください。

## 13. 文字列比較の型を意識しない

**症状**：`SELECTEDVALUE` の結果と比較しても常に FALSE になる。

**原因**：数値として保持されている列を文字列と比較している、または前後に空白がある。

```dax
-- 危険
判定 = IF( SELECTEDVALUE( Dim_商品[Category] ) = "家電 ", "対象", "対象外" )

-- 安全
判定 = IF( TRIM( SELECTEDVALUE( Dim_商品[Category] ) ) = "家電", "対象", "対象外" )
```

**なぜそうなるのか**：DAXの文字列比較は既定で大文字小文字を区別しませんが、**前後の空白は区別します**。データ側で `TRIM` するのが本筋で、DAX での TRIM は応急処置です。Power Query で洗ってください。

## 14. 循環依存を作る

**症状**：「循環依存関係が検出されました」というエラーで計算列が作れない。

**原因**：計算列Aが計算列Bを参照し、BがAを参照している。あるいは `CALCULATE` を含む計算列が同じテーブルの他の計算列に依存している。

```dax
-- 危険：同一テーブル内で CALCULATE を含む計算列を相互参照する
```

**なぜそうなるのか**：`CALCULATE` を含む計算列はコンテキスト遷移を起こし、そのテーブルの**全列**への依存が発生します。結果として、同じテーブルの他の計算列との間で循環が生まれます。解決策は、依存の一方をメジャーにするか、Power Query 側で列を作ることです。

## 16. 計算列を Power Query で作れるのにDAXで作る

**症状**：モデルサイズが想定より大きい。更新が遅い。

**原因**：DAXの計算列は、Power Query のカスタム列より圧縮が効きにくい。

**なぜそうなるのか**：Power Query で作った列は、他の列と同じタイミングでエンコードとソート最適化の対象になります。DAXの計算列は全列のロード後に評価されるため、**セグメント内での並べ替え最適化の恩恵を受けにくく**、圧縮率が落ちます。**上流でできることは上流でやる**のが原則です。

## 17. 使わない列を残す

**症状**：モデルが1GBを超え、更新に失敗する。

**原因**：ソースの全列をそのまま読み込んでいる。

**なぜそうなるのか**：VertiPaq は列単位で保存するため、**使わない列は1バイトも読まなければゼロコスト**です。逆に、読み込めば必ず容量を食います。特に「注文ID」「トランザクションGUID」のような一意な文字列列は、辞書が巨大になりモデルサイズの大半を占めます。**Power Query で列を削除してください。**

## 19. 変数を使わず同じ式を何度も書く

**症状**：メジャーが遅い。読みにくい。

**原因**：同じ計算を複数回書くと、そのぶん評価される。

```dax
-- 誤り：[売上合計] が3回評価される
成長率 = IF( [売上合計] > 0, ( [売上合計] - [前年売上] ) / [売上合計] )

-- 正しい
成長率 =
VAR Sales = [売上合計]
VAR PrevSales = [前年売上]
RETURN
    IF( Sales > 0, DIVIDE( Sales - PrevSales, Sales ) )
```

**なぜそうなるのか**：DAXエンジンは同一式の共通部分式除去をある程度行いますが、フィルターコンテキストが違えば別の式として扱われます。**VAR は宣言時に1度だけ評価され、以降は値が再利用されます。** 可読性と性能の両方が改善する、数少ない「完全に得な」書き換えです。

> [!DS] データサイエンス視点
> 20項目のうち 01・03・04 は、**集計の加法性（additivity）**という共通の問題に帰着します。合計は加法的、平均と個数（重複排除あり）は非加法的です。データウェアハウスの世界では指標を「加法的 / 半加法的 / 非加法的」の3つに分類します。在庫残高は「時間軸では非加法的、他の軸では加法的」な半加法的指標の典型で、`LASTNONBLANKVALUE` などの専用関数が必要になります。**この分類を意識すると、総計がおかしくなる指標を事前に予測できます。**

> [!EXAM] PL-300で問われる
> 01（SUMX の必要性）、06（ALL と ALLSELECTED）、10（USERELATIONSHIP）、11（DIVIDE）は試験の頻出項目です。特に「スライサーの選択を尊重するかどうか」を問う設問は、ALL 系関数の使い分けを問う形で繰り返し出題されます。

## 理解度チェック

**問1.** 次のメジャーの総計行が明細の合計と一致しません。これはバグですか。

```dax
顧客数 = DISTINCTCOUNT( Fact_売上[CustomerID] )
```

<details>
<summary>解答</summary>

**バグではありません。** 同じ顧客が複数の地域や月にまたがって購入していれば、各行では1人ずつ数えられ、総計では重複が排除されて1人になります。これは非加法的指標の正常な挙動です。ユーザーに誤解されないよう、レポートに注記を入れるのが正しい対応です。
</details>

**問2.** `CALCULATE( [売上合計], FILTER( Fact_売上, RELATED( Dim_商品[Category] ) = "家電" ) )` が遅い理由を、走査対象の観点から説明してください。

<details>
<summary>解答</summary>

FILTER が `Fact_売上` の全行（数百万行）を数式エンジンで1行ずつ走査し、各行で `RELATED` によるディメンション参照を行っているためです。`CALCULATE( [売上合計], Dim_商品[Category] = "家電" )` と書けば、走査対象がカテゴリの一意値だけになり、ストレージエンジンのフィルターとして処理されます。
</details>

**問3.** 「秒単位の日時列」がモデルサイズを圧迫する理由と、その対処を説明してください。

<details>
<summary>解答</summary>

辞書符号化では一意な値の数だけ辞書エントリが必要になり、秒単位の日時は3年で約860万通りになるためです。日付列と時刻列に分割すると、1,095 + 1,440 = 2,535 通りに激減し、圧縮が劇的に効きます。時刻の精度が分単位で足りるなら、さらに丸めてカーディナリティを下げます。
</details>

## 実務チェックリスト

- [ ] 列同士の演算を含む集計が、すべてイテレータで書かれているか確認した
- [ ] イテレータ内のメジャー参照が、意図どおりコンテキスト遷移を起こしているか確認した
- [ ] 平均を「平均の平均」で計算している箇所がないか確認した
- [ ] 非加法的指標（DISTINCTCOUNT など）にレポート上の注記を付けた
- [ ] FILTER の第1引数を、判定に必要な最小の列に絞った
- [ ] 構成比の分母が ALL か ALLSELECTED か、要件に照らして確認した
- [ ] ALL に渡しているのがテーブルか列かを、1つずつ確認した
- [ ] モデルの双方向リレーションを棚卸しし、CROSSFILTER に置き換えられないか検討した
- [ ] すべての除算が DIVIDE になっているか確認した
- [ ] BLANK と 0 の扱いが、ビジュアルの表示要件と一致しているか確認した
- [ ] 循環依存が出た計算列を、メジャーまたは Power Query に移した
- [ ] 使わない列を Power Query で削除した
- [ ] 秒単位の日時列を日付と時刻に分割した
- [ ] 同じ式の繰り返しを VAR にまとめた
- [ ] すべてのメジャーで総計行を目視確認した
