前のレッスンで、`CALCULATE` のフィルター引数は **上書き** だと確認しました。

```dax
家電売上 = CALCULATE( [売上合計], Dim_商品[Category] = "家電" )
```

これをカテゴリ別のテーブルに置くと、衣料の行にも食品の行にも `52` が出ます。
**では、「家電の行だけ52、他は空白」にしたいときはどうするのか。**

答えが `KEEPFILTERS` です。そしてもう1つ、条件が複雑になったときに必要になるのが `FILTER` です。
このレッスンで、条件の書き方3種類を完全に整理します。

```figure

    {"icon":"↔","title":"述語（既定）","text":"Dim_商品[Category] = \"家電\" — 同じ列の既存条件を上書きする。最も速い。","tone":"blue"},
```

## なぜ既定が「上書き」なのか

述語の正体を知ると、上書きの理由が腑に落ちます。

```dax
-- あなたが書く式
CALCULATE( [売上合計], Dim_商品[Category] = "家電" )

-- エンジンが内部で解釈する式
CALCULATE( [売上合計], FILTER( ALL( Dim_商品[Category] ), Dim_商品[Category] = "家電" ) )
```

```figure
{ "type":"formula", "lang":"dax", "title":"述語は ALL を含んでいる",
  "caption":"述語の内部には ALL があり、これがフィルターを外してから条件を掛け直している",
  "code":"FILTER( ALL( Dim_商品[Category] ), Dim_商品[Category] = \"家電\" )",
  "parts":[
    {"match":"FILTER","label":"表を1行ずつ見て条件に合う行を残す","tone":"amber"},
    {"match":"ALL( Dim_商品[Category] )","label":"ここで既存のCategory条件が外される。これが「上書き」の正体","tone":"violet"},
    {"match":"Dim_商品[Category] = \"家電\"","label":"残す条件","tone":"blue"} ] }
```

つまり述語は「**その列のフィルターを一度全部消してから、指定した条件を掛け直す**」動作です。
だから衣料の行でも、`Category = 衣料` が消えて `Category = 家電` になります。

> [!NOTE] 上書きは仕様であり、便利な性質
> 前年比・全体比較・条件付き集計は、すべてこの上書きがあるから短く書けます。
> 「上書きされて困る」ときだけ、次の `KEEPFILTERS` を使います。

## KEEPFILTERS — 既存の条件を残す

`KEEPFILTERS` は、`ALL` の部分を無効化し、既存の条件と **交差（AND）** させます。

```dax
家電売上KF = CALCULATE( [売上合計], KEEPFILTERS( Dim_商品[Category] = "家電" ) )
```

### 実務での典型例

「高額商品（定価5万円以上）の売上」を、価格帯スライサーと共存させたい場合を考えます。

```dax
-- ✗ 価格帯スライサーの選択が無視される
高額商品売上NG = CALCULATE( [売上合計], Dim_商品[ListPrice] >= 50000 )

-- ✓ スライサーの選択と交差する
高額商品売上 = CALCULATE( [売上合計], KEEPFILTERS( Dim_商品[ListPrice] >= 50000 ) )
```

利用者が「1万〜3万円」の価格帯を選んでいるとき、上の式は **その選択を無視して** 5万円以上を表示します。
下の式は「1万〜3万円 かつ 5万円以上」＝該当なしで空白になります。**後者のほうが誠実です。**

> [!TRAP] スライサーと喧嘩するメジャー
> 「スライサーを動かしても、このメジャーだけ値が変わらない」という苦情の原因は、ほぼこれです。
> 述語で指定した列が、スライサーで使われている列と同じなら、必ず上書きが起きます。
> **同じ列を触るメジャーには、KEEPFILTERS を検討する**と覚えてください。

述語には「1つの列しか参照できない」という制限がありました。
それを超える条件が必要なとき、`FILTER` を使います。

### 例1：複数列にまたがる条件

```dax
-- 1明細の金額が10万円を超える取引だけの売上
大口明細売上 =
CALCULATE(
    [売上合計],
    FILTER( Fact_売上, Fact_売上[Quantity] * Fact_売上[UnitPrice] > 100000 )
)
```

### 例2：メジャーを含む条件

```dax
-- 売上1,000万円超の店舗だけの合計
優良店舗売上 =
CALCULATE(
    [売上合計],
    FILTER( VALUES( Dim_店舗[StoreName] ), [売上合計] > 10000000 )
)
```

店舗ごとの売上で判定されます。これが `FILTER` の強力さであり、同時に重さの原因でもあります。

## FILTER と KEEPFILTERS の関係

`FILTER` で渡した表も、既定では **上書き** です。既存の条件を残したいなら `KEEPFILTERS` で包みます。

```dax
-- 既存の店舗フィルターを残しつつ、売上1,000万円超に絞る
CALCULATE(
    [売上合計],
    KEEPFILTERS( FILTER( VALUES( Dim_店舗[StoreName] ), [売上合計] > 10000000 ) )
)
```

ただし `FILTER( VALUES( … ), … )` の場合、`VALUES` がすでに現在のフィルターを反映しているため、
実質的に交差と同じ結果になることが多くあります。**`ALL` を使ったときだけ `KEEPFILTERS` が効いてくる** と理解してください。

```figure

  "nodes":[
    {"id":"p","label":"述語\n内部で ALL","tone":"blue"},
    {"id":"k","label":"KEEPFILTERS\nALL を無効化","tone":"violet"},
    {"id":"fv","label":"FILTER( VALUES )\n現在の値のみ","tone":"green"},
    {"id":"fa","label":"FILTER( ALL )\n全体から選ぶ","tone":"amber"},
```

> [!DS] 部分集団の定義は分析の出発点
> 「優良顧客」「大口取引」「高額商品」——分析はいつも部分集団の定義から始まります。
> そして定義には必ず **境界の恣意性** があります。売上1,000万円を境にした瞬間、
> 999万円の店舗は「優良でない」ことになります。
> 閾値を1つ動かすと結論が変わる分析は、結論ではなく閾値を報告すべきです。
> DAXで条件を書くときは、その閾値がどこから来たのかを説明できるようにしておいてください。

## 条件の合成

```dax
-- OR：同じ列の複数値
CALCULATE( [売上合計], Dim_商品[Category] IN { "家電", "食品" } )

-- AND：違う列（引数を分ける）
CALCULATE( [売上合計], Dim_商品[Category] = "家電", Dim_店舗[Region] = "関東" )

-- OR：違う列どうし（FILTER が必要）
CALCULATE(
    [売上合計],
    FILTER(
        ALL( Dim_商品[Category], Dim_店舗[Region] ),
        Dim_商品[Category] = "家電" || Dim_店舗[Region] = "関東"
    )
)
```

最後の形は、複数テーブルの列を1つの `ALL` にまとめる必要があるため、実務では
`CROSSJOIN` や `SUMMARIZE` を使った書き方に発展します。**まずは「違う列のORは難しい」と覚えてください。**

> [!EXAM] PL-300で問われる
> 「行のコンテキストを保ったまま追加条件を適用する」→ **KEEPFILTERS**。
> 「メジャーの値を条件にする」→ **FILTER**。
> 「単一列の単純な条件」→ **述語（FILTER不要）**。
> 選択肢に `FILTER( Fact_売上, … )` が並んでいたら、性能面で不適切な選択肢である可能性が高いと考えてください。

## 理解度チェック

**問1.** `CALCULATE( [売上合計], Dim_商品[Category] = "家電" )` がカテゴリ別テーブルの全行で52を返す仕組みを、述語の内部展開を使って説明せよ。

<details><summary>答え</summary>
述語は内部で `FILTER( ALL( Dim_商品[Category] ), Dim_商品[Category] = "家電" )` に展開される。`ALL` が行から来た Category の条件を外すため、どの行でも Category = 家電 に置き換わる。
</details>

**問2.** 価格帯スライサーがあるレポートで「定価5万円以上の売上」メジャーがスライサーに反応しない。原因と対処を述べよ。

<details><summary>答え</summary>
述語が `ListPrice` 列の既存フィルターを上書きしているため。`KEEPFILTERS( Dim_商品[ListPrice] >= 50000 )` で包むと、スライサーの選択と交差（AND）するようになる。
</details>

**問3.** `CALCULATE( [売上合計], FILTER( Fact_売上, RELATED( Dim_商品[Category] ) = "家電" ) )` の問題点は何か。

<details><summary>答え</summary>
ファクトテーブル全体を1行ずつ反復するため非常に遅い。同じ結果は `Dim_商品[Category] = "家電"` という述語で得られ、こちらは行数の少ないディメンション側で処理されるため桁違いに速い。
</details>

## よくあるエラーと原因

| 症状・エラー | 原因 | 対処 |
|---|---|---|
| スライサーが効かないメジャーがある | 同じ列を述語で上書きしている | `KEEPFILTERS` で包む |
| 該当しない行にも値が出る | 上書きの既定動作 | 意図どおりなら正常。空白にしたければ `KEEPFILTERS` |
| 「単一の列を参照する必要があります」 | 述語に複数列を書いた | 引数を分けるか `FILTER` を使う |
| ビジュアルが数十秒かかる | `FILTER( Fact_売上, … )` | 述語に書き換える／`VALUES( 列 )` を反復する |
| `FILTER` の中のメジャーが全体値になる | 反復対象が1行の表になっている | `VALUES( 列 )` や `ALL( 列 )` で対象を明示する |
| KEEPFILTERSを付けても結果が変わらない | もともと別の列への条件で衝突がない | 正常。衝突する場合のみ効果がある |
| 違う列どうしのORが書けない | 述語では表現できない | `FILTER` に複数列の表を渡す形に書き換える |

> [!NOTE] このレッスンのまとめ
> 述語は内部に `ALL` を含むため **上書き** になります。既存の条件を残したいときは `KEEPFILTERS`。
> 複数列やメジャーを含む条件では `FILTER` が必要ですが、**反復対象は必ず最小の表にする**。
> `FILTER( Fact_売上, … )` を書きそうになったら、いったん手を止めてディメンション側で書けないか考えてください。
