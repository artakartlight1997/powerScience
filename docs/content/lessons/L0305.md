レポートは、誰かに見られて初めて仕事になります。自分のPCの中にあるpbixは、まだ作品ではなく下書きです。

このレッスンで、保存 → 発行 → 共有 までを通します。ここまでできれば、ティア1の目標「自分のデータからレポートを1枚作って発行できる」が達成されます。

## 発行前チェックリスト

発行は簡単なので、確認を飛ばしがちです。次の8項目を習慣にしてください。

```figure

    {"icon":"2","title":"残ったフィルター","text":"作業中のフィルターが残っていないか","tone":"blue"},
    {"icon":"3","title":"ページ名","text":"「ページ1」のままになっていないか","tone":"green"},
    {"icon":"4","title":"タイトル","text":"全ビジュアルに意味のある名前があるか","tone":"green"},
    {"icon":"5","title":"ファイル名","text":"正式名称になっているか","tone":"amber"},
    {"icon":"6","title":"機密情報","text":"見せてはいけない列が含まれていないか","tone":"bad"},
    {"icon":"7","title":"更新日時の表示","text":"いつ時点のデータか画面に書いてあるか","tone":"violet"},
    {"icon":"8","title":"定義の記載","text":"主要指標の定義が書いてあるか","tone":"violet"} ] }
```

> [!DS] 共有には責任が伴う
> レポートを発行することは、**組織の意思決定に使われる数字を公開する**ということです。3つの責任が生じます。第一に**正確性**：数字が間違っていれば、間違った判断が下されます。第二に**説明可能性**：「この数字はどう計算したか」に答えられる必要があります。だから定義をレポート内に書きます。第三に**プライバシー**：個人が特定できるデータを不必要に広く公開しないこと。顧客名や連絡先を含むレポートは、本当に全員に必要かを検討してください。集計値だけで足りるなら、明細は出さないのが原則です。技術的にはRLS（行レベルセキュリティ）で制御できますが、**そもそもモデルに入れない**という判断が最も安全です。

## トラブルの切り分け

| 症状 | 原因 | 対処 |
|---|---|---|
| 発行ボタンが押せない | サインインしていない | 組織アカウントでサインイン |
| 発行先にワークスペースが出ない | ライセンス不足またはロール不足 | Pro以上を確認、ロールを確認 |
| 相手が「表示できません」 | 相手のライセンスか権限 | L0204の判定フローを確認 |
| 更新が失敗する | 資格情報未設定・ローカルパス | モデル設定で資格情報を入力 |
| グラフの枠だけ表示される | モデルへのアクセス権がない | 共有時に基になるコンテンツへのアクセスを許可 |
| 数字がDesktopと違う | Service側で編集された | Desktopから再発行して上書き |

## まとめ

- 保存はローカルへの記録、発行はクラウドへの公開。まったく別の操作
- 発行するとpbixは「レポート」と「セマンティックモデル」の2アイテムに分かれる
- 発行後は必ず「データソースの資格情報」と「スケジュール更新」を設定する
- Desktopの資格情報はServiceに引き継がれない。更新失敗の最大の原因
- 共有は直接共有・アプリ・Teams埋め込み・エクスポートの4択。人数と目的で選ぶ
- 発行前チェックリスト8項目を習慣にする。特に「残ったフィルター」と「機密情報」
- 更新時刻は「ソース確定 → 更新 → 閲覧」の順に余裕を持って並べる
- 公開には正確性・説明可能性・プライバシーの3つの責任が伴う
