明細が10億行あります。全部インポートすればメモリに乗りません。DirectQuery にすればメモリは不要ですが、ビジュアルを1つ動かすたびに10億行への集計クエリが飛び、応答は10秒を超えます。

この板挟みを解く道具が **複合モデル（Composite model）** と **集計テーブル（Aggregations）** です。考え方は単純で、**「よく使う粗い集計はメモリに載せ、めったに使わない明細だけソースに問い合わせる」**。

> ディメンションをインポートのままにして、ファクトだけ DirectQuery にすると、**そのリレーションシップは「制限付きリレーションシップ（limited relationship）」** になります。制限付きになると、結合をエンジンがまたいで解決する必要があり、性能が落ちるうえ、**ディメンション側に空白行が生成されなくなります**（不一致キーの検出ができなくなる）。**DirectQuery のファクトにつながるディメンションは、必ずデュアルにしてください。**

## 制限付きリレーションシップが発生する条件

| 条件 | 通常 / 制限付き |
|---|---|
| 両側がインポート | 通常 |
| 両側が同じソースのDirectQuery | 通常 |
| インポートのディメンション × DirectQueryのファクト | **制限付き** |
| デュアルのディメンション × DirectQueryのファクト | 通常 |
| 異なるソースのDirectQuery同士 | **制限付き** |
| 多対多カーディナリティ | **制限付き** |

制限付きリレーションシップでは、次の3つが起きます。

1. **ディメンション側に空白行が作られない。** 孤児レコードが見えなくなる
2. **結合がクエリ実行時に行われる。** ソースをまたぐため遅い
3. **一部のDAX（`RELATED` の一部の使い方など）が期待どおり動かない場合がある**

> [!DS] データサイエンス視点
> 「よく使う集計をあらかじめ計算して保存しておく」という考え方は、OLAP の時代から続く **事前集計（pre-aggregation）／マテリアライズド ビュー** の発想そのものです。クエリが来たときに、エンジンが「この質問なら、集計済みのテーブルで答えられる」と判断して問い合わせ先を差し替えることを **クエリ書き換え（query rewrite）** と呼びます。Power BI の集計テーブルは、この書き換えを自動で行います。データベースの世界では、コストベース オプティマイザが同じ判断を行っています。**「同じ答えを、より安く出せる経路があるなら、そちらを使う」** という発想は、性能設計の中核です。

## 集計テーブルを置いたモデル

```figure
{ "type":"star", "title":"集計テーブル付きのモデル",
  "caption":"Agg_売上月次はインポート、Fact_売上明細はDirectQuery、ディメンションはすべてデュアル",
  "fact":{"label":"Agg_売上月次（インポート）","lines":["年月 / 商品カテゴリID / 店舗ID","金額合計 / 数量合計 / 件数","約12万行"]},
  "dims":[
    {"label":"Fact_売上明細（DirectQuery）","lines":["10億行","ドリル時のみ参照される"]},
    {"label":"Dim_日付（デュアル）","lines":["年 / 月 / 日"]},
    {"label":"Dim_商品（デュアル）","lines":["カテゴリ / 商品名"]},
    {"label":"Dim_店舗（デュアル）","lines":["地域 / 店舗名"]}
  ],
  "edgeLabel":"1対多" }
```

集計テーブルは、**明細を粗い粒度でGROUP BYした結果**です。ソース側でビューやテーブルとして作っておくのが定石です。

```sql
-- 集計テーブルの元になるビュー
CREATE VIEW dbo.vw_AggSalesMonthly AS
SELECT
    FORMAT(売上日, 'yyyyMM')  AS 年月,
    商品カテゴリID,
    店舗ID,
    SUM(金額)                 AS 金額合計,
    SUM(数量)                 AS 数量合計,
    COUNT_BIG(*)              AS 件数
FROM dbo.FactSales
GROUP BY FORMAT(売上日, 'yyyyMM'), 商品カテゴリID, 店舗ID;
```

10億行が12万行になります。これをインポートすれば、メモリは数十MBで済みます。

> 集計テーブルとディメンションの間に**リレーションシップを張り忘れる**と、集計は永久にヒットしません。「集計の管理」で GroupBy を設定するだけでは足りず、**集計テーブルからディメンションへのリレーションシップも必要**です。設定後は必ず、次の方法でヒットを確認してください。

## ヒットしたかどうかを確認する

| 方法 | 手順 |
|---|---|
| パフォーマンス アナライザー | 表示タブ → パフォーマンス アナライザー → 記録開始。**「直接クエリ」の行が出なければヒット**している |
| SQL Server Profiler / DAX Studio | イベントに `Aggregate Table Rewrite Query` が出ればヒット。`match=true` を確認する |
| 応答時間 | 明細に飛べば数秒、ヒットすれば0.1秒台。桁で違うのですぐ分かる |

> [!TIP] 実務のコツ
> 集計を作ったら、**代表的なビジュアル5つについてヒットするかを1つずつ確認**してください。「作ったが一度もヒットしていなかった」は非常によくあります。特に、GroupBy 列の型が集計側と明細側で違う（片方が整数、片方がテキスト）と静かにミスします。

## 自動集計との違い

Premium / Fabric 容量では、**自動集計（Automatic aggregations）** という機能があり、実際のクエリログを機械学習で分析して集計テーブルを自動生成・更新します。

| 観点 | ユーザー定義集計 | 自動集計 |
|---|---|---|
| 設計 | 自分で粒度と列を決める | 利用実績から自動で決まる |
| 制御 | 完全に制御できる | ブラックボックス。訓練率で調整する |
| 必要な環境 | どの容量でも可 | Premium / Fabric 容量 |
| 対象 | DirectQuery のテーブル | DirectQuery のテーブル |
| 向き | 質問のパターンが分かっている場合 | 利用パターンが多様で予測しにくい場合 |

> [!WARN] 注意
> 自動集計は「設定すれば勝手に速くなる」機能ですが、**訓練にはクエリの実績が必要**です。導入直後は効果が出ません。また、レポートを大きく作り変えると、それまでの学習が合わなくなります。**まずユーザー定義集計で主要な質問をカバーし、それでも取りこぼす部分を自動集計に任せる**という順序が現実的です。

複合モデルは、集計だけの話ではありません。**インポートのテーブルと DirectQuery のテーブル、さらに他のセマンティックモデルまで、1つのモデルに同居させられます。**

## 更新の設計 — 集計と明細の整合

集計テーブルはインポートなので更新が必要です。明細は DirectQuery なので常に最新です。**この2つの間に時間差が生まれます。**

| 状況 | 起きること |
|---|---|
| 集計が朝6時更新、明細は常時最新 | 月次合計（集計ヒット）は前日まで、明細ドリル（DirectQuery）は当日を含む |
| 利用者が集計とドリルを見比べる | 「合計と明細の合計が合わない」という指摘になる |
| ソースで過去分が修正された | 集計を更新するまで、古い値が表示され続ける |

対処は3つです。

1. **集計テーブルの粒度を「確定した期間」に限る。** 当日分を含めず、前日までを集計対象にする。当日分は必ず明細に飛ぶよう設計する
2. **更新頻度を上げる。** 1時間ごとに集計を更新すれば、ずれは最大1時間になる
3. **レポートに基準時刻を明示する。** 「集計は本日6:00時点」とカードで表示する

> [!TRAP] つまずきポイント
> 「集計とドリルダウンで数字が合わない」は、複合モデルで最も多い問い合わせです。**技術的には正しく動いていても、利用者にとってはバグに見えます。** 設計段階で「どの時点のデータか」を決め、画面に表示してください。時間差を隠すのではなく、見せるのが正解です。

## DirectQuery のときにやるべきこと

DirectQuery を使う場合、性能はソースDBの設計で決まります。

- **集計に使う列にインデックスを張る。** 特に日付列と結合キー
- **ビューではなくテーブル、または索引付きビューを使う。** 複雑なビューは毎回展開されて遅い
- **不要な列をモデルから外す。** 列が多いと生成されるSQLが太る
- **「参照整合性を前提とする」オプションを検討する。** 有効にすると INNER JOIN が使われ速くなるが、**不一致キーの行が消える**ので、データ品質が保証されている場合だけ
- **相対日付スライサーや複雑な計算列を避ける。** 生成されるSQLが極端に複雑になる

> [!TRAP] つまずきポイント
> DirectQuery モデルには**同時実行クエリ数の上限**があり、ビジュアルの多いページを開くと後半のビジュアルが待たされます。1ページのビジュアル数を減らす、既定でフィルターを適用しておく、といったレポート側の設計も性能に直結します。「モデルは正しいのにレポートが遅い」場合は、1ページに何本のクエリが飛んでいるかをパフォーマンス アナライザーで数えてください。

> [!EXAM] PL-300で問われる
> **ストレージ モードの使い分け**、**デュアルの役割**、**集計テーブルによる性能改善**は出題範囲です。特に「DirectQuery のファクトに接続するディメンションのストレージ モードは何にすべきか」という設問には **デュアル** が正解になります。また、「インポートで容量に収まるならインポートを選ぶ」という原則も一貫して問われます。
