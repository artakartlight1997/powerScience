データに接続するとき、Power BI は必ず「どう取り込むか」を聞いてきます。この選択は**後から変えるのが非常に高くつく**決定です。使えるDAX関数、レポートの速度、更新の方法、必要なライセンスまで、すべてがここで決まります。

選択肢は3つ。インポート、DirectQuery、ライブ接続です。結論を先に言うと、**迷ったらインポート**です。ただし「なぜインポートが既定なのか」を理解していないと、DirectQuery を選ぶべき場面で選べません。

## 比較表

| 観点 | インポート | DirectQuery | ライブ接続 |
|---|---|---|---|
| データの場所 | Power BI内（圧縮保存） | 元のデータベース | 既存のセマンティックモデル |
| 速度 | 非常に速い | 元DBの性能次第 | モデル次第 |
| データ鮮度 | 更新した時点 | 常に最新 | 常に最新 |
| データ量の上限 | モデルサイズ制限あり | 実質無制限 | — |
| Power Query | 全機能が使える | 一部の変換のみ | 使えない |
| DAX | 全機能 | 一部の関数に制限 | 全機能（レポート側の制約あり） |
| 計算列 | 作れる | 制限あり | 作れない |
| リレーションシップ | 自由に作れる | 作れる（制約あり） | 作れない（既存モデルのまま） |
| オフライン | 可能 | 不可 | 不可 |
| ソースへの負荷 | 更新時のみ | 操作のたびに発生 | モデル側に発生 |

## なぜインポートが既定なのか

インポートが速い理由は、L0201で触れた **VertiPaq** の圧縮にあります。

```figure

  "caption": "列ごとに保存すると、同じ値の繰り返しをまとめて圧縮できる",
  "panels": [
    {"title":"一般的なデータベース（行指向）","tone":"blue","items":[
```

sales.csv の `Category` 列には3種類の値しかありません。列指向なら「家電が5,912回」という形で保持できるため、極めて小さくなります。この圧縮のおかげで、**元データの5分の1から10分の1のサイズ**に収まり、集計はメモリ上で完結します。


> [!DS] OLTPとOLAP
> データベースには2つの世界があります。**OLTP**（オンライン取引処理）は「1件の注文を登録する」ような日々の業務処理に最適化され、行指向で正規化されています。**OLAP**（オンライン分析処理）は「2年分の売上を地域別に集計する」ような分析に最適化され、列指向で非正規化されています。Power BI は完全に後者の設計です。**業務システムのデータベースをそのままDirectQueryで繋ぐと遅い**のは、OLTP向けの構造にOLAPの問い合わせを投げているからです。この構造的な不一致を理解しておくと、性能問題の原因が見えるようになります。

## ライブ接続 — 既存モデルを使う

**ライブ接続**は、他の人（あるいは自分）がすでに発行したセマンティックモデルに接続する方式です。

```figure
{ "type": "pipeline", "title": "ライブ接続による分業",
  "caption": "モデルは1つ、レポートは何枚でも。組織展開の基本形",
  "nodes": [
    {"id":"m","label":"共通モデル\n（認定済み）","tone":"amber"},
    {"id":"r1","label":"営業部レポート","tone":"blue"},
    {"id":"r2","label":"店舗運営レポート","tone":"green"},
    {"id":"r3","label":"経営ダッシュボード","tone":"violet"} ],
  "edges": [
    {"from":"m","to":"r1","label":"ライブ接続"},
    {"from":"m","to":"r2","label":"ライブ接続"},
    {"from":"m","to":"r3","label":"ライブ接続"} ] }
```

ライブ接続では**モデルを編集できません。** テーブルの追加もリレーションシップの変更もできず、できるのはレポート作成とレポート専用メジャーの追加程度です。これは制約ではなく、**指標定義を1か所に集約するための仕組み**です。

## 複合モデル — 組み合わせる

**複合モデル**は、1つのモデルの中にインポートのテーブルとDirectQueryのテーブルを混在させる方式です。

```figure
{ "type": "star", "title": "複合モデルの典型例",
  "caption": "変化しないマスタはインポート、巨大な明細はDirectQuery",
  "fact": {"label":"売上明細（DirectQuery）","lines":["数十億行","ソース側に置いたまま"]},
  "dims": [
    {"label":"商品（インポート）","lines":["32行・高速"]},
    {"label":"店舗（インポート）","lines":["14行・高速"]},
```

さらに**集計テーブル**（よく使う粒度の集計済みデータをインポートしておく仕組み）を併用すると、多くのクエリはインポート側で高速に処理され、詳細が必要なときだけDirectQueryが走るという構成が作れます。ティア3で扱う高度な手法です。

**制約が増える方向への変更は高くつきます。** だから最初の選択が重要なのです。判断に迷ったら、まずインポートで作って動かし、本当に必要になってからDirectQueryを検討してください。

> [!EXAM] PL-300での問われ方
> 「10億行あり、常に最新データが必要」→ DirectQuery。「複雑な計算を高速に実行したい」→ インポート。「他部署が作ったモデルを使ってレポートだけ作る」→ ライブ接続。この3択のシナリオ問題は必ず出ます。加えて、**DirectQueryでPower Queryの一部変換が使えない理由**（変換をSQLに翻訳できないため）も理解しておくと、応用問題に対応できます。

```figure
{ "type": "timeline", "title": "方式ごとの更新の意味",
  "items": [
    {"label":"インポート","title":"スケジュール更新","text":"決めた時刻にデータを取り直してモデルを差し替える。更新中はソースに負荷がかかる","tone":"good"},
    {"label":"DirectQuery","title":"データ更新は不要","text":"データは常に最新。ただしモデル構造の変更時は再発行が必要。キャッシュのクリア設定はある","tone":"amber"},
    {"label":"ライブ接続","title":"元モデルの更新に従う","text":"自分では更新できない。元のモデルの更新スケジュールに依存する","tone":"blue"} ] }
```

> [!DS] 鮮度とコストのトレードオフ
> データ分析の世界では、**鮮度（レイテンシ）を上げるほどコストと複雑さが跳ね上がる**という法則があります。日次バッチは安価で安定、1時間ごとは中程度、リアルタイムのストリーミング処理は設計も運用も桁違いに難しくなります。したがって設計の出発点は「どれだけ新しければ意思決定に十分か」という問いです。**判断のサイクルより速いデータ更新には価値がありません。** 月次で在庫方針を決める会議のために、秒単位の在庫データを用意しても、誰もその粒度で判断しません。要件定義では必ず「その数字を見て、どのくらいの頻度で何を決めるのか」を確認してください。

## まとめ

- 接続方式はインポート・DirectQuery・ライブ接続の3択。最初の選択が後の全てを決める
- **迷ったらインポート。** VertiPaqの列指向圧縮により、元データの5〜10分の1のサイズで高速に集計できる
- DirectQueryを選ぶ理由は「リアルタイム性」「巨大なデータ量」「コピー禁止」の3つだけ
- DirectQueryは速度・Power Query機能・一部DAX関数を失う。ソースにも負荷がかかり続ける
- 「常に最新」という要望は、多くの場合「朝までに前日分」を意味する。要件は時刻で確認する
- ライブ接続はモデルを編集できない。これは指標定義を1か所に集約するための設計
- 複合モデルはマスタをインポート、巨大な明細をDirectQueryにする折衷案
- 制約が増える方向（インポート→DirectQuery）の変更は作り直しに近い

## 理解度チェック（自分に説明してみる）

1. 「毎朝9時の会議で前日までの売上を見たい」という要件に対して、どの接続方式を選びますか。理由と、必要な設定を説明してください。
2. インポートが高速な理由を、列指向ストレージと圧縮の観点から説明してください。どんな列が圧縮されにくいですか。
3. 業務システムのデータベースにDirectQueryで接続したら非常に遅かった。考えられる原因をOLTPとOLAPの違いから説明し、取りうる対策を2つ挙げてください。
