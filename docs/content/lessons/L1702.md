会議で「先月の売上は？」と聞かれ、営業部が12.4億、経理部が11.8億と答える。どちらも嘘をついていません。**どちらも自分のモデルで定義された売上を正しく計算している**だけです。

この事故の原因は計算式ではありません。**モデルの境界をどこに引くかを誰も決めなかったこと**です。このレッスンはその境界線の引き方を扱います。

## セマンティックモデルとは何を持つ器か

まず定義を締め直します。セマンティックモデルとは、**データに業務上の意味を与える層**です。物理的にはテーブル・リレーションシップ・メジャー・階層・セキュリティ規則の集合ですが、担っている責務は1つです。

```figure
{ "type":"stack", "title":"セマンティックモデルが持つ5要素", "caption":"上ほど「意味」に近く、下ほど「データ」に近い。分割の判断は上2つが決める",
  "layers":[
    {"label":"セキュリティ規則","sub":"誰がどの行を見てよいか（RLS / OLS）","tone":"pink"},
    {"label":"メジャー（指標の定義）","sub":"「売上」とは何を指すのかという組織の合意","tone":"violet"},
    {"label":"階層と表示設定","sub":"どう掘り下げ、どう見えるか","tone":"cyan"},
    {"label":"リレーションシップ","sub":"表と表がどう関係するか","tone":"green"},
    {"label":"テーブルと列","sub":"読み込んだ事実そのもの","tone":"blue"} ] }
```

> [!NOTE] 要点
> **モデルを分けるとは、指標の定義を分けること**です。テーブルを分ける話ではありません。この一文を握っていれば、分割の議論はほぼ判断できます。

## 分割の3つの型

実務で見かける構成は3型に分類できます。それぞれの適合条件を明確にします。

```figure
{ "type":"compare", "title":"モデル構成の3つの型",
  "panels":[
    {"title":"① 全社1モデル（モノリス）","tone":"amber",
     "items":["すべての業務領域を1つのモデルに","指標の定義は必ず1つになる","サイズと更新時間が膨張する","変更の影響が全社に及ぶ","1人の担当者に依存しやすい"],
     "note":"適合：業務領域が2〜3個の中小規模"},
    {"title":"② ドメイン別モデル","tone":"good",
     "items":["販売／購買／人事など業務単位で分割","共有ディメンションを全モデルで共通化","所有者が明確になる","ドメインをまたぐ分析に一手間かかる"],
     "note":"適合：多くの組織の標準解"},
    {"title":"③ レポート別モデル","tone":"bad",
     "items":["レポートごとに専用モデル","作るのは最も速い","同名指標が乱立する","更新負荷が資産数に比例して増える"],
     "note":"適合：使い捨ての単発分析のみ"} ] }
```

型③は「悪い設計」ではなく「**寿命の短い資産に限って許される設計**」です。3か月で捨てる分析にドメイン設計は不要です。問題は、捨てるはずだったものが3年残ることです。

> [!TRAP] モデルが乱立して数字が食い違う
> 最も多い崩れ方は、型②で始めた組織に型③が混ざることです。ある部署が「共有モデルに欲しい列がない」という理由で、ゴールド層から自前のモデルを作る。悪意はありません。しかしそのモデルの「売上」には返品が含まれておらず、半年後の会議で数字が割れます。**対策は「列が足りない」という要望を受け付ける窓口を作ること**です。窓口がないと、人は必ず迂回路を作ります。

## 分割を決める6つの判断軸

「分けるべきか」を感覚で決めないために、軸を固定します。

```figure
{ "type":"cards", "cols":3, "title":"分割判断の6軸", "caption":"1つでも強い『分ける』理由があれば分ける。弱い理由が3つ集まっても分けない",
  "items":[
    {"icon":"🏷","title":"① 指標の定義","text":"同じ語（売上・稼働率）を別の意味で使うか。使うなら、そもそも語を分けるか、モデルを分ける。","tone":"violet"},
    {"icon":"🔗","title":"② 共有ディメンション","text":"同じ日付・組織・商品で分析するか。するなら1モデルにまとめる強い理由になる。","tone":"green"},
    {"icon":"👤","title":"③ 所有者","text":"変更を承認する人が違うなら分ける。承認者が同じなら分けない。","tone":"blue"},
    {"icon":"🔄","title":"④ 更新頻度","text":"日次と月次が同居すると、月次のために日次が遅くなる。差が大きいなら分ける。","tone":"amber"},
    {"icon":"🔐","title":"⑤ セキュリティ境界","text":"人事給与のように、一部の人しか見てはいけない領域は独立させる。","tone":"pink"},
    {"icon":"📏","title":"⑥ 粒度","text":"明細レベルと集計レベルを1モデルに混ぜると、誤集計と肥大の両方が起きる。","tone":"cyan"} ] }
```

### 軸の重みは同じではない

6軸は対等ではありません。優先順位があります。

| 順位 | 軸 | 判断への効き方 |
|---|---|---|
| 1 | ⑤ セキュリティ境界 | 単独で「分ける」を確定させる。技術ではなく規程の問題 |
| 2 | ① 指標の定義 | 定義が割れるなら分けるか、語を変える。放置は禁止 |
| 3 | ③ 所有者 | 所有者が違うモデルは必ず腐る |
| 4 | ② 共有ディメンション | 共有が多いほど「まとめる」に傾く |
| 5 | ④ 更新頻度 | 増分更新やパーティションで緩和できる |
| 6 | ⑥ 粒度 | 集計テーブルの併用で緩和できる |

下2つは技術で緩和できますが、**上3つは技術では解決できません**。ここが設計判断の核心です。

## 共有ディメンションという生命線

ドメイン別に分けたとき、モデル同士をつなぐのは**共有ディメンション（コンフォームドディメンション）**です。複数のファクトから同じ意味・同じキーで参照できるディメンションのことを指します。

```figure
{ "type":"star", "title":"共有ディメンションを軸にしたドメイン分割", "caption":"販売と購買が別モデルでも、日付と組織が同一なら数字を並べられる",
  "fact":{"label":"共有ディメンション群","lines":["Dim_日付 / Dim_組織","Dim_商品 / Dim_取引先"]},
  "dims":[
    {"label":"販売モデル","lines":["Fact_受注 / Fact_出荷","売上・粗利"]},
    {"label":"購買モデル","lines":["Fact_発注 / Fact_入荷","仕入・在庫"]},
    {"label":"生産モデル","lines":["Fact_生産実績","歩留・稼働率"]},
    {"label":"人事モデル","lines":["Fact_勤怠","人時・稼働"]} ],
  "edgeLabel":"同じキーを共有" }
```

### バスマトリクスで設計する

共有ディメンションの設計は、**バスマトリクス**という表で行います。行にビジネスプロセス（ファクト）、列にディメンションを置き、使う場所に印を付けます。

| ビジネスプロセス | 日付 | 組織 | 商品 | 取引先 | 従業員 | 通貨 |
|---|:--:|:--:|:--:|:--:|:--:|:--:|
| 受注 | ● | ● | ● | ● | ● | ● |
| 出荷 | ● | ● | ● | ● | | ● |
| 発注 | ● | ● | ● | ● | ● | ● |
| 生産実績 | ● | ● | ● | | ● | |
| 勤怠 | ● | ● | | | ● | |
| 予算 | ● | ● | ● | | | ● |

この表の効用は3つあります。

1. **統一すべきディメンションが一目で分かる**。日付と組織は全プロセスに出るので、最優先で共通化する。
2. **モデル分割の候補が見える**。印の重なりが多い行同士は同じモデルに入れる。勤怠は重なりが少ないので分けやすい。
3. **将来の拡張が計画できる**。新しいプロセスを足すとき、既存ディメンションで足りるかが即座に判定できる。

> [!DS] データサイエンス視点：コンフォームドディメンション
> Kimball の次元モデリングにおける中核概念です。定義は「**複数のファクトテーブルで同一の意味・同一のキー・同一の属性を持つディメンション**」。重要なのは「同じ名前」ではなく「同じ意味」であること。販売モデルの`Dim_商品`が販売可能商品のみ、購買モデルの`Dim_商品`が全品目（部材を含む）なら、名前が同じでもコンフォームドではありません。この不一致は、モデルを統合した瞬間に数字の欠落として現れます。**共通化の作業とは、名前を揃えることではなく、粒度と包含範囲を揃えることです。**

現場が「共有モデルにない列を足したい」と言ったとき、選択肢は3つあります。

- 共有モデル側の作成者が「他のモデルからの接続」を許可している必要がある
- 共有モデルのRLSは接続先でも効く。設計を確認せずに使うと想定外の欠落が起きる

> 複合モデルは便利ですが、**チェーンの深さを2段までに制限**してください。共有モデルAに接続した複合モデルBに、さらにCが接続する、という連鎖は、更新順序と障害の切り分けが人間の理解を超えます。深さの上限をルールとして明文化しておきます。

## 分割の粒度が変わると何が起きるか

分割の議論は抽象的になりがちなので、同じ要件を3通りで組んだときの結果を並べます。

```figure
{ "type":"chart", "kind":"bar", "title":"構成別の運用コスト（相対値）", "unit":"相対",
  "categories":["1モデル","ドメイン別5モデル","レポート別40モデル"],
  "series":[
    {"name":"更新に要する容量消費","values":[30,45,180],"tone":"amber"},
    {"name":"指標が割れるリスク","values":[5,20,150],"tone":"bad"},
    {"name":"変更1件の影響調査コスト","values":[90,35,60],"tone":"blue"}],
  "highlight":1 }
```

読み取れることは3つです。

- **1モデルは更新コストとリスクは低いが、変更の影響調査が最も重い**。全社が止まる可能性があるため、小さな変更でも大掛かりな検証が要る。
- **レポート別モデルは、更新コストとリスクの両方で最悪**。しかも資産数に比例して増える。
- **ドメイン別は、3指標のバランスが最も良い**。これが標準解と呼ばれる理由です。

> [!EXAM] PL-300で問われる
> 「複数のレポートで同じ指標を使いたい。最小限の労力で定義の一貫性を保つには？」という問い方をされます。答えは**共有セマンティックモデルへのライブ接続**です。「各レポートで同じメジャーを作る」「pbixをコピーする」は誤り。また「他のユーザーがこのモデルに接続できるようにする」設定と、`ビルド`アクセス許可が必要である点も頻出です。

## 判断の練習

次の3件について、分けるか統合するかを判断してください。理由は6軸で説明します。

| ケース | 状況 |
|---|---|
| A | 販売モデルに「見積」データを追加したい。日付・商品・顧客を共有。更新は日次で同じ。閲覧者も同じ。 |
| B | 人事部が給与データを分析したい。日付・組織を共有。閲覧者は人事部長と役員のみ。 |
| C | 経営企画が5年分の月次予算を管理したい。粒度は組織×月。実績は日次明細。 |

**A：統合する。**共有ディメンションが3つ一致し、所有者・更新頻度・閲覧者も同じ。分ける理由が1つもありません。受注と見積を同じモデルで見られる利益のほうが大きい。

**B：分ける。**軸⑤セキュリティ境界に該当し、これは単独で分割を確定させます。RLSでの制御も技術的には可能ですが、「そもそも見えない」ほうが事故率が低く、監査説明も簡単です。

**C：統合する（ただし設計が要る）。**粒度が違いますが、これは軸⑥で緩和可能なケースです。予算ファクトを月次粒度のまま同じモデルに置き、日付ディメンションとは月レベルでの関係を`TREATAS`または多対一の月キーで橋渡しします。予算だけ別モデルにすると、予実対比というこの分析の目的そのものが果たせません。

> [!NOTE] 判断の型
> 「分ける理由の強さ」を先に測り、強い理由（⑤①③）がなければ統合に倒す。これが基本姿勢です。**統合は後から分けられますが、分かれた定義を後から統合するのは組織政治の問題になり、技術では解けません。**

## 粒度違いを1モデルに同居させる

ケースCで触れた「日次実績と月次予算を1モデルに入れる」設計を、具体的に示します。粒度違いはモデル分割の理由になりがちですが、正しく組めば同居できます。

```figure

    {"id":"dd","label":"Dim_日付\n日単位","tone":"green"},
    {"id":"dm","label":"Dim_月\n月単位","tone":"green"},

    {"id":"fb","label":"Fact_予算\n組織×月","tone":"amber"},
    {"id":"do","label":"Dim_組織","tone":"cyan"}],
  "edges":[
    {"from":"dd","to":"fa","label":"1対多"},
    {"from":"dd","to":"dm","label":"多対1（年月キー）"},
    {"from":"dm","to":"fb","label":"1対多"},
    {"from":"do","to":"fa","label":"1対多"},
    {"from":"do","to":"fb","label":"1対多"} ] }
```

`Dim_日付` から `Dim_月` へ多対一の関係を張れば、日付でフィルターしても月次予算が正しく効きます。日単位でスライスされたときに予算を月合計のまま出さないよう、メジャー側で粒度を検査します。

```figure
{ "type":"formula", "lang":"dax",
  "code":"予算 = IF( ISINSCOPE( Dim_日付[日] ), BLANK(), SUM( Fact_予算[予算額] ) )",
  "parts":[
    {"match":"ISINSCOPE( Dim_日付[日] )","label":"日レベルで表示されているかを判定","tone":"violet"},
    {"match":"BLANK()","label":"予算が存在しない粒度では空にする（誤解を防ぐ）","tone":"amber"},
    {"match":"SUM( Fact_予算[予算額] )","label":"月以上の粒度でのみ合計を返す","tone":"blue"} ] }
```

> [!TIP] 実務のコツ
> 粒度が合わないとき、**間違った数字を出すより空欄を出すほうが良い**というのが原則です。日単位のセルに月予算がそのまま表示されると、利用者は「その日の予算」だと解釈します。`BLANK()` を返せば「この粒度では見られない」と伝わります。設計とは、誤読の余地を消す作業でもあります。

## モデル台帳を持つ

分割方針を決めても、実物が方針どおりかは別問題です。**台帳**で突き合わせます。

```figure
{ "type":"cards", "cols":3, "title":"モデル台帳に必須の項目", "caption":"スキャンAPIで自動取得できる項目と、人が書く項目を分けて管理する",

    {"icon":"🎯","title":"目的","text":"どの意思決定に使うか1文。書けないモデルは作らせない。","tone":"violet"},
    {"icon":"📥","title":"入力元","text":"接続しているデータソース一覧。系列ビューから取得できる。","tone":"green"},
    {"icon":"📊","title":"利用状況","text":"直近90日のユニーク利用者数とレポート数。アクティビティログから。","tone":"amber"},
    {"icon":"🏅","title":"認定状態","text":"認定済み / 昇格済み / なし。方針との差分がここに出る。","tone":"cyan"} ] }
```

台帳を見て次のような差分が出たら、それが手を入れるべき箇所です。

| 差分 | 意味 | 対応 |
|---|---|---|
| 利用者0かつ90日更新なし | 死んだ資産 | 廃止フローへ |
| 所有者が退職済み | 管理不能 | 引き継ぎか廃止を決める |
| 認定なしだが利用者50人超 | 実質の基幹資産が野良 | 品質確認のうえ認定へ |
| 同じソースに繋ぐモデルが5つ | 重複の疑い | 統合候補として調査 |
| ゴールド層以外に接続 | 層の違反 | 接続先を付け替える |

> [!DS] データサイエンス視点：Single Source of Truth の誤解
> 「唯一の正しいデータ源」という言葉は、**1つの物理データベースにすべてを集めること**だと誤解されがちですが、実務上の意味は「**ある指標について、権威ある定義が1つに決まっていること**」です。物理的な保管場所は複数あってよい。重要なのは、「純売上」を計算する式が組織に1つしかなく、それがどこにあるか全員が知っていることです。この観点に立つと、モデル分割は SSoT に反しません。**分割してよいのはファクトであり、指標の定義ではない**のです。

## 理解度チェック

1. 「販売モデル」と「購買モデル」の両方に`Dim_商品`という名前のテーブルがあります。これがコンフォームドディメンションと言えるために、名前が同じである以外に何が一致している必要がありますか。2つ挙げてください。
2. 部門が「共有モデルに自部門の目標値テーブルを足したい」と言ってきました。A（共有モデルに追加）、B（複合モデル）、C（自前モデル）のどれを勧めますか。判断に必要な追加質問を1つ挙げたうえで答えてください。
3. モデルを統合するより分割するほうが後から取り返しがつかない、と言われる理由を述べてください。

> [!NOTE] このレッスンのまとめ
> モデルを分けるとは指標の定義を分けること。判断は6軸（セキュリティ境界・指標の定義・所有者・共有ディメンション・更新頻度・粒度）で行い、上位3軸は技術で緩和できないため単独で分割理由になる。標準解はドメイン別モデル＋共有ディメンション＋シンレポート。そして分割方針は台帳で実物と突き合わせ続けなければ、方針は絵に描いた餅で終わる。
