## 1.4 データのクリーニング

### 必ず言えるようにすること

- エラー値の対処3種：**エラーの削除／エラーの置換／エラーを保持して調査**
- `null` と空文字列 `""` は別物であることを説明できる

> [!TRAP] 型変換のエラーは静かに広がる

## 2.2 リレーションシップの構成

### 必ず言えるようにすること

- 基数4種（1対多・多対1・1対1・多対多）と、それぞれの意味
- クロスフィルター方向（単一・双方向）と、双方向が危険な理由（曖昧性・性能）
- アクティブは1組につき1つ。非アクティブは `USERELATIONSHIP` で呼び出す
- ロールプレイングディメンション（受注日・出荷日）の扱い方
- 1側のキーに重複や空白があると、どんな問題が起きるか

| 症状 | 原因として疑うこと |
|---|---|
| 合計が本来より大きい | 多対多、または1側のキー重複によるファンアウト |
| ディメンションの一部の行が出てこない | 内部結合ではなくリレーションシップの不一致。ファクトにないキーはビジュアルで既定では非表示 |
| 「空白」という行が出る | ファクトにあるがディメンションにないキー（参照整合性違反） |
| 2つの日付で分析できない | 非アクティブなリレーションシップを `USERELATIONSHIP` で使う |
| フィルターが効かない | 方向が逆。ファクト側からディメンションへは伝播しない |

> [!EXAM] PL-300で問われる
> 「1つのファクトを2つの日付（受注日・出荷日）で分析したい。**最小限の労力で**」と来たら、答えは**非アクティブなリレーションシップ + USERELATIONSHIP** です。日付テーブルを複製する案は「労力が大きい」ため不正解になります。ただし「両方の日付を同時にスライサーで独立に使いたい」場合は、日付テーブルを2つ持つのが正解になります。**要件文の細部が答えを変えます。**

## 2.4 タイムインテリジェンス

### 必ず言えるようにすること

- タイムインテリジェンス関数を使うには、**連続した日付テーブル**が必要
- 「日付テーブルとしてマーク」を行うと、自動の日付階層に依存しなくなる
- 代表関数の役割を即答できる

| 関数 | 返すもの |
|---|---|
| `TOTALYTD` / `DATESYTD` | 年初からの累計 |
| `SAMEPERIODLASTYEAR` | 前年の同じ期間 |
| `DATEADD` | 指定した単位ぶんずらした期間 |
| `PARALLELPERIOD` | ずらした期間の**全体**（月を指定すると月まるごと） |
| `DATESINPERIOD` | 起点から相対的な期間（移動平均で使う） |
| `PREVIOUSMONTH` / `PREVIOUSYEAR` | 直前の月／年の全期間 |
| `ENDOFMONTH` / `LASTDATE` | 期間の末日 |

> [!TRAP] DATEADD と PARALLELPERIOD の違い
> 3月1日〜3月15日という部分期間に対して、`DATEADD(-1, MONTH)` は **2月1日〜2月15日**を返します。`PARALLELPERIOD(-1, MONTH)` は **2月1日〜2月28日（月まるごと）** を返します。「同じ日数で比較したい」なら `DATEADD`、「前月全体と比べたい」なら `PARALLELPERIOD` です。

## 2.5 モデルの最適化

### 必ず言えるようにすること

- VertiPaq は**列指向**で圧縮する。行数より**カーディナリティ（値の種類数）**がサイズを決める
- 不要な列を消すのが最も効果が大きい。特に高カーディナリティの列（ID、タイムスタンプ、GUID）
- 日時列は日付と時刻に分割すると圧縮が効く
- 自動の日付/時刻テーブルはモデルを膨らませるので、明示的な日付テーブルを使って無効化する
- パフォーマンスアナライザーで DAX クエリ・ビジュアル表示・その他の時間を分けて確認できる
- 集計テーブル（Aggregations）と複合モデルで大規模データを高速化できる

## 2.6 行レベルセキュリティ（RLS）

### 必ず言えるようにすること

- ロールの**定義は Desktop**、ユーザーへの**割り当ては Service**（ワークスペースまたはアプリのセキュリティ画面）
- 静的RLSは固定の値でフィルター、動的RLSは `USERPRINCIPALNAME()` で本人を特定する
- 複数のロールに属する場合、フィルターは **OR で結合**される（見える範囲が広がる）
- RLS はビューアーに効く。**ワークスペースの管理者・メンバー・共同作成者には既定で適用されない**
- ライブ接続時は、接続先のモデル側のRLSが効く
- 「ロールとして表示（Test as role）」で動作を検証する
- RLS は行を隠す。列やメジャーを隠すのは**オブジェクトレベルセキュリティ（OLS）**

## 迷いやすい論点まとめ

| 迷う場面 | 判断 |
|---|---|
| Power Query か DAX か | できるなら Power Query（取り込み時に確定するもの） |
| 計算列かメジャーか | 迷ったらメジャー。スライサーに置くなら計算列 |
| 双方向を使うか | 原則使わない。多対多のブリッジや、RLSの伝播が必要なときだけ |
| 日付テーブルを複製するか | 「最小限の労力」なら `USERELATIONSHIP`。独立スライサーが要るなら複製 |
| DirectQuery かインポートか | 「常に最新」以外はインポート |
| 増分更新を使うか | ファクトが大きく、フォールディングが効き、日付列があるとき |
| スノーフレークのままにするか | ディメンションを結合してスターに平坦化する |

## まとめ

- 領域1・2で出題の半分以上。ここを◎にするのが最短の合格ルート
- 接続方式は「常に最新＝DirectQuery、それ以外＝インポート」から入る
- 「将来の列にも対応」＝その他の列のピボット解除
- フォールディングを壊す操作は最後に置く。ネイティブクエリの表示で確認する
- スタースキーマ、1対多・単一方向が既定形。外れるなら理由を言えること
- 計算列とメジャーの違いは「いつ・何のコンテキストで評価されるか」
- `CALCULATE` は「外す→絞る」の順に読む
- RLS は Desktop で定義、Service で割り当て。複数ロールは OR
