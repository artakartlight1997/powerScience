営業部のレポート、経理部のレポート、経営会議用のレポート。3つとも同じ売上データを使っています。3人の作成者がそれぞれ Power Query で「返品を除外し、社内取引を除き、税抜に揃える」を実装しました。**3か月後、3つのレポートの売上合計は全部違う値を出しています。**

これは技術の失敗ではなく、**変換をどこに置くかの設計を誰もしなかった**ことの結果です。このレッスンでは、変換の置き場所を選ぶ基準を扱います。

## データフロー — pbixを越えて整形結果を共有する

**データフロー**は、Power BI Service 上で動く Power Query です。結果はクラウドストレージに保存され、複数のセマンティックモデルから参照できます。

```figure
{ "type":"pipeline", "title":"データフローの効果",
  "caption":"整形を1箇所に集約すると、定義のずれが構造的に発生しなくなる",
  "nodes":[
    {"id":"db","label":"基幹DB","tone":"blue"},
    {"id":"df","label":"データフロー\nDim_商品 / Dim_顧客 / Fact_売上","tone":"green"},
    {"id":"m1","label":"営業部モデル","tone":"violet"},
    {"id":"m2","label":"経理部モデル","tone":"violet"},
    {"id":"m3","label":"経営会議モデル","tone":"violet"}
  ],
  "edges":[
    {"from":"db","to":"df","label":"1回だけ整形"},
    {"from":"df","to":"m1","label":"同じ定義"},
    {"from":"df","to":"m2","label":"同じ定義"},
    {"from":"df","to":"m3","label":"同じ定義"}
  ] }
```

データフローを使う利点は4つです。

1. **定義の一元化。** 「売上」の定義が1箇所にしかない状態を作れる。
2. **ソースへの負荷削減。** 3つのモデルが3回ソースを叩くのをやめ、1回にできる。
3. **ゲートウェイ負荷の削減。** オンプレDBへのアクセスが1回で済む。
4. **作成者のスキル要求を下げる。** レポート作成者はMを書かずに済む。

```m
// データフローの成果物を、セマンティックモデルから参照する
let
    Src = PowerBI.Dataflows(null),
    WS  = Src{[workspaceId = pWorkspaceId]}[Data],
    DF  = WS{[dataflowId = pDataflowId]}[Data],
    Ent = DF{[entity = "Dim_商品"]}[Data]
in
    Ent
```

> [!TRAP] つまずきポイント
> データフローは **セマンティックモデルではありません**。データフローにはメジャーもリレーションシップもなく、レポートから直接接続することもできません。あくまで「整形済みテーブルの保管場所」です。「データフローを作ったからモデリングは不要」という誤解は非常に多く、実際にはデータフローの結果を取り込んだうえで、スタースキーマとメジャーを別途作る必要があります。

> [!TRAP] つまずきポイント
> データフローを挟むと、**更新の順序を自分で管理する必要が生まれます**。データフローの更新が終わる前にセマンティックモデルが更新されると、古いデータを取り込みます。スケジュールを時間差で組むか、Fabric のパイプライン／Power Automate で順序を制御してください。「データフローを入れたら数字が1日ずれるようになった」の原因はほぼこれです。

## リンクされたエンティティと計算エンティティ

データフロー同士を参照させると、ブロンズ→シルバー→ゴールドの層を Power BI 内だけで組めます。

| 機能 | 内容 | 必要な環境 |
|---|---|---|
| リンクされたエンティティ | 別のデータフローのテーブルを参照する | Premium / Fabric 容量 |
| 計算エンティティ | 取り込み済みのデータに対して、さらに変換した結果を保存する | Premium / Fabric 容量（拡張コンピューティング エンジン） |
| 標準データフロー | ソースから取得して保存する | Pro でも利用可 |

> [!WARN] 注意
> リンクされたエンティティと計算エンティティは **Premium / Fabric 容量が前提**です。Pro ライセンスのみの環境では、層を分けたいときは「ステージング用データフロー」と「モデル用データフロー」がそれぞれ独立にソースへ接続する形になり、ソースへのアクセスが2回発生します。設計前にライセンスを確認してください。

> [!DS] データサイエンス視点
> データ品質は「きれいにする」作業ではなく、**「何をもって正しいとするかを定義し、測り続ける」** 活動です。上の6つは業界で広く使われるディメンションで、それぞれに**測定可能な指標**を対応させます。たとえば完全性なら「顧客IDがnullの行の割合」、一意性なら「重複した伝票番号の件数」。これらを毎回の更新で記録し、閾値を超えたら気づける仕組みを作ることが、実質的なデータ品質管理です。

実装としては、品質チェック用のクエリをデータフローかステージング層に置き、結果を小さなテーブルとしてモデルに読み込みます。

```m
// クエリ名: chk_品質サマリー — 更新のたびに1行が生成される
let
    Fact = Fact_売上,
    行数 = Table.RowCount(Fact),
    顧客ID欠損 = Table.RowCount(Table.SelectRows(Fact, each [顧客ID] = null)),
    重複伝票 = Table.RowCount(Fact) - Table.RowCount(Table.Distinct(Fact, {"伝票番号"})),
    負の金額 = Table.RowCount(Table.SelectRows(Fact, each [金額] < 0)),
    未来日付 = Table.RowCount(Table.SelectRows(Fact, each [売上日] > Date.From(DateTime.LocalNow()))),
    結果 = #table(
        type table[チェック日時 = datetime, 総行数 = Int64.Type, 顧客ID欠損 = Int64.Type,
                   重複伝票 = Int64.Type, 負の金額 = Int64.Type, 未来日付 = Int64.Type],
        {{DateTime.LocalNow(), 行数, 顧客ID欠損, 重複伝票, 負の金額, 未来日付}})
in
    結果
```

このテーブルをレポートの管理ページに表示しておくと、**数字がおかしいという指摘を受ける前に自分で気づけます**。

## ステージングの設計 — 「そのまま」を残す

ステージング層は「ソースからそのまま取り込み、型付けだけを行った」層です。ここを持つかどうかで、後の柔軟性が大きく変わります。

```figure
    "head":["状況","必要な作業","所要"],

      ["社内取引の定義が変わった","!ステージングから再変換するだけ","!数分"],

```

ステージング層で行ってよいのは、次の3つだけです。

1. **列の型付け**（テキスト／数値／日付を確定させる）
2. **明らかに不要な列の削除**（バイナリ列、監査用の内部列など）
3. **取り込み日時・取込元の付与**（リネージのため）

業務ロジック（「社内取引を除く」「返品をマイナス計上する」など）は、**絶対にステージング層に入れないでください**。入れた瞬間に「生データ」ではなくなり、定義変更のたびにソースへ戻ることになります。

> [!TIP] 実務のコツ
> Power BI 内でステージングを持つ場合、データフローを「stg_」で始まる名前で作り、モデル用データフローと別ワークスペースに置くと管理しやすくなります。ただし、本格的にやるなら **Fabric の Lakehouse か、DBのステージングスキーマ**に持たせるほうが、容量と保持期間の面で現実的です。

## リネージと影響分析

Power BI Service のワークスペースには **リネージ ビュー**（データの流れを図で表示する画面）があります。データソース → データフロー → セマンティックモデル → レポート → アプリ の依存関係が一覧できます。

| 使いどころ | 具体的な操作 |
|---|---|
| ソース変更の影響範囲を知る | データソースを選び、下流のモデル・レポートを確認する |
| 使われていない資産を見つける | 下流に何もつながっていないモデルを特定して整理する |
| 障害時の連絡先を決める | 影響を受けるレポートの所有者を洗い出す |
| データフロー導入の効果を見る | 同じソースに直接つながるモデルが何本あるかを数える |

> [!TRAP] つまずきポイント
> リネージ ビューは**同一ワークスペース内の関係しか十分に見えません**。データフローをワークスペースAに置き、モデルをワークスペースBに置くと、依存関係の把握が難しくなります。共有データフローは**専用のワークスペースにまとめ、閲覧権限を広く付与する**設計にしてください。

## 理解度チェック

1. 「返品を除外した売上」を3つの部署のレポートで使います。実装場所の候補を3つ挙げ、それぞれの長所と短所を述べたうえで、あなたの選択と理由を説明してください。
2. データフローを導入したところ、レポートの数字が1日古い状態になりました。原因として最も可能性が高いものと、その対処を述べてください。
3. メダリオンアーキテクチャのシルバー層で保証すべきことを3つ挙げ、それぞれをPower BIでどう実装するか説明してください。
