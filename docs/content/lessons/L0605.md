### Power Query で作る

```m
let
    開始日 = #date(2023, 1, 1),
    終了日 = #date(2026, 12, 31),
    日数 = Duration.Days(終了日 - 開始日) + 1,
    日付リスト = List.Dates(開始日, 日数, #duration(1, 0, 0, 0)),
    テーブル化 = Table.FromList(日付リスト, Splitter.SplitByNothing(), {"Date"}),
    型設定 = Table.TransformColumnTypes(テーブル化, {{"Date", type date}}),
    年 = Table.AddColumn(型設定, "年", each Date.Year([Date]), Int64.Type),
    月番号 = Table.AddColumn(年, "月番号", each Date.Month([Date]), Int64.Type),
    月名 = Table.AddColumn(月番号, "月名", each Text.From(Date.Month([Date])) & "月", type text),
    年月 = Table.AddColumn(月名, "年月", each Date.ToText([Date], "yyyy-MM"), type text),
    四半期 = Table.AddColumn(年月, "四半期", each "Q" & Text.From(Date.QuarterOfYear([Date])), type text),
    曜日番号 = Table.AddColumn(四半期, "曜日番号", each Date.DayOfWeek([Date], Day.Monday), Int64.Type),
    曜日名 = Table.AddColumn(曜日番号, "曜日名", each Date.ToText([Date], "ddd", "ja-JP"), type text),
    会計年度 = Table.AddColumn(曜日名, "会計年度",
        each if Date.Month([Date]) >= 4 then Date.Year([Date]) else Date.Year([Date]) - 1,
        Int64.Type),
    会計月 = Table.AddColumn(会計年度, "会計月",
        each if Date.Month([Date]) >= 4 then Date.Month([Date]) - 3 else Date.Month([Date]) + 9,
        Int64.Type)
in
    会計月
```

`終了日` を固定値ではなく `Date.EndOfYear(DateTime.Date(DateTime.LocalNow()))` にすれば、更新のたびに当年末まで自動で伸びます。ただし**予算データが翌年まである場合は、それも含む範囲にしてください**。

### DAX で作る

```dax
Dim_日付 =
VAR 開始 = DATE( 2023, 1, 1 )
VAR 終了 = DATE( 2026, 12, 31 )
RETURN
ADDCOLUMNS(
    CALENDAR( 開始, 終了 ),
    "年",       YEAR( [Date] ),
    "月番号",   MONTH( [Date] ),
    "月名",     FORMAT( [Date], "M" ) & "月",
    "年月",     FORMAT( [Date], "yyyy-MM" ),
    "四半期",   "Q" & ROUNDUP( MONTH( [Date] ) / 3, 0 ),
    "曜日番号", WEEKDAY( [Date], 2 ),
    "会計年度", IF( MONTH( [Date] ) >= 4, YEAR( [Date] ), YEAR( [Date] ) - 1 )
)
```

`CALENDARAUTO()` を使うと、モデル内のすべての日付列の最小値と最大値から範囲を自動決定します。手軽ですが、**顧客の生年月日のような無関係な日付列があると、1950年から始まる巨大な日付テーブルになります**。範囲は明示するほうが安全です。

マークすると何が変わるのか。Power BI は「このテーブルが期間を表す」と認識し、**タイムインテリジェンス関数が内部で行うフィルターの置き換えを正しく実行できるようになります**。マークしていないと、`DATEADD` や `TOTALYTD` が想定と違う結果を返すことがあります。

> [!TRAP]
> マーク実行時に「日付列に重複または欠落があります」というエラーが出たら、生成条件を疑ってください。よくある原因は、(1) 日付列が日付時刻型のまま、(2) 開始日と終了日の計算がずれて末日が欠けている、(3) ソースから読んだカレンダーに欠損日がある、の3つです。**エラーを回避するためにマークを飛ばしてはいけません**。マークは検証機能でもあります。

## 会計年度への対応

日本企業では4月始まりの会計年度が一般的です。暦年の列とは別に、会計年度の列を持たせます。

| 暦日 | 年 | 月番号 | 会計年度 | 会計月 |
|---|---|---|---|---|
| 2024-03-31 | 2024 | 3 | 2023 | 12 |
| 2024-04-01 | 2024 | 4 | 2024 | 1 |
| 2024-12-31 | 2024 | 12 | 2024 | 9 |

会計月は「4月を1とする連番」です。この列があると、会計年度内の推移を正しい順序で表示できます。

> [!TIP]
> `TOTALYTD` などのタイムインテリジェンス関数には、年度末を指定する省略可能な引数があります。`TOTALYTD( [売上合計], Dim_日付[Date], "3/31" )` と書けば、3月末を年度末とする累計になります。**会計年度用に別のメジャーを大量に作る前に、この引数の存在を思い出してください**。

Step 3 で「1年前の日付集合」を作れるのは、**日付テーブルにすべての日が連続して存在するから**です。売上のあった日しか持たないテーブルでは、去年の同じ日がテーブルに存在せず、集合が不完全になります。これが「日付テーブルが必須」と言われる技術的な理由です。

> [!DS]
> 時系列分析では、**観測のない期間も系列上に存在させる**ことが基本です。統計ソフトで時系列を扱うときも、まず等間隔の時間軸を作り、そこに観測値を結合します。欠けた期間を詰めて並べると、移動平均や前期比が意味を失うためです。日付ディメンションはこの「時間軸の実体化」であり、データウェアハウス設計では最初に作るディメンションとされています。祝日・営業日・イベントフラグといった列を持たせておくと、「営業日ベースの平均」「セール期間の効果測定」といった分析が、追加のデータなしに実現できます。**日付テーブルの列は、そのまま分析の語彙になります**。

> [!EXAM]
> PL-300 の頻出テーマです。押さえるべきは、(1) 日付テーブルの要件（一意・連続・年の全体・date型）、(2)「日付テーブルとしてマーク」が必要なこと、(3) 自動の日付/時刻を無効にすべき理由（モデルサイズと制御性）、(4) 非アクティブなリレーションシップと `USERELATIONSHIP` の組み合わせ、の4点です。「CALENDARAUTO を使うべき場面」も問われますが、範囲を制御できない点が弱点だと理解しておいてください。

## 日付テーブルの範囲を動かす

固定の終了日を書くと、来年になった瞬間に足りなくなります。動的にするには、次のようにします。

```m
let
    // 売上データの最小日から、当年末までを自動で覆う
    開始日 = Date.StartOfYear( List.Min( Fact_売上[OrderDate] ) ),
    終了日 = Date.EndOfYear( Date.From( DateTime.LocalNow() ) ),
    日数 = Duration.Days( 終了日 - 開始日 ) + 1,
    日付リスト = List.Dates( 開始日, 日数, #duration(1, 0, 0, 0) ),
    テーブル化 = Table.FromList( 日付リスト, Splitter.SplitByNothing(), {"Date"} ),
    型設定 = Table.TransformColumnTypes( テーブル化, {{"Date", type date}} )
in
    型設定
```

`List.Min( Fact_売上[OrderDate] )` はファクトの最小日を取得します。**開始日を年初に丸めている**点が重要で、これで「年の全体を含む」要件を自動的に満たせます。

> [!WARN]
> ファクトを参照して日付テーブルを作ると、**クエリ間に依存関係が生まれます**。ファクト側のクエリが失敗すると日付テーブルも作られません。また、更新の順序にも影響します。小規模なモデルでは実用的ですが、複数ソースを扱う本番モデルでは、パラメーターで開始年と終了年を指定する方式のほうが安定します。

## 完成チェック

| 項目 | 確認方法 |
|---|---|
| 日付が連続している | マーク時にエラーが出ない |
| date 型である | 列のアイコンがカレンダー、時刻を含まない |
| 年の全体を含む | 最小値が1月1日、最大値が12月31日 |
| ファクトの期間をすべて覆っている | 売上の最小日・最大日が範囲内にある |
| 日付テーブルとしてマーク済み | テーブル名の横にカレンダーアイコンが付く |
| 自動の日付/時刻がオフ | 日付列を展開しても階層が出ない |
| 会計年度の列がある | 業務要件に合っていれば |

## 理解度チェック

1. 日付テーブルの5つの要件を挙げ、「売上があった日だけの一覧」が日付テーブルとして使えない理由を、`SAMEPERIODLASTYEAR` の動作に即して説明してください。
2. 「自動の日付/時刻」をオフにすべき理由を3つ挙げてください。オフにする前にやっておくべきことは何ですか。
3. 受注日と出荷日の両方で分析したい場合の2つの設計を挙げ、それぞれの利点を述べてください。日付テーブルを複製する場合の注意点は何ですか。

## よくあるエラーと対処

| 症状 | 原因 | 対処 |
