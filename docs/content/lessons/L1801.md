金曜の夕方、経営会議で使うレポートに数字の誤りが見つかりました。あなたは本番ワークスペースのレポートを開き、メジャーを直し、保存します。月曜の朝、まったく別の部署から「先週まで出ていた集計が消えた」と連絡が来ます。

**本番を直接編集する運用では、これが起きます。**検証されていない変更が、即座に全利用者に届くからです。このレッスンは、変更を安全にする仕組みを扱います。

## なぜ環境を分けるのか

環境分離が防ぐのは、次の3つの事故です。

```figure
{ "type":"cards", "cols":3, "title":"環境を分けないと起きる3つの事故",
  "items":[
    {"icon":"💥","title":"未検証の変更が本番に出る","text":"直したつもりが別の集計を壊す。誰も気づかないまま数字が配信される。","tone":"bad"},
    {"icon":"👀","title":"作りかけが利用者に見える","text":"開発中のページやテストデータが、本番のアプリに混ざる。","tone":"bad"},
    {"icon":"🔙","title":"戻せない","text":"上書き保存した瞬間に前の版が消える。何をどう直したかの記録もない。","tone":"bad"} ] }
```

> [!TRAP] 本番を直接編集して壊す
> この事故の恐ろしさは、**壊れたことに気づかない**点にあります。レポートはエラーで落ちません。静かに違う数字を出し続けます。発覚するのは数週間後、誰かが「去年と傾向が違う」と気づいたときです。そこから原因を辿ろうにも、変更履歴がないため何が起きたのか分かりません。**環境分離は、変更を検証する場所を確保すること**であり、臆病さではなく工学です。

## 3環境モデル

標準的な構成は3つの環境です。

```figure
{ "type":"pipeline", "title":"開発・テスト・本番の3環境", "caption":"データも権限も役割も異なる。同じものを3つ作るのではない",
  "nodes":[
    {"id":"d","label":"開発 Dev\n作る場所","tone":"green"},
    {"id":"t","label":"テスト Test\n確かめる場所","tone":"amber"},
    {"id":"p","label":"本番 Prod\n配る場所","tone":"pink"},
    {"id":"a","label":"アプリ\n利用者が見る","tone":"violet"}],
  "edges":[
    {"from":"d","to":"t","label":"デプロイ（開発者）"},
    {"from":"t","to":"p","label":"デプロイ（承認者）"},
    {"from":"p","to":"a","label":"アプリ更新"} ] }
```

### 3環境の性質の違い

| 項目 | 開発 | テスト | 本番 |
|---|---|---|---|
| データ | 少量サンプル／直近1か月 | 本番相当（可能なら本番と同一） | 本番 |
| 権限 | 開発者が Contributor | 開発者は閲覧、承認者が Member | 管理者のみ Member |
| 更新頻度 | 手動・随時 | 日次 | 本番スケジュール |
| 機密データ | マスクまたは合成データ | 実データ（アクセス制限） | 実データ |
| 誰が壊してよいか | 壊してよい | 壊してはいけない | 絶対に壊さない |

> [!TIP] 実務のコツ
> 開発環境のデータ量は**わざと少なくする**のが正解です。理由は2つ。更新が速く開発の回転が上がることと、**性能問題が本番相当のテスト環境で初めて見つかる**という切り分けができることです。ただし、少なすぎると集計の検証ができません。「直近1か月＋主要マスタ全件」が使いやすい落としどころです。

## デプロイメントパイプライン

Power BI / Fabric には、この3環境を管理する専用機能があります。

```figure
{ "type":"steps", "title":"デプロイメントパイプラインの動き",
  "items":[
    {"title":"3つのワークスペースを各ステージに割り当てる","text":"開発・テスト・本番のワークスペースをパイプラインに接続する。","tone":"blue"},
    {"title":"開発ステージで作業する","text":"レポートとモデルを開発ワークスペースで編集する。本番には一切影響しない。","tone":"green"},
    {"title":"テストへデプロイする","text":"差分が表示され、何が変わるかを確認してから実行する。","tone":"amber"},
    {"title":"デプロイ規則で接続先を切り替える","text":"テスト環境ではテストDBを見るよう、規則で自動置換する。","tone":"violet"},
    {"title":"検証後、本番へデプロイする","text":"承認者だけがこの操作をできるようにアクセス権を設定する。","tone":"pink"} ] }
```

デプロイで運ばれるのは**メタデータ（定義）だけ**です。データそのものは運ばれません。デプロイ後、そのステージのスケジュールで更新されて初めてデータが入ります。この点を理解していないと「デプロイしたのにデータが古い」と混乱します。

## デプロイ規則の2種類

環境ごとに接続先を変える仕組みが**デプロイ規則**です。2種類あり、使い分けます。

```figure
{ "type":"compare", "title":"データソース規則とパラメータ規則",
  "panels":[
    {"title":"データソース規則","tone":"blue",
     "items":["接続先そのものを置換する","例：dev-sql.contoso.com → prod-sql.contoso.com","接続の種類は同じである必要がある","設定が直感的"],
     "note":"サーバー名・データベース名の切り替え"},
    {"title":"パラメータ規則","tone":"good",
     "items":["Power Query のパラメータ値を置換する","サーバー名以外（フォルダーパス、期間、フラグ）も切り替えられる","モデル側でパラメータ化しておく必要がある","柔軟性が高い"],
     "note":"複雑な切り替えはこちら"} ] }
```

**推奨は、最初からパラメータ化しておくこと**です。接続文字列をパラメータに逃がしておけば、データソース規則でもパラメータ規則でも対応でき、後から構成を変えるときの自由度が高くなります。

> [!WARN] 注意
> デプロイ規則は**デプロイ先のステージに設定します**。「開発→テスト」のデプロイなら、規則はテストステージに設定されているものが適用されます。また、規則を設定しないままデプロイすると、**開発環境の接続先のまま本番に出ます**。これは本番から開発DBを読む状態であり、最も危険な誤設定の1つです。デプロイ規則の設定は、パイプライン構築時の必須手順として手順書に明記してください。

## 何をデプロイし、何をしないか

すべてをパイプラインで運ぶわけではありません。

| 対象 | パイプラインで運ぶ | 理由 |
|---|---|---|
| セマンティックモデル | ○ | 定義を揃える必要がある |
| レポート | ○ | 同上 |
| データフロー | ○ | 環境ごとに接続先を変える |
| アプリ | △ | 本番でのアプリ更新は別操作 |
| ワークスペースのアクセス権 | × | 環境ごとに異なるべき |
| 更新スケジュール | × | 環境ごとに異なるべき |
| ゲートウェイ接続 | × | 環境ごとに設定する |

> [!TRAP] 権限もデプロイされると思い込む
> デプロイの直後に「本番のレポートが利用者に見えない」という問い合わせがよく起きます。**アクセス権はデプロイされません。**本番ワークスペースの権限とアプリの対象者は、本番側で別途設定する必要があります。同様に更新スケジュールも運ばれないため、初回デプロイ後は必ず本番側で更新設定を行ってください。この2つは初回デプロイ時のチェックリストに入れます。

## 変更管理のフロー

パイプラインという道具があっても、**誰がいつ何を承認するか**を決めなければ運用になりません。

```figure
{ "type":"tree", "title":"変更の種類と必要な手続き", "caption":"すべての変更に同じ重さの手続きを課すと、運用が止まる",
  "root":{"label":"変更の依頼"},
  "children":[
    {"label":"軽微：表示の調整","sub":"色・並び順・タイトル文言","tone":"green",
     "children":[{"label":"→ 開発→テスト→本番","sub":"承認は担当者の自己確認。記録は残す"}]},
    {"label":"中：ビジュアル追加・ページ追加","sub":"既存の指標を使う範囲","tone":"amber",
     "children":[{"label":"→ 依頼者のテスト環境確認が必要","sub":"1営業日の確認期間を置く"}]},
    {"label":"重：指標の定義変更","sub":"メジャーの計算式、除外条件","tone":"bad",
     "children":[
       {"label":"→ 業務所有者の承認が必須","sub":"数字が変わることを事前通知"},
       {"label":"→ 変更前後の比較表を添付","sub":"影響額を数字で示す"}]},
    {"label":"重：モデル構造の変更","sub":"列削除・改名・関係変更","tone":"bad",
     "children":[{"label":"→ 影響分析で依存レポートを特定","sub":"下流の全レポートを検証する"}]} ] }
```

> [!TIP] 実務のコツ
> 「指標の定義変更」を軽微な変更と同じ扱いにすると、必ず事故ります。**メジャーの計算式が変わると、過去に配信済みの数字と食い違います**。前月の会議資料と今月のダッシュボードで同じ月の値が違う、という状況は組織の信頼を大きく損ないます。定義変更は必ず(1)業務所有者の承認、(2)変更日の記録、(3)利用者への事前通知、の3点をセットにしてください。

## 変更記録に残すこと

デプロイのたびに、次の項目を記録します。手作業でも構いませんが、記録がないデプロイをしないことが重要です。

| 項目 | 内容 |
|---|---|
| デプロイ日時 | いつ本番に出たか |
| 変更内容 | 何を変えたか。1〜3行で |
| 変更理由 | なぜ変えたか。依頼元と起票番号 |
| 影響範囲 | どのレポート・どの指標が変わるか |
| 承認者 | 誰が承認したか |
| 検証結果 | テスト環境で何を確認したか |
| 巻き戻し手順 | 問題が起きたらどう戻すか |

最後の「巻き戻し手順」を書かせることには意味があります。**戻し方が書けない変更は、実行してはいけない変更**だからです。書こうとした時点で「これは戻せないな」と気づくことがあります。

## リリースのリズムを決める

いつでもデプロイできる状態は、いつデプロイされたか分からない状態でもあります。**リズムを決める**と、利用者も開発者も予測可能になります。

```figure
{ "type":"timeline", "title":"リリースサイクルの例（隔週リリース）", "caption":"締切を設けると、検証が「余った時間でやること」から「工程」に変わる",
  "items":[

    {"label":"翌週月〜火","title":"依頼者による確認","text":"依頼した本人が数字を確認する。開発者だけで完結させない。","tone":"violet"},
```

| リリース頻度 | 向いている状況 | 注意点 |
|---|---|---|
| 随時（都度） | 立ち上げ期・利用者が少数 | 検証が省略されやすい |

| 隔週・月次 | 安定運用期・利用者が多い | 緊急修正の例外経路を別に定める |

> [!TIP] 実務のコツ
> どのリズムを選んでも、**緊急修正（ホットフィックス）の経路を別途定義**しておいてください。「明らかに数字が間違っている」場合に隔週まで待つのは不合理です。ただし緊急経路は乱用されるため、(1) 適用条件を「誤った数字が配信されている場合のみ」に限定し、(2) 事後にレビューを必ず行う、という2つの縛りを付けます。

3環境で最も設計が甘くなるのが、テスト環境のデータです。

右下の象限が最も難しく、**「テスト環境だから権限は緩くてよい」という前提が通用しません**。実データを置くなら、テスト環境も本番と同じセキュリティ水準で守る必要があります。この点を最初に決めておかないと、監査で必ず指摘されます。

> [!DS] データサイエンス視点：環境の等価性
> ソフトウェア工学では、**開発・テスト・本番の差異が小さいほど、本番での想定外が減る**ことが知られています（dev/prod parity）。BIで特に差が出やすいのは、(1) データ量、(2) データの偏り、(3) 権限設定の3つです。「開発では動いたのに」の原因はほぼこの3つに帰着します。完全な等価は現実的でないため、**どこを揃え、どこを揃えないかを意図的に決める**のがプロの設計です。テスト環境は本番相当のデータ量にする、権限だけは開発者が見られるようにする、といった線引きを明文化しておきます。

> [!EXAM] PL-300で問われる
> デプロイメントパイプラインは「4.1 ワークスペースの管理」「4.5 ガバナンスとライフサイクル」の範囲で出題されます。押さえるべきは、(1) **3ステージ（開発・テスト・運用）**という構成、(2) デプロイされるのは**メタデータであってデータではない**、(3) **データソース規則とパラメータ規則**で環境ごとの接続先を切り替える、(4) パイプラインの利用には**Fabric/Premium容量が必要**、の4点です。

## 小規模組織での現実解

3環境をフルに構築できない組織もあります。その場合の妥協点を示します。

| 制約 | 妥協案 | 失うもの |
|---|---|---|
| Fabric容量がない | ローカルのpbixを開発版とし、本番のみクラウド | 差分表示・自動デプロイ |
| 人が1人しかいない | 開発と本番の2環境。自己レビューをチェックリスト化 | 第三者の目 |
| ワークスペース数を増やせない | 開発は個人ワークスペース、本番は共有 | 開発の共同作業 |

> [!TIP] 実務のコツ
> どんなに小規模でも、**「本番と別の場所で編集し、動作を確認してから本番に置く」という順序だけは崩さない**でください。ツールがなくても、pbixのファイル名に日付を入れて別フォルダーに保存し、確認後にアップロードするだけで、事故率は劇的に下がります。仕組みが足りないことは、順序を崩す理由になりません。

## 障害が起きたときの動き方

準備の最後は、失敗したときの手順です。事前に決めていない組織は、障害時に「誰が判断するか」から議論を始めることになります。

最初の枝が重要です。**誤った数字が出ているときは、直すより先に止める（告知する）。**修正に30分かかるなら、その30分の間も誤った数字は使われ続けます。告知は1分でできます。

> [!DS] データサイエンス視点：変更の失敗率を下げる4指標
> ソフトウェア開発の研究では、組織のデリバリー能力を4つの指標で測ります。**デプロイ頻度・変更のリードタイム・変更失敗率・復旧時間**です。興味深いのは、頻度を上げることと失敗率を下げることが両立するという発見でした。小さく頻繁に出すほうが、大きくまとめて出すより安全なのです。BIでも同じ構造があります。3か月分の変更を一度にデプロイすれば、問題が起きたときにどれが原因か分かりません。**変更を小さく保つことが、そのまま安全性になります。**

## 設計チェックリスト

- [ ] 開発・テスト・本番の3環境を定義し、それぞれのデータ・権限・役割を明文化した
- [ ] デプロイメントパイプラインに3つのワークスペースを割り当てた
- [ ] デプロイ規則（データソース規則またはパラメータ規則）を全ステージに設定した
- [ ] 接続文字列をパラメータ化した
- [ ] 権限・更新スケジュール・ゲートウェイ設定は各環境で個別に設定した
- [ ] 本番へのデプロイ権限を承認者に限定した
- [ ] 変更の種類（軽微・中・重）ごとに必要な手続きを定めた
- [ ] 指標の定義変更に業務所有者の承認と事前通知を必須にした
- [ ] デプロイ記録の項目を決め、巻き戻し手順の記入を必須にした
- [ ] テスト環境のデータ方針（本番コピー／マスク／合成）を機密度から決めた
- [ ] テスト環境に実データを置く場合、本番同等のアクセス制限をかけた
- [ ] リリースのリズム（週次・隔週など）と緊急修正の適用条件を定めた
- [ ] 本番デプロイ直前チェックを固定リストにした
- [ ] 障害時の初動（まず告知、次に復旧）を手順書に書いた

## 理解度チェック

1. デプロイメントパイプラインでテスト環境へデプロイしたのに、テスト環境のデータが古いままです。原因として考えられることを説明してください。
2. デプロイ規則を設定せずに本番へデプロイしました。どのような状態になるか、なぜ危険かを述べてください。
3. 「デプロイメントパイプラインがあればロールバックできる」という理解のどこが誤っているか説明してください。
4. 本番デプロイ後に誤った数字が配信されていると分かりました。修正作業に30分かかります。最初にすべきことは何か、理由とともに答えてください。

> [!NOTE] このレッスンのまとめ
> 環境分離は、未検証の変更が本番に出ること・作りかけが見えること・戻せないことの3つを防ぐ。3環境はデータ・権限・役割がそれぞれ異なり、同じものを3つ作るのではない。デプロイで運ばれるのはメタデータだけで、権限も更新スケジュールも運ばれない。そして変更の重さに応じて手続きを変え、指標の定義変更には必ず承認と事前通知を付ける。真のロールバックには版の保存が要る——それが次のレッスンのテーマである。
