スタースキーマは「1つのディメンションの1行が、ファクトの複数行に対応する」1対多を前提にしています。ところが現実には、この前提が成り立たない関係が山ほどあります。

- 1つの銀行口座を、夫婦2人が共同保有している（口座↔顧客）
- 1冊の書籍に、著者が3人いる（書籍↔著者）
- 1件の商談に、複数の製品タグが付いている（商談↔タグ）
- 売上は日次で入るのに、予算は月次でしか存在しない（粒度の差）

これらを無理に1対多で組むと、**合計が静かに水増しされます**。しかも誰も気づきません。

## ブリッジテーブルで正しく組む

**ブリッジテーブル**（関連テーブル、ファクトレスファクトとも呼ぶ）は、2つの実体の対応関係だけを持つテーブルです。キーの組み合わせしか持たず、数値を持ちません。

```figure
{ "type":"star", "title":"ブリッジを挟んだモデル",
  "caption":"ブリッジは「顧客」と「口座」の両方から1対多で参照される。中心のFactは口座粒度のまま保つ",
  "fact":{"label":"Bridge_口座保有","lines":["口座ID / 顧客ID","（数値を持たない）","組み合わせは一意"]},
  "dims":[
    {"label":"Dim_顧客","lines":["顧客ID（一意）","顧客名 / セグメント"]},
    {"label":"Dim_口座","lines":["口座ID（一意）","口座種別 / 開設日"]},
    {"label":"Fact_残高","lines":["口座ID / 年月","残高"]},
    {"label":"Dim_日付","lines":["年 / 月 / 四半期"]}
  ],
  "edgeLabel":"1対多" }
```

関係の向きはこうなります。

| 関係 | カーディナリティ | フィルター方向 |
|---|---|---|
| `Dim_顧客` → `Bridge_口座保有` | 1対多 | 単方向 |
| `Dim_口座` → `Bridge_口座保有` | 1対多 | **双方向、または多対多で直接** |
| `Dim_口座` → `Fact_残高` | 1対多 | 単方向 |
| `Dim_日付` → `Fact_残高` | 1対多 | 単方向 |

顧客を選ぶ → ブリッジで該当口座が絞られる → その口座の残高が集計される、という流れです。

> [!TRAP] つまずきポイント
> ブリッジから `Dim_口座` へフィルターを戻すために、`Dim_口座` ↔ `Bridge` の関係を**双方向**にする人が多いのですが、これは次のレッスンで扱う副作用を招きます。**双方向にせず、メジャー側で `CROSSFILTER` を使うか、`TREATAS` でフィルターを移す**ほうが安全です。両方の書き方を後述します。

## ブリッジテーブルをMで作る

ブリッジは、ソースにそのままの形で存在することもあれば、自分で作る必要があることもあります。

```m
// パターン1: 明細に両方のキーがある場合 → 組み合わせを一意化するだけ
let
    明細 = Fact_口座明細,
    キーのみ = Table.SelectColumns(明細, {"口座ID", "顧客ID"}),
    // null を除いてから一意化する。null が混ざると空白メンバーが生まれる
    null除去 = Table.SelectRows(キーのみ, each [口座ID] <> null and [顧客ID] <> null),
    ブリッジ = Table.Distinct(null除去)
in
    ブリッジ
```

```m
// パターン2: タグがカンマ区切りの1列に入っている場合 → 分割して縦持ちにする
let
    Src = Dim_商品生データ,
    // "電子機器,セール対象,新商品" のような列を分割
    分割 = Table.TransformColumns(Src, {{"タグ", each Text.Split(_, ","), type list}}),
    展開 = Table.ExpandListColumn(分割, "タグ"),
    トリム = Table.TransformColumns(展開, {{"タグ", Text.Trim, type text}}),
    キーのみ = Table.SelectColumns(トリム, {"商品ID", "タグ"}),
    ブリッジ = Table.Distinct(Table.SelectRows(キーのみ, each [タグ] <> null and [タグ] <> ""))
in
    ブリッジ
```

タグの側のディメンションも、ブリッジから一意化して作ります。

```m
// Dim_タグ — ブリッジからタグの一意リストを作る
let
    B = Bridge_商品タグ,
    タグ列 = Table.SelectColumns(B, {"タグ"}),
    Dim = Table.Distinct(タグ列),
    ID付与 = Table.AddIndexColumn(Dim, "タグID", 1, 1, Int64.Type)
in
    ID付与
```

> [!DS] データサイエンス視点
> ここで付けている連番が **サロゲートキー（代理キー）** です。業務上の意味を持たない、システムが振った一意の番号を指します。対して「タグ名」や「商品コード」のように業務側で決まっているキーを **ナチュラルキー（自然キー）** と呼びます。サロゲートキーを使う理由は3つあります。**(1) 業務側でコード体系が変わっても壊れない、(2) 整数なので結合と圧縮が効率的、(3) 履歴管理（L1206のSCD Type2）で同じナチュラルキーの複数バージョンを区別できる**。ディメンションのキーは、原則としてサロゲートキーにします。

## 多対多カーディナリティ — 関係を直接張る方法

Power BI にはリレーションシップのカーディナリティとして「多対多」があり、ブリッジなしで2つのテーブルを直接つなげます。ただし、**内部的にはブリッジがあるのと同じ挙動**をするわけではありません。

```figure
{ "type":"compare", "title":"ブリッジ方式と多対多カーディナリティ",
  "caption":"多対多カーディナリティは手軽だが、挙動を理解していないと使いこなせない",
  "panels":[
    {"title":"ブリッジテーブル方式","tone":"good",
     "items":[
       "関係はすべて1対多。挙動が予測しやすい",
       "ブリッジ自体を「関係の一覧」としてレポートに出せる",
       "対応関係に属性（開始日、比率など）を持たせられる",
       "モデル図を見れば構造が理解できる",
       "テーブルが1つ増える"
     ],"note":"複雑な要件はこちら"},
    {"title":"多対多カーディナリティ","tone":"neutral",
     "items":[
       "テーブルを増やさずに済む",
       "両側に一意でない値があってもつなげる",
       "空白行（不一致の受け皿）が自動生成されない",
       "フィルターの伝播が「制限付きリレーションシップ」になる場合がある",
       "DAXの挙動が直感と異なることがある"
     ],"note":"単純なケース向け"}
  ] }
```

> [!TRAP] つまずきポイント
> 1対多のリレーションシップでは、ファクト側に「ディメンションに存在しないキー」があると、Power BI はディメンション側に**空白行**を自動生成し、そこに孤児レコードを集めます。だからスライサーに「（空白）」が現れ、不一致に気づけます。ところが**多対多カーディナリティでは、この空白行が作られません**。マスタ未登録の行は、どのカテゴリにも属さないまま合計にだけ含まれ、内訳の合計と総計が一致しなくなります。**多対多を使うときは、キーの整合性を自分でチェックする責任が生じます**（L1102 の `JoinKind.LeftAnti` が役に立ちます）。

## `TREATAS` — 関係を張らずにフィルターを移す

物理的なリレーションシップを作らずに、DAXで「このテーブルの値を、あのテーブルの列へのフィルターとして扱え」と指示するのが `TREATAS` です。

```figure
{ "type":"formula", "lang":"dax",
  "title":"TREATAS の構造",
  "caption":"第1引数のテーブルの列を、第2引数以降の列に対するフィルターとして適用する",
  "code":"TREATAS( VALUES( Dim_商品[カテゴリ] ), Fact_予算[カテゴリ名] )",
  "parts":[
    {"match":"TREATAS","label":"テーブルの値を、別の列のフィルターとして扱う","tone":"violet"},
    {"match":"VALUES( Dim_商品[カテゴリ] )","label":"現在のフィルターコンテキストで見えている値の一覧","tone":"blue"},
    {"match":"Fact_予算[カテゴリ名] ","label":"フィルターを適用する先の列。列の順序と個数を一致させる","tone":"amber"}
  ] }
```

粒度の異なるファクト（日次の売上と、月次・カテゴリ別の予算）を扱う典型例です。

```dax
-- 予算はカテゴリ×年月の粒度でしか存在しない。
-- Dim_商品 と Fact_予算 に関係を張らず、TREATAS でフィルターを渡す
予算額 =
CALCULATE(
    SUM( Fact_予算[予算金額] ),
    TREATAS(
        VALUES( Dim_商品[カテゴリ] ),
        Fact_予算[カテゴリ名]
    ),
    TREATAS(
        VALUES( Dim_日付[年月] ),
        Fact_予算[年月]
    )
)
```

```dax
-- 予実差異。予算がない粒度（商品単品レベル）では BLANK になり、
-- 「存在しない予算を按分して見せる」という誤解を防げる
予実差異 =
VAR 実績 = [売上合計]
VAR 予算 = [予算額]
RETURN
    IF( NOT ISBLANK( 予算 ), 実績 - 予算 )
```

`TREATAS` を使う利点は3つです。

1. **モデルに関係を増やさない。** 曖昧経路や意図しない伝播が起きない。
2. **メジャー単位で制御できる。** そのメジャーを使ったときだけフィルターが伝わる。
3. **粒度が合わない場合に、合わない粒度では空白にできる。** 誤った按分を防げる。

> [!TIP] 実務のコツ
> 予算・目標・計画のように「実績より粗い粒度でしか存在しないデータ」は、**共有ディメンション（カテゴリ、年月）を経由させるか、`TREATAS` で明示的に結ぶ**のが定石です。予算テーブルを商品ディメンションに直接つなごうとして「一意でないのでリレーションシップが作れません」と怒られるのは、そもそも設計が違うというサインです。

## ブリッジ経由でフィルターを効かせる2つの書き方

顧客を選んだときに口座の残高を絞る、という伝播を作る方法は2通りあります。どちらもモデル図の関係は単方向のままにできます。

```dax
-- 方法1: CROSSFILTER でメジャー内だけ双方向にする
顧客別残高 =
CALCULATE(
    SUM( Fact_残高[残高] ),
    CROSSFILTER( Bridge_口座保有[口座ID], Dim_口座[口座ID], BOTH )
)
```

```dax
-- 方法2: TREATAS でブリッジの口座IDをファクトに直接適用する
顧客別残高2 =
CALCULATE(
    SUM( Fact_残高[残高] ),
    TREATAS(
        VALUES( Bridge_口座保有[口座ID] ),
        Fact_残高[口座ID]
    )
)
```

| 観点 | CROSSFILTER 方式 | TREATAS 方式 |
|---|---|---|
| 影響範囲 | そのメジャー内だけ双方向 | そのメジャー内だけフィルター適用 |
| 経路 | ブリッジ→Dim_口座→Fact の順に伝播 | ブリッジ→Fact へ直接 |
| 中間ディメンションの属性 | 使える（口座種別で絞れる） | 使えない（口座IDだけ渡す） |
| 性能 | 経路が長いと遅くなることがある | 中間を飛ばすので速いことが多い |
| 可読性 | 「双方向にした」と読める | 「値をフィルターとして渡した」と読める |

> [!TRAP] つまずきポイント
> `CROSSFILTER` を使ったメジャーと、使っていないメジャーを同じ表に並べると、**同じ行で片方だけ値が出る**という状態になります。利用者からは「バグに見える」挙動です。関係する一連のメジャーは、フィルターの扱いを揃えてください。揃えられない場合は、メジャー名で違いが分かるようにします（`残高（顧客ベース）` など）。

## 配分比率を持つブリッジ

1件の売上を複数部門に按分する要件では、ブリッジに**比率列**を持たせます。

```figure
{ "type":"tablediff", "arrowLabel":"配分ブリッジを適用",
  "title":"按分を正しく行う",
  "caption":"ブリッジに比率を持たせ、メジャー側で掛け合わせる。合計は必ず元の金額に一致する",
  "before":{"title":"配分ブリッジ","tone":"neutral",
    "head":["案件ID","部門","配分比率"],
    "rows":[["C-01","営業1課","0.6"],["C-01","営業2課","0.4"],["C-02","営業1課","1.0"]]},
  "after":{"title":"按分後の売上","tone":"good",
    "head":["部門","案件","元金額","按分後"],
    "rows":[
      ["営業1課","C-01","1,000,000","!600,000"],
      ["営業2課","C-01","1,000,000","!400,000"],
      ["営業1課","C-02","500,000","500,000"],
      ["合計","—","1,500,000","!1,500,000"]]} }
```

```dax
按分売上 =
SUMX(
    Bridge_案件部門,
    VAR 案件 = Bridge_案件部門[案件ID]
    VAR 比率 = Bridge_案件部門[配分比率]
    RETURN
        CALCULATE( SUM( Fact_売上[金額] ), Fact_売上[案件ID] = 案件 ) * 比率
)
```

> [!TRAP] つまずきポイント
> 配分比率の合計が案件ごとに 1.0 になっていないと、按分後の総計が元の金額と一致しません。**ブリッジを作った直後に「案件ごとの比率合計が 1.0 でない行」を検出するチェッククエリを必ず作ってください**。実務では、部門の統廃合で比率が 0.6 + 0.3 = 0.9 のまま放置される、といった事故が起こります。

## 実装後に必ず行う検証

| 検証項目 | 方法 | 期待される結果 |
|---|---|---|
| 総計の一致 | ブリッジを介さない合計と、介した合計を比較 | 完全に一致する（按分の場合） |
| 内訳の合計 = 総計 | 顧客別の合計と全体の総計を比較 | 共有分があるので**一致しないのが正しい**。仕様として説明できる状態にする |
| 孤児レコード | `LeftAnti` でブリッジにないキーを検出 | 0件。0件でないなら原因を特定する |
| 比率の健全性 | 案件ごとの比率合計 | すべて 1.0 |
| 空白メンバー | スライサーに「（空白）」が出るか | 出るなら不一致がある |

> [!TIP] 実務のコツ
> 共有口座のように「顧客別の合計が全体と一致しない」ケースは、**レポート上に注記を書いてください**。「共有口座は各保有者に重複して計上されるため、顧客別の合計は全体残高と一致しません」。この一文があるかないかで、問い合わせの数が変わります。**モデルの仕様を隠さず表に出すことが、信頼されるレポートの条件です。**

## 設計判断チェックリスト

- [ ] 本当に多対多か。分析の粒度を変えれば1対多にできないか検討したか
- [ ] 多対多の型（タグ／共有／粒度差／配分）のどれかを特定したか
- [ ] ブリッジテーブルのキーの組み合わせを一意化したか。null を除いたか
- [ ] ディメンションのキーはサロゲートキーにしたか
- [ ] 多対多カーディナリティを使う場合、空白行が作られないことを踏まえたチェックを用意したか

- [ ] 配分比率がある場合、比率合計が 1.0 であることを検証するクエリを作ったか

## 理解度チェック

1. 1つの商談に複数の製品タグが付くモデルを設計します。必要なテーブルとリレーションシップの向き・カーディナリティを列挙してください。
2. 多対多カーディナリティで関係を張ったところ、カテゴリ別売上の合計が総計より小さくなりました。原因として最も可能性が高いものと、その確認方法を説明してください。
3. 日次の売上と、カテゴリ×月次の予算を比較するメジャーを `TREATAS` で書いてください。商品単品レベルで表示したときに何が起きるべきかも述べてください。
