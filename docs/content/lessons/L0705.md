次の式を見てください。前年比を求めるメジャーです。

```dax
-- ✗ 読みにくく、遅い
前年比NG =
DIVIDE(
    SUM( Fact_売上[SalesAmount] )
        - CALCULATE( SUM( Fact_売上[SalesAmount] ), SAMEPERIODLASTYEAR( Dim_日付[Date] ) ),
    CALCULATE( SUM( Fact_売上[SalesAmount] ), SAMEPERIODLASTYEAR( Dim_日付[Date] ) )
)
```

同じ式が2回書かれています。これは3つの問題を同時に抱えています。

1. **読めない** — どこからどこまでが1つのまとまりか分からない
2. **遅い可能性がある** — 同じ計算が2回実行される
3. **直すときに壊れる** — 片方だけ直して整合が崩れる

`VAR` はこの3つを一度に解決します。DAXで最初に覚えるべき「作法」です。

これが性能面での最大の利点です。

> [!NOTE] 使われなければ評価されない
> DAXの変数は **遅延評価** です。宣言しただけで使われなかった変数は、そもそも計算されません。
> つまり「念のため変数を宣言しておく」ことに性能上のコストはありません。安心して細かく分けてください。

## 最重要：VAR は「宣言した場所の文脈」で固定される

ここが本レッスンの核心であり、中級者が最もつまずく点です。

**変数の値は、宣言された時点のコンテキストで評価され、以降は変わりません。**
`CALCULATE` の中で使っても、`SUMX` の中で使っても、値は再計算されません。

```dax
-- ✗ 動かない：前年比が常に 0 になる
前年比NG2 =
VAR 当年 = [売上合計]
VAR 前年 = CALCULATE( 当年, SAMEPERIODLASTYEAR( Dim_日付[Date] ) )
RETURN
    DIVIDE( 当年 - 前年, 前年 )
```

`当年` はすでに「今年の売上 = 100」という **数値** になっています。
`CALCULATE( 当年, ... )` は「100という定数を、前年のフィルターで評価する」という意味になり、
フィルターを変えても **100のまま** です。結果として `前年 = 100`、差分は0、前年比は 0% になります。

```figure
{ "type":"tablediff", "arrowLabel":"CALCULATE の中で何が起きたか", "title":"変数は定数になっている",
  "caption":"CALCULATE はフィルターを変えるが、すでに確定した数値は変えられない",
  "before":{"title":"✗ 変数を CALCULATE に渡した","tone":"bad",
    "head":["変数","中身","CALCULATE後"],
    "rows":[["当年","100（数値）","!100 のまま"],["前年","CALCULATE( 当年, … )","!100"],["前年比","(100-100)/100","!0%"]]},
  "after":{"title":"✓ メジャーを CALCULATE に渡した","tone":"good",
    "head":["変数","中身","CALCULATE後"],
    "rows":[["当年","[売上合計]","100"],["前年","CALCULATE( [売上合計], … )","!88"],["前年比","(100-88)/88","!13.6%"]]} }
```

正しい書き方はこうです。**CALCULATE には「式」を渡す。「値」を渡してはいけません。**

```dax
-- ✓ 正しい
前年比 =
VAR 当年 = [売上合計]
VAR 前年 = CALCULATE( [売上合計], SAMEPERIODLASTYEAR( Dim_日付[Date] ) )
RETURN
    DIVIDE( 当年 - 前年, 前年 )
```

> [!TRAP] 「VARが再評価されない罠」の見分け方
> 変数を `CALCULATE`・`SUMX`・`AVERAGEX` などの **コンテキストを変える関数の引数** に渡していたら、
> ほぼ確実にこの罠です。症状は「フィルターを変えても値が変わらない」「前年比が常に0%」。
> ルールは1つ。**コンテキストを変えたい計算は、変数ではなくメジャーや式そのものを渡す。**

### この性質が「役に立つ」場合もある

固定されるのは欠点ではなく、意図的に使える道具でもあります。

```dax
-- 各カテゴリの売上を、全体売上と比較する
カテゴリ構成比 =
VAR このカテゴリ売上 = [売上合計]
VAR 全体売上 = CALCULATE( [売上合計], REMOVEFILTERS( Dim_商品 ) )
RETURN
    DIVIDE( このカテゴリ売上, 全体売上 )
```

`このカテゴリ売上` は宣言時点の文脈（＝いまの行のカテゴリ）で固定されているので、
後段でフィルターを外しても、その値は「家電の売上」のまま保たれます。
**固定されることを知って使えば、意図が明確な式になります。**

## 変数にはテーブルも入る

`VAR` はスカラーだけでなく、**テーブルも保持できます**。

```dax
上位カテゴリ売上 =
VAR 上位3カテゴリ =
    TOPN( 3, VALUES( Dim_商品[Category] ), [売上合計], DESC )
RETURN
    CALCULATE( [売上合計], 上位3カテゴリ )
```

ここでは `上位3カテゴリ` が3行の表になっています。テーブル変数は `CALCULATE` のフィルター引数として渡せます。
複雑な式を組み立てるとき、この使い方が非常に効きます。

> テーブル変数は「材料」であり、`COUNTROWS` や `CALCULATE` を通してスカラーに変換してから返します。

## 実務で効く書き方のパターン

長いメジャーは、次の順序で組み立てると読みやすくなります。

```dax

VAR 成長率 = DIVIDE( 当年 - 前年, 前年 )

-- 3. 例外を処理する
VAR 前年データなし = ISBLANK( 前年 ) || 前年 = 0

-- 4. 表示を決める
RETURN
    SWITCH(
        TRUE(),
        前年データなし,  "前年比較なし",
        成長率 >= 0.1,  "大幅増",
        成長率 >= 0,    "微増",
        "減少"
    )
```

## VAR を入れ子にする

変数の中でさらに変数を宣言することもできます。式が複雑になったら、この形で塊ごとに閉じ込めます。

```dax
顧客あたり売上の中央値 =
VAR 顧客別売上 =
    ADDCOLUMNS(
        VALUES( Fact_売上[CustomerID] ),
        "@売上",
            VAR この顧客売上 = [売上合計]
            RETURN IF( この顧客売上 > 0, この顧客売上 )
    )
RETURN
    MEDIANX( 顧客別売上, [@売上] )
```

内側の `VAR ... RETURN` は、その場所だけで完結する小さな式です。
外の世界に名前が漏れないので、命名の衝突を気にせず使えます。

> [!TIP] 追加列の名前には接頭辞を付ける
> `ADDCOLUMNS` で作る列名は `"@売上"` のように `@` を付ける慣習があります。
> モデルに実在する列と、その場で作った列を、見ただけで区別できるようにするためです。

## 理解度チェック

**問1.** `VAR 当年 = [売上合計]` と宣言した変数を `CALCULATE( 当年, SAMEPERIODLASTYEAR( Dim_日付[Date] ) )` に渡した。結果はどうなるか、理由とともに述べよ。

<details><summary>答え</summary>
`当年` は宣言時点の文脈で評価済みの定数になっているため、CALCULATEがフィルターを変えても値は変わらない。前年売上は当年と同じ値になり、前年比は常に0%になる。CALCULATEには変数ではなくメジャー `[売上合計]` を渡す。
</details>

**問2.** 5つの `VAR` を宣言したメジャーで、3番目の変数の中身を確認したい。どうするか。

<details><summary>答え</summary>
`RETURN` の後ろを一時的にその変数名だけに差し替えて、ビジュアルで値を確認する。確認後に元の式に戻す。DAXの標準的なデバッグ手法。
</details>

**問3.** `VAR 対象 = FILTER( Dim_商品, Dim_商品[ListPrice] > 10000 ) RETURN 対象` がエラーになる理由は。

<details><summary>答え</summary>
`FILTER` はテーブルを返し、メジャーの戻り値はスカラーでなければならないため。`COUNTROWS( 対象 )` や `CALCULATE( [売上合計], 対象 )` のようにスカラー化して返す。
</details>

## よくあるエラーと原因

| 症状・エラー | 原因 | 対処 |
|---|---|---|
| フィルターを変えても値が変わらない | 変数を `CALCULATE` に渡した | 変数ではなくメジャー・式を渡す |
| 「テーブル式は…変換できません」 | テーブル変数を `RETURN` した | `COUNTROWS` などでスカラー化する |
| 「名前 'X' が認識されません」 | 後ろの変数を前の変数から参照した | 宣言順を入れ替える（参照は上から下のみ） |
| 「RETURN が必要です」 | `RETURN` を書き忘れた／2つ書いた | `RETURN` は最後に1つだけ |
| 変数名が列名と衝突して混乱 | 変数名に `Sales` など汎用語を使った | 「当年売上」のように役割が分かる名前にする |
| 期待より遅い | 変数の中で重い計算を何度も呼んでいる | 共通部分をさらに変数に切り出す |

> [!NOTE] このレッスンのまとめ
> `VAR` は中間結果に名前をつけ、**一度だけ評価**して再利用する仕組みです。読みやすさと速度を同時に改善します。
> 最重要の性質は「**宣言した場所のコンテキストで固定される**」こと。これを忘れると前年比が0%になります。
> `CALCULATE` に渡すのは値ではなく式。この一線を守れば、次のレッスンのCALCULATEも安全に扱えます。
