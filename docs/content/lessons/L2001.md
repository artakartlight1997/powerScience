「先月、売上が7%落ちました。理由を説明してください」——この一文から始まる仕事が、プロの領域です。ここで手作業でスライサーを100回切り替える人と、AIビジュアルで候補を60秒で絞ってから検証に入る人とでは、出せる答えの質が変わります。

## 主要因分析 — 何を計算しているのか

主要因分析（Key Influencers）は、**分析対象のメジャーまたはカテゴリ列**を、**説明因子の候補列**で説明します。裏側では、対象が2値カテゴリなら**ロジスティック回帰**、連続値なら**線形回帰**に近い手法で各因子の寄与を推定し、「その因子がこの値のとき、対象が◯倍になりやすい」という形に翻訳しています。

```figure
{ "type":"formula", "lang":"text",
  "title":"主要因分析の出力の読み方",
  "code":"契約プランが 月額 のとき、解約する 可能性は 2.6 倍 になります",
  "parts":[
    {"match":"契約プランが 月額 のとき","label":"説明因子とその水準","tone":"blue"},
    {"match":"解約する","label":"分析対象（2値のカテゴリ）","tone":"pink"},
    {"match":"2.6 倍","label":"他の水準と比べた相対的な起こりやすさ。因果の強さではない","tone":"amber"} ] }
```

「2.6倍」は**その因子だけを見たときの相対的な起こりやすさ**です。他の因子との交絡（別の変数が両方に影響していて、見かけの関係を作ること）は完全には除かれません。

> [!TRAP] つまずきポイント
> 主要因分析で「サポート問い合わせ回数が多い顧客ほど解約率が高い」と出たとき、「問い合わせ窓口を閉じれば解約が減る」と読むのは完全な誤りです。問い合わせは**解約の原因ではなく、不満の症状**です。AIは相関を返すだけで、矢印の向きは判定しません。

### トップセグメントは何が違うのか

主要因分析には「主要な影響」タブと「トップセグメント」タブがあります。後者は**決定木**（条件で分岐して集団を分けるアルゴリズム）を使い、対象の割合が高い部分集団を探します。

```figure
{ "type":"compare", "title":"2つのタブの違い", "caption":"単一因子か、条件の組み合わせか",
  "panels":[
    {"title":"主要な影響","tone":"blue","items":["因子を1本ずつ評価する","「プランが月額なら2.6倍」","どの変数が効くかを知りたいとき"],"note":"変数のランキング"},
    {"title":"トップセグメント","tone":"violet","items":["条件の組み合わせで集団を切る","「月額 かつ 利用日数<5 の層は解約38%」","誰に打ち手を当てるか決めたいとき"],"note":"ターゲティング"} ] }
```

実務では**トップセグメントの方が使える場面が多い**です。打ち手は「変数」ではなく「人の集まり」に対して打つからです。

> [!DS] データサイエンス視点：シンプソンのパラドックス
> 全体では A の成績が良いのに、部門ごとに分けると全部門で B が良い——こういう逆転が実データでは頻繁に起きます。これを**シンプソンのパラドックス**と呼びます。原因は、部門ごとの母数の偏り（交絡）です。主要因分析の結果を報告する前に、**必ず主要なセグメントで層別して同じ傾向が出るかを確認**してください。層別すると消える発見は、たいてい交絡です。

### 使う前の準備

```figure
  "items":[

    {"title":"因子候補の粒度を揃える","text":"顧客を分析するなら、因子も顧客粒度の属性にする。明細行の属性を混ぜると意味が壊れる","tone":"green"},
    {"title":"高カーディナリティ列を外す","text":"顧客IDや注文番号を因子に入れてはいけない。全行を一意に説明してしまい無意味","tone":"amber"},
    {"title":"結果の因子を層別で再検証する","text":"地域別・期間別に同じ傾向が出るかを見る。出ないなら交絡を疑う","tone":"violet"} ] }
```

## 分解ツリー — 「どこで落ちたか」を追う

分解ツリー（Decomposition Tree）は、1つの指標を選んだ軸で次々に分解していく対話的なビジュアルです。売上減少の原因追跡では、これが最も速い道具になります。

```figure
{ "type":"tree", "title":"売上減の分解経路", "caption":"上から順に分解し、寄与の大きい枝だけを追う",
  "root":{"label":"売上 前年比 -7.0%"},
  "children":[
    {"label":"国内 -9.2%","sub":"寄与の大半","tone":"bad",
     "children":[
       {"label":"直営店 -14.1%","sub":"ここが主犯","tone":"bad",
        "children":[{"label":"客数 -16%","sub":"客単価は+2%","tone":"bad"}]},
       {"label":"EC +3.5%","sub":"むしろ好調","tone":"good"}]},
    {"label":"海外 +1.8%","sub":"問題なし","tone":"good"} ] }
```

この図が示す結論は「国内直営店の**客数**が落ちた」です。客単価は上がっているので、値下げの話ではなく**来店を止めた理由**を探すべきだと分かります。分解ツリーの価値は、この**問いの絞り込み**にあります。

### 「高い値」「低い値」分割の正体

分解ツリーの `+` を押すと、フィールドを自分で選ぶ以外に「高い値」「低い値」というAI分割が選べます。これは**残った軸の中から、次に分解したとき最も高い（低い）値を作る軸を自動で選ぶ**動作です。

```figure
{ "type":"compare", "title":"手動分割とAI分割", "caption":"AI分割はグリーディ探索であり、大域最適ではない",
  "panels":[
    {"title":"手動でフィールドを選ぶ","tone":"good","items":["仮説に沿って分解できる","報告のストーリーを作りやすい","再現性がある"],"note":"報告用はこちら"},
    {"title":"「高い値」で自動分割","tone":"amber","items":["各段階で局所的に最良の軸を選ぶ","経路全体として最適とは限らない","探索の初動には速い"],"note":"探索用"} ] }
```

> [!WARN] 注意
> AI分割は**グリーディ探索**（各段階でその場の最良を選び、後戻りしない探索）です。1段目で選ばれなかった軸に真の説明力があるケースは普通に起きます。**探索で当たりをつけたら、必ず手動分割で経路を組み直して検証**してください。

### 分解ツリーの設計上の注意

| 論点 | 指針 |
|---|---|
| 分解する指標 | **加法的な指標のみ**にする（売上、件数、原価）。比率（利益率、解約率）は枝を足しても親に戻らず、誤読を生む |
| 軸の数 | 5〜8本。多すぎると探索が発散する |
| 粒度 | 顧客IDのような一意列は入れない。1行1枝になり無意味 |
| 権限 | 分解ツリーは行レベルセキュリティに従う。RLS適用ユーザーには見える枝が変わる |

> [!TIP] 実務のコツ
> 比率を分解したいときは、**分子と分母を別々のツリーで分解**します。「解約率が上がった」は「解約者数が増えた」のか「母数が減った」のかで打ち手がまったく違い、その区別は比率のツリーでは絶対に見えません。

## 3つを組み合わせた実務フロー

現場では単独で使いません。**異常検知で気づき、分解ツリーで場所を絞り、主要因分析で属性を特定する**——この順番が定石です。

```figure
{ "type":"pipeline", "title":"原因追跡の標準フロー", "caption":"検知 → 局在 → 属性 → 検証",
  "nodes":[
    {"id":"a","label":"異常検知\nいつ？","tone":"amber"},
    {"id":"b","label":"分解ツリー\nどこ？","tone":"green"},
    {"id":"c","label":"主要因分析\n誰／何が？","tone":"violet"},
    {"id":"d","label":"仮説","tone":"blue"},
    {"id":"e","label":"現場確認・実験","tone":"good"} ],
  "edges":[
    {"from":"a","to":"b","label":"期間を特定"},
    {"from":"b","to":"c","label":"セグメントを特定"},
    {"from":"c","to":"d","label":"因子を列挙"},
    {"from":"d","to":"e","label":"検証する"} ] }
```

> [!DS] データサイエンス視点：相関から因果へ渡る3つの橋
> AIビジュアルが出すのは常に相関です。因果を主張するには、次のいずれかが必要です。**(1) 実験**：一部店舗だけ施策を打って比較する。**(2) 自然実験**：外部要因でたまたま分かれた群を比べる。**(3) 因果推論の仮定**：交絡因子をすべて観測して統制する。この3つのどれも通していない主張は、報告書では「〜と相関しています」と書くのが誠実です。

## AIビジュアルの限界を言語化する

上級者と初心者の差は、**限界を先に言えるか**に出ます。報告時に自分から限界を述べると、信頼が上がります。

| 限界 | 報告での言い方 |
|---|---|
| 相関しか分からない | 「因果は未検証です。A/Bテストで確認を提案します」 |
| 観測されていない変数は扱えない | 「競合の値下げはデータに無いため、この分析には含まれていません」 |
| データ品質に依存する | 「6月以降の欠損が結果に影響している可能性があります」 |
| サンプルが小さい枝は不安定 | 「この枝は該当32件のため、参考値として扱ってください」 |

> [!EXAM] PL-300で問われる
> AIビジュアルの出題は「どのビジュアルを選ぶか」に集中します。**主要因分析＝要因の順位づけ、分解ツリー＝対話的な階層分解、異常検知＝時系列の外れ値、スマートナラティブ＝自動要約**。加えて「主要因分析はサマリーテーブルではなく行レベルのデータを必要とする」「分解ツリーの『高い値』はAI分割」の2点が問われます。

## AIビジュアルが動く前提 — モデル側の準備

AIビジュアルは「置けば動く」ものではありません。動かないという相談の9割は、モデル側の問題です。

```figure
{ "type":"stack", "title":"AIビジュアルを支える3層", "caption":"下の層が崩れていると、上の層のAIは意味のある答えを返せない",
  "layers":[
    {"label":"AIビジュアル層","sub":"主要因分析・分解ツリー・異常検知","tone":"violet"},
    {"label":"セマンティックモデル層","sub":"粒度・メジャー定義・リレーションシップ・表示名","tone":"amber"},
    {"label":"データ層","sub":"行レベルの粒度・欠損なし・連続した日付","tone":"blue"} ] }
```

| 前提 | 崩れているときの症状 | 対処 |
|---|---|---|
| 行レベルの粒度がある | 主要因分析が「データが足りません」と表示する | 集計済みテーブルではなく明細を読み込む |
| 日付テーブルが連続している | 異常検知が有効化できない、または期待範囲が暴れる | 期間の全日付を持つ日付テーブルを作り、リレーションを張る |
| 列の表示名が業務語になっている | 出力の文章が `CUST_SEG_CD` のような文字列で読めない | モデル側で日本語の表示名に変更する |
| カーディナリティが適切 | 分解ツリーが1件ずつの枝に分かれる | ID列を因子から外し、属性列に置き換える |

> [!TIP] 実務のコツ
> AIビジュアル専用に**「分析用ビュー」テーブル**を作るのが最短です。顧客1行 × 属性20列 × フラグ数本、という形に整えたテーブルを1本用意しておけば、主要因分析もトップセグメントも安定して動きます。ファクトテーブルをそのまま突っ込むより、はるかに再現性が高くなります。

## ケーススタディ：解約率の上昇を追う

実際の思考の流れを追ってみます。SaaS事業で、月次解約率が 2.1% から 3.4% に上がりました。

## 理解度チェック

1. 主要因分析で「サポート問い合わせ回数が多い顧客は解約率が3.1倍」と出ました。この結果から実務上、**やってはいけない結論**と、**取るべき次の一手**をそれぞれ1つ挙げてください。
2. 「解約率」を分解ツリーで分解しようとしている同僚に、なぜそれが危険なのかを説明し、代わりに何をすべきかを答えてください。
3. 異常検知を有効にしたら毎日3〜5件の警告が出るようになりました。感度を下げる以外に取れる対処を2つ挙げてください。
