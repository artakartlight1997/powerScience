「顧客マスタから、休眠フラグが立っている行を除き、法人格の表記ゆれを正規化し、都道府県コードを付ける」。この20行のMコードが、あなたの組織にいくつあるでしょうか。

調べると、たいてい**モデルの数だけあります**。そして中身は微妙に違います。あるモデルは休眠を除いていない。あるモデルは表記ゆれの辞書が古い。数字が合わない原因の多くは、ここに埋まっています。

## 変換をどこに置くかという1つの問い

このレッスンの問いは1つです。**ある変換処理を、どの層のどの道具で実装するか。**候補は5つあります。

```figure
{ "type":"stack", "title":"変換を置ける5つの場所", "caption":"下ほど広く再利用され、上ほど個別の都合に応えられる",
  "layers":[
    {"label":"⑤ DAX（計算列・メジャー）","sub":"モデル内。利用時に評価される。最も個別的","tone":"pink"},
    {"label":"④ モデル内 Power Query","sub":"そのモデル専用。更新時に実行される","tone":"violet"},
    {"label":"③ データフロー（Dataflow Gen1 / Gen2）","sub":"複数モデルで再利用できる。ローコード","tone":"amber"},
    {"label":"② レイクハウス / ウェアハウス","sub":"Notebook・SQLで処理。大量データに強い","tone":"green"},
    {"label":"① ソース側（ビュー・ストアドプロシージャ）","sub":"最も上流。全利用者に効く","tone":"blue"} ] }
```

> [!NOTE] 要点
> 原則は「**できるだけ下の層で、できるだけ一度だけ**」です。下で処理すれば再利用され、上流で1回済ませれば下流の全員が恩恵を受けます。ただし下に行くほど変更に他部署の承認が要り、動きが遅くなります。この綱引きが設計判断の本体です。

## 5つの選択肢の性質

それぞれの適材適所を、5観点で比較します。

| 観点 | ①ソース側 | ②レイクハウス | ③データフロー | ④モデル内PQ | ⑤DAX |
|---|---|---|---|---|---|
| 再利用範囲 | 全システム | 全モデル | 複数モデル | 1モデル | 1モデル |
| 実装者 | DBA / 基幹担当 | データエンジニア | BI担当 | BI担当 | BI担当 |
| 変更の速さ | 遅い（申請） | 中 | 速い | 最速 | 最速 |
| 大量データ耐性 | 高 | 最高 | 中 | 低 | 低 |
| 実行タイミング | 常時 | スケジュール | スケジュール | モデル更新時 | クエリ実行時 |

> [!TRAP] 「Power Queryで書けるから」で④を選ぶ
> 最も多い判断ミスがこれです。書けることと、そこに置くべきことは別問題です。④に置いた変換は**そのモデルの中でしか存在しません**。翌月、別チームが同じデータを使うとき、その人は同じロジックをゼロから書き直します。書き直した結果はあなたのものと微妙に違います。**「これは自分だけが使うか？」を毎回問う**だけで、この事故の大半は防げます。

## メダリオンアーキテクチャ

②のレイクハウス層では、データを3段階に分けて置くのが標準です。

```figure
{ "type":"stack", "title":"メダリオンアーキテクチャ", "caption":"層をまたぐたびに「信頼できる度合い」が上がる",
  "layers":[
    {"label":"🥇 ゴールド（Gold）","sub":"分析用に整えた形。ファクトとディメンション。セマンティックモデルはここだけを読む","tone":"amber"},
    {"label":"🥈 シルバー（Silver）","sub":"クレンジング済み・統合済み。型が揃い、重複が除かれ、キーが繋がる状態","tone":"gray"},
    {"label":"🥉 ブロンズ（Bronze）","sub":"ソースそのまま。取り込んだ生データ。加工しない。再処理の出発点","tone":"cyan"} ] }
```

### 各層のルール

| 層 | 入れるもの | やってはいけないこと |
|---|---|---|
| ブロンズ | ソースの生データ＋取込日時 | 列の削除、型変換、フィルター |
| シルバー | 型・重複・欠損を整えた統合データ | ビジネスルールによる集計 |
| ゴールド | スタースキーマ、事前集計、業務語の列名 | 特定レポートだけの都合の加工 |

> [!DS] データサイエンス視点：なぜブロンズを加工しないのか
> ブロンズを「生のまま」保つ理由は**再処理可能性**です。シルバーの変換ロジックに誤りが見つかったとき、ブロンズが原形を保っていれば、過去分をすべて作り直せます。ブロンズの段階でフィルターしていると、除いた行は永久に戻りません。これは**冪等性（べきとうせい）**の設計と対になる考え方です。「同じ入力に対して何度実行しても同じ結果になる」パイプラインを作れば、障害時にただ再実行するだけで復旧できます。逆に、実行のたびに追記されて重複が増えるような処理は、障害のたびに人手の後始末を要求します。

## クエリフォールディングを設計の道具として使う

クエリフォールディングとは、**Power Query の操作をソース側のクエリ（SQLなど）に変換して実行させる仕組み**です。フォールディングが効いている間、データはPower Queryのエンジンに降りてきません。ソース側で処理され、結果だけが返ります。

```figure
{ "type":"compare", "title":"フォールディングが効く場合と切れる場合",
  "panels":[
    {"title":"効いている","tone":"good",
     "items":["ソース側で WHERE / JOIN / GROUP BY が実行される","ネットワークを流れるのは結果行のみ","ソースのインデックスが使われる","増分更新の期間フィルターも押し込まれる"],
     "note":"更新時間が短く、ソース負荷も低い"},
    {"title":"切れている","tone":"bad",
     "items":["全行を取得してから手元で絞り込む","1000万行を落としてから10万行に絞る","ソースの計算資源を活かせない","増分更新が実質的に機能しない"],
     "note":"「なぜか遅い」の主要因"} ] }
```

フォールディングを切る代表的な操作を覚えておきます。

| 操作 | フォールディング | 代替 |
|---|---|---|
| フィルター・列選択・並べ替え | 効く | — |
| マージ（同一ソース同士） | 効くことが多い | — |
| マージ（異なるソース間） | 切れる | 上流で結合しておく |
| カスタム関数の適用 | 切れる | SQL側の式かデータフローで実施 |
| インデックス列の追加 | 切れる | 本当に必要か再検討する |
| Table.Buffer | 意図的に切る | 使いどころを限定する |

> [!TIP] 実務のコツ
> Power Query エディターで各ステップを右クリックし、**「ネイティブクエリの表示」が有効かどうか**でフォールディングを確認できます。有効な最後のステップまでがソース側で実行されています。**フォールディングを切る操作を、可能な限り後ろのステップに移す**だけで、更新時間が大きく変わることがあります。これは設計判断ではなく手順の並べ替えなので、費用ゼロで効く数少ない改善です。

```figure
    {"from":"md","to":"nt"} ] }
```

この構成の要は**④の品質チェックを③と⑤の間に挟むこと**です。行数が前日比で半分になった、キーの欠損が急増した、といった異常を検知したらモデル更新を止めます。**壊れたデータで更新するくらいなら、昨日のデータのまま止まっているほうがましだ**というのが、BI運用の基本姿勢です。

| 制御方式 | 内容 | 評価 |
|---|---|---|
| 時刻でずらす | 1:00取込、2:00変換、3:00モデル更新 | 上流が遅れると破綻する。避ける |
| 完了イベントで起動 | パイプラインが成功を確認して次へ | 標準解 |
| 手動起動 | 人が確認して次を押す | 月次の重要処理では有効 |

> [!TRAP] 時刻をずらしただけで「依存を制御した」と思う
> 「取り込みは1時、モデル更新は3時にしてあるから大丈夫」という設計を非常によく見ます。しかし月末や連休明けに取り込みが2時間延びた日、モデルは前日のデータで更新されます。しかも**成功として記録される**ため、誰も気づきません。時刻のずらしは制御ではなく祈りです。パイプラインで完了を待たせてください。

## 更新時間の内訳を見る

変換の配置を変えると更新時間がどう動くか、典型的な例を示します。

```figure
{ "type":"chart", "kind":"hbar", "title":"モデル更新時間の内訳（同一要件・構成違い）", "unit":"分",
  "categories":["ソースから直接取得＋モデル内で全変換","データフローで共通変換＋モデルは読むだけ","レイクハウスのゴールド層から読み込み"],
  "series":[{"name":"モデル更新時間","values":[47,18,6],"tone":"blue"}],
  "highlight":2 }
```

同じ要件でも、変換を下の層に押し込むほどモデルの更新は短くなります。ただし**組織全体の総処理時間が減るとは限りません**。レイクハウスでの処理時間はどこかに存在します。それでも下層に移す価値があるのは、次の3点です。

1. **一度の処理が全モデルに効く**ので、総処理量は減る
2. **モデル更新の失敗率が下がる**（工程が少ないほど壊れにくい）
3. **障害の切り分けが容易になる**（どの段で失敗したかが明確）

> [!EXAM] PL-300で問われる
> 「複数のレポートで同じ変換処理を使いたい。最小限の労力で再利用するには？」という設問では、**データフロー**が答えです。「各pbixで同じクエリを作る」「テンプレートを配る」は誤り。また「更新時間を短縮するために変換を上流へ移す」「クエリフォールディングが効く順序に整える」も頻出の考え方です。

## 理解度チェック

1. 取引先マスタに重複が存在します。Power Query で名寄せする対応と、基幹システム側で統合する対応。どちらを選ぶべきか、判断に必要な条件を挙げて説明してください。
2. メダリオンアーキテクチャで、ブロンズ層に対して型変換もフィルターも行わない理由を述べてください。
3. データフローのチェーンを2段までに制限すべき理由を、更新時間と障害対応の2観点から説明してください。

> [!NOTE] このレッスンのまとめ
> 変換は「できるだけ下の層で、できるだけ一度だけ」。ただし下ほど変更が遅くなるため、再利用範囲と変更速度の綱引きで決める。レイクハウス層はブロンズ・シルバー・ゴールドの3段に分け、ブロンズは加工せず再処理可能性を残す。取り込みは冪等に作り、障害復旧を再実行だけで済ませる。そして共通化は、旧経路を閉じるところまでやって初めて完了する。
