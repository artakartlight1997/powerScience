5年分・1億行のファクトテーブルがあります。毎日更新しますが、変わるのは**直近数日分だけ**です。それでも全件を読み直していれば、更新は毎日3時間かかり、いつかタイムアウトの上限に達します。

**増分更新（Incremental refresh）** は、テーブルを期間で分割して保持し、**変わり得る範囲だけを取り直す**仕組みです。設定は10分で終わり、効果は桁で出ます。

> [!NOTE] 要点
> 増分更新は、テーブルを日／月／年単位の**パーティション**（分割された保存単位）に分けます。更新のたびに再取得するのは「増分範囲」に入るパーティションだけで、それより古いパーティションはモデル内にそのまま残り続けます。

> [!DS] データサイエンス視点
> データエンジニアリングでは **ウォーターマーク方式の差分取得** と呼ばれる古典的なパターンです。「前回どこまで取り込んだか」を示す基準（ウォーターマーク）を持ち、それ以降だけを取りに行く。Power BI の増分更新は、この基準を「日付範囲」という形でパラメータ化し、パーティション管理まで自動化したものです。同時に **冪等性**（同じ範囲を何度取り直しても結果が同じになる性質）も設計に組み込まれています。パーティション単位で丸ごと置き換えるので、途中で失敗して再実行しても二重に積み上がりません。

## `RangeStart` と `RangeEnd` を作る

「ホーム」→「パラメーターの管理」→「新規作成」で、次の2つを作ります。

| 項目 | RangeStart | RangeEnd |
|---|---|---|
| 名前 | `RangeStart` | `RangeEnd` |
| 種類 | 日付/時刻 | 日付/時刻 |
| 推奨値 | 任意の値 | 任意の値 |
| 現在の値 | 例：2026/01/01 0:00:00 | 例：2026/02/01 0:00:00 |

> [!TRAP] つまずきポイント
> 名前は **`RangeStart` / `RangeEnd` の綴りと大文字小文字が完全一致**していなければなりません。`rangeStart` や `Range_Start` では増分更新ダイアログが「必要なパラメータが見つかりません」と言って先に進めません。また **型は「日付/時刻（datetime）」でなければならず、「日付（date）」では認識されません**。ここで詰まる人が非常に多い箇所です。

Desktop上での「現在の値」は、**開発時に読み込むデータ量を決めるためだけの値**です。Serviceに発行すると、Power BI がパーティションごとに値を差し替えて実行します。開発時は1か月分など小さい範囲にしておくと、Desktopの動作が軽くなります。

## フィルターの書き方 — 境界の閉じ方が決定的に重要

```m
let
    Src = Sql.Database(pServer, pDatabase),
    Fact = Src{[Schema="dbo", Item="FactSales"]}[Data],
    // 開始は「以上」、終了は「より小さい」。この非対称が重要
    増分フィルター = Table.SelectRows(Fact,
        each [売上日] >= RangeStart and [売上日] < RangeEnd)
in
    増分フィルター
```

GUIで設定する場合は、日付列のフィルター→「日付フィルター」→「指定の値の間」で、次のように選びます。

- 「次の値以降」→ `RangeStart` を選択（**パラメータ**に切り替えて選ぶ）
- 「次の値より前」→ `RangeEnd` を選択

増分範囲の外で修正が入る可能性がある場合に使うオプションです。**検出列**（`最終更新日時` のような列）を指定すると、Power BI は各パーティションについて検出列の最大値を記録します。

```figure

    {"id":"skip","label":"同じ → 再取得しない","tone":"good"},
    {"id":"reload","label":"違う → 再取得","tone":"pink"}
  ],
  "edges":[
    {"from":"p","to":"q","label":"軽い問い合わせ"},
    {"from":"q","to":"c"},
    {"from":"c","to":"skip","label":"変更なし"},
    {"from":"c","to":"reload","label":"変更あり"}
  ] }
```

```sql
-- ソース側のビューに検出列を用意しておく例
CREATE VIEW dbo.vw_FactSales AS
SELECT
    伝票番号,
    売上日,
    商品ID,
    金額,
    -- 訂正・キャンセルを含めて必ず更新される列
    ISNULL(更新日時, 登録日時) AS 最終更新日時
FROM dbo.FactSales;
```

> [!TRAP] つまずきポイント
> 検出列が **物理削除に反応しない**点に注意してください。ソースで行が DELETE されると、最終更新日時の最大値は変わらないことがあり、パーティションが再取得されずに削除済みの行がモデルに残ります。**論理削除（削除フラグ列を立てて更新日時も更新する）** の運用に変えるか、定期的に全体更新を挟む運用にしてください。

## 発行後の制約

増分更新を設定したモデルには、通常のモデルとは違う制約が付きます。ここを知らずに運用すると、ある日突然データが消えます。

| 制約 | 何が起きるか | 回避策 |
|---|---|---|
| Desktop から同じ pbix を再発行すると、既存パーティションが**破棄される** | 過去5年分が消え、次の更新で作り直しになる | 発行後の変更は最小限にする。Premium/Fabric なら XMLA での配置に切り替える |
| Desktop 側にはアーカイブ期間のデータが存在しない | Desktop で見ると直近しか見えず、不安になる | 仕様。Service 側で行数を確認する |
| 折りたたみが切れていると効果ゼロ | 毎回全件取得したうえでフィルターされる | L1103 の診断を必ず行う |
| クエリの構造を変えるとポリシーが無効になることがある | 更新が失敗する | 変更後は必ずテスト環境で更新を通す |
| ソース側のスキーマ変更に弱い | 列が消えると全パーティションの更新が失敗する | ビューを挟んで、モデル側の列構成を固定する |

> [!TRAP] つまずきポイント
> **「pbix を再発行するとパーティションが失われる」は、増分更新で最も痛い事故です。** 「レポートの色を少し変えただけ」で再発行し、翌日に5年分のデータが消えていることに気づく、というパターンが実際に起こります。増分更新を入れたモデルは、**レポート（.pbix のビジュアル）とセマンティックモデルを分離する**（レポートは別ファイルにしてライブ接続する）運用に切り替えるのが正解です。

> [!EXAM] PL-300で問われる
> 増分更新は頻出です。押さえるべきは、**(1) `RangeStart` / `RangeEnd` という名前と日付/時刻型が必須**、**(2) クエリ フォールディングが前提条件**、**(3) アーカイブ期間と増分範囲の意味**、**(4) 初回更新は全期間を取得する**の4点です。「増分更新が効かない原因は」という設問では、折りたたみが切れていることが正解になります。

| 行数の急変 | ソース側の障害やフィルター条件のミスを示す |

> [!TIP] 実務のコツ
> **モデルに「最終更新日時」を表示するメジャー**を1つ作り、レポートの隅に置いてください。`最終更新 = MAX('更新ログ'[取込日時])` のような単純なもので構いません。更新が止まっていることに閲覧者が最初に気づく、という状態を避けられます。増分更新では取込日時列を各行に持たせておくと、どのパーティションが古いかも追えます。

## テスト環境での検証手順

増分更新は本番でしか本当の姿を見せません。それでも、事故を減らす検証手順があります。

1. **Desktop の RangeStart / RangeEnd を狭い範囲（1週間など）にして、行数と合計を控える。**
2. 同じ条件のSQLをDB側で直接実行し、**行数と合計が一致するか**を突き合わせる。ここがずれていれば、境界条件かタイムゾーンの問題です。
3. テスト用ワークスペースに発行し、**アーカイブ期間を1か月**に縮めた状態で初回更新を通す。
4. 翌日にもう一度更新し、**更新履歴の所要時間が短くなっているか**を確認する。短くなっていなければ折りたたみが効いていません。
5. アーカイブ期間を本番値に戻し、本番ワークスペースへ配置する。

> [!TRAP] つまずきポイント
> **タイムゾーンのずれ**は増分更新の隠れた事故要因です。`RangeStart` / `RangeEnd` は日時型で、Service 側は UTC で動きます。ソースDBの日時が現地時間で格納されていると、日付の境界が9時間ずれ、**毎日の境界付近の伝票が抜けたり重複したりします**。ソース側で UTC に統一するか、ビューでオフセットを吸収してください。「月末だけ数字が合わない」という症状の犯人はたいていこれです。

## 設計判断チェックリスト

- [ ] `RangeStart` / `RangeEnd` を、綴りと型（日付/時刻）を正確に作成したか
- [ ] フィルター条件を `>= RangeStart and < RangeEnd` の半開区間にしたか
- [ ] そのフィルターがソース側の WHERE 句に翻訳されているか（ネイティブ クエリの表示で確認）
- [ ] アーカイブ期間を、業務要件（何年分見るか）と容量から決めたか
- [ ] 増分範囲を、業務担当者に確認した「訂正が入る期間」から決めたか
- [ ] ソースで物理削除が起きるか。起きるなら対処を決めたか
- [ ] 初回更新が容量・時間の上限に収まるか見積もったか
- [ ] レポートとセマンティックモデルを分離し、再発行事故を防ぐ体制にしたか
- [ ] ソースのスキーマ変更に備えて、ビューを挟んで列構成を固定したか

## 理解度チェック

1. 増分更新を設定したのに更新時間がまったく変わりませんでした。最初に確認すべきことは何ですか。確認方法も含めて説明してください。
2. `>= RangeStart and <= RangeEnd` と設定した場合に起きる問題を、パーティションの境界を例に説明してください。
3. ソース側で古い伝票が物理削除されることがあります。増分範囲を10日に設定している場合、どんな不整合が起きますか。対処を2つ挙げてください。
