共有フォルダーを開くと、こう並んでいます。

```text
売上分析.pbix
売上分析_v2.pbix
売上分析_v2_修正.pbix
売上分析_最終.pbix
```

これは誰かの怠慢ではありません。**pbix が1つのバイナリファイルである**ことの必然的な結果です。中身を比較できず、部分的に戻すこともできないから、ファイルごと複製するしかない。

PBIP形式とGit統合は、この前提を変えます。BIをソフトウェア開発と同じ規律に乗せる話です。

### TMDL とは何か

**TMDL（Tabular Model Definition Language）**は、テーブルモデルの定義を人が読める形で書くための言語です。テーブル1つが1ファイルになります。

```text
table Fact_売上
	lineageTag: 8f3a...

	measure 売上金額 = SUM ( Fact_売上[金額] )
		formatString: #,##0
		displayFolder: 01_主要指標
		description: 値引後・返品控除後の売上。社内取引を除く。

	column 金額
		dataType: int64
		isHidden: true
		summarizeBy: none
		sourceColumn: Amount
```

この形式の価値は3つあります。

1. **差分が読める** — メジャーの式が変わったことが1行の差分で分かる
2. **一括編集ができる** — テキスト置換やスクリプトで100個のメジャーに説明を追加できる
3. **レビューできる** — 変更内容をプルリクエストのコメントで議論できる

### PBIR とは何か

**PBIR（Power BI Enhanced Report Format）**は、レポート定義をページ・ビジュアル単位のJSONファイルに分割した形式です。従来は `report.json` 1ファイルに全ページが入っていたため、2人が別ページを編集しても競合しました。PBIRではページごとにファイルが分かれるため、**別ページの編集は競合しません**。

> [!WARN] 執筆時点の情報
> PBIP・TMDL・PBIRは進化が速い領域です。執筆時点（2026年）でPBIRは正式版として利用できますが、一部のビジュアルや機能に制限が残る場合があります。採用前に、対象のレポートで実際に保存・再読込を試し、公式ドキュメントで既知の制限を確認してください。**「構造をテキストで管理し、差分をレビューする」という設計思想は変わりません**が、対応範囲は変わります。

Fabric の**Git統合**は、ワークスペースとGitリポジトリのブランチを接続する機能です。ワークスペース側の変更をコミットしたり、リポジトリの内容をワークスペースに反映したりできます。

|---|---|---|
| ワークスペース → Git | コミット | ブラウザ上で行った変更を記録する |
| Git → ワークスペース | 更新 | 他の人がマージした内容を取り込む |

> Git統合を使い始めた組織が最初に踏む地雷です。ある人はDesktopでPBIPを編集してpushし、別の人は同じワークスペースをブラウザで編集してコミットする。両者が同じアイテムを触っていれば競合します。**編集の入り口を1つに決めてください。**「モデルはDesktop＋Git、レポートはワークスペース」のような分担でも構いませんが、決めていない状態が最悪です。

## 競合が起きたときの扱い

テキスト形式になっても、同じ行を2人が変えれば競合します。BI特有の注意点があります。

| 競合の場所 | 難易度 | 対処 |
|---|---|---|
| 別テーブルのTMDL | 起きない | ファイルが違う |
| 同じメジャーの式 | 易 | どちらが正しいかを人が決める |
| relationships.tmdl | 中 | 関係の追加が両方に必要か確認する |
| model.tmdl の annotations | 難 | 内部管理情報。片方を採用し、Desktopで開き直して検証 |
| PBIR の同一ページ | 中 | ビジュアルの配置が競合。片方を採用して手で再適用 |

> [!WARN] 注意
> TMDLやPBIRの競合を**テキストエディタだけで解決して終わりにしない**でください。構文としては正しくても、モデルとして壊れていることがあります（存在しない列を参照する関係が残る、など）。マージ後は必ずDesktopで開き、保存し直して、モデルが正常にロードされることを確認します。**「マージできた」は「動く」ではありません。**

## TMDLで一括作業をする

TMDLがテキストであることの実利を、具体例で示します。次のような要望は、GUIでは1つずつ手作業になります。

| やりたいこと | GUIでの作業量 | TMDL/スクリプトでの作業量 |
|---|---|---|
| 全メジャーに表示フォルダーを設定 | 80個×数クリック | 1スクリプト |
| 金額メジャーの書式を一括変更 | 30個×数クリック | 1置換 |
| キー列をすべて非表示に | 25個×数クリック | 1スクリプト |
| 全テーブルに説明を追加 | 12個×入力 | CSVから流し込み |
| 命名規約違反を洗い出す | 目視 | BPAで自動 |

```figure
{ "type":"formula", "lang":"text",
  "code":"foreach (var m in Model.AllMeasures) { if (m.FormatString == \"\") m.FormatString = \"#,##0\"; }",
  "parts":[
    {"match":"Model.AllMeasures","label":"モデル内の全メジャーを走査する","tone":"violet"},
    {"match":"m.FormatString == \"\"","label":"書式が未設定のものだけを対象にする","tone":"amber"},
    {"match":"m.FormatString = \"#,##0\"","label":"標準の書式を一括で適用","tone":"blue"} ] }
```

Tabular Editor のC#スクリプトの例です。**このような自動化ができること自体が、標準化を現実的にします。**「規約を決めたが既存資産に適用する工数がない」という詰まりが、ここで解けます。

> [!TIP] 実務のコツ
> スクリプトによる一括変更は強力ですが、**必ずブランチを切ってから実行**してください。80個のメジャーを一度に変更した結果が間違っていた場合、Gitがなければ手作業で戻すことになります。逆にGitに乗っていれば、間違っていたら破棄するだけで済みます。**大胆な自動化は、安全に戻せる仕組みとセットで初めて成立します。**

> 「環境の構成をコードとして記述し、バージョン管理し、再現可能にする」という考え方をInfrastructure as Code（IaC）と呼びます。PBIPは、BI資産に対するIaCの実装です。得られるものは3つ。**再現性**（同じコミットから同じモデルが作れる）、**追跡可能性**（いつ誰が何を変えたか）、**自動化の入口**（CIでチェックを回せる）。逆に言えば、これらが要らない小規模な運用では、PBIPの導入コストが上回ることもあります。**規模と要求から判断する**のは、他の設計判断と同じです。

```figure
    {"title":"部分導入","text":"人は多いが変更は少ない。共有モデルだけGit管理し、レポートはpbixのままでもよい。","tone":"amber"} ] }
```

判断の基準は「困っているか」です。**競合が起きていない、戻したい場面がない、レビューが必要ない組織に、仕組みだけ導入しても定着しません。**痛みがあるところから入れるのが、あらゆる仕組み導入の鉄則です。

## 理解度チェック

1. PBIXでは2人の同時編集がマージできず、PBIPではできる理由を、ファイル構造の違いから説明してください。
2. プルリクエストのTMDL差分で、あるメジャーの計算式が変わっていることに気づきました。承認する前に確認すべきことを述べてください。
3. TMDLの競合をテキストエディタで解決した後、Desktopで開いて確認すべき理由を説明してください。

> [!NOTE] このレッスンのまとめ
> PBIPはモデルをTMDL、レポートをPBIRというテキストに分解する保存形式であり、これによりBI資産がGitに乗る。得られるのは差分レビュー・履歴・巻き戻し・並行開発。Gitは変更の記録、デプロイメントパイプラインは環境間の移動を担当し、両者は競合しない。編集の入り口は1つに決め、PRは1目的に絞り、機械にできる検査はCIに任せて、人は「この定義は業務的に正しいか」だけを見る。
