## スコアを載せるモデル設計

予測スコアは**ディメンションではなくファクト**です。日々生成され、時点を持ち、履歴が積まれます。

```figure
{"type":"star","title":"スコアテーブルを含むモデル","caption":"スコアは時点を持つファクト。顧客ディメンションの列にしない",
"fact":{"label":"Fact_解約スコア","lines":["スコア日 / 顧客SK","スコア（0〜1）","予測ラベル / モデルVer"]},
"dims":[{"label":"Dim_日付","lines":["日 / 月 / 会計年度"]},{"label":"Dim_顧客","lines":["顧客名 / 契約プラン / 地域"]},
{"label":"Dim_モデル","lines":["モデル名 / バージョン / 学習日"]},{"label":"Dim_施策","lines":["施策名 / 対象群 / 実施日"]}],"edgeLabel":"1対多"}
```

> [!TRAP] つまずきポイント
> スコアを `Dim_顧客` の列にして上書きすると、①過去の予測が消え精度を検証できない ②先月リスク高だった顧客の追跡ができない ③モデル改善の効果を比較できない、を同時に失います。

| 設計上の決定 | 推奨 | 理由 |
|---|---|---|
| 保持期間 | 最低13か月 | 前年同月比とモデル評価に必要 |
| 粒度 | 顧客 × スコア日 | 日次でなく週次で十分な場合が多い |
| 生スコアの保持 | 必須 | 閾値を後から変えて再評価できる |
| モデルバージョン列 | 必須 | 精度変化の原因切り分けに使う |
| 実績（正解ラベル） | 別テーブルで結合 | 予測時点では未確定のため分離する |

## 理解度チェック

1. 解約率5%で精度95%。この数字を評価できない理由と、代わりに見る指標を2つ。
2. 引き留めが成功するとモデルの見かけの精度はどうなるか。現象名と評価上の対処は。
3. 「対照群は機会損失だ」と役員に言われた。1分で反論する内容を組み立てよ。
