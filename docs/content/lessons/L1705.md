「開発では3秒で開いたレポートが、本番公開の翌朝に30秒かかる」。原因は2つです。

本番の**データ量**が桁違いなこと、そして**同時利用者数**が1人から数百人になったこと。効く打ち手が違うので、まず切り分けます。

## 設計チェックリスト

- [ ] データ量と同時利用者数のどちらがボトルネックかを測定で特定した
- [ ] 高カーディナリティ列（注文番号・伝票番号・日時）を削除または分割した
- [ ] 未使用の列を削除した
- [ ] 増分更新を設定し、フォールディングが効いていることを実測で確認した
- [ ] 集計テーブルの粒度をクエリログの実績から決めた
- [ ] 1ページあたりのビジュアル数とスライサー数を見直した
- [ ] 更新のピークと閲覧のピークが重ならないよう配置した
- [ ] RLSの実装方式が性能に与える影響を確認した
- [ ] ピーク時の容量利用率が80%以下に収まる見積もりを出した
- [ ] 配信をアプリに集約し、個別共有を排除した
- [ ] 対策を費用対効果順で計画した

## 理解度チェック

1. 1000万行で1.8GBのモデル。行数を減らさずにサイズを下げる方法を2つ挙げ、なぜ効くか説明してください。
2. 容量の利用率90%で安定している基盤は「効率的」と言えますか。待ち行列の観点から答えてください。
3. 「レポートが遅い」への対応として、容量増強の前に実施すべきことを費用対効果の順に3つ挙げてください。

> [!NOTE] このレッスンのまとめ
> スケールはデータ量と同時利用者数の2軸で、効く打ち手が違う。容量増強は最後の手段で、設計の問題は容量では消えない。利用率70%超で待ち時間は非線形に伸びる。
