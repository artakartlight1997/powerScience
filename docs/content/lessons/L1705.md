「開発環境では3秒で開いたレポートが、本番公開の翌朝に30秒かかる」。この現象には2つの原因があります。**データ量**が本番で桁違いに大きいこと、そして**同時利用者数**が開発時の1人から数百人になったこと。

スケールとは、この2軸のことです。それぞれ効く打ち手が違うので、まず切り分けます。

```figure
  "xLow":"〜1000万行","xHigh":"1億行〜","yLow":"〜50人","yHigh":"500人〜",

    {"title":"両方必要","text":"最も難しい領域。集計テーブル＋増分更新＋容量分離＋配信設計を総動員。","tone":"bad"},
    {"title":"標準構成で足りる","text":"インポート＋日次更新。過剰設計しない。","tone":"good"},

```

> [!NOTE] 要点
> **どちらの軸で詰まっているかを先に測る**。データ量の問題に同時実行の打ち手を当てても効きません。パフォーマンスアナライザーとキャパシティメトリックの両方を見て、ボトルネックを特定してから手を打ちます。

## データ量のスケール

### モデルサイズを決めるのは行数ではない

まず誤解を解きます。インポートモデルのサイズを決める最大の要因は行数ではなく、**列のカーディナリティ（異なる値の個数）**です。

```figure
{ "type":"chart", "kind":"hbar", "title":"1000万行のファクトで、列を削るとサイズがどう変わるか", "unit":"MB",
  "categories":["元の状態（32列）","注文番号を削除","日時を日付＋時刻に分割","小数を整数（円）に","未使用列15本を削除"],
  "series":[{"name":"モデルサイズ","values":[1840,1120,780,610,430],"tone":"blue"}],
  "highlight":4 }
```

効いた順に理由を説明します。

| 施策 | なぜ効くか |
|---|---|
| 注文番号（高カーディナリティの文字列）を削除 | 全行が異なる値＝辞書圧縮がまったく効かない。最も重い列 |
| 日時を日付と時刻に分割 | 1列で864万通り→日付3650通り＋時刻86400通りに分解。組み合わせが減る |
| 浮動小数点を整数に | 小数は圧縮しにくい。単位を円にして整数化する |
| 未使用列の削除 | 使わない列も圧縮・格納されている |

> [!TRAP] 「あとで必要になるかもしれない」列を残す
> モデルサイズ肥大の最大の原因はこれです。**注文番号・伝票番号・備考欄**の3つは、分析に使われないのに残されがちで、しかもカーディナリティが最悪です。ドリルスルーで明細を見たいという要件があるなら、明細は集計モデルに含めず、**DirectQueryの複合モデルか別レポート**に分離します。「念のため」で1.4GBが乗ります。

### 増分更新とハイブリッドテーブル

大きなファクトは、全体を毎回読み直す必要がありません。

```figure
{ "type":"pipeline", "title":"増分更新のパーティション構成", "caption":"更新するのは直近だけ。過去は一度作ったら触らない",
  "nodes":[
    {"id":"a","label":"2019-2023\nアーカイブ","tone":"gray"},
    {"id":"b","label":"2024-2025\n履歴パーティション","tone":"blue"},
    {"id":"c","label":"直近3か月\n増分パーティション","tone":"green"},
    {"id":"d","label":"当日\nDirectQuery","tone":"amber"},
    {"id":"r","label":"レポート","tone":"pink"}],
  "edges":[
    {"from":"a","to":"r","label":"更新しない"},
    {"from":"b","to":"r","label":"更新しない"},
    {"from":"c","to":"r","label":"毎日更新"},
    {"from":"d","to":"r","label":"リアルタイム"} ] }
```

一番右の「当日 DirectQuery」を含む構成を**ハイブリッドテーブル**と呼びます。過去はインポートで高速、当日だけDirectQueryで最新、という組み合わせです。

| 構成 | 更新時間 | 鮮度 | 複雑さ |
|---|---|---|---|
| 全体更新 | 長い（全行） | 更新時点 | 最も単純 |
| 増分更新 | 短い（直近のみ） | 更新時点 | 中。パラメータ設定が必要 |
| ハイブリッドテーブル | 短い | リアルタイム | 高。ソースの性能が直接効く |

> [!WARN] 注意
> 増分更新は**クエリフォールディングが効いていることが前提**です。`RangeStart` / `RangeEnd` パラメータによる期間フィルターがソース側のSQLに押し込まれないと、結局全件を取得してから絞ることになり、効果がありません。設定後は必ず更新時間の実測で確認してください。

### 集計テーブル

数億行のファクトに対して「月×商品カテゴリ別の売上」を毎回スキャンするのは無駄です。あらかじめ集計した小さいテーブルを用意し、**粒度が足りる質問はそちらで答える**設計にします。

```figure
{ "type":"tree", "title":"集計テーブルによるクエリの振り分け", "caption":"エンジンが自動で判断する。利用者は意識しない",
  "root":{"label":"クエリが到着"},
  "children":[
    {"label":"月×カテゴリの粒度で足りる？","sub":"集計テーブルの粒度以上","tone":"good",
     "children":[{"label":"→ 集計テーブルで応答","sub":"数百万行のスキャンで済む。ミリ秒","tone":"good"}]},
    {"label":"日×商品の粒度が必要？","sub":"集計テーブルより細かい","tone":"amber",
     "children":[{"label":"→ 明細テーブルへフォールバック","sub":"時間はかかるが正しい結果が返る","tone":"amber"}]} ] }
```

集計テーブルの設計判断は3点です。

1. **どの粒度で作るか** — 実際のクエリログ（キャパシティメトリック）を見て、最も多い粒度を選ぶ。推測しない
2. **どこまで細かくするか** — 細かいほど当たりやすいが小さくならない。元の1/100以下を目安にする
3. **管理コストに見合うか** — 集計テーブルは二重管理になる。効果が2倍未満なら作らない

> [!DS] データサイエンス視点：事前集計はキャッシュの一種
> 集計テーブルは、データウェアハウスで言う**マテリアライズドビュー**と同じ発想です。「よく聞かれる質問の答えを、聞かれる前に計算しておく」。トレードオフも同じで、**鮮度と正確さを、速度と引き換えにしています**。元データが更新されたのに集計テーブルが古いままなら、速いけれど間違った答えが返ります。だから集計テーブルは、必ず元テーブルと同じ更新サイクルに縛り付けなければなりません。

## 同時利用者のスケール

### ボトルネックはどこにあるか

利用者が増えたときに詰まる場所は、データ量のときとは違います。

```figure
{ "type":"stack", "title":"同時実行時のボトルネック（上から詰まりやすい順）",
  "layers":[
    {"label":"① クエリ実行（CPU）","sub":"1ページに20個のビジュアル×300人 = 6000クエリが同時に走る","tone":"bad"},
    {"label":"② メモリ","sub":"モデルの常駐＋クエリの一時メモリ。容量の上限に当たると退避が起きる","tone":"amber"},
    {"label":"③ 更新処理との競合","sub":"朝9時の閲覧ピークと更新が重なると両方遅くなる","tone":"violet"},

```

### ①への対策：クエリの本数を減らす

同時実行の問題は、**1人あたりのクエリ本数を減らす**ことで最も効率よく解けます。

```figure
{ "type":"compare", "title":"同じ情報量でクエリ数を減らす",
  "panels":[
    {"title":"クエリが多い構成","tone":"bad",
     "items":["1ページに24個のビジュアル","スライサーが8個（それぞれが値の一覧を取得）","初期表示で全部が同時に走る","ページを開くたびに全部が再実行"],

     "items":["1ページ8ビジュアルに整理し、詳細はドリルスルー","スライサーはフィルターペインに集約","既定の選択で最初から絞る","カード類は1つのマトリックスにまとめる"],
     "note":"1人が開くと約10クエリ"} ] }
```

35→10で、同じ利用者数に対する負荷が3分の1になります。**容量を増やすより、まずページを設計し直すほうが安く速い。**

### ②③への対策：分離と時間差

```figure
{ "type":"cards", "cols":2, "title":"競合を減らす構成上の打ち手",
  "items":[
    {"icon":"🗂","title":"容量を分ける","text":"開発用と本番用、あるいは重い部門と全社共通で容量を分離する。1つの重い処理が全社を巻き込まない。","tone":"blue"},
    {"icon":"🕐","title":"更新を閲覧ピークから外す","text":"更新は5:00に完了させ、9:00の閲覧ピークと重ねない。日中更新が必要なら昼休みなど谷に置く。","tone":"green"},
    {"icon":"📈","title":"クエリスケールアウト","text":"読み取り専用のレプリカを作り、閲覧クエリを分散させる。更新中も旧レプリカで応答できる。","tone":"violet"},
    {"icon":"🔀","title":"配信をアプリに集約","text":"個別共有ではなくアプリで配布する。権限の評価が単純になり、管理コストも下がる。","tone":"pink"} ] }
```

> [!TRAP] 容量が逼迫して更新が失敗する
> 最も痛い事故です。日中に誰かが重いデータフローを回し、CU（容量ユニット）を食い尽くす。その状態で夜間の更新が始まると、**メモリ不足で更新が失敗**します。翌朝、全社のレポートが前日のままになります。しかも失敗の原因は「更新処理そのもの」ではないため、更新設定をいくら見ても原因が分かりません。**対策は容量の分離と監視**です。詳細はM19で扱いますが、設計段階で「重い処理をどこで走らせるか」を決めておく必要があります。

## 測ってから手を打つ

対策の話をする前に、どこが遅いのかを特定する手順を固定しておきます。**推測で手を打った改善は、効果が測れず、次に活かせません。**

```figure
{ "type":"steps", "title":"性能問題の切り分け手順",
  "items":[
    {"title":"再現条件を確定する","text":"誰が・いつ・どのページで・どの選択状態で遅いのか。特定のスライサー選択でのみ遅いことは多い。","tone":"blue"},
    {"title":"パフォーマンスアナライザーで内訳を見る","text":"DAXクエリ／ビジュアル表示／その他の3項目に分解する。どれが支配的かで打ち手が変わる。","tone":"green"},
    {"title":"DAXが支配的ならクエリを取り出す","text":"DAXクエリビューやDAX Studioで単体実行し、ストレージエンジンとフォーミュラエンジンの比率を見る。","tone":"violet"},
    {"title":"ビジュアル表示が支配的なら描画量を疑う","text":"数千行のテーブルビジュアル、カスタムビジュアル、地図が典型。データ量ではなく描画の問題。","tone":"amber"},
    {"title":"環境要因を確認する","text":"同じレポートが他の時間帯で速いなら、容量の競合。キャパシティメトリックで裏を取る。","tone":"pink"} ] }
```

| 内訳 | 支配的なときの主因 | 打ち手 |
|---|---|---|
| DAXクエリが長い | メジャーの書き方、モデル設計、データ量 | 式の見直し、集計テーブル、カーディナリティ削減 |
| ビジュアル表示が長い | 描画する要素数、カスタムビジュアル | 行数を絞る、標準ビジュアルへ置換 |
| その他が長い | 他のビジュアルの待ち、容量の競合 | ビジュアル数削減、容量分離 |

> [!EXAM] PL-300で問われる
> パフォーマンスアナライザーの3項目（**DAXクエリ／ビジュアルの表示／その他**）の意味と、それぞれが長いときの対処は頻出です。「その他」が長い場合は**他のビジュアルの完了待ち**であり、そのビジュアル自体の問題ではない、という点が引っかけとしてよく使われます。

## 更新の設計を分解する

同時実行と並んで、更新そのものが容量を最も食う処理です。更新は4つの局面に分かれ、それぞれ性質が違います。

```figure
{ "type":"pipeline", "title":"モデル更新の4局面", "caption":"メモリのピークは③で来る。ここが容量上限に当たると失敗する",
  "nodes":[
    {"id":"a","label":"① ソース照会\nデータ取得","tone":"blue"},
    {"id":"b","label":"② 変換\nPower Query実行","tone":"green"},
    {"id":"c","label":"③ エンコード\n圧縮・辞書構築","tone":"bad"},
    {"id":"d","label":"④ 再計算\n計算列・関係・階層","tone":"violet"},
    {"id":"e","label":"完了\n新データを公開","tone":"pink"}],
  "edges":[
    {"from":"a","to":"b"},
    {"from":"b","to":"c","label":"最もメモリを使う"},
    {"from":"c","to":"d"},
    {"from":"d","to":"e"} ] }
```

局面ごとの対処法は次のとおりです。

| 局面 | 遅い／失敗する原因 | 対処 |
|---|---|---|
| ① ソース照会 | フォールディング切れ、ソース側の負荷 | クエリの順序見直し、ゴールド層から読む |
| ② 変換 | 重い結合、カスタム関数 | 変換を下層へ移す（L1703） |
| ③ エンコード | 高カーディナリティ列、メモリ不足 | 列削減、増分更新でパーティション単位に |
| ④ 再計算 | 計算列が多い、双方向関係 | 計算列を上流の列に置き換える |

> [!TIP] 実務のコツ
> 更新失敗のメッセージに「メモリが不足しています」と出たとき、多くの人は容量を疑いますが、**同じ容量でも増分更新に切り替えるだけで解決することがあります**。フルリフレッシュはモデル全体を作り直すためピークメモリが大きく、増分更新なら対象パーティションだけを再構築するため、ピークが小さく収まるからです。容量を触る前に、まず更新方式を確認してください。

## RLSがスケールに与える影響

行レベルセキュリティは、同時実行の負荷を静かに増やします。

| RLSの実装 | 負荷への影響 |
|---|---|
| 静的ロール（部門ごとに固定） | 影響小。ロールごとにキャッシュが効く |
| 動的RLS（`USERPRINCIPALNAME`で判定） | 影響中。ユーザーごとにキャッシュが分かれる |
| 動的RLS＋組織階層の再帰（`PATH`） | 影響大。行ごとの評価コストが高い |
| 双方向リレーションシップ＋RLS | 影響最大。フィルター経路が複雑になり最適化が効きにくい |

> [!TIP] 実務のコツ
> 組織階層のRLSで性能が出ないとき、`PATHCONTAINS` を実行時に評価する代わりに、**「ユーザー × 見てよい組織」のブリッジテーブルを事前に展開しておく**方法が有効です。行数は増えますが、実行時の計算がただの結合になり、劇的に速くなります。「実行時に計算する」を「事前に展開しておく」に置き換えるのは、性能設計の基本パターンです。

> [!DS] データサイエンス視点：なぜ70%で止めるのか
> 待ち行列理論では、**利用率が高まるほど待ち時間は非線形に伸びます**。利用率50%のときの待ち時間を1とすると、80%では約4倍、90%では約9倍、95%では約19倍になります（M/M/1の近似）。つまり「容量の90%まで使えているから効率的」という考えは誤りで、その状態は**わずかな負荷増で待ち時間が爆発する崖の上**にいます。BI基盤の設計では、平常時60〜70%、ピークで80%を上限に見るのが安全域です。余裕は無駄ではなく、応答時間を買う費用です。

```figure
{ "type":"chart", "kind":"line", "title":"利用率と待ち時間の関係", "unit":"相対待ち時間",
  "categories":["50%","60%","70%","80%","90%","95%"],
  "series":[{"name":"平均待ち時間","values":[1,1.5,2.3,4,9,19],"tone":"bad"}],
```

> 「遅いので容量を上げましょう」は、最も高くつき、最も効果が読めない提案です。しかも**設計の問題は容量を上げても消えません**。倍にすれば倍の利用者で同じ問題が起きます。第1手と第2手（費用ゼロ）を試さずに増強を提案すると、その後の信頼を失います。まず測り、まず削る。

## 大規模時の配信設計

利用者が数百人を超えると、配信の設計自体が性能に効いてきます。

| 配信方法 | 大規模での適性 | 理由 |
|---|---|---|
| アプリ（Power BI アプリ） | ◎ | 権限評価が単純。対象者グループで一括管理 |
| ワークスペースへの直接アクセス | △ | 編集権限が混ざりやすく、事故の元 |
| 個別のレポート共有 | × | 管理不能。誰が見られるか把握できなくなる |
| Excel（Analyze in Excel） | ○ | クエリは重いが利用者体験が良い。人数を把握しておく |
| メール配信（サブスクリプション） | ○ | 閲覧のピークを分散できる。ただし配信時に負荷が集中する |

> [!TIP] 実務のコツ
> サブスクリプション（定期メール配信）は同時実行対策として有効です。**「毎朝レポートを開いて数字を確認するだけ」の利用者を、メールのスナップショットに移す**と、9時のピークからその人数分が消えます。数百人規模では効果が大きい。ただし配信自体も容量を消費するため、配信時刻は分散させます。

## 理解度チェック

1. 1000万行のモデルが1.8GBあります。行数を減らさずにサイズを下げる方法を2つ挙げ、なぜ効くのかを説明してください。
2. 容量の利用率が90%で安定している基盤は「効率的」と言えるでしょうか。待ち行列の観点から答えてください。
3. 「レポートが遅い」という報告を受けました。容量増強を提案する前に確認・実施すべきことを、費用対効果の順に3つ挙げてください。

> [!NOTE] このレッスンのまとめ
> スケールにはデータ量と同時利用者数の2軸があり、効く打ち手が違う。データ量はカーディナリティ削減・増分更新・集計テーブルで、同時実行はクエリ本数削減・容量分離・時間差・配信設計で対処する。容量増強は最後の手段であり、設計の問題は容量では消えない。そして利用率は70%を超えたあたりから待ち時間が非線形に伸びるため、余裕は無駄ではなく応答時間を買う費用である。
