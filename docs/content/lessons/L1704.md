モデルを開いた利用者が最初にする質問は、いつも同じです。「**どの列を使えばいいんですか**」。

フィールドリストに `金額`、`金額2`、`売上金額`、`SalesAmount`、`Amount_JPY` が並んでいれば、その質問は必然です。そして毎回あなたが答えることになります。100人が使うモデルでは、この質問が100回来ます。

**標準化とは、その質問が発生しない状態を作る作業です。**センスの問題ではなく、規約の問題です。

## 標準化が効く3つの場所

```figure
{ "type":"stack", "title":"標準化の対象3層", "caption":"下から順に整えると、上の層の作業が楽になる",
  "layers":[
    {"label":"③ レポート標準","sub":"配色 / フォント / 余白 / ビジュアルの選択規則 / アクセシビリティ","tone":"pink"},
    {"label":"② モデル標準","sub":"命名規約 / 表示フォルダー / 非表示設定 / 説明 / 書式","tone":"violet"},
    {"label":"① データ標準","sub":"テーブル名 / 列名 / キーの型 / 日付テーブル / コード体系","tone":"green"} ] }
```

このレッスンは①と②を中心に扱います。③は上級のレポート設計で扱った内容の組織展開です。

> [!NOTE] 要点
> 標準化の目的は「きれいにすること」ではありません。**利用者の判断回数を減らすこと**です。判断が要らない状態は、間違いが起きない状態です。

## 命名規約を設計する

### テーブル名

```figure
     "note":"開発チームが主に使うモデル向け"},
    {"title":"業務語方式","tone":"good",
     "items":["売上 / 商品 / 日付 / 顧客","利用者にとって最も自然","役割は表示フォルダーとアイコンで示す","開発時に種別が判別しにくい"],
     "note":"セルフサービス利用者が多いモデル向け"} ] }
```

判断基準は明確です。**そのモデルを直接触る人が誰か**。開発者だけならどちらでもよく、業務部門が自分でレポートを作るなら業務語方式が圧倒的に使いやすい。ハブアンドスポーク構成で共有モデルを作るなら、業務語方式を推奨します。

### 列名の規約

| 種別 | 規約 | 例 |
|---|---|---|
| キー列 | `<エンティティ>ID`／利用者には非表示 | `商品ID`、`顧客ID` |
| 金額列 | 単位を名前に含める | `売上金額（円）` または `売上金額` ※単位を書式で表現 |
| 日付列 | 何の日付かを明示 | `受注日`、`出荷日`（`日付`単独は禁止） |
| 区分列 | 区分名のみ、コードは非表示 | `商品カテゴリ`（`カテゴリコード`は隠す） |
| フラグ列 | 肯定形の疑問文にしない | `休眠区分`（値は「休眠／稼働」。真偽値より読みやすい） |

> [!TRAP] 「金額」という列が5個ある
> 最も多い実害はこれです。`Fact_売上[金額]`、`Fact_発注[金額]`、`Fact_予算[金額]`。テーブルが違うので技術的には衝突しませんが、利用者がフィールドリストで検索すると5つ出てきて、どれを選ぶべきか判断できません。**列名は、テーブル名を見なくても意味が確定するようにする**。`売上金額`、`発注金額`、`予算金額`。これだけで問い合わせが激減します。

> ファクトの数値列を非表示にして、**暗黙のメジャー（列をドラッグしたときに自動でSUMされる動作）を封じる**のは、共有モデルでは必須の設計です。暗黙のメジャーが使えると、利用者が `Fact_売上[金額]` をそのまま集計してしまい、返品や社内取引の除外が入らない数字が出ます。列を隠し、`売上金額`メジャーだけを見せれば、定義に反する集計は物理的に不可能になります。

## メタデータを埋める

命名の次に効くのが、説明（Description）です。フィールドにマウスを乗せたときに出るツールチップになります。

| 埋めるべき項目 | 書く内容 | 例 |
|---|---|---|
| テーブルの説明 | 何の事実か、粒度、期間 | 「受注明細。1行＝1受注1明細。2019年4月以降」 |
| 列の説明 | 定義と注意点 | 「出荷日。未出荷の受注はBLANK」 |
| メジャーの説明 | 計算定義と除外条件 | 「値引後・返品控除後の売上。社内取引を除く」 |
| モデルの説明 | 所有者・更新時刻・問い合わせ先 | 「販売ドメイン共有モデル／所有:BI課／毎日6:00更新」 |

> [!TRAP] ドキュメントを別ファイルに書く
> Word や Wiki にモデル仕様書を書く運用は、ほぼ確実に陳腐化します。理由は単純で、**モデルを直す人と仕様書を直す人の作業場所が違うから**です。説明はモデルの中（Description プロパティ）に書きます。Tabular Editor で一括編集でき、PBIP形式ならテキストとして差分レビューできます。**ドキュメントは資産の中に置く**、が原則です。

### ベストプラクティスアナライザーで自動化する

BPA は Tabular Editor に組み込まれた検査機能で、モデルの構造を規則に照らして自動チェックします。標準規則に加え、組織固有の規則を追加できます。

| 規則の例 | 検出するもの | 重要度 |
|---|---|---|
| すべてのメジャーに説明があること | メタデータ欠落 | 中 |
| キー列が非表示であること | 利用者への露出 | 高 |
| 日付テーブルがマークされていること | タイムインテリジェンスの誤動作 | 高 |
| 浮動小数点型の金額列がないこと | 丸め誤差 | 高 |
| 双方向リレーションシップがないこと | 曖昧なフィルター経路 | 中 |
| 未使用の列が残っていないこと | モデルサイズの無駄 | 低 |

> [!TIP] 実務のコツ
> BPA規則は最初から厳しくしないでください。**警告が200件出るチェックは、誰も見なくなります。**まず「高」の5規則だけを必須にし、全モデルが0件になったら次の規則を昇格させる。この段階的な締め方でないと、規約は形骸化します。

## データ品質を6次元で点検する

標準化は見た目の話に留まりません。**データそのものの品質**を測る枠組みを持っておきます。

```figure
{ "type":"cards", "cols":3, "title":"データ品質の6次元", "caption":"それぞれ測定方法があり、モデル内のメジャーとして常設できる",
  "items":[
    {"icon":"✅","title":"正確性 Accuracy","text":"値が現実と一致しているか。基幹システムの合計と突合して測る。","tone":"blue"},
    {"icon":"🧩","title":"完全性 Completeness","text":"必要な行・値が欠けていないか。必須列のNULL率で測る。","tone":"green"},
    {"icon":"🔗","title":"一貫性 Consistency","text":"システム間で矛盾がないか。売上合計が販売と会計で一致するか。","tone":"violet"},
    {"icon":"⏰","title":"適時性 Timeliness","text":"必要な時点までに揃っているか。最終更新時刻とSLOの差で測る。","tone":"amber"},
    {"icon":"🆔","title":"一意性 Uniqueness","text":"重複がないか。業務キーの重複件数で測る。","tone":"pink"},
    {"icon":"📏","title":"妥当性 Validity","text":"取りうる値の範囲に収まっているか。マイナス数量、未来日付の件数。","tone":"cyan"} ] }
```

> [!DS] データサイエンス視点：品質は「良い／悪い」ではなく測定値
> 品質を感想で語る限り、改善は進みません。6次元それぞれに**測定式と目標値**を決めます。例：「顧客IDのNULL率 < 0.1%」「販売と会計の売上差異 < 0.5%」「日次更新の完了 7:30まで」。これを品質ダッシュボードとしてモデル内にメジャー化し、BI基盤自身が自分の健康状態を表示するようにします。**BIチームが最初に作るべきレポートは、BI基盤の品質レポートです。**

### 品質メジャーの例

```figure
{ "type":"formula", "lang":"dax",
  "code":"顧客ID欠損率% = DIVIDE( COUNTROWS( FILTER( Fact_売上, ISBLANK( Fact_売上[顧客ID] ) ) ), COUNTROWS( Fact_売上 ) )",
  "parts":[
    {"match":"DIVIDE","label":"0件のときにエラーを出さない除算","tone":"violet"},
    {"match":"FILTER( Fact_売上, ISBLANK( Fact_売上[顧客ID] ) )","label":"キーが欠けている行を抽出","tone":"amber"},
    {"match":"COUNTROWS( Fact_売上 )","label":"母数となる全行数","tone":"blue"} ] }
```

このメジャーを「99_補助」フォルダーに入れ、品質ダッシュボードで監視します。閾値を超えたらアラートを出す設定にすれば、**利用者より先に異常に気づけます**。

モデル標準の次は、③のレポート標準です。ここは「見た目の好み」に見えるため後回しにされがちですが、実際には**読み違いを防ぐ安全装置**として機能します。

```figure
{ "type":"cards", "cols":3, "title":"組織で決めるべきレポート標準", "caption":"どれも「決めておけば毎回考えなくてよくなる」ものばかり",

    {"icon":"📊","title":"ビジュアルの選択規則","text":"時系列は折れ線、内訳は横棒、構成比は円を使わない、など。判断を規則にする。","tone":"blue"},
    {"icon":"🔤","title":"書式","text":"金額は千区切り・単位を軸ラベルに。小数桁は指標ごとに固定。","tone":"green"},
```

> 色の意味は、テーマJSONの中で**セマンティックな名前を持つ色として定義**しておきます。`good`/`bad`/`neutral`/`target` のように役割で管理すれば、後でブランドカラーが変わっても、意味を保ったまま一括で差し替えられます。個別のビジュアルで直接色コードを指定すると、変更のたびに全レポートを開くことになります。

```figure
  "items":[
    {"label":"Day 1","title":"カタログで探す","text":"認定済みモデルの一覧から、自分の業務領域のモデルを見つける。説明で用途が分かる。","tone":"blue"},
    {"label":"Day 1","title":"フィールドを理解する","text":"表示フォルダーとツールチップだけで、どの指標を使うか判断できる。","tone":"cyan"},
    {"label":"Day 2","title":"テンプレートから作る","text":"pbitを開けば、テーマ・書式・レイアウトが揃った状態から始まる。","tone":"green"},
```

> [!DS] データサイエンス視点：データディクショナリとメタデータ管理
> **データディクショナリ**とは、データ要素の定義・型・制約・所有者を一元的に記述したものです。モデルの説明プロパティに書いた内容は、そのままディクショナリの一部になります。重要なのは**単一の記述場所を決めること**。Wiki、Excel、モデル内の3か所に書けば、3つとも古くなります。記述場所を1つに決め、そこから他のビューを生成する（スキャンAPIやTMDLから抽出してカタログに載せる）のが、破綻しないメタデータ管理の形です。

## 規約書の作り方

最後に、規約そのものの作り方です。守られる規約には共通点があります。

```figure
{ "type":"compare", "title":"守られる規約と守られない規約",
  "panels":[
    {"title":"守られない","tone":"bad",
     "items":["30ページのWord文書","「〜が望ましい」という書き方","例が抽象的","チェックが人力","違反しても何も起きない"],
     "note":"読まれないので存在しないのと同じ"},
    {"title":"守られる","tone":"good",
     "items":["1〜2ページ。表が中心","「必須／推奨／任意」を明示","良い例と悪い例を並記","BPAで自動チェック","認定の条件に組み込まれている"],
     "note":"守るほうが楽な状態を作る"} ] }
```

> [!WARN] 注意
> 規約を後から既存資産に一括適用すると、レポートが壊れます。列名やメジャー名を変更すると、**それを参照している既存のビジュアルが「フィールドが見つかりません」になる**からです。既存資産への適用は、(1) 影響分析で依存レポートを洗い出す、(2) 開発環境で改名して検証する、(3) 予告してからデプロイする、の順で行います。新規資産から適用し、既存は改修のタイミングで揃えるのが現実的です。

> [!EXAM] PL-300で問われる
> 命名と表示の設計は「レポート作成者が使いやすいモデル」という文脈で出題されます。頻出は次の3点です。(1) **キー列は非表示にする**、(2) **メジャーには適切な書式と説明を設定する**、(3) **フィールドを表示フォルダーで整理する**。さらに「特定の列を集計させたくない」場合の対処として、列の非表示に加えて**集計の既定を「集計しない」に設定する**方法も問われます。

## 標準化の投資対効果

標準化は成果が見えにくく、後回しにされます。効果を数字で語れるようにしておきます。

```figure
{ "type":"chart", "kind":"bar", "title":"標準化前後の運用指標（ある製造業・利用者120名の例）", "unit":"相対",
  "categories":["問い合わせ件数/月","レポート1本の開発日数","レビュー指摘のうち書式・命名","誤った指標の使用報告/四半期"],
  "series":[
    {"name":"標準化前","values":[100,100,100,100],"tone":"bad"},
    {"name":"標準化後","values":[38,55,12,15],"tone":"good"}],
  "highlight":2 }
```

読み取るべきは3列目です。**レビュー指摘のうち書式・命名に関するものが88%減った**。これは人のレビュー時間がそのまま内容の議論に回ったことを意味します。標準化の本当の効果は、作業が減ることではなく、**人の時間が判断に使われるようになること**です。

| 効果 | 測り方 | 目安 |
|---|---|---|
| 問い合わせの削減 | 「どの列を使うか」型の質問件数 | 3か月で半減 |
| 開発速度 | レポート1本の着手から公開まで | 2〜3割短縮 |
| 品質 | 誤った指標を使った報告の件数 | 大幅減 |
| 属人性 | 担当者以外が変更できる資産の割合 | 8割以上を目標 |

> [!TRAP] 標準化を「一度やる作業」と考える
> 規約を作った時点で終わりにする組織が多いのですが、標準は**生き物**です。新しい業務領域が増えれば命名規約に追記が要り、Fabric の新機能が出れば配置ルールを見直す必要があります。四半期に1回、規約の見直し会を設定してください。**見直されない規約は、現実と乖離した瞬間に無視され始めます。**

## 設計チェックリスト

- [ ] テーブル命名を接頭辞方式か業務語方式のどちらかに統一した
- [ ] 列名がテーブル名なしで意味が確定する形になっている
- [ ] メジャー名を業務語・単位明示・修飾後置・略語禁止の4原則で統一した
- [ ] キー列・作業列・ファクトの数値列を非表示にした
- [ ] 暗黙のメジャーが使えないようにし、指標はメジャー経由に一本化した
- [ ] メジャーを表示フォルダーで分類し、番号接頭辞で順序を制御した
- [ ] テーブル・列・メジャー・モデルの説明をモデル内に書いた
- [ ] pbit テンプレート、テーマJSON、共有日付テーブルを配布した
- [ ] BPA規則を配布し、必須規則を段階的に設定した
- [ ] データ品質の6次元それぞれに測定式と目標値を定めた
- [ ] 品質メジャーを常設し、閾値超過を検知できるようにした
- [ ] 規約書を1〜2ページに収め、必須／推奨／任意を明示した
- [ ] レポート標準（色の意味・ビジュアル選択規則・注記）を決めて配布した
- [ ] 規約の四半期見直しを予定に組み込んだ

そして、標準を決める会議で最も大切なのは**決め切ること**です。命名規約の議論は、正解がないぶん永遠に続けられます。「接頭辞方式と業務語方式のどちらが優れているか」に答えはありません。答えがあるのは「**この組織はどちらを使うか**」だけです。決めた事実そのものが価値であり、内容の優劣は二次的な問題だと理解しておくと、議論を短く終わらせられます。

## 理解度チェック

1. 共有モデルでファクトの数値列を非表示にする理由を、暗黙のメジャーという語を使って説明してください。
2. データ品質の6次元のうち「一貫性」と「正確性」の違いを、それぞれの測定方法を挙げて説明してください。
3. モデル仕様書を別のWord文書ではなくモデル内の説明プロパティに書くべき理由を述べてください。

> [!NOTE] このレッスンのまとめ
> 標準化の目的は利用者の判断回数を減らすこと。列名はテーブル名なしで意味が確定するようにし、メジャーは業務語で命名する。何を見せるかより何を隠すかが品質を決め、ファクトの数値列を隠して暗黙のメジャーを封じるのが共有モデルの必須設計。規約は文書ではなくテンプレートとBPAで配り、守るほうが楽な状態を作る。そしてデータ品質は6次元で測り、BI基盤自身の健康状態をレポートにする。
