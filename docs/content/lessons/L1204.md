「全社の売上レポートを作りました。ただし、各支店長には自分の支店の数字だけ見せてください」。この要求に、支店の数だけレポートを複製して対応した組織は、支店が20個になった時点で運用が崩壊します。

**行レベルセキュリティ（RLS: Row-Level Security）** は、1つのモデル・1つのレポートのまま、**閲覧するユーザーによって見える行を変える**仕組みです。レポートは1つ、モデルも1つ。変わるのはデータだけです。

```dax

```


> [!TRAP] つまずきポイント
> フィルターは **ディメンションテーブルに書きます**。`Fact_売上` に直接書くと、リレーションシップで他のディメンションに伝播せず、スライサーには他支店の名前が出続けます。「支店スライサーに他支店が出るが、選んでも数字は0」という中途半端な状態になり、**他支店の存在という情報が漏れます**。フィルターは必ず1側（ディメンション）に置いてください。

> [!TRAP] つまずきポイント
> 静的RLSは支店が20個あればロールを20個作ることになり、しかも**支店が増えるたびにDesktopで編集して再発行**が必要です。3つ4つを超えたら、次に述べる動的RLSに切り替えてください。静的RLSが適するのは「本社／支店」「社内／社外」のような、**数が増えない大分類**だけです。

## 動的RLS — ログインユーザーで判定する

`USERPRINCIPALNAME()` は、レポートを開いているユーザーのログインID（メールアドレス形式）を返します。これを使えば、ロールは**1つだけ**で済みます。

```figure
{ "type":"star", "title":"動的RLSのためのセキュリティ用テーブル",
  "caption":"ユーザーと閲覧可能範囲の対応表をディメンションとして持ち、そこにRLSを掛ける",
  "fact":{"label":"Fact_売上","lines":["売上日 / 支店ID / 商品ID","金額"]},
  "dims":[
    {"label":"Dim_ユーザー支店","lines":["メール / 支店ID","RLSはここに掛ける","1人が複数支店を持てる"]},
    {"label":"Dim_支店","lines":["支店ID / 支店名 / 地域"]},
    {"label":"Dim_日付","lines":["年 / 月 / 四半期"]},
    {"label":"Dim_商品","lines":["商品名 / カテゴリ"]}
  ],
  "edgeLabel":"1対多" }
```

ロールは1つだけ作り、`Dim_ユーザー支店` に次の式を書きます。

```dax
-- ロール「動的RLS」を Dim_ユーザー支店 テーブルに設定
[メール] = USERPRINCIPALNAME()
```

このとき、フィルターの伝播は次のように起きます。

1. `Dim_ユーザー支店` が、ログインユーザーの行だけに絞られる
2. その行が持つ `支店ID` が、`Dim_支店` へ伝播する（**この関係だけは双方向、またはブリッジ構成が必要**）
3. `Dim_支店` から `Fact_売上` へ伝播する

```figure
{ "type":"pipeline", "title":"動的RLSの伝播経路",
  "caption":"ユーザー表 → 支店 → 売上 の順に絞られる。ユーザー表と支店の間の伝播をどう作るかが設計の要点",
  "nodes":[
    {"id":"upn","label":"USERPRINCIPALNAME()\ntanaka@example.com","tone":"pink"},
    {"id":"du","label":"Dim_ユーザー支店\n該当行のみ（支店ID: 03, 07）","tone":"amber"},
    {"id":"ds","label":"Dim_支店\n03=新宿, 07=渋谷 のみ","tone":"cyan"},
    {"id":"f","label":"Fact_売上\n2支店の行のみ","tone":"green"},
    {"id":"v","label":"すべてのビジュアル\n合計も2支店分","tone":"violet"}
  ],
  "edges":[
    {"from":"upn","to":"du","label":"RLSフィルター"},
    {"from":"du","to":"ds","label":"双方向 or ブリッジ"},
    {"from":"ds","to":"f","label":"通常の1対多"},
    {"from":"f","to":"v"}
  ] }
```

`Dim_ユーザー支店` と `Dim_支店` の間の伝播を作る方法は2つあります。

| 方法 | 設定 | 注意点 |
|---|---|---|
| 双方向にする | `Dim_支店` ↔ `Dim_ユーザー支店` を双方向にし、「両方向にセキュリティ フィルターを適用する」をオン | 前レッスンの副作用に注意。RLS専用の経路として最小限にとどめる |
| ユーザー表をファクト側に置く | `Dim_ユーザー支店` を多側にして、`Dim_支店` から1対多で結ぶ | 伝播が逆になるため、RLSは支店側に `PATHCONTAINS` 等で書く必要がある |

> [!TIP] 実務のコツ
> 動的RLSの最大の利点は、**支店が増えてもモデルを触らなくてよい**ことです。`Dim_ユーザー支店` に行を追加するだけで、新しい支店長にアクセス権が付きます。この対応表を**人事システムや Entra ID のグループから自動生成**できれば、権限管理が運用に乗ります。手作業のExcelで管理すると、退職者の行が残り続けます。

> [!TRAP] つまずきポイント
> `USERNAME()` は、Power BI Service では `USERPRINCIPALNAME()` と同じ値を返しますが、Desktop では `DOMAIN\ユーザー名` 形式を返します。**動的RLSでは必ず `USERPRINCIPALNAME()` を使ってください。** `USERNAME()` を使うと、Desktopでは動くのにServiceで誰も何も見えない、という現象が起きます。

> [!TRAP] つまずきポイント
> 対応表にメールアドレスが**1文字でも違う形で登録されている**と、そのユーザーには何も見えません。大文字小文字は区別されませんが、`tanaka@example.com` と `tanaka@example.co.jp`、旧姓のアドレス、エイリアスなどは別物です。「レポートが真っ白」という問い合わせの原因は、9割がこれです。**対応表に存在しないユーザーを検出するチェッククエリ**を用意してください。

## 階層RLS — `PATH` と `PATHCONTAINS`

組織図のように「自分と、自分の配下すべて」を見せたい場合は、親子関係を平坦な文字列に展開して判定します。

```figure
{ "type":"tree", "title":"組織階層と見える範囲",
  "caption":"部長は自分の配下すべて、課長は自分の課だけ。同じロール1つで、階層の位置に応じて範囲が変わる",
  "root":{"label":"社長 E001","sub":"全社が見える","tone":"pink"},
  "children":[
    {"label":"営業部長 E002","sub":"営業部の配下すべて","tone":"amber",
     "children":[
       {"label":"営業1課長 E004","sub":"E004 と配下","tone":"cyan",
        "children":[{"label":"担当 E007","sub":"自分だけ","tone":"gray"},{"label":"担当 E008","sub":"自分だけ","tone":"gray"}]},
       {"label":"営業2課長 E005","sub":"E005 と配下","tone":"cyan",
        "children":[{"label":"担当 E009","sub":"自分だけ","tone":"gray"}]}
     ]},
    {"label":"管理部長 E003","sub":"管理部の配下すべて","tone":"green",
     "children":[{"label":"経理課長 E006","sub":"E006 と配下","tone":"cyan"}]}
  ] }
```

`Dim_社員` には `社員ID` と `上司ID` があるとします。まず計算列でパスを作ります。

```dax
-- 計算列：自分から最上位までの経路を | 区切りの文字列にする
-- 例: E007 の場合 → "E001|E002|E004|E007"
社員パス = PATH( Dim_社員[社員ID], Dim_社員[上司ID] )
```

`PATH( 子の列, 親の列 )` は、その行から親をたどって最上位までの ID を `|` で連結した文字列を返します。この列に対して、`PATHCONTAINS` で判定します。

```figure
{ "type":"formula", "lang":"dax",
  "title":"階層RLSのフィルター式",
  "caption":"「自分のIDが、その行のパスのどこかに含まれているか」を判定する。含まれていれば自分の配下",
  "code":"PATHCONTAINS( Dim_社員[社員パス], LOOKUPVALUE( Dim_社員[社員ID], Dim_社員[メール], USERPRINCIPALNAME() ) )",
  "parts":[
    {"match":"PATHCONTAINS","label":"パス文字列に指定のIDが含まれるかを返す","tone":"violet"},
    {"match":"Dim_社員[社員パス]","label":"PATH で作った経路文字列の列","tone":"blue"},
    {"match":"LOOKUPVALUE( Dim_社員[社員ID], Dim_社員[メール], USERPRINCIPALNAME() )","label":"ログインユーザーのメールから社員IDを引く","tone":"amber"}
  ] }
```

ロール「階層RLS」を `Dim_社員` テーブルに設定します。

```dax
PATHCONTAINS(
    Dim_社員[社員パス],
    LOOKUPVALUE( Dim_社員[社員ID], Dim_社員[メール], USERPRINCIPALNAME() )
)
```

E002（営業部長）がログインすると、社員パスに `E002` を含む行、すなわち E002・E004・E005・E007・E008・E009 が残ります。E004（営業1課長）なら E004・E007・E008 だけです。**同じ1つのロール定義で、階層の位置に応じた範囲が自動的に決まります。**

関連する `PATH` 系関数もまとめて押さえます。

| 関数 | 返すもの | 使いどころ |
|---|---|---|
| `PATH( 子, 親 )` | 最上位から自分までを縦棒で連結した文字列 | 階層の展開。計算列で作る |
| `PATHCONTAINS( パス, ID )` | そのIDがパスに含まれるか（真偽値） | RLSの判定 |
| `PATHLENGTH( パス )` | パスの要素数 = 階層の深さ | 「第3階層まで表示」などの制御 |
| `PATHITEM( パス, n )` | n番目の要素（上から） | 階層をレベル別の列に展開する |
| `PATHITEMREVERSE( パス, n )` | n番目の要素（下から） | 直属の上司を取り出す |

```dax
-- 階層を列に展開して、ドリルダウン可能な階層を作る
レベル1 = PATHITEM( Dim_社員[社員パス], 1 )
レベル2 = PATHITEM( Dim_社員[社員パス], 2 )
レベル3 = PATHITEM( Dim_社員[社員パス], 3 )
階層の深さ = PATHLENGTH( Dim_社員[社員パス] )
```

> [!TRAP] つまずきポイント
> `PATH` は **自己参照（自分が自分の上司）や循環参照（AがBの上司で、BがAの上司）があるとエラーになります**。組織マスタは意外と汚れており、退職者が上司として残っていたり、上司IDが空だったりします。`PATH` を作る前に、Power Query で **(1) 上司IDが自分自身の行、(2) 上司IDがマスタに存在しない行、(3) 循環** を検出してください。最上位の行は上司IDが null であることが必要です。

> [!DS] データサイエンス視点
> `PATH` が行っているのは、**隣接リスト（各行が親のIDだけを持つ形式）を、マテリアライズド パス（経路を文字列に展開した形式）に変換する**操作です。階層データの表現方法には、隣接リスト、マテリアライズド パス、入れ子集合モデル、閉包テーブルなどがあり、それぞれ「更新が容易か」「祖先の検索が速いか」のトレードオフを持ちます。DAXの `PATH` はマテリアライズド パスを採用しており、**祖先判定が文字列検索1回で済む**という利点があります。代わりに、階層が変わるたびに全行の再計算が必要です。

## 運用に乗せる — Entra ID グループを使う

Service でロールにメンバーを割り当てるとき、**個人ではなく Microsoft Entra ID のセキュリティ グループを割り当ててください**。

| 割り当て方 | 異動が起きたとき |
|---|---|
| 個人を直接割り当て | Power BI の設定画面を開いて手作業で修正する。忘れる |
| セキュリティ グループを割り当て | 人事側でグループのメンバーを変えれば自動で反映される |

動的RLSの場合、ロールに割り当てるグループは「レポートを見る人全員」の1つで足ります。**誰が何を見られるかは対応表が決め、ロールへの割り当ては「このモデルを使ってよいか」だけを決める**、という役割分担にすると運用が単純になります。

```m
// 対応表に存在しないユーザーを検出するチェッククエリ（読み込みは無効にする）
let
    利用者 = 利用者一覧,              // Entra ID グループから同期した一覧
    対応表 = Dim_ユーザー支店,
    未登録 = Table.NestedJoin(利用者, {"メール"}, 対応表, {"メール"}, "m", JoinKind.LeftAnti),
    結果 = Table.SelectColumns(未登録, {"メール", "表示名"})
in
    結果
```

> [!TRAP] つまずきポイント
> ゲストユーザー（B2B、社外の共同編集者）の `USERPRINCIPALNAME()` は、**元のメールアドレスとは異なる形式**（`user_example.com#EXT#@tenant.onmicrosoft.com` のような形）になることがあります。社外パートナーにレポートを共有する場合、対応表にはこの形式で登録する必要があります。実際にログインしてもらい、`USERPRINCIPALNAME()` を表示するカードで値を確認してから登録してください。

## 検証 — 「ロールとして表示」

RLSは、設定しただけでは信用できません。必ず検証します。

| 検証場所 | 方法 | 確認すること |
|---|---|---|
| Desktop | モデリング →「ロールとして表示」 | ロールを選ぶ。動的RLSは「他のユーザー」にメールを入力して検証 |
| Service | セマンティックモデル → セキュリティ → ロールの「…」→「テスト」 | 実環境での挙動。ゲートウェイ経由の場合はこちらが確実 |
| 実ユーザー | 対象者に実際に開いてもらう | 最終確認。特に階層RLSは必須 |

> [!TIP] 実務のコツ
> 検証用のページに **「あなたのログインID」「見えている支店の数」「見えている行数」** を表示するカードを置いてください。

```dax
ログインID = USERPRINCIPALNAME()
見える支店数 = COUNTROWS( ALLSELECTED( Dim_支店 ) )
見える行数 = COUNTROWS( Fact_売上 )
```

問い合わせが来たとき、このページのスクリーンショットを送ってもらうだけで原因の大半が分かります。

> RLSは出題頻度が高い領域です。押さえるべきは、**(1) ロールはDesktopで作り、メンバーの割り当てはServiceで行う**、**(2) RLSが適用されるのはビューアーのみ**、**(3) 動的RLSでは `USERPRINCIPALNAME()` を使う**、**(4) フィルターはディメンション側に書く**、**(5) 「ロールとして表示」で検証する**の5点です。

## オブジェクトレベルセキュリティ（OLS）との違い

| 仕組み | 制御する対象 | 見え方 |
|---|---|---|
| RLS | **行** | テーブルは見えるが、行が減る |
| OLS | **テーブル・列そのもの** | テーブルや列の存在自体が見えなくなる |

給与額のように「その列があること自体を隠したい」場合はOLSを使います。ただしOLSはDesktopのUIからは設定できず、**外部ツール（Tabular Editor など）とXMLAエンドポイントが必要**です。また、隠した列を参照しているビジュアルは、権限のないユーザーにはエラーとして表示されます。

## 性能への影響

RLSは、すべてのクエリに追加のフィルターを掛けます。当然、負荷は増えます。

- **フィルターは1側（ディメンション）に書く。** ファクトに書くと、大量行の走査が毎回発生する
- **`LOOKUPVALUE` を計算列で先に解決する。** RLSの式の中で毎回呼ぶより、事前に列として持つほうが速い
- **`PATH` の計算列は更新時に1度だけ計算される。** メジャーでパスを組み立てるのは避ける
- **双方向フィルターとRLSの組み合わせは重い。** 必要最小限にする

> [!TIP] 実務のコツ
> RLSを入れると応答時間が2〜3倍になることは普通にあります。**RLSを入れる前に、パフォーマンス アナライザーでベースラインを取っておいてください。** 後から「遅くなった」と言われたとき、どれだけ遅くなったかを数字で説明できます。

## 設計判断チェックリスト

- [ ] フィルターをディメンション側に書いたか。ファクトに直接書いていないか
- [ ] ロールの数が増え続ける設計になっていないか。動的RLSに切り替えるべきではないか
- [ ] `USERNAME()` ではなく `USERPRINCIPALNAME()` を使ったか
- [ ] ユーザー対応表のメールアドレスは、実際のログインIDと完全に一致しているか
- [ ] 対応表に存在しないユーザーを検出する仕組みがあるか
- [ ] 階層RLSの場合、循環参照と自己参照を事前に検出したか
- [ ] Desktop・Serviceの両方で「ロールとして表示 / テスト」を実行したか
- [ ] 対象ユーザーのワークスペース ロールは「閲覧者」になっているか
- [ ] レポート上に、全社合計などをハードコードしていないか
- [ ] RLS導入前後で応答時間を計測したか
- [ ] 退職者・異動者の対応表を更新する運用フローを決めたか

## 理解度チェック

1. 支店が50あり、毎月増減します。静的RLSと動的RLSのどちらを選びますか。理由と、必要なテーブル構成を説明してください。
2. `Dim_社員` に `社員ID` と `上司ID` があります。「自分と自分の配下すべてを見せる」RLSを、使う関数と計算列を含めて説明してください。
3. RLSを設定したのに、ある管理職が全支店の数字を見られていました。考えられる原因を3つ挙げ、それぞれの確認方法を述べてください。
