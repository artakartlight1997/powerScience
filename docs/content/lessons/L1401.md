## 速さの理由その2：圧縮

列指向のもう1つの利点は、**同じ列の値は似ている**ことです。似た値が並んでいると、圧縮がよく効きます。

VertiPaq は3つの符号化方式を、列ごとに自動で選びます。

```figure
{ "type":"cards", "cols":3, "title":"VertiPaq の3つの符号化",
  "items":[
    {"icon":"📖","title":"辞書符号化","text":"一意な値を辞書に登録し、本体は辞書のインデックス番号だけを持つ。文字列列で必ず使われる","tone":"blue"},
    {"icon":"🔢","title":"値符号化","text":"数値から最小値を引くなどして、必要なビット数を減らす。整数列で使われる","tone":"green"},
    {"icon":"🔁","title":"ランレングス符号化（RLE）","text":"同じ値の連続を「値 × 回数」にまとめる。上の2つと組み合わせて使われる","tone":"violet"} ] }
```

### 辞書符号化（Dictionary Encoding）

```figure
{ "type":"tablediff", "title":"辞書符号化", "arrowLabel":"一意な値を辞書に切り出す",
  "before":{"title":"元の列（8行）","tone":"neutral","head":["Category"],
    "rows":[["家電"],["家電"],["衣料"],["食品"],["家電"],["衣料"],["食品"],["家電"]]},
  "after":{"title":"辞書 + インデックス","tone":"good","head":["辞書","本体（2ビットで足りる）"],
    "rows":[["0 = 家電","!0"],["1 = 衣料","!0"],["2 = 食品","!1"],["","!2"],["","!0"],["","!1"],["","!2"],["","!0"]]} }
```

「家電」という文字列は辞書に**1回だけ**保存され、本体には 0 という番号が入ります。一意な値が3つなら2ビットで表現できます。8行 × 2ビット = 16ビット = 2バイトです。元の文字列をそのまま持てば数十バイト必要でした。

> [!NOTE] 要点
> **辞書のサイズは、一意な値の数（カーディナリティ）で決まります。** 行数ではありません。100万行あっても、カテゴリが8種類なら辞書は8エントリです。逆に、100万行すべてが異なる注文IDなら、辞書も100万エントリになります。

### 値符号化（Value Encoding）

数値列では、辞書を作らずに数学的な変換で済ませることがあります。

```figure
{ "type":"tablediff", "title":"値符号化", "arrowLabel":"最小値を引いてビット幅を縮める",
  "before":{"title":"元の列","tone":"neutral","head":["Year","必要ビット数"],
    "rows":[["2023","!11ビット"],["2024","!11ビット"],["2025","!11ビット"]]},
  "after":{"title":"2023 を引いた後","tone":"good","head":["Year - 2023","必要ビット数"],
    "rows":[["0","!2ビット"],["1","!2ビット"],["2","!2ビット"]]} }
```

最小値を引く、公約数で割る、といった可逆な変換でビット幅を減らします。**整数列でのみ使われ、文字列列では使えません。** 数値を文字列型で持つと圧縮が効かなくなるのはこのためです。

### ランレングス符号化（RLE）

同じ値が連続していれば、その繰り返しをまとめます。

```figure
{ "type":"tablediff", "title":"ランレングス符号化と並び順の効果", "arrowLabel":"ソートしてから RLE を適用",
  "before":{"title":"ランダムな並び（RLEが効かない）","tone":"bad","head":["Region","RLEの結果"],
    "rows":[["関東","関東 × 1"],["関西","関西 × 1"],["関東","関東 × 1"],["中部","中部 × 1"],["関西","関西 × 1"],["関東","!5ブロック必要"]]},
  "after":{"title":"ソート済み（RLEがよく効く）","tone":"good","head":["Region","RLEの結果"],
    "rows":[["関東","関東 × 3"],["関東",""],["関東",""],["関西","関西 × 2"],["関西",""],["中部","!3ブロックで済む"]]} }
```

> [!NOTE] 要点
> **RLE の効き方は、データの並び順に依存します。** VertiPaq は取り込み時に、圧縮率が最大になる並び順を自動的に探索します。ただし探索には制限時間があり、大きなテーブルでは最適解に届かないことがあります。**Power Query 側でカーディナリティの低い列を先頭にしてソートしておくと、圧縮が改善することがあります。**

> [!DS] データサイエンス視点
> 圧縮率の理論的な上限は、その列の**情報エントロピー**で決まります。すべての値が同じなら情報量ゼロで、ほぼ完全に圧縮できます。すべての値が異なりランダムなら、圧縮の余地はほとんどありません。つまり「圧縮率を上げる」とは「その列が持つ情報量を減らす」ことと等価です。**必要な情報だけを持つ**という設計原則が、そのまま性能に直結します。


VertiPaq はテーブルを**セグメント**という単位に分割して管理します。

> [!DS] データサイエンス視点
> 列指向は分析用データベースの標準的な設計です。Apache Parquet、Amazon Redshift、Google BigQuery、ClickHouse、DuckDB はいずれも列指向で、辞書符号化と RLE を組み合わせて使っています。**「分析クエリは少数の列を全行読む」という性質**が共通しているためです。Power BI で学んだ原理は、そのままこれらのシステムに転用できます。

## 理解度チェック

**問1.** 100万行のテーブルに、一意な値が5種類しかない文字列列と、100万通りある文字列列があります。どちらがモデルサイズを食いますか。理由も説明してください。

<details>
<summary>解答</summary>

**100万通りある列**です。辞書符号化では、辞書のサイズが一意な値の数（カーディナリティ）に比例します。5種類なら辞書は5エントリで済み、本体も3ビットで表現できます。100万通りなら辞書に100万個の文字列を保持する必要があり、本体も20ビット必要になります。**行数ではなくカーディナリティがサイズを決める**というのが要点です。
</details>

**問2.** 数値を文字列型（テキスト型）で保持していると、なぜ非効率になりますか。

<details>
<summary>解答</summary>

文字列列では**値符号化が使えず、辞書符号化しか選べない**ためです。値符号化は「最小値を引く」「公約数で割る」といった数学的変換でビット幅を減らせますが、文字列にはこの操作が適用できません。さらに、文字列そのものを辞書に保持するコストも加わります。数値として扱う列は必ず数値型にしてください。
</details>

**問3.** Power Query で列をソートしておくと圧縮率が改善することがあります。なぜですか。

<details>
<summary>解答</summary>

**ランレングス符号化（RLE）がデータの並び順に依存する**ためです。同じ値が連続していれば「値 × 回数」にまとめられますが、ばらばらに散っていればまとめられません。カーディナリティの低い列を優先してソートすると、その列で長い連続が生まれ、RLE がよく効きます。ただし VertiPaq も取り込み時に自動で並べ替えを試みるため、効果が出るのは大規模なテーブルに限られます。
</details>
