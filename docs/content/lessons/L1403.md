### CallbackDataID を消す書き換え

```dax
-- 発生する：行ごとの条件分岐が SE に埋め込まれる

```

```dax
-- 発生しない：フィルターで2つに分け、それぞれ純粋な集計にする
売上_割引後 =
CALCULATE( SUM( Fact_売上[SalesAmount] ) * 0.9, Fact_売上[Quantity] > 10 )
    + CALCULATE( SUM( Fact_売上[SalesAmount] ), Fact_売上[Quantity] <= 10 )
```

## 実際の書き換えパターン

### パターン1：イテレータ内の条件分岐を分割する

```dax
-- 遅い
売上_家電割増 =
SUMX( Fact_売上, IF( RELATED( Dim_商品[Category] ) = "家電", Fact_売上[SalesAmount] * 1.1, Fact_売上[SalesAmount] ) )

-- 速い
売上_家電割増 =
CALCULATE( [売上合計] * 1.1, Dim_商品[Category] = "家電" )
    + CALCULATE( [売上合計], Dim_商品[Category] <> "家電" )
```

### パターン2：FILTER をディメンションに寄せる

```dax
-- 遅い：ファクト全行を FE で走査する
X = CALCULATE( [売上合計], FILTER( Fact_売上, RELATED( Dim_店舗[Region] ) = "関東" ) )

-- 速い：SE のフィルターとして処理される
X = CALCULATE( [売上合計], Dim_店舗[Region] = "関東" )
```

### パターン3：イテレートする粒度を落とす

```dax
-- 遅い：500万行を走査する
X = AVERAGEX( Fact_売上, [売上合計] )

-- 速い：850行を走査する
X = AVERAGEX( VALUES( Dim_顧客[CustomerID] ), [売上合計] )
```

### パターン4：計算を上流に移す

```dax
-- 遅い：毎クエリ計算する
粗利 = SUMX( Fact_売上, Fact_売上[SalesAmount] - Fact_売上[Quantity] * RELATED( Dim_商品[StandardCost] ) )

-- 速い：Power Query で GrossProfit 列を作っておく
粗利 = SUM( Fact_売上[GrossProfit] )
```

### パターン5：DISTINCTCOUNT の扱いに注意する

`DISTINCTCOUNT` は SE で実行できますが、他の集約より重い処理です。

```dax
-- 重い：高カーディナリティ列の一意カウント
顧客数 = DISTINCTCOUNT( Fact_売上[CustomerID] )

-- 代替案：リレーション先のディメンションで数える
顧客数 = COUNTROWS( VALUES( Dim_顧客[CustomerID] ) )
```

後者は `Dim_顧客` 側でフィルター後に残った行を数えるため、ファクトの高カーディナリティ列をスキャンせずに済むことがあります。**必ず両方を計測して比べてください。** モデルによってはどちらが速いか変わります。

> [!TIP] 実務のコツ
> パターン4は最も効果が大きく、最も見落とされます。**「この計算は本当にクエリ時に必要か」**——フィルターによって結果が変わらない計算は、すべて上流に移せます。原価が固定なら粗利は行ごとに確定しており、毎回計算する理由はありません。

> [!DS] データサイエンス視点
> SE と FE の関係は、**データベースの実行計画**そのものです。RDBMS でも「述語プッシュダウン」——WHERE 句をできるだけストレージ層に押し下げてスキャン量を減らす——が最重要の最適化です。DAXでの「SE に寄せる」はこれと同じ発想です。また、FE がシングルスレッドである点は、**アムダールの法則**の典型例でもあります。並列化できない部分（FE）が全体の実行時間を支配するため、コアを増やしても頭打ちになります。改善すべきは並列化できない部分です。

> [!EXAM] PL-300で問われる
> PL-300 で xmSQL や CallbackDataID が直接問われることはありませんが、「メジャーのパフォーマンスを改善する方法」として**FILTER にテーブル全体を渡さない**、**計算列や Power Query で事前計算する**、**不要な列を削除する**は出題範囲です。原理を知っていれば選択肢を根拠つきで選べます。

## 理解度チェック

**問1.** Server Timings で SE 12ms、FE 3,400ms、SE が返した行数 4,800,000 と表示されました。何が起きていますか。

<details>
<summary>解答</summary>

**マテリアライゼーション**です。SE は12msで仕事を終えていますが、480万行という巨大な中間結果を返しており、それをシングルスレッドの FE が処理するのに3.4秒かかっています。イテレートする粒度が細かすぎる（ファクトテーブルを直接走査している）可能性が高いので、ディメンションの粒度に落とせないかを検討します。
</details>

**問2.** 同じメジャーを2回実行しても、2回目が速くなりません。考えられる原因は何ですか。

<details>
<summary>解答</summary>

**CallbackDataID が発生している**可能性が高いです。SE がスキャン中に FE を呼び出している場合、その結果は SE キャッシュに保存されないため、何度実行しても同じ時間がかかります。xmSQL を確認し、CallbackDataID を含む式（イテレータ内の IF や DIVIDE など）を CALCULATE によるフィルター分割で書き換えます。
</details>

**問3.** `CALCULATE( [売上合計], FILTER( Fact_売上, RELATED( Dim_店舗[Region] ) = "関東" ) )` を高速化してください。理由も説明してください。

<details>
<summary>解答</summary>

`CALCULATE( [売上合計], Dim_店舗[Region] = "関東" )` に書き換えます。元の式は FILTER がファクトテーブルの全行を FE で走査し、行ごとに RELATED でディメンションを参照します。書き換え後は、SE が `Dim_店舗[Region]` の一意な値（数十件）でフィルターを解決し、リレーションを通じてファクトを絞るため、すべて SE 内で完結します。
</details>
