「毎月、支店から届く30個のExcelを同じ手順で整形して1つにまとめる」。この作業をクエリ30本のコピペで作った人と、カスタム関数1本で作った人では、**仕様が1つ変わったときの作業量が30倍違います**。

このレッスンでは、Mの処理を部品化する2つの道具を扱います。**パラメータ**（値を外から差し替える箱）と**カスタム関数**（引数を受け取って値を返す再利用可能な処理）です。

## カスタム関数の文法

Mの関数は `(引数) => 式` という形をしています。関数もまた「値」なので、クエリに名前を付けて保存できます。

```figure
{ "type":"formula", "lang":"m",
  "title":"カスタム関数の宣言",
  "caption":"引数に型を書いておくと、呼び出し側で間違った型を渡したときにすぐ気づける",
  "code":"(税抜金額 as number, 税率 as number) as number => Number.Round(税抜金額 * (1 + 税率), 0)",
  "parts":[
    {"match":"(税抜金額 as number, 税率 as number)","label":"引数リスト。as で型を宣言できる","tone":"blue"},
    {"match":"as number","label":"戻り値の型。省略可だが書くと安全","tone":"amber"},
    {"match":"=>","label":"「この引数を受け取って、右の式を返す」という記号","tone":"violet"},
    {"match":"Number.Round(税抜金額 * (1 + 税率), 0)","label":"本体。1つの式であればよい","tone":"green"}
  ] }
```

複数ステップが必要なら、本体を `let ... in` にします。

```m
// クエリ名: fn税込計算
(税抜金額 as number, optional 税率 as number) as number =>
let
    率 = if 税率 = null then 0.10 else 税率,
    税込 = 税抜金額 * (1 + 率),
    丸め = Number.Round(税込, 0)
in
    丸め
```

`optional` を付けた引数は省略できます。省略されると `null` が渡るので、`if ... = null then 既定値` で受けます。

| 書き方 | 意味 |
|---|---|
| `(x)` | 型を問わない引数 |
| `(x as text)` | テキストのみ受け付ける。違う型を渡すとエラー |
| `(optional x as date)` | 省略可能。省略時は null |
| `(x as any) as table` | 戻り値がテーブルであることを宣言 |

> [!TRAP] つまずきポイント
> 引数に `as number` と書いたのに、呼び出し側がテキストの `"1200"` を渡すと **「型が一致しません」** で失敗します。ソースの型が保証できない場合は、`as any` で受けて関数の内部で `Number.From` するか、呼び出す前に型変換ステップを入れてください。「関数の中で型を整える」設計にしておくと、呼び出し側が楽になります。

自分で書くとこうなります。

```m
// クエリ名: fnファイル変換 — Binary を受け取ってテーブルを返す
(中身 as binary) as table =>
let
    Csv = Csv.Document(中身, [Delimiter=",", Encoding=65001, QuoteStyle=QuoteStyle.Csv]),
    Head = Table.PromoteHeaders(Csv, [PromoteAllScalars=true]),
    Typed = Table.TransformColumnTypes(Head, {{"売上日", type date}, {"金額", Currency.Type}, {"数量", Int64.Type}}),
    不要行除去 = Table.SelectRows(Typed, each [売上日] <> null)
in
    不要行除去
```

```m
// クエリ名: Fact_売上 — フォルダの全CSVに関数を適用する
let
    Src = Folder.Files(pDataPath),
    CSVのみ = Table.SelectRows(Src, each Text.Lower([Extension]) = ".csv"),
    // 一時ファイル（~$ で始まる）を除外する。Excel を開いたまま更新すると混入する
    除外 = Table.SelectRows(CSVのみ, each not Text.StartsWith([Name], "~$")),
    // 各行のバイナリに関数を適用して、テーブルを入れ子の列として持たせる
    適用 = Table.AddColumn(除外, "データ", each fnファイル変換([Content])),
    // どのファイル由来かを残す。障害調査でこれがないと詰む
    ファイル名付き = Table.AddColumn(適用, "取込元", each [Name], type text),
    絞り込み = Table.SelectColumns(ファイル名付き, {"取込元", "データ"}),
    展開 = Table.ExpandTableColumn(絞り込み, "データ", {"売上日", "金額", "数量"})
in
    展開
```

> [!TIP] 実務のコツ
> **`取込元` のような由来列を必ず残してください。** 「合計が合わない」と言われたとき、どのファイルの行が原因かを1分で特定できます。取り込み日時（`each DateTime.LocalNow()`）を足しておくのも有効です。これはデータエンジニアリングで**リネージ（データの出自の追跡）** と呼ばれる考え方です。

> [!TRAP] つまずきポイント
> `Folder.Files` はサブフォルダも再帰的に拾います。過去分アーカイブのフォルダが下にあると、**去年のデータまで毎回読み込まれます**。`[Folder Path]` 列で絞るか、`Folder.Contents` に切り替えて明示的に階層を制御してください。また、Excelを開いたままだと `~$売上.xlsx` という一時ファイルができ、これが `Folder.Files` に混入して更新を失敗させます。上のコードの `~$` 除外はそのための防御です。

## `Table.NestedJoin` — 結合を自分で書く

GUIの「クエリのマージ」が生成するのが `Table.NestedJoin` です。結合結果を**入れ子のテーブル列として一旦持ち**、そのあと `Table.ExpandTableColumn` で必要な列だけ展開する、という2段構えになっています。

```figure
{ "type":"tablediff", "arrowLabel":"Table.NestedJoin → ExpandTableColumn",
  "title":"入れ子で結合してから、必要な列だけ展開する",
  "caption":"NestedJoin の直後は「テーブルが入った列」が1本増えるだけ。展開して初めて列になる",
  "before":{"title":"NestedJoin 直後","tone":"neutral",
    "head":["伝票番号","商品ID","金額","商品情報"],
    "rows":[["A-001","P01","1200","!Table"],["A-002","P07","800","!Table"],["A-003","P99","500","!Table (0行)"]]},
  "after":{"title":"ExpandTableColumn 後","tone":"good",
    "head":["伝票番号","商品ID","金額","商品名","カテゴリ"],
    "rows":[["A-001","P01","1200","ノートPC","電子機器"],["A-002","P07","800","マウス","周辺機器"],["A-003","P99","500","!null","!null"]]} }
```

```m
let
    Fact = Fact_売上,
    Dim = Dim_商品,
    // 引数: 左テーブル, 左キー列のリスト, 右テーブル, 右キー列のリスト, 新しい列名, 結合の種類
    結合 = Table.NestedJoin(
        Fact, {"商品ID"},
        Dim,  {"商品ID"},
        "商品情報",
        JoinKind.LeftOuter
    ),
    展開 = Table.ExpandTableColumn(結合, "商品情報",
        {"商品名", "カテゴリ"},           // 取り出す列
        {"商品名", "カテゴリ"}            // 展開後の列名（衝突するなら別名にする）
    )
in
    展開
```

`JoinKind` は6種類あります。

| JoinKind | 残る行 | 実務での使いどころ |
|---|---|---|
| `LeftOuter` | 左は全部、右はマッチしたもの | 既定。ファクトに属性を付ける |
| `Inner` | 両方にあるものだけ | マスタにない行を落としたいとき（**行が減る点に注意**） |
| `LeftAnti` | 左にあって右にないもの | **マスタ未登録の検出**。データ品質チェックの定番 |
| `RightAnti` | 右にあって左にないもの | 一度も売れていない商品の抽出 |
| `FullOuter` | 両方の全行 | 2系統の突き合わせ |
| `RightOuter` | 右は全部、左はマッチしたもの | 使う場面は少ない |

> [!TIP] 実務のコツ
> `JoinKind.LeftAnti` で作ったチェック用クエリを1本持っておくと、「マスタに存在しない商品IDが今月3件増えた」を毎回検出できます。**このクエリは読み込みを無効にしておき、更新前にPower Queryで目視する**運用で十分に価値があります。

> [!TRAP] つまずきポイント
> 右テーブルのキーに重複があると、**結合後に行が増えます**（1対多になるため）。売上100行に対して商品マスタが同じIDで2行あると、結合後は200行になり、金額が倍になります。マージ前に必ず右テーブルのキーの一意性を確認してください。GUIのマージダイアログ下部に出る「一致した行数」の表示は、この確認のためにあります。

## 関数の中でエラーを扱う

関数化すると、失敗したときに「どのファイルで失敗したか」が分からなくなりがちです。関数の呼び出し側で `try` を使い、失敗を行として残します。

```m
let
    Src = Folder.Files(pDataPath),
    CSVのみ = Table.SelectRows(Src, each Text.Lower([Extension]) = ".csv"),
    // 各ファイルの処理を try で包む
    試行 = Table.AddColumn(CSVのみ, "結果", each try fnファイル変換([Content])),
    成功 = Table.SelectRows(試行, each [結果][HasError] = false),
    失敗 = Table.SelectRows(試行, each [結果][HasError] = true),
    // 失敗一覧は別クエリとして保持し、更新後に確認する
    失敗一覧 = Table.AddColumn(失敗, "理由", each [結果][Error][Message], type text),
    データ = Table.AddColumn(成功, "データ", each [結果][Value]),
    展開 = Table.ExpandTableColumn(
        Table.SelectColumns(データ, {"Name", "データ"}),
        "データ", {"売上日", "金額", "数量"})
in
    展開
```

> [!DS] データサイエンス視点
> パイプラインは **冪等（べきとう）** であるべきです。冪等とは「同じ入力で何度実行しても、結果が同じになる」性質のこと。1回目の実行で30ファイル読み、2回目も同じ30ファイルなら同じ結果になる、という状態を保ちます。「実行するたびに行が追加されていく」設計や、「実行時刻によって結果が変わる」設計は冪等ではなく、障害からの再実行が怖くなります。`DateTime.LocalNow()` を**フィルター条件**に使うと冪等性が崩れる点に注意してください（記録用の列に使うのは問題ありません）。

## 関数のバージョン管理と共有

| 方法 | 共有範囲 | 向き不向き |
|---|---|---|
| pbix内のクエリとして持つ | そのpbixのみ | 小規模。最も手軽 |
| テンプレート（.pbit）に含める | 新規作成時にコピー | 標準の型を配りたいとき |
| データフローに置く | ワークスペース内の全pbix | 組織で共通化するならこれ |
| Gitでpbipのクエリ定義を管理 | 開発チーム | 差分レビューが必要な規模 |

> [!WARN] 注意
> 関数を修正すると、**呼び出している全クエリの結果が同時に変わります**。これは利点であり、リスクでもあります。関数を変更するときは「どのクエリがこの関数を呼んでいるか」を必ず確認してください。Power Query の「クエリの依存関係」ビュー（表示タブ）で参照関係を図として確認できます。

## 関数を単体でテストする

関数はクエリの中に埋め込んだままだと検証できません。**呼び出し専用のテストクエリを作り、既知の入力に対して既知の出力が返るか**を確認する習慣をつけてください。

```figure
{ "type":"cards", "cols":2, "title":"関数の検証で最低限見る4点",
  "caption":"「動いた」ではなく「境界で壊れない」を確認する。ここを飛ばすと本番で1件だけ壊れる",
  "items":[
    {"icon":"✅","title":"正常系","text":"想定どおりの入力で、期待した値が返るか。行数と合計を控えておく","tone":"good"},
    {"icon":"␀","title":"null と空文字","text":"空セル・空文字列を渡したときにエラーで止まらないか。null が伝播する挙動を確認する","tone":"amber"},
    {"icon":"🔢","title":"型のゆらぎ","text":"数値のはずが文字列で来たとき、どう扱われるか。Number.From が失敗する入力を試す","tone":"cyan"},
    {"icon":"📭","title":"0件のケース","text":"空のファイル・0行のテーブルを渡したとき、列構成を保った空テーブルが返るか","tone":"violet"}
```

```m
// クエリ名: テスト_fn税込計算（読み込みは無効にする）
let
    ケース = #table(
        type table[入力 = number, 税率 = number, 期待値 = number],
        {
            {1000, 0.10, 1100},
            {1000, 0.08, 1080},
            {999,  0.10, 1099},
            {0,    0.10, 0}
        }),
    実測 = Table.AddColumn(ケース, "実測値", each fn税込計算([入力], [税率]), type number),
    判定 = Table.AddColumn(実測, "結果", each if [実測値] = [期待値] then "OK" else "NG", type text)
in
    判定
```

「結果」列がすべて OK になることを確認してから、本番クエリに組み込みます。**0件・null・境界値の3つを必ずケースに入れてください**。実務で壊れるのはほぼこの3つです。

> [!TRAP] つまずきポイント
> 空のCSVファイルが1つ混ざっただけで、`Table.ExpandTableColumn` が「列 '売上日' が見つかりません」で失敗することがあります。0行のテーブルには列定義が残らないケースがあるためです。関数の最後に `Table.SelectColumns(結果, {"売上日","金額","数量"}, MissingField.UseNull)` を入れておくと、列が欠けても null 列で補われて止まりません。

## 命名規約を決めておく

関数とパラメータが増えると、クエリ一覧が混沌とします。接頭辞で種類が分かるようにしておきます。

| 接頭辞 | 対象 | 例 |
|---|---|---|
| `fn` | カスタム関数 | `fnファイル変換`, `fn税込計算` |
| `p` | パラメータ | `pServer`, `pDataPath`, `RangeStart` |
| `stg_` | ステージング（読み込み無効） | `stg_売上生データ` |
| `Dim_` / `Fact_` | モデルに読み込むテーブル | `Dim_商品`, `Fact_売上` |
| `chk_` | データ品質チェック（読み込み無効） | `chk_マスタ未登録商品` |

さらに、Power Query の「グループ」機能（クエリ一覧で右クリック→グループへ移動）でフォルダ分けすると、20本を超えても見通しが保てます。

> [!TIP] 実務のコツ
> グループは「パラメータ / 関数 / ステージング / モデル / チェック」の5つで始めてください。この分類は、そのままレッスンL1105で扱う**層の設計**に対応します。クエリ一覧の構造が、パイプラインの構造を表している状態が理想です。

## 設計判断チェックリスト

- [ ] ハードコードされたサーバー名・パス・年度がクエリ内に残っていないか。パラメータに切り出したか
- [ ] パラメータに資格情報を入れていないか
- [ ] 関数の引数に型を宣言したか。型が保証できない場合の受け方を決めたか
- [ ] フォルダ取り込みで、サブフォルダと一時ファイル（`~$`）を除外したか
- [ ] 取込元ファイル名などの由来列を残したか
- [ ] マージ前に、右テーブルのキーの一意性を確認したか
- [ ] `JoinKind.LeftAnti` によるマスタ未登録チェックのクエリを用意したか
- [ ] 関数の変更が影響する範囲を「クエリの依存関係」で確認したか
- [ ] `DateTime.LocalNow()` をフィルター条件に使って冪等性を壊していないか
