アプリのバグは派手に落ちる。**BIのバグは落ちません。**グラフは描画され、数字も出る。ただ違うだけです。

だからBIのテストは「動くか」ではなく「**合っているか**」を問います。

```dax

VAR 実測 = CALCULATE( [売上金額], Dim_日付[年月] = "2025-01" )
VAR 期待 = 1234500
RETURN
    ROW( "テスト名", "売上金額_2025年1月", "期待値", 期待, "実測値", 実測,
         "判定", IF( 実測 = 期待, "PASS", "FAIL" ) )
```

> [!WARN] 信頼できないテストは、テストがないより悪い
> 50件中10件が慢性的に不合格だと誰も結果を見なくなる。不合格を放置せず、更新を止めるものと通知だけのものに分ける。

> [!EXAM] PL-300で問われる
> 列の品質・列の分布・列のプロファイルで欠損と一意性を確認／プロファイリングの既定は先頭1000行なので「データセット全体に基づく」へ切り替える／エラー行は削除せず保持して原因を確認する。

## 理解度チェック

1. 「更新が成功した」だけでは検知できない異常を1つ挙げ、検知するテストを設計してください。
2. 期待値を「前回リリース時の値」にする方法の利点と限界を述べてください。
3. BIと会計の数字が2%ずれています。「BI側を修正する」と即断してはいけない理由は何ですか。

## よくあるエラーと対処

| 症状 | 原因 | 対処 |
|---|---|---|
| 更新は成功するのに件数が半減 | 絶対閾値しか見ていない | 前日比の相対検査を追加する |
| 明細は合うのに総計が合わない | メジャーの評価コンテキスト | 総計行をテストケースに含める |
| 前年比が100%減になる | データがない期間の扱い | BLANKと0の扱いを決めてテストする |
| 開発では速いのに本番で遅い | 開発のデータ量が少ない | 本番相当の環境で性能テストする |
| アラートが誰にも見られない | 慢性的な不合格を放置 | 直すか基準を見直すかテストを削除する |
