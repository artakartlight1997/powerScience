アプリケーションのバグは、たいてい派手に落ちます。画面が真っ白になる、エラーが出る、処理が止まる。誰かが気づきます。

**BIのバグは落ちません。**レポートは開き、グラフは描画され、数字が表示されます。ただその数字が違うだけです。誰も気づきません。気づくのは、その数字で判断した後です。

だからBIのテストは、「動くか」ではなく「**合っているか**」を問う設計でなければなりません。

## BIのテストは4層ある

```figure
{ "type":"stack", "title":"BIテストの4層", "caption":"下の層が壊れていると上の層のテストは意味を持たない。下から順に固める",
  "layers":[
    {"label":"④ 表示・体験テスト","sub":"レイアウト崩れ / モバイル / アクセシビリティ / 操作の意図どおりの動き","tone":"pink"},
    {"label":"③ 性能テスト","sub":"初期表示時間 / 更新時間 / 同時実行時の応答","tone":"violet"},
    {"label":"② 計算テスト","sub":"メジャーが期待値を返すか / 境界条件 / 空・ゼロ・マイナスの扱い","tone":"amber"},
    {"label":"① データテスト","sub":"行数 / 重複 / 欠損 / 参照整合性 / 値域 / 鮮度","tone":"green"} ] }
```

> [!NOTE] 要点
> 4層は独立ではありません。**①が壊れていれば②の結果は無意味**です。データが欠けているのにメジャーだけ検証しても、正しく計算された間違った数字が出るだけです。テストは必ず下から積み上げます。

## ① データテスト

最初の層は、モデルに入ったデータそのものの検査です。データ品質の6次元（L1704）に対応させると、何を測るべきかが機械的に決まります。

| 次元 | 検査 | 判定例 |
|---|---|---|
| 完全性 | 必須列のNULL率 | 顧客IDのNULL < 0.1% |
| 一意性 | 業務キーの重複件数 | 受注番号＋明細番号の重複 = 0 |
| 妥当性 | 値域の逸脱 | 数量 < 0 の件数 = 0、未来日付 = 0 |
| 一貫性 | システム間の突合 | 販売合計と会計計上額の差 < 0.5% |
| 適時性 | 最終更新時刻 | 更新完了が 7:30 まで |
| 正確性 | 基準値との突合 | 前月確定値と一致 |

```figure
{ "type":"pipeline", "title":"データテストを更新の途中に挟む", "caption":"合格しなければモデルを更新しない。壊れたデータで更新するより、古いままのほうがよい",
  "nodes":[
    {"id":"g","label":"ゴールド層\n更新完了","tone":"green"},
    {"id":"t1","label":"完全性チェック\nNULL率","tone":"amber"},
    {"id":"t2","label":"一意性チェック\n重複","tone":"amber"},
    {"id":"t3","label":"一貫性チェック\n他システムと突合","tone":"amber"},

    {"id":"ng","label":"不合格 → 停止＋通知","tone":"bad"}],

    {"from":"g","to":"t1"},
    {"from":"t1","to":"t2"},
    {"from":"t2","to":"t3"},
    {"from":"t3","to":"ok","label":"すべて合格"},
    {"from":"t3","to":"ng","label":"1つでも不合格"} ] }
```

### 相対的な検査を入れる

絶対値の閾値だけでは、静かな異常を見逃します。**前回との比較**を必ず入れます。

```figure
{ "type":"compare", "title":"絶対閾値だけの検査と、相対比較を足した検査",
  "panels":[
    {"title":"絶対閾値のみ","tone":"bad",
     "items":["「行数 > 0 なら合格」","ソース側の抽出条件が壊れて件数が1/10になっても合格","1件しか入っていなくても合格","異常を検知できない"],
     "note":"最低限のガードにしかならない"},
    {"title":"相対比較あり","tone":"good",
     "items":["「行数が前日比 ±30% 以内」","「売上合計が前週同曜日比 ±40% 以内」","「新規キーの割合が通常範囲内」","急激な変化を検知できる"],
     "note":"実務で異常を捕まえるのはこちら"} ] }
```

> [!TRAP] 「更新が成功した」を「データが正しい」と読み替える
> 更新のステータスが緑になっていても、それは**処理が例外なく終わったこと**しか意味しません。ソース側のビューが変更されて対象が半分になっていても、更新は成功します。**成功通知だけを見ている運用は、静かな欠損に対して無防備**です。行数の相対比較を1本入れるだけで、この種の事故の大半が捕まえられます。

## ② 計算テスト

メジャーが正しい値を返すかの検査です。BIで最も重要でありながら、最も実施されていない層です。

### ゴールデンデータセットを作る

```figure
{ "type":"steps", "title":"計算テストの組み立て方",
  "items":[
    {"title":"検証可能な小さいデータを固定する","text":"手計算できる規模（数十行）のテスト用データを用意し、変更しない。これがゴールデンデータセット。","tone":"blue"},
    {"title":"期待値を人が計算して記録する","text":"「2025年1月の売上金額 = 1,234,500」を表計算で手計算し、根拠とともに残す。","tone":"green"},
    {"title":"境界条件を必ず含める","text":"データがない期間、値がゼロ、マイナス（返品）、キーが欠けた行、未来日付。","tone":"amber"},
```

### DAXクエリビューでのテスト

Power BI Desktop の**DAXクエリビュー**を使うと、モデルに対して直接クエリを実行できます。テストの実体はこの形になります。

```dax
DEFINE
    MEASURE '_Test'[期待_売上金額_202501] = 1234500

EVALUATE
VAR 実測 = CALCULATE( [売上金額], Dim_日付[年月] = "2025-01" )
VAR 期待 = 1234500
RETURN
    ROW(
        "テスト名", "売上金額_2025年1月",
        "期待値", 期待,
        "実測値", 実測,
        "判定", IF( 実測 = 期待, "PASS", "FAIL" )
    )
```

複数のテストを `UNION` で束ねれば、1回の実行で全件の合否が表になります。**結果が表で返るので、CIから実行して自動判定できます。**

```figure
{ "type":"tablediff", "arrowLabel":"テスト実行",
  "before":{"title":"テストケース定義","tone":"neutral","head":["テスト名","期待値"],
    "rows":[["売上金額_2025年1月","1234500"],["粗利率_2025年1月","0.283"],["顧客数_全期間","4821"],["返品を含む月の売上","892300"]]},
  "after":{"title":"実行結果","tone":"good","head":["テスト名","期待値","実測値","判定"],
    "rows":[["売上金額_2025年1月","1234500","1234500","PASS"],["粗利率_2025年1月","0.283","0.283","PASS"],["顧客数_全期間","4821","4821","PASS"],["返品を含む月の売上","892300","!915400","!FAIL"]] } }
```

最後の行のような結果が出たときが、テストが仕事をした瞬間です。**返品の控除が漏れている**ことが、利用者に届く前に分かります。

> [!TIP] 実務のコツ
> 期待値は「正しい計算結果」ではなく、「**前回リリース時の値**」でも十分に価値があります。これを**回帰テスト**と呼びます。値が変わったこと自体を検知し、変わってよい変更だったかを人が判断する。この形なら、複雑な指標でも手計算なしにテストが作れます。多くの現場で現実的なのはこちらです。

### 境界条件のチェックリスト

計算テストで見落とされやすい条件を挙げます。

| 条件 | よくある不具合 |
|---|---|
| データがない期間 | 0が表示されるべきかBLANKか。前年比が誤って100%減になる |
| 分母がゼロ | エラーになる（DIVIDEを使っていない） |
| マイナス値（返品） | 集計から除外されている／二重に引かれている |
| キーが欠けた行 | リレーションシップで消える。合計が合わなくなる |
| 期間の境界 | 月初・月末・期首・期末の1日がずれる |
| 総計行 | 明細の合計と総計が一致しない（メジャーの評価コンテキスト） |

最後の「総計行」は、DAX特有の典型的な不具合です。**明細行では正しいのに総計だけ合わない**メジャーは、実務で頻繁に発生します。必ずテストに含めてください。

## ③ 性能テスト

性能は「速いか」ではなく「**基準を満たすか**」で判定します。基準がなければテストになりません。

```figure
{ "type":"cards", "cols":3, "title":"性能テストで測る3項目と基準の例",
  "items":[
    {"icon":"⚡","title":"初期表示時間","text":"主要ページを開いてから全ビジュアルが描画されるまで。基準例：5秒以内。","tone":"blue"},
    {"icon":"🔄","title":"更新時間","text":"モデル更新の所要時間。基準例：60分以内、かつ7:30までに完了。","tone":"green"},
    {"icon":"👥","title":"同時実行時の応答","text":"ピーク時の応答劣化。基準例：平常時の2倍以内。","tone":"amber"} ] }
```

性能テストは**本番相当のデータ量を持つテスト環境でのみ意味を持ちます**。開発環境の1か月分データで5秒だったからといって、本番の3年分で5秒とは限りません。ここがL1801で「テスト環境は本番相当のデータ量にする」と書いた理由です。

## ④ 表示・体験テスト

最後の層は、人が見て確認するしかない領域です。ただしチェックリスト化すれば、担当者の経験に依存しません。

| 確認項目 | 見るところ |
|---|---|
| 画面サイズ | 13インチノートで横スクロールが出ないか |
| 数値の書式 | 桁区切り、単位、小数桁が指標ごとに統一されているか |
| 空状態 | フィルターで該当0件のとき、意味の分かる表示になるか |
| 相互作用 | ビジュアルをクリックしたときの絞り込みが意図どおりか |
| アクセシビリティ | 色だけで情報を伝えていないか、代替テキストがあるか |
| 注記 | データ更新時刻・対象期間・除外条件が表示されているか |
| モバイル | モバイルレイアウトが設定されているか |

> [!DS] データサイエンス視点：テストピラミッドとBIへの適用
> ソフトウェアのテストピラミッドは「単体テストを多く、E2Eテストを少なく」という原則です。理由は、**上位のテストほど実行が遅く、壊れやすく、失敗の原因が特定しにくい**から。BIでも同じ構造があります。データテストは数分で終わり、失敗したら原因が明確です。表示テストは人が30分かけ、失敗しても「なんとなく変」としか分かりません。**下を厚くするほど、問題の発見が早く、原因の特定が速くなります。**

> 「未使用のメジャー・列」の検出は、モデルの掃除に非常に効きます。ただし**注意点が1つ**あります。Excelから接続している利用者や、他のモデルから参照しているレポートは、テナント内のメタデータだけでは追い切れないことがあります。削除の前に必ず(1)影響分析で依存を確認し、(2)まず非表示にして1か月様子を見る、という2段階を踏んでください。**削除は最後の手段であり、非表示は取り消せます。**

## 誰がテストを実施するか

テスト設計と同じくらい重要なのが、**役割の割り当て**です。ここが曖昧だと、全部が開発者に集まって形骸化します。

| テストの種類 | 実施者 | 理由 |
|---|---|---|
| データテスト | 自動（パイプライン） | 頻度が高く、判定が機械的 |
| 構造テスト・BPA | 自動（CI） | 規約に照らすだけ |
| 計算テスト（回帰） | 自動（CI） | 前回値との比較 |
| 計算テスト（新規指標の正しさ） | 業務所有者 | 何が正しいかは業務が決める |
| 性能テスト | 開発者 | 測定と改善が一体 |
| 表示・体験テスト | 依頼者＋利用者代表 | 使う人でないと判断できない |
| 受け入れ判定 | 業務所有者 | リリースの可否を持つ人 |

> [!TRAP] 開発者が自分で「正しい」と判定する
> 最も多い運用の欠陥です。開発者は「自分が意図したとおりに動いているか」しか判定できません。**その意図自体が業務的に間違っている可能性を、開発者は検出できない**のです。「返品を除くべきだった」「対象部門に子会社を含めるべきだった」といった誤りは、業務所有者だけが気づけます。だから受け入れ判定は必ず業務側が持ちます。開発者が兼ねる場合でも、**確認の依頼を明示的に出し、返答を記録に残してください。**

> 突合で差異が出たとき、多くの場合BI担当が疑われます。しかし実際には**両者の定義が違うだけ**であることが最も多い。会計は計上日、販売は出荷日で集計していれば、月末月初の数日分がずれます。どちらも正しい。**このとき必要なのは修正ではなく、定義の明文化と、どちらの数字をどの目的で使うかの合意です。**差異の原因を層ごとに切り分け、事実を示してから議論してください。

## 受け入れ基準を先に決める

テストは作った後に考えるものではありません。**要件定義の時点で「何が満たされたら完成か」を書きます。**

```figure
{ "type":"compare", "title":"曖昧な要件と、テスト可能な受け入れ基準",
  "panels":[
    {"title":"曖昧（テストできない）","tone":"bad",
     "items":["「売上を見られるようにする」","「速く表示されること」","「使いやすいこと」","「正確なデータであること」"],
     "note":"完成の判定が主観になる"},
    {"title":"テスト可能","tone":"good",
     "items":["「2023年4月以降の月次売上を、組織3階層でドリルダウンできる」","「主要3ページの初期表示が5秒以内」","「操作説明なしで、対象部門の担当者3名が目的の数字に到達できる」","「会計システムの月次計上額と差異0.5%以内」"],
     "note":"合否が誰にでも同じように判定できる"} ] }
```

> [!TIP] 実務のコツ
> 受け入れ基準を書くときのコツは、**「誰が・何を・どうやって確認するか」を含めること**です。「正確であること」ではなく「経理課の○○さんが、会計システムの月次帳票と突合して差異0.5%以内であることを確認する」。ここまで書くと、テストの実施者と手順が自動的に決まります。

> [!EXAM] PL-300で問われる
> 品質保証は「データのプロファイリング」と「ガバナンス」の両方から出題されます。頻出は、(1) Power Query の**列の品質・列の分布・列のプロファイル**で欠損と一意性を確認する、(2) プロファイリングの既定は**先頭1000行**なので**データセット全体に基づく**へ切り替える必要がある、(3) エラー行は**削除ではなく保持して原因を確認**する、の3点です。「エラーを削除して先に進む」は常に誤答です。


> [!WARN] 注意
> テストは**増やしすぎると回らなくなります**。50件のデータテストのうち10件が慢性的に不合格の状態が続くと、誰も結果を見なくなります。これをアラート疲れと呼びます。対策は、(1) 不合格を放置しない（直すか、基準を見直すか、テストを削除する）、(2) 重要度で分ける（更新を止めるものと、通知だけのもの）、の2点です。**信頼できないテストは、テストがないより悪い。**

> [!DS] データサイエンス視点：テストは仕様の記述でもある
> テストコードには、実装の正しさを検証する以外にもう1つの役割があります。**「このシステムは何をすべきか」を実行可能な形で記述している**ということです。「2025年1月の売上金額は1,234,500である」というテストは、仕様書の1行でもあります。ドキュメントは古くなりますが、テストは古くなると失敗して知らせてくれます。**古くなったことが自動的に分かるドキュメント**、というのがテストの隠れた価値です。

## 設計チェックリスト

- [ ] データ・計算・性能・表示の4層それぞれにテストを用意した
- [ ] データテストを更新パイプラインに組み込み、不合格時に更新を止めるようにした
- [ ] 絶対閾値だけでなく、前回比の相対検査を入れた
- [ ] ゴールデンデータセットと期待値を作り、根拠を記録した
- [ ] 境界条件（データなし・ゼロ除算・マイナス・キー欠損・期間境界・総計行）をテストに含めた
- [ ] 計算テストをDAXクエリとして書き、自動実行できる形にした
- [ ] 性能テストを本番相当のデータ量を持つ環境で実施した
- [ ] 表示テストをチェックリスト化し、15分で終わる範囲に絞った
- [ ] 他システムとの突合手順を定め、差異の切り分けを層ごとに追えるようにした
- [ ] 受け入れ基準を要件定義の時点で、テスト可能な形で書いた
- [ ] テストの実行タイミングを層ごとに定めた
- [ ] 慢性的な不合格を放置しない運用ルールを決めた

## 理解度チェック

1. 「更新が成功した」というステータスだけでは検知できないデータの異常を1つ挙げ、それを検知するテストを設計してください。
2. 計算テストの期待値を「手計算した正しい値」ではなく「前回リリース時の値」にする方法があります。この方法の利点と限界を述べてください。
3. BIの数字と会計システムの数字が2%ずれています。「BI側を修正する」と即断してはいけない理由を説明してください。
4. 新しい指標の「正しさ」を開発者が単独で判定してはいけない理由を述べてください。

> [!NOTE] このレッスンのまとめ
> BIのバグは落ちず、静かに間違った数字を出す。だからテストは「動くか」ではなく「合っているか」を問う。データ・計算・性能・表示の4層を下から積み上げ、下ほど自動化して厚くする。データテストは絶対閾値に加えて前回比を見る。計算テストはDAXクエリで書けば自動化でき、回帰テストなら手計算なしで作れる。そして受け入れ基準は要件定義の時点で、誰が見ても同じ合否になる形で書く。
