スタースキーマを作る作業は、実際にはたった1つの問いの繰り返しです。**「この表はファクトか、ディメンションか」**。この判定さえ間違えなければ、モデルは自然と正しい形になります。

判定は感覚ではなく、5つの観点で機械的に行えます。

## 粒度を宣言する

分類の次にやるべき、そして最も飛ばされがちな作業が **粒度（グレイン）の宣言** です。Kimball は次元モデリングの4ステップの2番目に「グレインを宣言する」を置きました。それほど重要な工程です。

## 数値なら何でもファクトに入れてよいか

ここが中級者のつまずきどころです。**数値だからといってファクトに置くとは限りません**。判断基準は「合計して意味があるか」です。

| 数値 | 合計して意味があるか | 置き場所 |
|---|---|---|
| 数量（Quantity） | ある | ファクト |
| 売上金額（SalesAmount） | ある | ファクト |
| 標準原価（StandardCost） | ない（商品の属性） | Dim_商品 |
| 定価（ListPrice） | ない（商品の属性） | Dim_商品 |
| 販売単価（UnitPrice） | ない（合計しても無意味） | ファクトに残すが合計しない |
| 割引率（Discount） | ない（率は足せない） | ファクトに残すが合計しない |
| 在庫数量 | 時点では足せるが期間では足せない | ファクト（半加法的） |

**率や単価は足してはいけません**。「割引率の合計」に意味はなく、正しくは「割引額の合計 ÷ 定価の合計」で計算します。

```figure
{ "type": "cards", "cols": 3, "title": "加法性の3分類",
  "caption": "測定値がどの軸で足せるかを、設計時に分類しておく",
  "items": [
    {"icon": "✅", "title": "加法的", "text": "すべての軸で足せる。売上金額、数量、原価。ファクトの主役はこれ。", "tone": "good"},
    {"icon": "⚠️", "title": "半加法的", "text": "一部の軸でしか足せない。在庫数量や口座残高は、商品や店舗では足せるが、日付では足せない（最終日の値を使う）。", "tone": "amber"},
    {"icon": "🚫", "title": "非加法的", "text": "どの軸でも足せない。率・比率・単価・平均値。必ず分子と分母を保存し、割り算はメジャーで行う。", "tone": "bad"} ] }
```

> [!DS]
> 加法性（additivity）は次元モデリングの中心的な概念です。半加法的な測定値の代表は在庫と残高で、日付軸で合計すると「毎日の在庫を足した数」という無意味な値になります。正しくは期末時点の値を取るため、DAX では `LASTNONBLANKVALUE` や `CLOSINGBALANCEMONTH` を使います。非加法的な測定値については、**比率をデータとして保存しないのが鉄則**です。比率を保存して平均すると、各行の重みが無視されて誤った結果になります（平均の平均問題）。分子と分母を保存し、集計後に割る。これは統計における加重平均の考え方そのものです。

ファクトテーブルは、記録の仕方によって3種類に分かれます。

```figure

  "items": [
    {"icon": "🧾", "title": "トランザクションファクト", "text": "出来事が起きるたびに1行。売上明細、入出金。最も一般的で、最も細かい粒度を持つ。", "tone": "blue"},
    {"icon": "📅", "title": "定期スナップショット", "text": "一定間隔で状態を記録する。日次在庫、月末残高。半加法的な測定値を持つことが多い。", "tone": "green"},
```

`sales.csv` には `OrderDate` と `ShipDate` の2つの日付があります。これは受注から出荷までの進行を1行で持っている形で、累積スナップショットの性質を帯びています。この構造は L0603 の「非アクティブなリレーションシップ」と L0605 の「役割を持つ次元」に直結します。

## 縮退ディメンション

`sales.csv` の `OrderID` は、どのディメンションにも属さないのに、分析上は意味を持ちます（受注件数を数える、明細をまとめる）。

このように、**ディメンションテーブルを作るほどの属性を持たないキーを、ファクトにそのまま残したもの**を **縮退ディメンション（degenerate dimension）** と呼びます。

## ディメンションの2つの特殊形

**役割を持つ次元（role-playing dimension）** とは、1つのディメンションが複数の役割で使われることです。`OrderDate` と `ShipDate` は、どちらも `Dim_日付` を参照しますが、意味が違います。Power BI ではアクティブなリレーションシップが1本に限られるため、扱い方に工夫が要ります（L0603、L0605で扱います）。

**緩やかに変化するディメンション（SCD: Slowly Changing Dimension）** とは、属性が時とともに変わるディメンションのことです。顧客が引っ越して地域が変わった場合、過去の売上を旧地域で集計するか新地域で集計するかという問題が生じます。

| 型 | 扱い方 | 結果 |
|---|---|---|
| Type 1 | 上書きする | 過去の売上も新しい地域で集計される。履歴は失われる |
| Type 2 | 履歴行を追加する | 過去は旧地域、以降は新地域。行が増えるのでキー設計が必要 |
| Type 3 | 旧値の列を持つ | 「前回の地域」列を持つ。1世代前まで追える |

実務では Type 1 が最も多く、履歴分析が必要な場合に Type 2 を採用します。Type 2 では、同じ顧客に対して複数行が存在するため、**業務キー（CustomerID）とは別に、行を一意に識別するサロゲートキーが必要**になります。

> [!EXAM]
> PL-300 では「このテーブルはファクトかディメンションか」「粒度を宣言せよ」という直接的な問い方はされませんが、「どの列をどのテーブルに配置すべきか」という形で頻繁に問われます。判断の軸は、**合計する数値はファクト、絞り込みや軸に使う属性はディメンション**です。また「在庫数量を日付で合計してはいけない」という半加法性の理解も、タイムインテリジェンスの設問で前提になります。

> サロゲートキーは「毎回振り直される」と役に立ちません。更新のたびに行の順序が変わると、同じ商品に別の番号が付き、過去のファクトとの対応が壊れます。**サロゲートキーを使うなら、キーの割り当てはデータウェアハウス側で永続化するのが原則**です。Power Query 内で毎回採番する方法は、単一ソース・単一更新の小規模モデルに限って有効な簡便法だと理解してください。判断に迷うなら、まずナチュラルキーで始めるのが安全です。

```figure
  "edgeLabel": "1対多" }
```

売上は「受注1商品」の粒度、在庫は「1商品1日」の粒度です。**粒度が違うので、同じテーブルには絶対に入りません**。それぞれ別のファクトとして持ち、日付と商品という共有ディメンションでつなげば、「在庫回転率＝売上原価 ÷ 平均在庫」のような、2つのファクトをまたぐ指標も計算できます。

> [!TIP]
> 共有ディメンションを作るとき、**両方のファクトで使われる値がすべて含まれているか**を確認してください。売上にしか出てこない商品、在庫にしか出てこない商品の両方が Dim_商品 に存在する必要があります。実装としては、両方の商品IDを追加（Append）してから重複を削除する、という作り方をします。片方だけから作ると、もう片方に一致しないキーが生まれます。

## 分類を間違えたときに何が起きるか

分類ミスは、モデルを組んだ直後ではなく、**分析を始めてから**症状として現れます。

```figure
  "dir": "col",
  "items": [
    {"label": "ディメンションをファクトとして扱う", "sub": "商品マスタを中心に据える", "tone": "bad"},

```

この連鎖を断つ唯一の方法は、**最初に分類と粒度を紙に書くこと**です。テーブル名、1行が何を表すか、キー、測定値。この4項目を全テーブルについて書き出せば、設計ミスはモデルを作る前に見つかります。

## 理解度チェック

1. ファクトとディメンションを見分ける質問を3つ挙げ、`customers.csv` に適用して判定してください。
2. `StandardCost`（標準原価）をファクトに置くべきでない理由を、加法性の観点から説明してください。ではファクトの `UnitPrice` はどう扱うべきですか。
3. 「1行は、1件の受注における1商品の販売を表す」という粒度宣言をしたモデルに、受注全体にかかる送料を追加したいと言われました。どう設計しますか。

## よくあるエラーと対処

| 症状 | 原因 | 対処 |
|---|---|---|
| 割引率の合計が 300% になる | 非加法的な値を合計している | 割引額と定価を保存し、メジャーで割り算する |
| 在庫数量の年間合計が異常に大きい | 半加法的な値を日付で合計している | 期末時点の値を取る DAX に変更する |
| ディメンションの行数がファクトと同じ | 分類を誤っている、または粒度が間違っている | 判定質問に戻る。縮退ディメンションとしてファクトに残す |
| モデルサイズが急に膨らんだ | 一意に近い列（伝票番号・タイムスタンプ）を残した | 要件を確認して削除、または日付と時刻に分割する |
| 単価をディメンションに置いたら合わない | 受注時点の単価は取引ごとに変わる | 定価は Dim_商品、実売単価は Fact_売上 に置く |
| 顧客の地域を直したら過去の集計も変わった | SCD Type 1（上書き）で運用している | 履歴が必要なら Type 2 を検討する |
| 粒度が説明できないテーブルがある | 粒度を宣言していない | 「1行は〜を表す」の1文を書き、合わない列を移動する |
