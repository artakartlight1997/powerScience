Excel で「毎月同じ加工を手でやり直す」作業には、決まった終わり方があります。担当者が異動し、手順を知る人がいなくなり、誰も数字を再現できなくなる。Power Query が解決するのはこの問題です。

Power Query は**データを加工しません。加工の手順を記録します**。ボタンを押すたびに「何をしたか」が1行ずつ台本に書き足され、次回はその台本を頭から再生するだけで同じ結果が得られます。この台本が **適用したステップ** です。

```figure
    {"title": "Excel で手作業", "tone": "bad",
```

## 適用したステップの正体

適用したステップの1行は、**M言語のコード1行**です。M言語（正式には Power Query M formula language）は、Power Query の変換手順を記述する専用言語です。

エディター右上の「詳細エディター」を開くと、記録された全ステップがまとめて見えます。

```m
let
    ソース = Csv.Document(
        File.Contents("C:\data\sales.csv"),
        [Delimiter=",", Columns=10, Encoding=65001, QuoteStyle=QuoteStyle.Csv]
    ),
    昇格されたヘッダー数 = Table.PromoteHeaders(ソース, [PromoteAllScalars=true]),
    変更された型 = Table.TransformColumnTypes(
        昇格されたヘッダー数,
        {
            {"OrderID", type text},
            {"OrderDate", type date},
            {"ShipDate", type date},
            {"StoreID", type text},
            {"CustomerID", type text},
            {"ProductID", type text},
            {"Quantity", Int64.Type},
            {"UnitPrice", Int64.Type},
            {"Discount", type number},
            {"SalesAmount", Int64.Type}
        }
    ),
    フィルターされた行 = Table.SelectRows(変更された型, each [Quantity] > 0)
in
    フィルターされた行
```

構造は単純です。

```figure
{ "type": "steps", "title": "let 〜 in の読み方",
```

> この構造は、データ分析の世界でいう **再現可能なパイプライン（reproducible pipeline）** そのものです。R の dplyr のパイプ（`%>%`）、Python の pandas のメソッドチェーン、SQL の CTE（`WITH` 句）はどれも同じ発想で、「入力 → 変換 → 出力」を宣言的に連ねます。結果ではなく手順を保存する設計は、科学における実験ノートに相当します。数字を再現できないレポートは、再現できない実験と同じ扱いをされます。

## ステップを操作する

適用したステップは、後から自由に編集できます。ここが Excel と決定的に違う点です。

| 操作 | やり方 | 使う場面 |
|---|---|---|
| 選択 | ステップ名をクリック | その時点のデータを確認する。デバッグの基本 |
| 削除 | ステップ左の × | 不要になった操作を取り消す |
| 名前変更 | 右クリック → 名前の変更 | 意図を残す。最重要の習慣 |
| 並べ替え | ドラッグ、または右クリック → 上へ移動 | 順序が結果を変えるとき |
| 設定の変更 | 歯車アイコン | フィルター条件などを後から修正 |
| 途中に挿入 | 途中のステップを選んでから操作 | 後戻りして修正する |

**ステップをクリックすると、その時点のデータが表示されます。** これは強力なデバッグ機能です。「どこで行が消えたのか」を調べるときは、上から順にステップをクリックして行数の変化を追えば必ず犯人が見つかります。

> [!TIP]
> ステップ名は既定で「フィルターされた行」「削除された列」のような機械的な名前になります。同じ名前が続くと `フィルターされた行1`、`フィルターされた行2` になり、3か月後の自分が読めません。**「小計行を除外」「テスト店舗を除外」のように、目的を名前にしてください**。M コード上の変数名も同時に変わるため、詳細エディターの可読性も上がります。

## 途中のステップを消すと壊れる理由

ステップは前のステップに依存しています。したがって、**途中のステップを削除すると、それを参照している後続ステップがエラーになることがあります**。

たとえば「列の削除」で `備考` 列を消した後、「行のフィルター」で `備考` 列を条件に使うことはできません。逆に、`備考` 列を条件にフィルターした後で `備考` 列を削除するのは問題ありません。

## 順序が結果を変える

ステップは順番に実行されるため、**同じ操作でも順序が違えば結果が違います**。

```figure
{ "type": "tablediff", "arrowLabel": "順序の違いが結果を変える",
  "before": {"title": "先に集計 → 後で絞る", "tone": "bad",
    "head": ["店舗", "合計金額"],
    "rows": [["新宿本店", "!5,000,000"], ["渋谷店", "3,000,000"]]},
  "after": {"title": "先に絞る（家電のみ）→ 後で集計", "tone": "good",
    "head": ["店舗", "合計金額"],
    "rows": [["新宿本店", "!2,100,000"], ["渋谷店", "1,300,000"]]} }
```

「家電だけの店舗別売上」を出したいのに、集計してから家電で絞ろうとしても、集計した時点でカテゴリの情報は消えています。**絞り込みは、必要な情報がまだ残っているうちに行う**のが原則です。

さらに実務的な理由もあります。**行を減らす操作（フィルター、列の削除）は、できるだけ早い段階に置くほど処理が速くなります**。後続のステップが処理するデータ量が減るからです。

## クエリの折りたたみ

Power Query には **クエリの折りたたみ（Query Folding）** という仕組みがあります。これは、記録したステップを Power Query 自身が実行するのではなく、**データソース側が理解できる言語（SQL など）に翻訳して、ソースに実行させる**機能です。

```figure
{ "type": "pipeline", "title": "折りたたみが効くとき／効かないとき",
  "caption": "SQLに翻訳できたステップはサーバー側で実行され、転送量が激減する",
  "nodes": [
    {"id": "pq", "label": "Power Query\nのステップ", "tone": "green"},
    {"id": "sql", "label": "SQL に翻訳\nSELECT ... WHERE", "tone": "blue"},
    {"id": "db", "label": "データベース\nが実行", "tone": "violet"},
    {"id": "local", "label": "全件を取り込んで\nPower BI側で処理", "tone": "bad"} ],
  "edges": [
    {"from": "pq", "to": "sql", "label": "折りたたみ可能な操作"},
    {"from": "sql", "to": "db", "label": "サーバーで絞る（速い）"},
    {"from": "pq", "to": "local", "label": "折りたたみ不可の操作"} ] }
```

| 折りたたみやすい操作 | 折りたたみを壊しやすい操作 |
|---|---|
| 行のフィルター | カスタム関数の呼び出し |
| 列の選択・削除・名前変更 | 「例からの列」の一部の変換 |
| グループ化 | Table.Buffer の使用 |
| マージ（同一ソース同士） | 異なるソース同士のマージ |
| 型変換の多く | インデックス列の追加以降の一部操作 |

ステップを右クリックして「**ネイティブクエリの表示**」が有効なら、そこまでは折りたたまれています。灰色なら、そのステップで折りたたみが止まっています。

> [!TIP]
> 折りたたみを壊す操作は、**できるだけ後ろに置いてください**。フィルターや列削除を先に済ませてから、折りたたみ不可の操作を行えば、サーバーから受け取るデータ量を最小にできます。CSV や Excel ファイルが相手のときは折りたたみ自体が起きないので、この観点は不要です。

> [!EXAM]
> PL-300 では「更新が遅い。折りたたみを維持するにはどうするか」という形で問われます。答えの方向は一貫して「**ソース側で絞る**」です。具体的には、(1) 行のフィルターと列の削除をクエリの先頭付近に置く、(2) 折りたたみを壊す操作を後ろに移す、(3) ネイティブクエリの表示で折りたたみの境界を確認する。「Table.Buffer を使う」は折りたたみを**止める**選択肢なので、性能改善の答えとしては誤りです。

型の指定には**ロケール**が関わります。`2025/03/04` という文字列は、日本のロケールでは3月4日、米国のロケールでも3月4日ですが、`04/03/2025` は日本では解釈できず、英国では4月3日になります。日付や小数の型変換でエラーが出たら、「変換 → データ型 → ロケールを使用」で明示的にロケールを指定してください。

> 「変更された型」ステップは、列を1つ触るたびに自動で追加されがちです。気づくと `変更された型`、`変更された型1`、`変更された型2` が散らばり、どこで何の型になっているか追えなくなります。**型変換ステップは原則1つに集約**し、後から型を変えたいときはその1ステップの中身を編集してください。

## どこで行が消えたかを突き止める

実務で最も多い調査依頼は「売上合計が先月より少ない。どこかで行が落ちている」です。適用したステップがあれば、この調査は機械的に終わります。

やり方は単純で、**ステップを上から順にクリックし、画面左下に出る行数を記録する**だけです。

```figure
{ "type": "chart", "kind": "bar", "title": "ステップごとの行数",
  "categories": ["ソース", "ヘッダー昇格", "型の確定", "小計行を除外", "内部結合"],
  "series": [{"name": "行数", "values": [6948, 6947, 6947, 6903, 5120], "tone": "blue"}],
  "highlight": 4, "unit": "行" }
```

このグラフでは、内部結合のステップで 6,903 行が 5,120 行に落ちています。**1,783 行が結合先で一致しなかった**ということです。原因はキーの表記ゆれか、マスタ側の欠落のどちらかで、どちらも L0502 と L0505 で扱います。

重要なのは、犯人を特定するのに推測が1回も要らなかったことです。手作業の Excel では、この調査に半日かかります。

> [!TIP]
> 行数が知りたいだけなら、ステータスバーの表示に頼らず「変換 → 行数のカウント」を一時的に追加するのが確実です。確認したらそのステップを削除します。ステップは足したり消したりが自由なので、**調査用のステップを一時的に挿す**のは推奨される使い方です。

## クエリを整理する

クエリが 10 本を超えると、左ペインは急速に散らかります。右クリック →「グループへ移動」でフォルダーを作れます。

| グループ名 | 入れるもの |
|---|---|
| `00_パラメーター` | フォルダーパスや接続文字列などのパラメーター |
| `10_ソース` | 生データをそのまま読むクエリ（読み込みは無効にする） |
| `20_中間` | 共通クレンジング済みの参照元クエリ（読み込みは無効） |
| `30_モデル` | 実際に Power BI に読み込むファクトとディメンション |

この分類は、後のモジュールでスタースキーマを組むときにそのまま効いてきます。**モデルに載せるクエリだけを `30_モデル` に置く**という規律があると、モデルビューが常にきれいに保たれます。

## よくあるエラーと対処

| 症状 | 原因 | 対処 |
|---|---|---|
| 列 'XXX' は見つかりませんでした | 参照している列を削除・改名した | 該当ステップの歯車から列を選び直す。または名前変更ステップを先頭に追加する |
| ステップを消したら以降が全部エラー | 後続ステップが消したステップの結果に依存 | Ctrl+Z で戻し、依存関係を確認してから最後尾のステップから順に消す |
| 更新が異常に遅い | 折りたたみが早い段階で切れている | ネイティブクエリの表示で境界を特定し、フィルター・列削除を前へ移動する |
| プレビューと実際の行数が違う | プレビューは先頭部分のみ | 「変換 → 行数のカウント」で確認し、確認後そのステップを削除する |
| 詳細エディターが構文エラーになる | `let` と `in` の対応、カンマの過不足 | 各ステップ行の末尾カンマ（最終行にはカンマなし）を確認する |
| 同じ名前のステップが増え続ける | 既定名のまま操作を重ねた | 右クリック → 名前の変更で目的を書く。名前は M コードの変数名にも反映される |
