## トップNとその他パターン

性能と可読性を同時に改善する、最も費用対効果の高い書き換えです。

```dax
売上_トップN =
VAR N = 10
VAR Ranked =
    RANKX( ALLSELECTED( Dim_商品[ProductName] ), [売上合計], , DESC )
RETURN
    IF( Ranked <= N, [売上合計] )
```

```dax
売上_その他 =
VAR N = 10
VAR TotalSales = CALCULATE( [売上合計], ALLSELECTED( Dim_商品[ProductName] ) )
VAR TopSales =
    SUMX(
        TOPN(
            N,
            ADDCOLUMNS( ALLSELECTED( Dim_商品[ProductName] ), "@売上", [売上合計] ),
            [@売上], DESC
        ),
        [@売上]
    )
RETURN
    TotalSales - TopSales
```

> [!DS] データサイエンス視点
> レポートの性能は、**レイテンシとスループット**の両面で考えます。1人のユーザーが感じる待ち時間がレイテンシ、同時に何人を捌けるかがスループットです。ビジュアル数を減らすとレイテンシが下がり、同時に1リクエストあたりのリソース消費も減るのでスループットも上がります。一方、容量を増やしてもレイテンシはあまり下がりません（1クエリの処理そのものは速くならないため）。**設計の改善はレイテンシとスループットの両方に効き、増強はスループットにしか効きません。**

> [!EXAM] PL-300で問われる
> 「レポートのパフォーマンスを改善する方法」として、**ビジュアル数の削減**、**不要な列の削除**、**集計テーブルの使用**、**増分更新の構成**が出題されます。また、増分更新の前提として **RangeStart / RangeEnd パラメーター**が必要であること、**クエリの折りたたみ**が効いている必要があることは頻出です。

<details>
<summary>解答</summary>

**パフォーマンスアナライザーで記録を取り、時間の降順に並べます。** 18個を均等に直そうとしてはいけません。通常は1〜2個のビジュアルが全体の大半を占めているので、そこに集中します。並行して、ページを目的別に分割してビジュアル数を8個前後まで減らす設計変更も検討します。
</details>

**問2.** 増分更新を設定したのに、更新時間がまったく変わりません。何を確認しますか。

<details>
<summary>解答</summary>

**クエリの折りたたみが効いているか**を確認します。RangeStart / RangeEnd によるフィルターがソース側のSQLに変換されていなければ、結局全件を取得することになります。Power Query でフィルターステップを右クリックし、「ネイティブクエリの表示」が有効かどうかを見ます。グレーアウトしていれば、その前のステップ（カスタム関数や一部の変換）が折りたたみを壊しています。
</details>

**問3.** 集計テーブルを追加したのに、Server Timings を見ると明細テーブルがスキャンされています。考えられる原因は何ですか。

<details>
<summary>解答</summary>

クエリが**集計テーブルの粒度で答えられない**ためです。集計テーブルが「日×カテゴリ」粒度なのに、ビジュアルが商品別を要求していれば、明細を見に行くしかありません。また、集計の管理での列マッピングが不完全な場合（対応する明細列が指定されていない、集計関数が一致しない）もヒットしません。ビジュアルが要求する粒度と、集計テーブルの粒度・マッピングを突き合わせて確認します。
</details>
