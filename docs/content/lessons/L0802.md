DAXには文脈が **2種類** あります。前のレッスンで扱ったフィルターコンテキストと、もう1つが **行コンテキスト** です。

この2つを混同していると、次のような現象がすべて「謎」のままになります。

- メジャーの中で列を書くとエラーになるのに、計算列では書ける
- 計算列で `SUM` を書いたら、全行が同じ数字になった
- `SUMX` の中では列を直接書けるのに、外では書けない
- `AVERAGEX` の中でメジャーを呼ぶと、なぜか行ごとの値になる

**この4つは、すべて同じ1つの原理で説明できます。** それをこのレッスンで手に入れます。

```figure
{ "type":"cards", "cols":2, "title":"DAXの2つの評価コンテキスト", "caption":"名前が似ているが、やっていることは正反対に近い",
  "items":[
    {"icon":"⛃","title":"フィルターコンテキスト","text":"「どの行が見えているか」を決める。集合を絞る。メジャーが受け取るのはこちら。","tone":"amber"},
    {"icon":"→","title":"行コンテキスト","text":"「いまどの1行を処理しているか」を指す。絞らない。列の値を1つに確定させるためのもの。","tone":"blue"} ] }
```

## 行コンテキストの定義

**行コンテキスト**とは、「いま処理している行はこれだ」という指し示しです。
これがあるからこそ、`Fact_売上[Quantity]` という列参照が **1つの値** に確定します。

行コンテキストが発生する場所は2つだけです。

```figure
{ "type":"flow", "dir":"row", "title":"行コンテキストが生まれる2つの場所", "caption":"この2つ以外では、行コンテキストは存在しない",
  "items":[
    {"label":"計算列","sub":"表の全行を1行ずつ処理する","tone":"blue","icon":"▤"},
    {"label":"反復関数","sub":"SUMX / AVERAGEX / FILTER / ADDCOLUMNS など","tone":"violet","icon":"↻"} ] }
```

だから、メジャーの中で（反復関数を使わずに）列を直接書くとエラーになります。
そこには行コンテキストが無く、どの行の値を返せばよいか決まらないからです。

```dax
-- 計算列：行コンテキストがあるので OK
利益額 = Fact_売上[SalesAmount] - Fact_売上[原価額]

-- メジャー：行コンテキストが無いので エラー
利益額NG = Fact_売上[SalesAmount] - Fact_売上[原価額]

-- メジャー：反復関数が行コンテキストを作るので OK
利益額合計 = SUMX( Fact_売上, Fact_売上[SalesAmount] - Fact_売上[原価額] )
```

> [!NOTE] 一文で覚える
> **行コンテキストは「どの行か」を教えるだけで、データを絞り込まない。**
> フィルターコンテキストは「どの行が見えるか」を絞るが、「どの行か」は指さない。
> 役割がまったく違います。

## 最重要：行コンテキストはフィルターしない

ここが本レッスンの核心です。実験で確かめます。

```dax

全社売上列 = SUM( Fact_売上[SalesAmount] )
```

### では、どう書けば商品ごとになるか

方法は2つあります。どちらも「行コンテキストをフィルターに変換する」ことをしています。

```dax
-- 方法1：関連する行を明示的に取りに行く
商品別売上A = SUMX( RELATEDTABLE( Fact_売上 ), Fact_売上[SalesAmount] )

-- 方法2：CALCULATE でコンテキスト遷移を起こす
商品別売上B = CALCULATE( SUM( Fact_売上[SalesAmount] ) )
```

## コンテキスト遷移 — 2つの文脈をつなぐ橋

`商品別売上B = CALCULATE( SUM( Fact_売上[SalesAmount] ) )` は、`CALCULATE` にフィルター引数が1つもありません。
それでも商品ごとの値になりました。なぜでしょうか。

`CALCULATE` には、フィルターを変える以外にもう1つの働きがあります。

**行コンテキストが存在する場所で `CALCULATE` が呼ばれると、その行の値がフィルターコンテキストに変換されます。**
これを **コンテキスト遷移** と呼びます。

> [!TRAP] メジャーを呼ぶと、勝手にコンテキスト遷移が起きる
> DAXでは **メジャー参照は暗黙的に `CALCULATE` で包まれています**。
> つまり `SUMX( VALUES( Dim_商品[ProductName] ), [売上合計] )` と書いたとき、
> `[売上合計]` は `CALCULATE( [売上合計] )` として評価され、コンテキスト遷移が起きます。
> これが「反復関数の中でメジャーを呼ぶと行ごとの値になる」理由です。便利ですが、**知らないと必ず混乱します**。

| 式 | 結果 | 説明 |
|---|---|---|
| `SUMX( VALUES(...), SUM( Fact_売上[SalesAmount] ) )` | 300,000,000 | 100,000,000 が3回足された |

> [!TIP] 迷ったらメジャーを呼ぶ
> 反復関数の中では、**式を直接書くよりメジャーを呼ぶほうが安全**です。
> コンテキスト遷移が自動的に働き、直感どおりの「行ごとの値」になります。
> ただし遷移は処理コストが高いので、行数の多い表を反復する場合は注意が必要です。

## 行コンテキストは入れ子になる

反復関数の中でさらに反復関数を使うと、行コンテキストが2つ重なります。
古い書き方では `EARLIER` で外側の行を参照しましたが、**現在は `VAR` を使うのが標準です**。

```dax
-- 旧：EARLIER を使う（読みにくい）
売上順位列 =
COUNTROWS(
    FILTER(
        Dim_商品,
        [商品別売上B] > EARLIER( [商品別売上B] )
    )
) + 1

-- 新：VAR で外側の値を捕まえる（推奨）
売上順位列2 =
VAR この商品の売上 = [商品別売上B]
RETURN
    COUNTROWS(
        FILTER(
            Dim_商品,
            [商品別売上B] > この商品の売上
        )
    ) + 1
```

```figure

  "layers":[
    {"label":"内側の FILTER","sub":"Dim_商品 を1行ずつ見る。ここが「いまの行」","tone":"pink"},
    {"label":"VAR で確保した値","sub":"外側の行の売上。すでに数値として固定済み","tone":"violet"},
    {"label":"外側の計算列","sub":"Dim_商品 を1行ずつ見る。P001 の行を処理中","tone":"blue"} ] }
```

> [!NOTE] EARLIER は覚えなくてよい
> `EARLIER` は「1つ外側の行コンテキスト」を指す関数ですが、`VAR` があれば不要です。
> 既存モデルで見かけたときに読めれば十分で、**新しく書くときは必ず `VAR`** を使ってください。

| | 行コンテキスト | フィルターコンテキスト |
|---|---|---|
| 何を指すか | いま処理している1行 | 見えている行の集合 |
| 発生源 | 計算列、反復関数 | ビジュアル、スライサー、CALCULATE |
| 列の直接参照 | できる | できない（集計が必要） |
| データを絞るか | 絞らない | 絞る |
| 他テーブルへの影響 | なし | リレーションを通って伝播する |
| 変換方法 | CALCULATE でフィルターコンテキストへ | — |

> [!DS] レコード単位の計算と集合単位の計算
> データ処理には、常にこの2階層があります。SQLでいえば、
> 行ごとの式（SELECT句の四則演算）と、集合に対する集計（GROUP BY と集約関数）の違いです。
> Pandas なら `df["a"] * df["b"]` と `df.groupby(...).sum()` の違いに対応します。
> **どの言語でも、レコード単位と集合単位を混同すると必ず誤集計が起きます。**
> DAXはこの2階層を「行コンテキスト」「フィルターコンテキスト」として明示的に扱う、珍しい言語です。

## 理解度チェック

**問1.** `Dim_商品` の計算列に `売上 = SUM( Fact_売上[SalesAmount] )` と書いたら、全商品が同じ値になった。理由と対処を述べよ。

<details><summary>答え</summary>
計算列の行コンテキストは `Fact_売上` を絞らず、フィルターコンテキストは空のままなので全社合計が返る。対処は `CALCULATE( SUM( Fact_売上[SalesAmount] ) )` としてコンテキスト遷移を起こすか、`SUMX( RELATEDTABLE( Fact_売上 ), Fact_売上[SalesAmount] )` と書く。
</details>

**問2.** `SUMX( VALUES( Dim_商品[ProductName] ), [売上合計] )` が商品ごとの売上を合計した値になる理由を、「暗黙のCALCULATE」という語を使って説明せよ。

<details><summary>答え</summary>
メジャー参照は暗黙的に `CALCULATE` で包まれるため、`SUMX` が作った行コンテキスト（1商品）がフィルターコンテキストに変換され、その商品だけの売上が返るから。これがコンテキスト遷移である。
</details>

**問3.** `Fact_売上` の計算列で `RELATED( Dim_商品[Category] )` は動くが、`Dim_商品` の計算列で `RELATED( Fact_売上[SalesAmount] )` はエラーになる。なぜか。

<details><summary>答え</summary>
`RELATED` は多側から1側を参照する関数で、対応行が1つに定まる場合しか使えない。1側（商品）から多側（売上明細）を見ると対応行が複数あり、1つの値に決まらないため。この向きでは `RELATEDTABLE` を使い、集計関数と組み合わせる。
</details>

## よくあるエラーと原因

| 症状・エラー | 原因 | 対処 |
|---|---|---|
| 計算列の値が全行同じ | 行コンテキストがフィルターに変換されていない | `CALCULATE` で包む／`RELATEDTABLE` を使う |
| 「1つの値が必要ですが…」 | メジャーで列を直接参照した | 集計関数または反復関数を使う |
| `RELATED` がエラー | 1側から多側を参照している | `RELATEDTABLE` + 集計関数に変える |
| `RELATED` が空を返す | リレーションが無い、または非アクティブ | モデルビューで関係を確認する |
| `EARLIER` の結果が想定と違う | 入れ子の階層を取り違えた | `VAR` に書き換える |
| 反復の中の集計が全体値になる | メジャーではなく式を直接書いた | メジャー参照にするか `CALCULATE` で包む |
| 計算列が非常に遅い | 行ごとにコンテキスト遷移が発生している | メジャー化するか、Power Query 側で処理する |

> [!NOTE] このレッスンのまとめ
> 行コンテキストは「いまどの行か」を指すだけで、**データを絞りません**。
> 発生源は計算列と反復関数の2つだけ。
> 行コンテキストをフィルターに変えるのが **コンテキスト遷移** で、`CALCULATE`（およびメジャー参照に含まれる暗黙のCALCULATE）が引き起こします。
> この仕組みが分かれば、次のレッスンの `CALCULATE` は「もう半分知っている関数」になります。
