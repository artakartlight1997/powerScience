更新が止まったレポートは、間違ったレポートより危険です。**古い数字が「最新」の顔をして意思決定に使われる**からです。

配布まで終わったレポートに残る最後の仕事が、データ更新の自動化です。このレッスンでは、更新の仕組み、ゲートウェイの役割、そして更新が失敗したときの体系的な切り分け方を扱います。

> [!TIP] 実務のコツ
> 更新時刻は、**元データが確定する時刻の後**に設定します。基幹システムの日次バッチが 5:00 に終わるなら、更新は 6:00 に置きます。バッチ終了前に更新すると、前日分が欠けたデータで正常終了してしまい、**エラーにならないまま数字が間違う**という最も厄介な失敗になります。

> 更新回数の上限（**共有容量 1日8回 / Premium・Fabric 容量 1日48回**）、**更新のタイムアウト（共有容量では 2 時間、Premium 系では 5 時間）**、ゲートウェイが必要なケース、個人モードと標準モードの違いは頻出です。「更新が2時間で失敗する」→ 共有容量のタイムアウト上限、が正解として問われます。

## 増分更新 — 大きなテーブルを速く更新する

```figure
{ "type":"tablediff", "arrowLabel":"増分更新を設定",
  "before":{"title":"フル更新（既定）","tone":"bad",
    "head":["対象","行数","所要時間"],
    "rows":[["過去5年分の売上","24,000,000","1時間52分"],["更新のたびに","全行を再取得",""]]},
  "after":{"title":"増分更新（直近のみ）","tone":"good",

    "rows":[["過去5年分（アーカイブ済み）","!変更なし","0分"],["直近10日分のみ再取得","!130,000","!4分"]]} }
```

増分更新は、**「古い期間はそのまま残し、直近の期間だけ取り直す」**仕組みです。Power Query で `RangeStart` と `RangeEnd` という 2 つの日付/時刻パラメーターを作り、それでデータをフィルターしておくのが前提条件になります。

```text
// Power Query の M でのフィルター（増分更新の前提）
= Table.SelectRows(
    ソース,
    each [受注日] >= RangeStart and [受注日] < RangeEnd
  )
```

> 増分更新は**過去データの遡及修正を反映しません**。3 か月前の受注が訂正されても、増分範囲が「直近10日」なら取り直されないため、モデルの数字は古いままになります。遡及修正が起きる業務では、増分範囲を長めに取るか、月次でフル更新を別途走らせる運用にします。この特性を理解せずに導入すると、原因不明の数字ズレに悩まされます。

    {"title":"日次複数回","text":"共有容量は8回まで。時刻を業務の節目に置く","tone":"amber"} ] }

> [!DS] データサイエンス視点：鮮度は要件であってコストである
> データの鮮度（freshness）は「高いほど良い」ものではなく、**要件とコストのトレードオフ**です。1 時間ごとの更新は、日次更新の 24 倍の計算資源とソース側の負荷を発生させます。実際には「毎朝見て、その日の行動を決める」用途がほとんどで、その場合の適切な鮮度は日次 1 回です。
>
> 要件定義では「**その数字が変わったら、誰が、いつ、何をするのか**」を聞きます。行動が翌朝にしか起きないなら、リアルタイム更新には価値がありません。逆に在庫欠品の検知のように分単位で行動が変わるなら、DirectQuery を含む設計を検討します。鮮度の要件は、行動の頻度から逆算して決めます。

## 理解度チェック

1. 社内 SQL Server を参照するインポートモデルを発行したが、「このモデルに使えるゲートウェイがありません」と表示される。考えられる原因を 2 つ挙げ、確認手順を述べよ。
2. 毎朝 4:30 に更新するよう設定したところ、月曜だけ前週末の売上が欠ける。原因として何が考えられるか。
3. 2,400 万行のテーブルの更新が 2 時間でタイムアウトする。共有容量を使っている。取りうる対策を 3 つ挙げよ。

<details>
<summary>解答の要点</summary>

1. (1) **ゲートウェイにそのデータソースが登録されていない**。設定 → ゲートウェイの管理でデータソースを追加する。(2) **接続文字列が Desktop 側と一致していない**（`SQL01` と `SQL01.corp.local` など）。Desktop のクエリ設定でサーバー名・データベース名を確認し、同じ表記で登録する。加えて (3) 自分がそのデータソースの「ユーザー」に追加されていない、も原因になる。
2. **元データが確定する前に更新が走っている**可能性が高い。基幹システムの週末バッチが月曜の早朝まで動いており、4:30 時点では土日分が未反映であると考えられる。この場合エラーにはならず、欠けたまま「成功」するのが厄介な点。対処は、バッチ完了時刻の後ろに更新時刻をずらす、または API/Power Automate でバッチ完了をトリガーに更新を起動する。
3. (1) **増分更新を設定する**（アーカイブ期間と増分範囲を定義し、直近分だけ取り直す）。(2) **不要な列・行を Power Query で削除する**（列の削除はモデルサイズと更新時間に直接効く）。(3) **Premium / Fabric 容量に移す**（タイムアウトが 5 時間に延び、更新回数上限も 48 回になる）。加えて、変換処理をソース側（ビューやウェアハウス）に寄せてクエリフォールディングを効かせる、も有効。

</details>
