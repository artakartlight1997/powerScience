# 長時間エージェントの原価構造

**「8時間走らせる」の原価は、トークン単価ではなくキャッシュ設計で決まる。**

## 1. エージェント負荷の特性 `[S-129]`

| 事実 | 数値 |
|---|---|
| 本番のエージェント推論で **prefill が占める割合** | **85〜95%** |
| 入力対出力の生トークン比 | **267 : 1**（1トークン生成するたびに267トークンを読み直す） |
| エージェント型ワークフローのトークン消費（対 通常のチャット） | **5〜30倍** |
| トークン単価の低下（2023→2026） | **80%減。にもかかわらず総額は増加**（量が価格低下を上回った） |

> **含意**: エージェントの原価は「賢く考える（出力）」ではなく
> **「同じ文脈を何度も読み直す（入力）」**で決まる。

## 2. キャッシュが最大のコストレバー `[S-129]`

| 施策 | 効果 |
|---|---|
| キャッシュヒット率 **0% → 90%** | 同じワークロードで月額 GPU 費用が **$20,000 → $2,000** |
| **プレフィックスキャッシュ**（ヒット時） | **85〜95% のコスト削減**。エージェントループで **60〜85% のヒット率**が達成可能 → **1呼び出しあたり 5〜12倍**のコスト減 |
| Anthropic のプレフィックスキャッシュ | 長プロンプトで **コスト90%減・レイテンシ85%減** |
| Gemini DR の暗黙キャッシュ | 入力トークンの **50〜70%** をカバー `[S-020]` |

### 制約
**KV キャッシュは DRAM に置かれ、DRAM は有限**。
2026年の各社の課金体系では**キャッシュ書き込みウィンドウの有効時間と長時間セッションの割増**が異なるが、
**必ず上限がある** `[S-129]`。

## 3. IP への設計要件

> **キャッシュヒット率は、品質指標ではなく粗利率そのものである。**

| 要件 | 内容 |
|---|---|
| **プレフィックスの安定化** | 案件ごとに「不変の前置き」（ファンドの方針、業界の固定知識、ツール定義）を先頭に固定し、変動部分を末尾に置く |
| **モデル固定 vs ルーティングの葛藤** | ベンダを跨ぐとキャッシュが効かない。**案件内では同一モデルに固定**し、検証など**独立性が必要な工程だけ別ベンダ**にする（→ [t-model-routing](model-routing-and-cascades.md)） |
| **文脈を積まない設計が原価にも効く** | IterResearch 型の再構成は、**ノイズ低減（品質）とキャッシュ設計（原価）の両方**に効く（→ [t-context-engineering](context-engineering.md)） |
| **長時間セッションの分割** | 8時間の単一セッションではなく、**チェックポイント付きの短いセッションの連鎖**にする（DRAM 上限とキャッシュ失効への対処） |
| **検索コストの別勘定** | Gemini DR では 1 run の半分以上が検索コスト `[S-020]`。**EIG による検索予算配分は原価施策**でもある |

### 概算（IP の想定単価との整合、`C`）
```
1案件 = 数百〜数千の LLM 呼び出し ＋ 数百の検索 ＋ 数十の高価な検証
  キャッシュなし: 数万円/案件
  キャッシュ90%: 数千円/案件
→ 想定売価 ¥100,000〜¥1,000,000 に対し、粗利率は十分に確保できる
→ ただし ★人間の検証時間★ が入ると、これが最大の原価になる（→ 人的コストの最小化が粗利の鍵）
```
