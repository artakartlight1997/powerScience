# モデルルーティングとカスケード

## 1. 基本

- **ルーティング** = リクエストごとに1つのモデルを選ぶ方策。**コスト・レイテンシ・品質**の三すくみを操作する `[S-089]`
- **カスケード** = 安いモデルを先に試し、必要なときだけ上位に昇格させる。
  **単一フロンティアモデルをコストと品質の両方で上回りうる唯一のパターン** `[S-089]`
  （フロンティアのトークンを「本当に必要だった要求」にだけ使うため）

## 2. 実績値

| 手法 | 結果 |
|---|---|
| **FrugalGPT**（2023） | カスケード/ルーティング研究の基礎 `[S-089]` |
| **RouteLLM**（UC Berkeley + Anyscale, ICLR 2025） | MT-Bench で **最大約85%のコスト削減**、**GPT-4 品質の約95%を維持**、**フロンティア呼び出しは約26%** `[S-089]` |
| 実務チームの報告 | **請求額 40〜85% 削減**、回答品質の目立った低下なし `[S-089]` |

**背景**: 2026年のアプリは単一モデルではなく**モデルのメニュー**（フロンティア/中位/安価/自社ホスト）に話しかける。
品質-コストの**パレートフロンティア**上を動けるのがルーティングの価値 `[S-089]`。

## 3. IP における三つの用途

| 用途 | 内容 | 根拠 |
|---|---|---|
| **① 品質（集合知）** | どのモデルを呼ぶかを**探索の一次元**にする | AB-MCTS `[S-010]` |
| **② 原価（カスケード）** | 安いモデルで前段、必要時のみ昇格 | RouteLLM `[S-089]` |
| **③ 独立性（クロスベンダ）** | **生成と検証を必ず別ベンダにする** | 検証器の非対称性 `[S-036]` |

**③が IP 固有の主張**。①②は既知だが、③は
「同一モデルは同一の盲点を共有する」という**信頼性の議論**であり、
金融顧客への説明（「特定ベンダに依存しません」）としても効く。

## 4. 設計上の注意

| 論点 | 内容 |
|---|---|
| **ルーティングの判断コスト** | ルータ自体が高いと本末転倒。軽量分類器 or ヒューリスティックで |
| **不確実性による昇格** | 較正済みの不確実性で昇格を決める（UCCI 等の研究方向 `[S-089]`） |
| **ベンダ跨ぎの摩擦** | レイテンシ、契約、データ取扱条件、可用性 — 運用負荷は実在する（→ 未決論点 D4） |
| **キャッシュとの相互作用** | モデルを変えるとキャッシュが効かない。**案件内では同一モデルに固定**する方が安い場合がある `[S-020]` |
