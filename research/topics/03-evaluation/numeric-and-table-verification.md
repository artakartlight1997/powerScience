# 数値・表・財務データの検証

> **設計原則 P5 で「検証器に数値再計算権を与える」と書いた。その実現可能性の検証。**
> **結論: 現状の素の LLM には無理。だからこそ、ここは工学的な堀になる。**

## 1. 現状はかなり悪い（定量）

| 事実 | 数値 | 出典 |
|---|---|---|
| **FinAuditing の数値整合性タスク**（XBRL 監査規則の検証） | **最強モデルで 13.86%** | `[S-130]` |
| Daloopa ベンチ: マルチエージェントの財務データ**抽出** | 約 **88%** | `[S-131]` |
| 同: **LLM の素の数値計算** | 約 **52%** | `[S-131]` |
| Finance Agent Benchmark（実世界の金融リサーチ課題）: 最良モデル(o3) | **46.8%**、1クエリあたり平均 **$3.79** | `[S-131]` |
| 不完全な原文書に直面したときの**数値の捏造** | 主要6モデル中 **4つが捏造** | `[S-131]` |

**AUDITFLOW の問題設定** `[S-130]`:
> 単一の監査ルールでも、**分散した XBRL 文書のリンク、タクソノミ関係の走査、期待値の再計算、
> 構造化された証拠へのルール適用**を要する。

**タスクの性質** `[S-130]`:
> 金融・表形式の QA は自動レポートや監査パイプラインの分析基盤として配備されつつあるが、
> **「流暢だが誤った導出」への許容度はゼロ**である。
> **セルの読み違い1つ、数式の誤り1つが、最終的な数値を静かに壊す。**

## 2. 何が分かるか

### (a) 「LLM に計算させる」は禁止事項
抽出88% に対し**素の計算52%** `[S-131]`。実務で推奨されている型も明快 `[S-131]`:
> **LLM は解釈と説明に使い、計算はスクリプト／計算エンジンに任せる。**
> スプレッドシートを処理する Python コードを LLM に書かせ、結果を LLM に説明させる。

> ### 🔑 設計原則 P19
> **数値は必ずコードで計算する。モデルに計算させない。モデルの役割は
> 「どの数値をどう計算すべきか」の指定と、結果の解釈に限定する。**

### (b) 「データが無い」を返せることが決定的
主要6モデル中4つが**不完全な原文書で数値を捏造する** `[S-131]`。
これは VC DD 研究の「**構造的フォールバックがデータ不在を明示フラグする**」`[S-090]` と完全に一致する。
→ IP の抽出層は **`value | NOT_FOUND | AMBIGUOUS`** の三値を返す（既に C-029 として登録済み）。

### (c) ここは工学的な堀になる
FinAuditing 13.86% `[S-130]` は「**フロンティアモデルでも解けていない**」ことを意味する。
つまり:
- **モデルの進歩を待っても、当分は埋まらない**（→ Class B/D の性質）
- **XBRL のタクソノミ走査、期間整合、勘定科目の対応づけ**といった
  **ドメイン固有のデータ工学**で殴れる領域である
- 日本の有報はさらに難しい（企業別タクソノミ拡張、注記の非定型性 `[S-078]`）
→ **「難所であること」がそのまま参入障壁になる。**

## 3. 関連する評価基盤（借用できる）

| ベンチ | 内容 |
|---|---|
| **AUDITFLOW / FinAuditing**（arXiv:2606.03031）`[S-130]` | XBRL 財務報告検証の**実行可能な記号環境** |
| **WorkstreamBench / MBABench**（arXiv:2605.22664）`[S-132]` | **エンドツーエンドのスプレッドシート課題**。既存ベンチが「原子的な操作」しか測っていない点を批判 |
| **MoCA-Agent**（arXiv:2606.11537）`[S-132]` | 金融・数値推論のための **market-of-claims コードエージェント** |
| **GAUGE**（arXiv:2607.24889）`[S-132]` | **正解のない状態で、エージェントが構築した財務モデルを採点する** ← IP の評価設計に直結 |
| **BigFinanceBench**（arXiv:2606.03829）`[S-132]` | 金融リサーチエージェントの**ワークフロー接地型**ベンチ |
| **PortBench**（arXiv:2605.27887）`[S-132]` | 相関を考慮したフルパイプラインのポートフォリオ管理 |

> **GAUGE が特に重要**: 財務モデルには唯一の正解がない（前提の置き方で変わる）。
> **「正解なしで採点する」**枠組みは、IP の評価設計（反実仮想 DD、ルーブリック）に直接使える。

## 4. IP の実装方針

```
① 抽出   : レイアウト認識 OCR ＋ XBRL 直参照。三値（value | NOT_FOUND | AMBIGUOUS）
② 正規化 : 勘定科目のマッピング、会計期間の整合、単位・通貨、企業別タクソノミ拡張の吸収
③ 計算   : ★ 決定論的なコード（Python / 計算エンジン）。LLM は式の指定と解釈のみ
④ 検証   : 恒等式チェック（BS 一致、CF と PL の整合、前期比の連続性）、
           XBRL の計算リンクベース検証、複数ソース間の突合
⑤ 説明   : 差異が出たら「どの数値が、どのソースと、どれだけ食い違うか」を提示（平均しない）
```

**④が「検証器の特権」の実体**である。生成側の LLM はこれを持たない。
