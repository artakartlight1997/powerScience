# 設計が正しかったと、どう分かるか

**「良さそう」を禁じるために、観測可能な指標と実験を先に決める。**

## 1. 先行指標（数日〜数週で分かる）

| # | 指標 | 測り方 | 合格ライン `推定` | 何を意味するか |
|---|---|---|---|---|
| **L1** | **根拠なし主張の検出数** | 実 IC メモ1本あたり | **3件以上** | 実益の存在（0件なら W1 が成立しない） |
| **L2** | **矛盾の検出数** | 同上 | **1件以上** | 差別化の存在（汎用 LLM は矛盾を平均する `[S-125]`） |
| **L3** | **誤検出率** | 「根拠なし」と言ったが実は根拠がある割合 | **5%未満** | 信頼の前提。ここが高いと一発で見放される |
| **L4** | **差分の気づき率** | 人間の死因になく AI が出した論点のうち、**「言われてみれば」と評価された割合** | **30%以上** | E6（当たり前しか出ない）の回避 |
| **L5** | **裏取り時間** | 主張1件の出典確認にかかる秒数 | **300秒 → 30秒** | 実益 V1 の具体 |
| **L6** | **再訪率** | 初回利用の翌週に自発的に再利用したか | **50%以上** | F4′（定着しない）の早期検知 |

> **L4 が最も重要で、最も測りにくい。**
> 測り方: 差分論点を1件ずつ提示し、**「これは IC で聞かれると思うか」を Yes/No で聞く**。
> 「役に立ったか」ではなく「**IC で聞かれるか**」を聞くのがコツ（社交辞令を排除できる）。

## 2. 遅行指標（数ヶ月〜年）

| # | 指標 | 測り方 | 意味 |
|---|---|---|---|
| **T1** | **見落とし率** | 反実仮想 DD（下記3節） | V2 の証明。**主力の売り文句** |
| **T2** | **Brier / ECE** | 予測命題と実現の突合 | 較正の証明（F2 が偽なら効く） |
| **T3** | **人時削減** | IC 提出までの実績人時 | V1（副次） |
| **T4** | **拡大率** | 1工程 → 複数工程への広がり | 正本化の成否 |
| **T5** | **更新率** | 契約更新 | 総合的な価値の証明 |

## 3. 反実仮想 DD の実験プロトコル（詳細設計）

**T1 を測る唯一の方法。ここを厳密にしないと、数字が信用されない。**

```
【設計】
  対象     : 過去の実案件 N=20–40（投資したもの / 見送ったもの 両方）
  時点     : T = IC 実施日
  入力     : T 以前に入手可能だった情報のみ（as_of ≤ T をインデックス側で分離）
  出力     : 未解決論点リスト（重要度順）
  正解     : T+2〜3年に実際に問題化した事象（決算・報道・PMI記録から抽出）

【評価】
  ① Recall  : 実際に問題化した事象のうち、事前に論点として挙がっていた割合
  ② Precision: 挙げた論点のうち、実際に問題化した割合
     ★ Precision は低くてよい（保険と同じ）。★ Recall が主指標
  ③ 比較対象: 当時の実際の IC メモに挙がっていた懸念事項
     → 「人間が挙げた懸念 vs 我々が挙げた論点」の差分が価値

【リーク対策】（★ここを厳密に）
  a. as_of フィルタではなく ★インデックス分離★（「見えたが使わなかった」を許さない）
  b. 固有名詞の匿名化（社名・人名・地名・製品名）
  c. モデルのカットオフ後の案件を優先的に含める
  d. 出力に「T 以降にしか知り得ない事実」への言及がないか機械チェック
  e. 架空の対照案件を混ぜ、既知案件との性能差を測る（差が大きければリーク）

【統計】
  N=20 では検出力が足りない。★最低 N=30、できれば 50
  ブートストラップで信頼区間を出す。「6/10 で指摘」のような点推定を単独で使わない
```

> **この実験は数人月かかる。** だが **これ自体が製品の売り文句**であり、
> **内製化と大手への最大の参入障壁**でもある（→ ウォーゲーム W-4）。

## 4. 「今のやり方」との比較実験（穴 H5 の解消）

**最大の競合は Excel と人力である。** そこと定量比較する。

```
【設計】同一案件を2群で処理
  群A: 従来通り（アナリスト2名）
  群B: IP あり（アナリスト2名 + IP）
  ※ 同じ案件を別チームで、またはクロスオーバー設計

【測定】
  - IC 提出までの人時
  - 挙がった懸念事項の数と質（★パートナーによるブラインド評価）
  - IC でパートナーに指摘された「事前に気づくべきだった」件数 ← ★核心指標
  - アナリストの主観（NASA-TLX 等の負荷指標も可）

【ブラインド化】
  パートナーには、どちらの群のメモか伏せて評価させる
  → 「AI が作った」というだけで評価が動くのを防ぐ
```

**この実験の結果が、A1（実益は V2）の最終的な検証になる。**

## 5. 撤退・転換のトリガー（数値で）

| 観測 | 意味 | 行動 |
|---|---|---|
| L1 < 1件/メモ（10本連続） | 実 IC メモに穴がない | W1 を捨て、W3（財務）へ |
| L3 > 15% | 誤検出が多すぎる | 検証設計をやり直し。出荷しない |
| L4 < 10% | 当たり前しか出ない（E6） | 仮説空間の供給源を作り直す（型・記憶・人間） |
| L6 < 20% | 定着しない（F4′） | 楔と UI を作り直す |
| T1 が人間と同等 | 見落としを減らせていない | **V2 の主張が崩れる** → 価値提案の再設計 |
| 24ヶ月で顧客 0 | シナリオ3 | 撤退 |

## 6. 測らないと決めたもの（意図的な非目標）

- **レポートの「読みやすさ」** — 生成は100倍安い `[S-112]`。差別化にならない
- **処理速度** — 30分以内なら十分。それ以上速くしても価値が増えない `推定`
- **対応データソース数** — 多いほど良いわけではない（P16）
- **汎用ベンチのスコア** — 飽和・汚染で信用されない `[S-116]`
