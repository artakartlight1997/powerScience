# 競合ウォーゲーム

**「彼らが賢く動いたら、我々はどうなるか」を先に考える。** 相手を過小評価しない。

## 1. 各プレイヤーの最善手と、我々の応手

### Sakana AI（最も近い脅威）
| 彼らの最善手 | 実現可能性 | 我々への打撃 | 応手 |
|---|---|---|---|
| Marlin に**引用の機械検証**を足す | **高**（技術的には容易） | **中** — L0/L1 の差は消える | L3（反証）L4（較正）と**顧客データ**で戦う。検証だけでは元々戦っていない |
| **EDINET-Bench + Namazu + Marlin** で日本語金融特化 | **高**（部品は揃っている `[S-016][S-105]`） | **大** | **実務工程（IC/PMI）**へ。彼らは工程に入っていない `C` |
| Fugu をオーケストレーション API として外販 | 中 | 小 | **むしろ使う側に回る** |
| PE ファンドと直接提携 | 中 | 大 | 先に楔を打つ（W1）。**速度が全て** |

### Google / OpenAI
| 最善手 | 可能性 | 打撃 | 応手 |
|---|---|---|---|
| DR API の値下げ・grounding 強化 | **高** | 小 | 我々は生成量で戦っていない |
| **引用検証を標準搭載** | 中 | 中 | L0/L1 はコモディティ化する前提で設計済み |
| **較正・棄権の改善** | **低** | 大 | **評価が棄権を罰する構造** `[S-108]` があるため動機が弱い ← ここが我々の賭け |
| 金融特化の垂直製品 | 低 | 大 | 規制・顧客データ・工程で防御 |

### Hebbia / Rogo / BlueFlame
| 最善手 | 可能性 | 打撃 | 応手 |
|---|---|---|---|
| **矛盾検出**を足す | **高** | **中** | 矛盾検出は単体では機能にすぎない。**ACH 行列＋EVPI＋記憶**の組で戦う |
| 反証・想定問答を足す | 中 | **大** | **最も痛い手**。→ 先に「IC レディネス」の言葉を取る（カテゴリの先取り） |
| 既存顧客に無料でバンドル | **高** | **大** | 我々は**単価の高い層**（ディール費用）で勝負。SaaS 席課金と戦わない |

### PitchBook / S&P / FactSet（データ層）
| 最善手 | 可能性 | 打撃 | 応手 |
|---|---|---|---|
| Navigator が判断層へ降りる `[S-134]` | 中 | 大 | **彼らは VDR・面談・自社の判断履歴を持たない**。顧客固有データで戦う |
| コネクタ供給を絞る（囲い込み） | 低 | 中 | 複数ベンダ対応。公開データ経路を確保 |
| **我々を買収 or 提携** | 中 | — | **これは勝ち筋の一つ**。設計を疎結合に保つ |

### PE ファンドの内製化
| 最善手 | 可能性 | 打撃 | 応手 |
|---|---|---|---|
| 大手が自前で作る | 中（技術者を雇っている） | 中 | **評価基盤（反実仮想 DD）は自前で作りにくい**。数人月かかる。そこが参入障壁 |
| 既存ツール＋人手で回す | **高** | 中 | 「今のやり方」が最大の競合。**60秒デモで差を見せる**しかない |

## 2. 2年間のシナリオ（3本）

### シナリオ1: ベース（確率 50% `推定`）
```
6ヶ月  : 我々が W1 で3社に導入。Sakana は Marlin の機能拡張を継続（金融特化は限定的）
12ヶ月 : Hebbia/Rogo が「矛盾検出」を追加。我々は反実仮想 DD の実績を1本作る
18ヶ月 : 我々の顧客が10社。記憶の蓄積が効き始める
24ヶ月 : カテゴリとして「IC レディネス」が認知される
→ 勝ち筋: 評価実績と顧客データの蓄積が堀になる
```

### シナリオ2: 加速（確率 20%）
```
6ヶ月  : Sakana が日本語金融特化を発表（Marlin for Finance）
12ヶ月 : PE 各社が Sakana を採用。我々の商談が止まる
→ 応手: ①Sakana の上に載る（検証層として） ②DD ファーム向けに転換
        ③特定ファンドの深い正本化に賭ける
→ 生存条件: 「Marlin の出力を検証する」という位置づけが成立するか
```

### シナリオ3: 悪夢（確率 10%）
```
6ヶ月  : フロンティアが引用検証と較正を標準搭載。同時に PitchBook が判断層へ
12ヶ月 : 「わざわざ専用ツールを入れる理由」が消える
→ 応手: 顧客固有データと規制対応（監査・署名）だけが残る
→ 生存条件: 3-5社の深い顧客で、正本として定着していること
→ ★この場合、24ヶ月時点で顧客がゼロなら撤退
```

（残り 20% は「市場自体が立ち上がらない」＝ F4′ が支配的なケース）

## 3. ウォーゲームから出た設計要件 🔒

| # | 要件 | 理由 |
|---|---|---|
| **W-1** | **疎結合を保つ**（Sakana/Google/Hebbia の上に載れる形にする） | シナリオ2 の応手に必要 |
| **W-2** | **カテゴリの言葉を先に取る**（「IC レディネス」） | 後発が同じ機能を出しても、言葉は取られている |
| **W-3** | **顧客データの蓄積を最速で開始** | どのシナリオでも最後に残るのはこれ |
| **W-4** | **評価基盤（反実仮想 DD）を早く作る** | 内製化と大手への最大の参入障壁 |
| **W-5** | **買収されうる形にしておく** | データ層との提携・売却は勝ち筋の一つ |
| **W-6** | **24ヶ月の撤退条件を先に決めておく** | シナリオ3 |

## 4. 最も警戒すべき手

> **Hebbia / Rogo が「想定問答」を足すこと。**
>
> 理由: ①技術的に容易 ②既に PE の中に入っている ③既存契約にバンドルできる
> → **我々の唯一の防御は「早さ」と「深さ（記憶・評価）」**。機能では守れない。
> → だから **W1（IC メモを叩く）を最速で出し、記憶の器を最初から作る**。
