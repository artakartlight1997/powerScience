# 確定 — 内製利用と、入力ゼロ化

ユーザー（意思決定者）による2つの確定を記録する。**以後の全文書はこの前提で読む。**

---

## 確定1: Integral Prism は売らない。自社ファンドの投資プロが使う内製システムである

### 内製の定義（ユーザーの言葉を正確に）

| 契約して使う（コモディティ入力） | 契約しない | 内製する |
|---|---|---|
| フロンティアモデル（Claude / GPT / Gemini の API） | **Sakana Marlin 等の「リサーチシステム」** | **判断の層**：証拠台帳・検証・優先順位づけ・ファンド固有の記憶 |
| Google Deep Research（収集係として） | 他社の金融AI SaaS（Hebbia/Rogo等）※要再検討 | |
| Speeda / 帝国データバンク / EDINET | | |
| エキスパートネットワーク / コンサルの Biz DD | | |

**問い**: サカナと契約するより、内製の方がよいのではないか。
**回答**: **内製が正しい。** 根拠は3つで、うち1つが決定的である。

### 根拠① 買えるものは競合も買える（差別化の消滅）
Marlin は競合ファンドも月¥150,000で契約できる。AI 採用の進展でシグナル半減期は
5-7年 → **18ヶ月**に短縮し、同じデータ・同じモデルを使う機関のポートフォリオは
**42%収束**する `[S-117]`。**購入したシステムは「他社と同じ視力」しか与えない。**

### 根拠②（決定的）「Deep Research が薄い」のは構造的な理由による
ユーザーの原不満は「**DR では内容が薄い。完全な DD 情報がほしい**」だった。この薄さの正体:

> **薄いのはモデルが弱いからではない。公開情報しか食べていないからである。**
>
> DD の深い情報 — **VDR の中身、エキスパートコールの生記録、経営者Q&A、
> 自社の過去 IC メモと見送り履歴** — は、セキュリティと MNPI の制約により
> **外部 SaaS には原理的に入れられない**（入れた瞬間に情報統制が崩れる）。
> つまり **契約したシステムの深さは、公開情報の深さで頭打ちになる。**
> どれほど Marlin が賢くなっても、この天井はモデルの賢さと無関係に残る。
>
> **私有情報を安全に食べられるのは、自社の統制下にある内製システムだけ**（P18 の隔離設計込み）。
> 「深さ」を求めるなら、内製は選好ではなく**論理的必然**である。

### 根拠③ 蓄積が自社に残る
案件ごとの検証結果・外した理由・ファンド固有の reference class は、内製なら
100%自社資産になる（→ P24: 近期は台帳、長期は較正）。per-run 課金の外部システムには何も残らない。

### Marlin 契約との比較（内部利用の観点）

| | Marlin を契約 | 内製 Prism |
|---|---|---|
| 深さの上限 | **公開情報まで**（VDR・専門家・IC履歴は入れられない） | 私有情報まで（隔離設計の下で） |
| 競合との差 | ゼロ（誰でも契約可） | 蓄積分だけ開き続ける |
| コスト | 月¥150,000〜 + ¥9,800/run | 機械 ¥6-18k/案件 + **エンジニア1-2名**（最大のコスト） |
| 監査・署名 | 不明 | 追記専用台帳（P12） |
| 成果物 | 事後の100ページ | 着手時の優先順位 + 生きた台帳 |

**内製の正直なコストとリスク**: エンジニアの人件費と**保守**（enterprise AI の定着は10-15% `[S-076]`、
ハーネスはモデル更新で陳腐化 `[S-113]`）。緩和は既定路線の通り——**判断層だけを薄く作り、
それ以外は全部買う**（coding-strategy/01, 04）。実装は AI コーディングに積極的に任せる `[S-137]`。

### この確定が既存文書に与える影響

| 03（誰が払うか）04（商品形態の販売文脈）05（楔の営業設計）11（単価・損益分岐） | **外販シナリオのアーカイブ**として保持。11 の原価計算は「1案件あたりの運用コスト」として読み替えて生きる |

## 確定2: Decision Compiler Stage 0 の入力ゼロ化（P23 改訂）

前版の「人間が着手時に30秒で死因を3行書く（必須）」は**誤りだったので撤回**する。
ユーザー指摘: 「Biz DD にどんな情報が必要かは明白。どこが薄いかは毎回変わるから、インプットは入れようがない」——正しい。

### 誤りの構造
DD で必要な情報には2種類あり、前版は**変わらない方まで人間に聞こうとしていた**。

| 型 | 例 | 案件ごとに変わるか | 供給源 |
|---|---|---|---|
| **カテゴリ**（何を見るか） | 市場 / 顧客集中・解約 / 競合 / 価格転嫁力 / チャネル / 規制 / 経営体制 / オペレーション / ESG の**約10箱** | **変わらない**（業界標準） | 業界テンプレート（人間に聞かない） |
| **急所**（今回どの箱が致命傷か）と**閾値** | 「この案件は顧客集中が急所」 | 変わる | **初期資料からの自動検出**（人間に聞かない） |

### 改訂後の Stage 0（人間の入力ゼロ）
```
案件着手 → ① 業種・ビジネスモデルからテンプレートを自動選択
        → ② 初期資料（ティーザー/IM/財務）を読み、10箱それぞれを自動スコアリング
             例: 上位顧客集中度は資料に数値がある → 閾値超えで自動フラグ
                 成長率が業界統計と乖離 → 自動フラグ／会計方針の変更 → 開示から自動検出
        → ③ ファンド標準の閾値（IRRハードル・許容集中度等）は ★一度だけ設定★。案件ごとに聞かない
        → ④ 人間の入力ゼロで「この案件の急所候補」の優先順位が出る
        → ⑤ 任意: 資料に絶対現れない耳打ち情報（経営陣の退任の噂 等）を人間が足せる。
             これは補強であり、起動条件ではない
```

### P17（人間先出し）との整合
P17 の狙い（AI の出力を先に見せると過信を招く）は保持するが、**必須入力としては課さない**。
「差分の提示」は人間入力なしでも自動生成できる:
**「業界テンプレートが標準的に警戒する急所」vs「この案件の資料から実際に検出された急所」の差分**が、
そのまま「この案件はどこが普通と違うか」になる。人間の見立てとの差分は、入力があった場合のボーナス。

### 必須検証の差し替え
- 旧: 「忙しい投資プロから意思決定モデルの最小形を30秒で取れるか」
- **新: 「初期資料だけ・人間の入力ゼロで、業界標準の10箱に対する妥当な優先順位が自動で出るか」**
  （先行指標 L4 の読み替え: 検出された急所が、後の DD・IC で実際に争点化した率で測る）

### P23 改訂文
> **P23（改訂）: 意思決定モデルの入力を実務家に要求しない。**
> カテゴリは業界標準テンプレート、急所は初期資料からの自動検出、
> 閾値はファンド標準として一度だけ設定する。
> 人間の入力（耳打ち情報・見立て）は任意の補強であり、起動条件にしない。

## 補正（同日）: 確定2の趣旨の訂正 — 「毎回変わる」のは Deep Research の結果の側

上の確定2は、ユーザーの発言「どこが薄いかは毎回変わる」を
「案件ごとに急所が変わる」と読んでいたが、**これは読み違いだった**。正しい趣旨:

> **毎回変わるのは Google Deep Research が返す結果の方。**
> 実行のたびにどこが濃くどこが薄いかが変動する。
> だから投資プロに「どこが薄いか」を毎回聞くのは有効でない —
> **本人も結果を見るまで知りようがないし、読んで判定させるのは時間の浪費**だから。

### 訂正後の中核機構: カバレッジ監査ループ

Biz DD に必要な情報は明白（＝**固定の物差し**）。変動するのはリサーチ結果の側。
ゆえに機械の仕事は「結果を物差しに突き合わせ、薄い所を検出し、埋めに行く」こと。

```
固定スペック: Biz DD 標準チェックリスト（約10箱 × 必須項目。一度作れば不変）

毎案件:
1. 収集: Google DR / Speeda / TDB / EDINET / コンサル報告書 を実行・投入
2. 監査: 返ってきた中身をスペックに突き合わせ、項目ごとに自動判定
     filled  = 検証済みの証拠で埋まっている
     thin    = 記述はあるが薄い（単一ソース / 未検証 / 古い / 伝聞）
     missing = 触れてすらいない
     unknown = 公開情報では取れないと判定（→ VDR・専門家へ）  ← P21 の三値と接続
3. 充填: thin/missing ごとに最適チャネルで埋めに行く（Action Router）
     狙い撃ちの追加DR / 有償DB / VDR請求リスト / エキスパートへの質問案
4. 反復: 全項目が filled か「unknown＋理由＋取得手段」になるまで（Stop Rule）

成果物: カバレッジ台帳 1枚 — 「DDとして何が埋まり、何が薄く、なぜか」
```

**「完全な DD 情報」の操作的定義**:
全項目が検証済みで埋まるか、埋まらない場合は理由と取得手段が明示されている状態。

### ★成立条件: 薄さは文字数では測れない
DR は薄いところほど流暢に埋める（一般論と幻覚で）。決着済みの論点は短く書かれる。
よって thin の判定は **「検証済み・独立・新しい証拠の密度」** で行う:
- 同一プレスリリース由来の5記事 = 証拠1つ（P22 独立性クラスタ）
- 原文と照合できない記述 = ゼロ（L1 接地検証）
- 古い時点の数値 = 減価（as_of）
**見た目の厚さに騙されない監査ができることが、本機構の成立条件**であり、
既存の検証スタックがそのまま土台になる。

### 必須検証の再差し替え
- 旧（確定2時点）: 「入力ゼロで妥当な急所の優先順位が出るか」
- **新: ①機械の filled/thin 判定が、実務家が読んで下す判定と一致するか（κで測る）
  ②充填ループが、実際に薄い箱を厚くできるか（充填前後の検証済み証拠密度の変化）**

※ 確定2の「急所の自動検出」は誤読由来だが、機構としては**優先順位づけ（どの薄い箱から埋めるか）**
として生き残る。カバレッジ監査が「何が薄いか」を出し、決定感度が「どれから埋めるか」を決める。

## 補正2（同日）: 根拠②の撤回 — 私有情報の取り込みは内製の決定的根拠ではない

ユーザー訂正: **VDR の中身などをまとめるのは外部コンサルタントである。**
「私有情報は外部 SaaS に入れられないから、深さを求めるなら内製が論理的必然」という
確定1の根拠②は、**実務の分業を誤解していたため撤回する**。

### 正しいワークフローとペイン（ユーザーの言葉から）

```
フェーズ1: 初期 Biz DD — 投資プロが単独で行う。ほぼ Google Deep Research を活用
  ペインA: DR が完璧でないため、コンサルなしの初期 Biz DD には限界がある

フェーズ2: 外部コンサルタントへ Biz DD を依頼
  ペインB: コンサルはドメインのプロ。投資プロの知識が浅いと反論できない
  ペインC: コンサルも DR 等を活用するため、リサーチが単調になりがち
```

> **深さの用途の再定義**: 深さは「レポートを厚くする」ためではなく、
> **コンサルタントと対等に渡り合うための知識武装**である。
> サカナ AI のように深くリサーチできれば、①コンサルと同等にやりあえる
> ②要求事項がより具体的になる ③よりハードルの高い要求を出せる。

### カバレッジ台帳の3つの射影（＝上の①②③に一対一で対応）

| # | 射影 | 中身 |
|---|---|---|
| ① **対峙資料** | 発注前に filled 項目（自前で検証済みの知識）を装備。コンサルの主張が自前の検証済み証拠と食い違えば、原文つきで突ける |
| ② **発注仕様書（自動生成）** | filled →「検証済み。発注不要。工数を使うな」／ unknown →「公開では取れないと判定済み。これがスコープ」＋具体的質問リスト ／ thin →「単一ソースのみ。独立ソースでの裏取りを要求」 |
| ③ **納品物 QC** | コンサル報告書を台帳に突き合わせ、**「何%が既に公開情報で検証済みの内容か」を機械測定**。単調な DR 再構成の部分を数字で特定し、一次調査への要求水準を上げる。全員が同じ DR を使う同質化 `[S-117]` の時代に、**単調性を検出できる発注側は希少** |

※ ②は討論16の作戦盤「コンサルに発注すべきスコープ」の具体化であり、新規要素ではなく先鋭化である。

### 内製の根拠の改訂（確定1の更新）

| 根拠 | 状態 |
|---|---|
| ① 差別化（買えるものは競合も買える `[S-117]`） | **据え置き**。ユーザー自身の出発点 |
| ② 私有情報の取り込みは内製だけ | **撤回**（VDR はコンサルが扱う。機密性は運用上の考慮点に格下げ） |
| ③ 蓄積が自社に残る | **据え置き**。検証結果・発注履歴・コンサル QC の記録も蓄積対象に加わる |
| **④（新・②の代替）用途固有性** | Marlin を契約しても返るのは**レポート**であり、固定スペックへのカバレッジ判定・発注仕様書・納品物 QC は返らない。この3射影は自社の DD 物差しを持つ内製層でしか作れない |

### 成功指標への追記
- 初期 Biz DD のカバレッジ（コンサル発注前に filled にできた項目の割合）
- 発注仕様書の具体性（コンサル提案の差し戻し・スコープ交渉での使用実績）
- 納品物 QC: コンサル報告書のうち「公開情報で再現可能・既検証」と判定された比率と、
  その指摘が追加調査・価格交渉に繋がった件数

## 拡張（同日）: 第2の物差し — EBITDA ドライバーツリーと見逃し防止のウォッチリスト

ユーザー追記: 価値は「対コンサルの知識武装」**だけではない**。
EBITDA 成長にはドライバーが多数あり（市場・競合・単価・コスト…）、
**投資プロ自身もミスや見逃しをする。どこを見ておくべきかをカバーしてほしい**。

### 物差しの2軸化

これまでの固定スペック（情報カテゴリの10箱）は「情報が存在するか」しか測れない。
第2の物差しとして **EBITDA ドライバーツリー**を追加する。

```
EBITDA = 売上 − コスト
  売上 = 数量 × 単価
    数量 = 市場規模 × シェア
      市場   ← 成長率 / 構造変化 / 規制 / 代替品
      シェア ← 競合の動き / チャネル / 製品力 / スイッチングコスト
    単価 ← 値上げ余地 / 価格転嫁力 / ミックス / 契約形態
  コスト ← 原価（仕入・労務費インフレ）/ 固定費レバレッジ / 規模効果
※ 業種テンプレートでツリーの形を変える（SaaS なら NRR・解約・CAC が幹）
```

監査は **情報カテゴリ × ドライバーツリー のクロス**で行う。各ドライバーノードに:
1. **検証状態**（filled / thin / unknown — カバレッジ監査と同じ三態）
2. **脅威フラグ**（競合の新製品・規制変更等。資料と公開情報からの構造化検出）
3. **エクイティストーリー依存度**（この投資仮説はどのドライバーに賭けているか）

### 最優先の見逃しの機械的定義

> **「投資仮説が依存しているのに、未検証か、誰も見ていないドライバー」**
> = ストーリー依存度 高 × 検証状態 thin/unknown/missing

これが自動生成される**ウォッチリスト**になる:

```
▍このディールで見ておくべき所（依存度 × 検証状態）
1. 値上げ余地 — ストーリーの中核依存なのに過去の値上げ実績が資料にない ★最優先
2. 上位顧客の更新率 — thin: マネジメント資料のみ、独立ソースなし
3. 競合Xの新製品 — 資料に言及なし。公開情報から検出 ← 投資プロがまだ見ていない論点
4. 労務費インフレ — 業種標準の警戒項目。依存度は中
```

### なぜ機械が人間の見逃しを拾えるか（誇張しない）

賢いからではない。**列挙が毎回完全で、注意が疲れないから**（チェックリストの原理）。
- 資料からの**構造化検出**（会計方針変更・集中度閾値・競合同時成長）が主。
  LLM の自由発想は主流バイアスで「当たり前」しか出ない `[S-061]` ため従とする
- 将来はケース記憶（M4）が「自社が過去に見逃した型」を警戒ノードとして追加していく

### 位置づけ: 設計の原点回帰
本 corpus の最初の実益定義から、主指標は **見落とし率（Critical Issue Recall）**だった。
対コンサルの3射影（補正2）はその応用形であり、**本丸は投資プロ自身のための安全網**。
KPI は既存の Critical Issue Recall をそのまま使う（新指標は増やさない）。

### 実装への反映
- 固定スペックのデータ構造を「10箱のリスト」から「**10箱 × ドライバーツリー（業種テンプレ可変）**」へ
- Evidence Graph: Hypothesis ノードに `driver_node_id`（ツリー上の位置）と
  `thesis_dependence(高/中/低)` を追加（次のスキーマ改訂で）
- ウォッチリストは作戦盤（Phase 0）と生きた台帳（Phase 1）の両方に常設セクションとして載る

## 補正3（同日）: 蓄積（根拠③）の格下げ

ユーザー指摘: **蓄積は難しい。コンサルタントとのやり取りはあまり残らない。
残っても DD のパワポだけで、そこから（証拠の系譜は）読み取れない。**

### 訂正
1. **過去案件からの遡及的な蓄積は諦める。** パワポは結論のみで、
   「何を確認し・何が根拠で・何を確認しなかったか」の系譜を持たない
2. 蓄積は「**これからシステムを使うことの副産物**」としてのみ成立する。
   台帳は追記専用なので、使った瞬間に記録になる（追加作業ゼロ）。
   コンサルループは**2接点で捕捉**: 発注仕様書はシステムが生成（入口）、
   納品物は QC のためアップロード（出口）。**中間のメール・会議は捕捉できない — 諦める**
3. **根拠③は「内製を選ぶ理由」から「使い続けた場合の副産物」へ格下げ。**
   内製の根拠は **①差別化 ④用途固有性 の2本柱**に整理し直す（P24 とも整合）

### 副作用: レトロスペクティブ評価の実施可能性
過去案件での検証（当時の資料だけで見逃しを拾えたか）は、
**アーカイブに何が残っているか次第**（IM・IC メモ・当時の開示が残っていれば成立、パワポのみなら縮小）。
→ **Q32（新規宿題）**: 過去案件のアーカイブに実際に何が残っているかの棚卸し
