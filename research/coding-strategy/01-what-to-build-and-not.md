# 作るもの / 作らないもの

**判定基準は ∂V/∂M（P16）**。モデルが賢くなったときに価値が上がるものだけを自作する。

## 1. 作らない（Class A: モデルに食われる）🔒

| 作らないもの | 理由 | 代わりに |
|---|---|---|
| **汎用 Web 探索エージェント基盤** | DR は各社の標準機能、$2/task `[S-020]` | 既存 API / OSS を薄いアダプタで呼ぶ |
| **マルチモデル・オーケストレータ** | **Sakana Fugu が商用モデル化済み** `[S-104]` | 薄いルータ（カスケードのみ）。必要なら Fugu 等を呼ぶ |
| **探索アルゴリズムの自作** | TreeQuest が Apache-2.0 `[S-009]` | TreeQuest / 既存 MCTS 実装 |
| **モデルの学習・ファインチューン** | 資源がない。データもない。**コモディティ化する** `[S-088]` | プロンプト/ルーブリックの版管理で代替（GEPA 型）`[S-098]` |
| **OCR / レイアウト解析エンジン** | 商用が既に強い。RealDoc-Bench F1 0.847 `[S-136]` | 買う（複数ベンダを差し替え可能に） |
| **汎用 RAG 基盤** | コモディティ | 既存。ただし**索引は二層**にする `[S-049]` |
| **日本語の言語品質改善** | Namazu が特化済み `[S-105]` | モデルを選ぶだけ |
| **長文レポート生成の作り込み** | 生成は専門家の 100倍安い `[S-112]` | 証拠グラフからの**射影**として最小実装 |
| **データベース（企業/ディール情報）** | ベンダーがコネクタで全アプリに供給 `[S-134]` | 買う・組む |
| **凝ったスキャフォールド** | モデル更新で目減りする `[S-113]` | 単純に保つ。状態管理だけ丁寧に |

> **リポジトリ構成での表現**: 上記は全て `adapters/` 配下の薄い層に閉じ込める。
> **`adapters/` が厚くなったら設計が間違っている。**

## 4. 境界線の引き方（迷ったときの判定）

```
その機能は、モデルが2倍賢くなったら不要になるか？
  YES → 作らない（adapters/ に薄く包む）
  NO  → 次へ

その機能は、証拠グラフのスキーマに載るか？
  NO  → 設計を疑う（載らないなら、監査も検証も効かない）
  YES → 作る

その機能は、P1–P20 のどれに紐づくか？
  紐づかない → 作らない
```

## 5. 「薄っぺらくしない」ことの意味（誤解の防止）

ユーザ要求は「単調で薄いシステムにしない」であった。
**これは「機能を増やす」ことではない。** リサーチが示したのは逆で、

- 機能を増やすほど**引用精度は落ちる**（-42%）`[S-057]`
- 探索を長くするほど**プロキシと実質が乖離する**（26.4%→57.8%）`[S-103]`
- 複雑なスキャフォールドは**単純なものに負けることが多い** `[S-113]`

> **深さは「機能の数」ではなく「構造の厚み」で出す。**
> 具体的には ①多層の目的関数 ②役割ごとに権限の違う異質なエージェント
> ③時間の一級市民化 ④失敗の記録 ⑤停止条件の理論 ⑥介入点 ⑦監査の一次記録。
> **この7つは全て証拠グラフの上に載る。** 機能追加ではなく、構造で厚くする。
