# 06. ビルド計画

## 1. リポジトリ構成

```
prism/
  templates/        # スペック・アーキタイプ・ツリー・ファンド標準（YAML、人間承認で版管理）
  core/             # 台帳（events/graph）・スペック実体化・カバレッジ判定・停止規則 ← 価値の本体
  adapters/         # コレクタ・LLM・document AI（全て差し替え可能な薄い層。★厚くなったら設計ミス）
  verify/           # 接地・数値・独立性・時点・矛盾
  router/           # 充填プランナ・Action Router・ポリシーゲート(C12)
  project/          # 射影 O1–O6（md/html 生成）
  gates/            # 不変条件 I1–I10 のテスト・judge κ 測定・実験ハーネス
  ui/               # v0: 投入フォルダ監視 + 静的HTML出力（Webアプリは後）
```

## 2. v0 の範囲（6週間目安、AI コーディング前提）

| 週 | 作るもの |
|---|---|
| 1 | templates（箱0–10 v0.3 + SES×受託 + 稼働率/受注型ツリー）、events/台帳スキーマ、I1–I9 テスト |
| 2 | 取り込み（手動投入フォルダ＋PDF パース＋三値抽出）、sources/evidences 構築 |
| 3 | コレクタ: Google DR API・Web 検索・EDINET。C12 ゲートと trust_label |
| 4 | 検証: 接地（別ベンダ・二値・順序入替）、独立性クラスタ、矛盾検出、数値恒等式 |
| 5 | カバレッジ判定・充填プランナ・停止規則・O1/O2/O3 射影 |
| 6 | O4 発注仕様書・実験E の実施と採点 |

**v0 で作らない**: Speeda/TDB API 連携（手動投入で代替）／記憶・較正ループ／thesis tracking／
凝った UI／Fugu 等の外部エージェント連携／確率の数値表示。

## 3. 実験E（v0 の合否 = 内製 GO/NO-GO）

```
対象: 実在の非上場 IT サービス企業 1〜2社（可能なら過去に検討した案件）
入力: 社名のみ（フェーズN 相当）＋ 手元にある Speeda/TDB PDF を投入
測定:
  E-1 filled/thin/unknown 判定と、投資プロの目視判定の一致          → κ ≥ 0.6
  E-2 矛盾検出（IM があれば IM vs 外部）                            → 1件以上、誤検出なし
  E-3 ウォッチリストのうち「言われてみれば見るべき」と評価される率     → 30%以上
  E-4 発注仕様書を実際のコンサル/VDR依頼のドラフトに使えるか（定性）   → 使えると判定
  E-5 素の Google DR 出力との読み比べ（ブラインド）                  → 台帳側を選ぶ
  所要: 投入から O2 まで 3時間以内 / 機械原価 ¥20,000 以内
```

## 4. 撤退・転換基準（内製版 Kill criteria）

| 観測 | 判断 |
|---|---|
| E-1 が κ < 0.4（校正1周後も） | **中止**。判定が実務と合わない＝全射影が砂上。「買った方がマシ」 |
| E-3 < 10%（当たり前しか出ない） | ウォッチリストを降ろし、台帳＋発注仕様書に縮小して継続 |
| unknown 過多で価値が感じられない | 業界パック＋質問リスト特化（シナリオB）に転換 |
| 2〜3案件使って再訪しない | 正直に棚上げ。DR＋現行プロセスに戻る |

## 5. 事前予測の記録（較正の実践第1号）

実験E 実施前の事前確率（2026-08-22 時点、討論での見積り）:
**A 実用的成功 50% / B 部分的成功（unknown過多・質問リスト特化）27% / C 中止 23%**。
実験E の結果でこの予測を採点し、以後の全ての確度提示の較正記録の起点とする。
