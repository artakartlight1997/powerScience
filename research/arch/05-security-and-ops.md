# 05. セキュリティ・運用・コスト

## 1. 前提（内製・単一テナント）
- 利用者は自社の投資プロのみ。外販しないため、マルチテナント設計は不要
- ただし**案件間の隔離は必須**（MNPI）: 案件ごとに DB スキーマ分離＋スナップショットのプレフィックス分離
- フロンティア API は**学習非利用の契約条件**を確認の上で利用。IM・VDR 由来の文書を API に送る可否は
  **社内の情報管理規程に従い、案件ごとに送信可否フラグを持つ**（送信不可なら該当文書はローカル処理のみ）

## 2. 二層 LLM と taint（P18、v0 での現実的な縮退）
```
未信頼側（C2 収集ワーカ）: Web 由来テキストを扱う。ツール権限・認証情報を持たない
信頼側（統率・射影）      : 台帳の構造化データのみを読む
taint: 全 evidence に trust_label。untrusted 由来の値は C12 ゲートで特権ツール引数を遮断（I4）
v0 の縮退: 単一利用者・内部ネットワークのため egress 制御は allowlist の最小実装。
           ただし trust_label と C12 は v0 から入れる（後付け不可のため）
```

## 3. コスト設計
| レバー | 方針 |
|---|---|
| プレフィックスキャッシュ | 案件の不変部（スペック・テンプレ・ツール定義）を先頭固定。ヒット率を計器に |
| 生成モデル | **案件内で固定**（キャッシュ効率）。検証は**別ベンダ**（独立性）— この分担は固定 |
| 検索・DR 予算 | 項目単位の上限＋停止規則。1案件の機械原価目標: **¥5,000–20,000** |
| 高価な検証 | filled 候補と矛盾のみ全数。その他はサンプル（粒度の適応制御） |

## 4. 運用
- ジョブは Postgres のジョブテーブル＋ワーカープロセス（キュー基盤は入れない。規模不要）
- 全実行はイベントからリプレイ可能。失敗はチェックポイントから再開
- テンプレ変更は PR ＋人間承認（P13）。judge κ・接地合格率・キャッシュヒット率をダッシュボード化
